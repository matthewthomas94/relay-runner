# Relay Remote (iOS)

The iPhone app for Relay Remote ([spec](../docs/specs/relay-remote.md), [design](../docs/design/relay-remote-ios/README.md)): text frames between the phone and the user's Mac over one SSH connection to the Mac's own OpenSSH server. Speech on the phone turns a spoken request into an `utterance` frame addressed to one of the Mac's agents and speaks the Mac's `speech` frames while the Mac stays silent. The app is the final design: splash, permissions, pairing and a tutorial on first launch, then the Agents, Workspace and Settings tabs. There is no debug screen (removed in RR-546; the early RR-428 and RR-429 debug surface is in git history).

## Decisions

- **Project:** the committed `RelayRemote.xcodeproj` is the source of truth (RR-533). The `RelayRemote/` and `RelayRemoteTests/` folders are file-system-synchronised groups (Xcode 16 and later), so a new Swift file, font or other resource saved anywhere under `ios/RelayRemote/` builds into the app, and a test file under `ios/RelayRemoteTests/` into the tests, with no edit to `project.pbxproj`. Only `RelayRemote/Info.plist` is excluded from the app's membership. `project.yml` is kept as a record of the targets and settings but is no longer regenerated from; change target settings in the project itself and keep `project.yml` in step by hand.
- **App layout (RR-533):** `AppFlow/AppFlowRouter.swift` routes splash → permissions → pairing → tutorial → app on first launch and, later, to the app when paired or to pairing when not; `OnboardingProgress` persists the finish. Each stage is its own view in `Onboarding/` (`SplashView`, `PermissionsFlowView`, `PairingFlowView` with `QRScannerView`, `TutorialView`) and each tab in `MainApp/` (`AgentsTabView`, `WorkspaceTabView`, `SettingsTabView`); `MainTabView` only switches tabs. `Glow/AppGlowLayer.swift` is the slot behind every screen for the state glows. `DesignSystem/` holds the tokens (`RelayColor`, `RelayTextStyle`, `RelayGlass`, `RelayMotion`), the buttons, glass panel, banner, `GlassTabBar`, `OnboardingHeroLayout` (hero at y 300, cursor, chips, Skip, 52 pt action), `StatusGlyph`, `AgentOrb` and `DotField`, plus Bai Jamjuree (copied from the desktop, registered with `UIAppFonts`) and the Lucide icons (`ios/scripts/generate-lucide-icons.py` reuses the desktop generator; add a name there and re-run it). `Preferences/` holds `TalkModePreference` and `ReplyNotificationsPreference`.
- **Debug launch arguments:** see [Reaching each screen](#reaching-each-screen). They exist only in Debug builds; Release builds ignore them. The design-system gallery (`--gallery`) and the scripted Mac (`--scripted-mac`) are kept deliberately as development tools; there is no debug screen in the app itself.
- **Permissions (RR-538):** `Onboarding/PermissionsFlowModel.swift` walks microphone, local network, camera and notifications (`PermissionsClient` is faked in tests); steps already decided are dropped, Skip never prompts, and notifications set `ReplyNotificationsPreference` (on only when granted). There is no speech-recognition step (design screen 08 is left out): `SpeechTranscriber`/`SpeechAnalyzer` run on device and need only the microphone permission, and nothing in the app uses `SFSpeechRecognizer`, whose authorisation prompt is what `NSSpeechRecognitionUsageDescription` backs, so that key was removed from `Info.plist`. Apple's docs describe the speech-recognition permission for the server-based `SFSpeechRecognizer`; the simulator reports `SpeechTranscriber` as unsupported, so this was not exercised end to end there and should be confirmed once on a device. Local network has no request API; the step browses `_ssh._tcp` like discovery does and moves on when the browser reports a result or after 8 s.
- **Agents tab (RR-540):** `Agents/` holds the screen. `AgentsModel` keeps the selected agent (persisted, and `select(_:)` is how other code opens a chat), each agent's chat, the Mac's per-agent state and the tabs marked by a reply that arrived elsewhere. Every `speech` frame becomes an agent message and every `status` frame a status line, filed under the agent the frame names; a frame that names none (a Mac before RR-534) belongs to the Mac's active agent, or the selected agent when it reports none. `ChatStore` keeps the newest 200 messages per agent as one JSON file per agent in Application Support. `AgentsScreenState` derives what the screen draws from the model and the voice layer, so the sample screens build it the same way. `AgentDock` is reusable: its controls can be dimmed from outside (`DockControl`). Glyphs map `off`, `starting` (the spinning glyph, as the desktop's starting notch), `ready`, `working`, `listening` and `playing`; the phone's own talking and playback win over the Mac's report. In Queue mode a waiting reply shows as "New reply from <agent>" in that agent's chat, and Play plays it with `SpeechPlaybackQueue.play(seq:skipping:)`, skipping only that agent's older replies. Stop silences the phone and sends `stop` for the selected agent and the one playing; Replay sends `replay` for the selected agent. A message to a stopped agent sends `start` for it with no project first.
- **Deployment target: iOS 26.** RR-421 chose `SpeechAnalyzer` and `AVSpeechSynthesizer` for RR-429, and `SpeechAnalyzer` requires iOS 26. Nothing in the transport needs more than iOS 18, so a lower floor would only have to be revisited for speech.
- **Layout:** `RelayRemoteKit/` is a local SwiftPM package holding all transport, pairing and session logic. It depends on the repository root package for `RelayRemoteProtocol` (RR-422). `swift` fetches only what that product needs; Xcode also resolves the root package's Mac dependencies (FluidAudio, Sparkle and others) but builds none of them. The app target `RelayRemote/` is a thin SwiftUI shell.
- **Transport:** swift-nio-ssh over swift-nio-transport-services, pinned to the revisions the RR-420 spike read (`149f32ff`, `f85ed684`). Each connection has one `session` channel with an `exec` request, an empty command and no PTY. The `authorized_keys` `command=` runs `relay-remote-shell`, which accepts only an empty `SSH_ORIGINAL_COMMAND` or `status`. Remote EOF closes the channel because it means the helper exited.
- **Host key pinning:** `validateHostKey` accepts only the `SHA256:` fingerprints from the pairing code. There is no trust-on-first-use path. A mismatch fails during key exchange, before user authentication. No frame is written, no other address is tried, and the session stops in a visible error state until the user taps Try again.
- **Device key:** a Secure Enclave P-256 key (`NIOSSHPrivateKey(secureEnclaveP256Key:)`, exported as `ecdsa-sha2-nistp256`) when `SecureEnclave.isAvailable`. Otherwise an Ed25519 key stored in the Keychain. The Secure Enclave key is persisted only as its enclave-wrapped `dataRepresentation` in the Keychain. Items use `AfterFirstUnlockThisDeviceOnly`, so a locked phone can reconnect and nothing syncs or migrates. The iOS 26 simulator on Apple silicon has a Secure Enclave, so the Ed25519 fallback is covered by tests rather than by the simulator.
- **Logging:** the kit logs only through `RemoteLogger` with fixed event names and error codes. Key material, fingerprints, tokens, the pairing code and utterance text never reach it. A test captures the sink across pairing and a session and checks that none of them appear. Fingerprints are shown only in the UI.
- **Session:** `hello` carries `resume_after_seq`. Every sequenced Mac frame gets exactly one `ack`, sent by the playback queue in seq order: `played: true` after the synthesizer finished the text, `played: false` for a frame that was stopped, skipped or never speaks (`status`, `speech_control`). The Mac honours only the first ack per seq, so nothing is acknowledged on arrival. A frame at or below the acknowledged watermark is ignored. Acks that cannot be sent during a disconnect wait in an outbox and go out after the next `welcome`, except ones above the Mac's `server_seq`, which belong to a sequence that no longer exists. Utterances stay queued until `accepted` and are resent with their original `client_id` after each `welcome`; they are dropped after five minutes rather than run late. The first ping after `welcome` acts as the replay barrier. A bridge restart, where `resume_after_seq` is greater than `server_seq`, adopts the new sequence.
- **Speech (RR-429):** STT is `SpeechAnalyzer` with `SpeechTranscriber` (`.progressiveTranscription`, on device, model installed through `AssetInventory` on first use). One analyzer serves one utterance, opened by the Talk control and finalized when it is released (Hold) or tapped again (Toggle). There is no hands-free mode (removed in RR-540; RR-546 deleted the kit's now-unused `UtteranceEndpointer`). The transcript is sent through `RemoteSession.send(text:)`, so it gets the same `client_id` and `captured_at` handling as a typed request. TTS is `AVSpeechSynthesizer`, preferring a Premium or Enhanced voice for the device language when one is installed; `SpeechPlaybackQueue` in the kit plays `speech` frames in seq order, honours `speech_control` stop and skip, and owns the acks. Capture pauses while the phone speaks. The audio session (`playAndRecord`) is active only while recording or playing; `UIBackgroundModes` declares `audio`, so a reply keeps playing with the screen locked, and the app stops the session only once audio is idle in the background. An interruption pauses playback and resumes it when the system says so; losing the output route ends the open utterance. Stop, Replay and Cancel send `control` frames; Stop and Cancel also silence the phone at once.
- **Session control (RR-456, RR-534):** with no session running, the Mac's helper joins the channel to Relay Runner's session-control socket (`RemoteSession.State.connectedToApp`). The phone has no project picker: a message to an agent that is not running sends `start` for that agent with no project, which the Mac starts in its general-tasks project (or beside the running agents in the running project), and the agent's tab shows "isn't running" with a Start button until it is up. Settings › Mac shows the Mac's name, whether it is reachable and which agents run, and Stop all (after a confirmation). When the session the phone watched start becomes ready, the phone reconnects at once and attaches; a channel that is already ready on arrival reconnects after the normal backoff. Typed requests wait for the session. After each `welcome` the phone asks the app which project is running. "Relay Runner is not running" comes from the helper; "Mac unreachable" means SSH did not get through.
- **Reconnect:** exponential backoff with equal jitter: attempt `n` waits a random time in `[c/2, c]` where `c = min(30 s, 0.5 s × 2ⁿ)`. The backoff resets only after a connection stays welcomed for 15 s, so a flapping Mac is not hammered. A network path change skips the remaining wait.
- **Liveness:** swift-nio-ssh has no client keepalive API. The app pings every 15 s and closes after 40 s without an inbound line. TCP keepalive is idle 30 s, interval 10 s, count 3. sshd's `ClientAliveInterval` covers the Mac side. These are first values and need device measurement.
- **Network changes:** Network.framework does not drop an unviable connection (Apple DTS, forum thread 746449). The transport closes on `ViabilityUpdate(false)` and `BetterPathAvailable`, then reconnects and resumes.
- **Lifecycle:** foreground-first. Leaving the foreground saves `resume_after_seq` and closes the channel, which the Mac sees as a clean disconnect and buffers for. Returning reconnects and replays. Background audio is RR-429's decision. With Reply notifications on and allowed, the channel stays open instead (next item).
- **Reply notifications (RR-545):** local notifications only, posted by the app itself while it stays alive in the background. There is no APNs, no push service and no cloud relay; nothing leaves the phone. `Notifications/ReplyNotifier.swift` owns the rules and `AudioSessionController` the audio hold. When the Settings › Voice › Reply notifications preference is on and iOS notification permission is granted, going to the background holds the audio session for `KeepAliveReason.replyNotifications` and keeps the channel to the Mac open. The hold is the least intrusive configuration that keeps the app running: the `playback` category with `mixWithOthers`, so the user's music keeps playing and the microphone stays closed, and an `AVAudioEngine` rendering silence, since an active session that plays nothing is suspended. A reply that plays aloud switches to the usual `playAndRecord` configuration and back, so whether a reply is spoken in the background still follows Remote mode and Replies. `playAndRecord` was not used for the hold: on the simulator, turning input on from the background blocked the main thread for 30 s and then failed, and the hold needs no input. The cost is battery: audio I/O runs for as long as the app is in the background. `KeepAliveReason` is the one place a later reason (the Relay ring) joins the hold. `ReplyNotificationAssembler` joins the `speech` frames of one reply (one agent, one `relay_command_seq`, ended by `final`, `clarification` or `fallback`) into one notification titled with the agent's name, its body cut to about 240 characters at a word; a frame with no command is a reply of its own, `control` speech is skipped, and a frame replayed after a reconnect is not counted twice. Notifications are threaded per agent (`agent.<slug>`), only for replies that end while the app is not in the foreground. Tapping one opens the Agents tab on that agent's chat, from a backgrounded app or a relaunched one (`RelayRemoteAppDelegate` sets the notification centre's delegate before launch finishes). Opening the app clears the delivered notifications of the chat on screen and releases the hold. If the connection drops in the background and the session's own reconnects fail six times (the drop and five retries, about 16–32 s of backoff), or the Mac refuses the phone, the app posts "Lost connection to your Mac. Open to reconnect." once, releases the audio session and stops the session; it does not post it again until the app has been opened. With the preference off or permission not granted, nothing changes: the app backgrounds exactly as before. Accepted trade-offs: nothing arrives once the app is swiped away or killed, or after a reboot; battery use is higher; the orange microphone indicator may show while the session is in its voice configuration (recording, or playing a reply), as before; the hold itself uses no input, which needs confirming on a device.
- **Reachability:** a Bonjour `_ssh._tcp` browse for 1.5 s, keeping the service whose `DNSServiceResolve` host target is the paired `LocalHostName.local`. Then stored addresses: Tailscale (`100.64.0.0/10`), LAN, then `.local` names.
- **Network restriction:** "Only from my home network and Tailscale" on the Mac's pairing confirmation adds a `from=` list to the device's `authorized_keys` line, fixed at pairing time. Home means every Mac interface that holds a private IPv4 address (`10/8`, `172.16/12`, `192.168/16`): its IPv4 subnet, its IPv6 link-local range and its unique-local (`fc00::/7`) and global IPv6 `/64` prefixes. Tailscale means `100.64.0.0/10` and `fd7a:115c:a1e0::/48`. Loopback, public IPv4 addresses and interfaces without a private IPv4 address (for example a VPN tunnel) are left out. sshd compares a link-local client address together with its interface scope, so a bare `fe80::/10` never matches. The range is written per interface as `fe80::%en0/10` and matches only peers on that link; this was checked against a throwaway OpenSSH 10.3 `sshd` (RR-433). If the LAN's global IPv6 prefix or the Mac's interfaces change after pairing, pair again to refresh the list.
- **Refused key:** the phone tries every candidate address in order. A refused host key stops at once. A refused device key moves on to the next address, since a restricted key can be refused on one address and accepted on another (for example on IPv6 but not over the stored LAN IPv4 address). The session stops with "pair again" only when no address connected and every address that answered refused the key; unreachable addresses do not count as answers, so a revoked key still stops while Tailscale is down.
- **Pairing:** QR scan with VisionKit, or paste of the copied code. The phone connects with the one-time Ed25519 key from the code, pins its host keys, and sends `pair` with the token, a new device id, the device name and the device public key. It then waits up to ten minutes for the user to allow the device on the Mac. Forget this Mac clears only the phone; unpair in Relay Runner's Settings to remove the key from the Mac.

## Reaching each screen

Debug builds only. Launch the installed app with `xcrun simctl launch booted com.relayrunner.remote <arguments>` (terminate it first with `xcrun simctl terminate`), then `xcrun simctl io booted screenshot <file>.png`. A fresh install needs no argument: it walks the stages in order. Numbers are the design's reference images in `docs/design/relay-remote-ios/`.

| Screens | Arguments |
| --- | --- |
| 01–05 splash (about 11 s; screenshot at 0.5, 2.5, 6, 7.3 and 9.6 s) | `--reset-onboarding --stage=splash` |
| 06, 09, 10, 11 permissions | `--stage=permissions --permission-step=microphone\|localNetwork\|camera\|notifications` (opens the step even if decided) |
| 07 system prompt | raised by the system when the step's Allow button is tapped; not capturable by argument |
| 08 speech recognition | not built, see Permissions |
| 12, 13, 14 pairing | `--stage=pairing`, `--stage=pairing --pairing-step=scan`, `--stage=pairing --pairing-step=check` |
| 15–20 tutorial | `--stage=tutorial --tutorial-step=basics\|hold\|release\|play\|stop\|done` |
| 21–25 Agents | `--stage=app --tab=agents --agents-sample=ready\|holding\|playing\|not-running\|unreachable` (`long-draft`: the dock at five lines) |
| 26 Workspace | `--stage=app --tab=workspace --workspace-sample=list\|empty\|error\|unreachable\|truncated` |
| 27 Settings | `--stage=app --tab=settings --sample-settings` (`--scroll-bottom` for the lower half) |
| 28 lock-screen notification | `--stage=app --scripted-mac=10`, allow notifications, lock or background the app and wait for a reply; capture with `simctl io` |
| 29 ticket modal | `--stage=app --workspace-sample=list --ticket-sample=short\|long\|loading\|error\|truncated\|unsupported\|done` (add `--workspace-sample=unreachable` for the banner) |
| design-system gallery | `--gallery` or `--gallery=<type\|controls\|glyphs\|orbs\|listening\|playback>` |

`--scripted-mac=<seconds>` connects to a scripted Mac inside the app that sends a two-frame reply from George every `seconds`, and `--scripted-mac-drop=<seconds>` makes it unreachable after that long (RR-545). With it, `--stage=app` is a first-launch-free way to type or speak an exchange with an agent on the simulator without a real Mac. The same arguments on a Release build do nothing.

## Background behaviour

Summarised from Lifecycle and Reply notifications above. Reply notifications on and allowed: the app holds a silent, mixable audio session in the background, keeps the channel open, and posts one local notification per reply that ends while it is not in the foreground; a lost connection posts one "Lost connection to your Mac" notice and stops. Otherwise: leaving the foreground saves `resume_after_seq` and closes the channel (after any reply still playing), and returning reconnects and replays. Nothing arrives once the app is force-quit or after a reboot.

## Build and test

Simulator, all app and kit tests:

```bash
cd ios
xcodebuild test -project RelayRemote.xcodeproj -scheme RelayRemote \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro'
```

macOS, the kit alone, including the end-to-end SSH tests:

```bash
cd ios/RelayRemoteKit
swift test
```

`SSHTransportIntegrationTests` (macOS only) needs no privileges and does not need Remote Login. It starts a per-user `sshd` on a loopback high port with a temporary host key and `authorized_keys`. It compiles and runs the real `relay-remote-shell` forced command, and runs the real `services/relay_remote.py` bridge module with a scripted ingress. It covers the exec channel, Secure Enclave and Ed25519 authentication, host-key refusal before the forced command runs, rejection of an unknown key, pairing with the ephemeral key, and replay after a reconnect. It is skipped when `sshd` or `python3` is missing.

## Device builds

Create `ios/Config/Signing.local.xcconfig` (gitignored) containing `DEVELOPMENT_TEAM = <team id>`, then run the `RelayRemote` scheme on a connected iPhone.

Physical-device checks, with Remote Login on for the current user and Relay Runner running. Each is something the simulator cannot confirm:

1. Pair: Relay Runner Settings, Relay Remote, Pair a device; scan the code with the in-app camera (not the paste fallback); compare the fingerprint; Allow.
2. First launch: the system microphone, local network, camera and notification prompts each appear at their step, and the local-network step finds the Mac within 8 s.
3. Hold to talk: hold Talk, speak to George, release. The transcript appears in the chat, the Mac handles it, and the reply is spoken on the phone while the Mac stays silent. Speech recognition works with only the microphone permission and no speech-recognition prompt appears (README Permissions note).
4. Address another agent: switch to Sky's tab and send a message; the reply is filed under Sky's tab and the other tabs show the reply marker if it arrived elsewhere. Message a stopped agent: it starts, its glyph spins, then goes ready.
5. Lock the phone during a long spoken reply: playback continues and no frame is spoken twice after unlock. Stop silences the phone at once; Replay speaks the last reply again.
6. Bluetooth headphones: replies play through them; disconnecting them mid-reply ends the open utterance and does not crash.
7. Lock the phone while a reply is pending, then unlock. The app reconnects with `resume_after_seq` and shows the replayed frames without a missed-updates notice.
8. With Tailscale connected on both devices, turn off Wi-Fi. The app reconnects over the Tailscale address on cellular, and again when Wi-Fi returns.
9. Network restriction: pair with "Only from my home network and Tailscale" on. On the home Wi-Fi the app connects. With Tailscale off, from a network outside the Mac's home subnets, `sshd` logs the key as not from a permitted host and the app shows the refused-key error.
10. Workspace: the tickets match the Mac's board and change within a few seconds of a change on the Mac; tapping a ticket reads its text; turning Wi-Fi off shows the unreachable banner over the list and the modal.
11. Settings: changing the model, effort, sizing or speech speed on the phone changes the Mac's Settings window, and a change on the Mac shows on the phone.
12. In Console, filter subsystem `com.relayrunner.remote` and confirm only event names and codes appear.

Reply notification checks (RR-545 acceptance), with Reply notifications on and notifications allowed:

13. Lock the phone and wait several minutes, then an hour, then ask an agent something from the Mac. A notification titled with the agent's name arrives with the reply's text; tapping it opens that agent's chat. Repeat after force-quitting the app from a tapped notification.
14. While locked, put the Mac to sleep. Within about half a minute "Lost connection to your Mac. Open to reconnect." arrives once, and the app stops holding audio (Control Center shows no app audio).
15. Play music in another app, then lock the phone: the music keeps playing at full volume while the app waits, and the microphone indicator does not show. Note battery use over an hour.

Also watch for reconnect loops from `BetterPathAvailable` over the Tailscale tunnel, and measure idle NAT timeouts to tune the ping and keepalive values.
