Relay Runner overview

One voice turn, one authority chain, many local workers.

Relay Runner keeps voice interaction, project planning, tool use, board state, and code changes inside the local repo and the running macOS app. The messenger speaks, the foreground orchestrator decides, the daemon dispatches, and workers execute in isolated worktrees.

Provider parity Codex and Claude share the same architecture, ticket flow, and authority boundaries. Differences stay in transport, model names, and CLI flags.
Privacy boundary Raw voice captures stay private runtime metadata until the foreground orchestrator refines them into user-safe ticket prose.
Newest intent wins Seq/id metadata lets the foreground session suppress stale follow-up actions and stale spoken output.

Persistent Messenger

Tool-free messenger

Warm, fast, and deliberately limited. It turns user turns plus public orchestrator context into spoken updates, but it cannot plan or act.

  • Codex and Claude both run a provider-specific low-latency messenger

Foreground Authority

Foreground orchestrator / PM

The authoritative Codex or Claude session. It classifies commands, answers directly when possible, authors refined tickets, and manages workers.

  • Checks newest-intent metadata before follow-up actions and spoken output
  • Never turns raw command captures into visible ticket prose unchanged

Command action contract

Each substantive turn becomes one explicit action: answer inline, create/refine a ticket, update an existing ticket, dispatch ready work, or steer running work.

Private metadata

Raw voice transcripts, relay command files, and seq/id claims stay runtime evidence, not board cards. Visible tickets are rewritten as cold-start-safe work items.

Provider-neutral authority

Codex and Claude differ in launch details, not in who can decide, dispatch, review, or publish outcomes.

Ticket And Worker Flow

Work that should outlive the current turn becomes a refined repo-local ticket. The board is the source of truth, and ready is the dispatch trigger.

Repo-local state
backlog
ready
in_progress
done
Refined ticket in .orchestrator/

The foreground orchestrator writes title, description, acceptance criteria, sizing fields, and dependencies into version-controlled markdown.

move to ready
Board + daemon dispatch

The board auto-calls dispatch as soon as a card lands in ready. Manual dispatch uses the same daemon path.

spawn worktree
Implementation worker

A one-shot Codex or Claude worker runs in an isolated relay/<id> branch and worktree, claims the ticket, verifies the change, commits code, and appends a run log.

review evidence
Review / merge worker

Review and merge stay distinct. Accepted merge publishes the finished branch back to the working branch and only then makes the board state truly complete.

Dependency progression

Only the first ticket in a chain needs a manual move to ready. When a predecessor is merged and published as done, dependents can auto-promote from backlog to ready.

Worker boundary

Workers can edit code in their worktree and their own ticket file. They do not rewrite other board state or other tickets.

Audit trail

Ticket diffs, worker commits, review evidence, and merge publication all live in git instead of an external orchestration service.

Response Loop And Preemption

The bridge can deliver turns in parallel without losing control because public traces, final replies, and stale-command checks all route back through the same foreground authority.

Newest intent wins

1. Claim the newest turn

Relay command state

The bridge records a newest-intent seq/id when input arrives and copies claimed metadata for the active action. Both providers follow the same stale-action contract.

2. Check before follow-up

Foreground checkpoints

If a newer command appears, already-running shell or MCP work may finish, but no follow-up action, ticket edit, or spoken reply may continue under stale intent.

3. Mirror bounded context

Public-only updates

Reasoning summaries, worker lifecycle traces, clarification requests, and the final authoritative outcome are mirrored to the messenger without exposing hidden chain-of-thought or raw transcripts.

4. Speak the outcome

Messenger to user

The messenger speaks the bounded reply through local TTS. If the messenger fails, the authoritative foreground reply can still be spoken directly.

5. Keep the repo clean

User-safe ticket prose

Private runtime metadata stays private unless the foreground session deliberately refines it into a visible ticket that another worker can pick up cold.
