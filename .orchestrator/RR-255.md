## Description

Make Relay Runner's **Start Session** lifecycle truthful and diagnosable when
the app-owned voice bridge starts successfully but the embedded Codex or Claude
process exits before a usable interactive session exists. The observed failure
shows `launchctl submit exit_status=0`, followed by a bridge socket, a persistent
orchestrator heartbeat, and the normal waiting-for-voice-input loop, while the
Workspace terminal immediately presents a successful provider exit and no
embedded agent remains. Treat launchd acceptance, bridge readiness, provider
startup, and interactive-session readiness as separate lifecycle stages; do
not report a successful launchd submission as either provider success or a
bridge process exit.

Capture enough bounded, privacy-safe evidence on every Start Session attempt to
explain early provider exits without requiring a developer-only marker to have
been enabled beforehand. Preserve the useful diagnostics currently available
from the generated launcher, bridge log, embedded process termination status,
provider identity, configured workspace folder, and project/workspace resolver,
while avoiding raw terminal transcripts, voice transcripts, prompts, tokens, or
other secrets. Surface an actionable failure state in the Workspace rather than
leaving a healthy orphan bridge and a generic `Session exited (0)` presentation.

Also make failed voice-to-ticket requests durable and auditable. If a command is
classified as project work but cannot be claimed or applied because the
embedded provider exits, the selected route is only a workspace root, the
target project is unresolved, or ticket mutation fails, retain a private
provider-neutral command-action outcome that distinguishes queued, claimed,
created, rejected, superseded, and delivery-failed states. Do not create a
visible ticket until the foreground orchestrator has resolved a concrete
project and refined user-safe content, and never copy a raw voice transcript
into the board. On recovery or the next usable session, expose a concise safe
status or retry path so authorized work is not silently dropped.

## Acceptance criteria

- [ ] Model and record separate provider-neutral stages for launch request, launcher start, launchd bridge submission, bridge socket readiness, embedded provider spawn, interactive provider readiness, and session end/failure.
- [ ] `launchctl submit exit_status=0` is documented and presented only as successful launchd job submission; it is never described as the bridge or provider exiting successfully.
- [ ] A deterministic regression starts a bridge successfully, then makes the embedded Codex process exit `0` before readiness; the UI reports a failed/unusable session with the provider exit code, keeps the bridge and provider outcomes distinct, and performs deliberate orphan-bridge cleanup or recovery.
- [ ] The equivalent early-exit regression covers Claude, with provider-specific launch details allowed but the same lifecycle semantics and user-facing recovery behavior.
- [ ] Every embedded Start Session attempt writes a bounded owner-only diagnostic record before provider startup and finalizes it on normal exit, signal termination, setup failure, provider early exit, app-requested stop, and app relaunch; useful lifecycle evidence does not depend on a marker enabled before the failure.
- [ ] Diagnostics include timestamps, provider, child identity when available, configured workspace folder, resolved route kind/project identity, sanitized launch stage, bridge socket outcome, and decoded termination status without storing raw terminal output, raw voice text, prompts, environment secrets, credentials, or tokens.
- [ ] Starting from a workspace folder such as a parent containing multiple git repositories is represented as a valid workspace route, not silently attributed to a child project's board; project mutations require an explicitly resolved child repo.
- [ ] When project work arrives without a concrete target project, Relay records a durable `clarification_required` or equivalent private outcome and asks for a target; it does not create a parent workspace `.orchestrator/` directory or claim that a ticket was created.
- [ ] Durable command-action records distinguish received, classified, queued, claimed, mutation-authorized, created/updated/dispatched, superseded, rejected, and delivery-failed outcomes using Relay command sequence/id checks.
- [ ] If the embedded provider exits before claiming or completing an authorized ticket action, the command remains recoverable or receives a terminal failure outcome; it cannot disappear merely because `/tmp/voice_command_state.json` and `/tmp/voice_cmd_claimed.json` are absent after bridge teardown.
- [ ] Recovery never replays a revoked, replaced, interrupted, canceled, or stale command, and never duplicates a ticket whose successful mutation was already recorded.
- [ ] User-visible recovery/status text names the actual outcome—session failed before provider readiness, waiting for project choice, ticket created, action superseded, or delivery failed—without exposing raw transcripts or internal prompts.
- [ ] Focused Swift and Python tests cover successful startup, launchd submission failure, bridge socket timeout, Codex/Claude early exit `0`, nonzero exit, signal exit, workspace-root routing, missing project clarification, provider death before claim, mutation failure, stale-command revocation, retry deduplication, and app relaunch recovery.
- [ ] Existing Start Session, bridge watchdog, workspace-folder routing, messenger, ticket schema, dispatch authorization, and provider-parity tests continue to pass.
