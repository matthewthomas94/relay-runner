## Description

Agents operating Relay Runner today have no direct way to act on the app itself. Relay Actions exposes only `toggle_board` and `activate_project`, so configuring a setting or re-pairing a phone means screenshots and coordinate clicks (on 2026-11-03 a single re-pair took five Relay Vision screenshots and seven clicks). The user's rule: the app we own must be controllable through a first-party MCP, with pixels reserved for things that are genuinely visual.

RR-456 adds an app-owned Unix control socket (session control for the phone: list projects, start, stop, state). This ticket generalises that socket into the app's command surface and ships a thin MCP server over it, following the existing pattern in `Sources/relay-actions-mcp/` and `Sources/relay-vision-mcp/` (Swift MCP servers that talk to the app over a socket and send `tool_fired` so ActionGlow pulses).

Tools for `relay-app-mcp` (namespace `mcp__relay-app__*`), each returning structured JSON and an error when the app is not running:

1. `app_status`: version, build, session state and project, Remote mode, paired devices count, permissions summary.
2. `navigate`: open the Workspace, Notetaker, Terminal or Settings, and a specific settings page (`permissions`, `speech_to_text`, `text_to_speech`, `general`, `awareness`, `relay_remote`).
3. `get_settings` / `set_settings`: read the effective `AppConfig` and apply a partial update through `AppState.saveConfig` (the same validation and restart behaviour as Save in the UI). Reject unknown keys; never expose credentials.
4. `list_projects`, `select_project`, `start_session {project_id}`, `end_session`: through the RR-456 socket handlers.
5. `relay_remote_devices`, `relay_remote_unpair {device_id}`, `relay_remote_begin_pairing` (returns the pairing payload and expiry), `relay_remote_pending_approval`, `relay_remote_approve {restrict_to_network}`, `relay_remote_deny`: driving `RelayRemoteController` exactly as the settings page does, including the "Only from my home network and Tailscale" option.
6. `keep_awake {on}`: via `KeepAwakeController.toggle()` semantics (report pending states).

Rules: every tool is idempotent or reports clearly when it is not; destructive ones (`end_session`, `relay_remote_unpair`) require an explicit `confirm: true` argument; every call emits `tool_fired` so ActionGlow pulses; the socket accepts connections only from the same user. Add the instruction chunk under `services/instructions/` (prefer `relay-app` over screenshots and clicks for anything in Relay Runner itself), regenerate with `scripts/build-instructions`, register the server wherever Relay Runner registers `relay-actions-mcp` for Claude and Codex sessions, and document it in `docs/specs/` and the Naming notes in CLAUDE.md.

Tests: unit tests for the app-side command parser and each handler through injected closures; MCP server tests mirroring `relay-actions-mcp`'s; a loopback test that drives `navigate`, `set_settings` and the pairing sequence against a fake socket.

## Acceptance criteria

- [ ] `relay-app-mcp` builds, lists the tools above, and each call reaches the app over the control socket and returns structured JSON; when the app is not running the error says so.
- [ ] `set_settings` applies a partial update through the same path as the Settings Save button and the change is visible in `config.toml` and the UI (test through injected AppState handlers).
- [ ] The pairing sequence can be completed end to end through the MCP with `restrict_to_network: true`, producing an `authorized_keys` entry with a `from=` clause (test with the existing pairing test doubles).
- [ ] `end_session` and `relay_remote_unpair` refuse without `confirm: true`.
- [ ] Every tool emits `tool_fired`; the instruction chunks for Claude and Codex are regenerated and tell agents to prefer `relay-app` over Relay Vision and Relay Actions for Relay Runner's own UI.
- [ ] `swift build` and `RelayRunnerTests` pass; the run log shows a session where the pairing page was configured without a screenshot.
