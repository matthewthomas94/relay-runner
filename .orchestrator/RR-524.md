## Description

The bridge's deterministic voice-turn classifier treats any occurrence of a cancel word, anywhere in a turn, as a cancel command, and splits a turn into separate work items at "and/then/but" followed by an action verb. Both rules misfire on long dictated descriptions, where the user is describing behaviour, not giving Relay an order.

Both failures happened on 2026-11-22 in one general session while the user dictated a feature description. Nothing was running, so nothing was lost, but with accepted work in flight the first one would have revoked its authorization.

### Failure 1: a description was classified as a cancel

The turn was about 250 words describing a new session menu. It contained this sentence, describing what an X button in the UI does:

> If there is a session active, that plus will turn into an X and that's how they stop the session. Uh that's what I'm thinking.

The claimed command carried `action: control`, `reason: cancel`, `disposition: cancellation`, `outcome: control action cancel`, `cancellation_scope: item`, `authorization_relationship: redirect`, route `replace_current`, effect `revoke_conflicting`, and `target: "session uh s what i m"`.

Why it matched:

- `CANCEL` in `rust/relay-intents/src/arbitration.rs` is `\b(cancel|stop|abort|scratch\s+that|never\s+mind|nevermind)\b`, searched anywhere in the text. `explicit_cancel_requested` is that search after removing negated forms. There is no check that the word is an instruction to Relay: here its subject is "they" and it sits in the middle of a long description.
- `classify_command` in `rust/relay-services/src/command_actions.rs` returns `Control` / `cancel` on that match before it considers discussion or work.
- `CANCEL_TARGET` then takes everything after the first cancel word as the target, which produced the nonsense target above. A target makes the scope `item`, and `matching_prior_item` can then mark an earlier item in the same turn cancelled if it shares a word with that target.

### Failure 2: the end of a sentence became a separate desktop action

The next turn ended with this sentence:

> A session doesn't get started from the wheel unless they go into the submenu and click one of the four names that appear in that submenu.

`ITEM_BOUNDARY` in `arbitration.rs` split it at "and click", because "click" is in `ITEM_START`. The tail, "click one of the four names that appear in that submenu.", was injected into the PM as its own item with `action: direct_action`, `reason: desktop_control`, under the foreground computer-action contract. The subject of "click" is "they" (the app's users); it was not a request to click anything.

### What to change

Make both rules require that the verb is an instruction addressed to Relay, not a verb inside a description. The exact rule is yours to design; the constraints are:

- A cancel word counts only in imperative position: at the start of the turn or of a sentence/item, optionally after fillers and politeness ("okay", "uh", "um", "actually", "please", "can you", "could you"), or in an existing explicit form such as "cancel RR-400" or "scratch that". A cancel word with its own subject ("they stop", "it stops", "the user stops", "that's how they stop", "how to stop", "when it stops") is not a cancel.
- An item boundary at "and/then/but + verb" must not be created inside a clause whose subject is a third party ("unless they go into the submenu and click …", "the user opens the menu and selects …"). When unsure, keep the text in one item: the PM reads the whole turn and is authoritative, so a missed split costs less than a false action.
- When a long turn contains a cancel word that is not in imperative position, classify the turn by its other content and do not produce a cancellation, a redirect, or a cancel target.
- Keep the change deterministic. Do not add a model call.

Read the existing tests first (`arbitration.rs` tests for item, all-work, ticket and vague scopes and for negation; `command_actions.rs` tests `internal_controls…` and `negated_stop_status_request_is_not_a_cancel_control`) so the short commands they cover keep their behaviour.

## Acceptance criteria

- [ ] A test feeds the full text of Failure 1's sentence, inside a turn of at least 100 words of description, through `classify_command` and `normalize_voice_work_items` / `resolve_intent_disposition`: the result is not `Control` / `cancel`, has no cancellation disposition, no cancel target, and does not use route `replace_current` or effect `revoke_conflicting`.
- [ ] A test feeds Failure 2's sentence through `normalize_voice_work_items`: it yields one item, and nothing in the turn is classified `desktop_control`.
- [ ] Tests cover at least these non-cancel descriptions: "that's how they stop the session", "the X is how the user stops it", "it should stop playing when the lid closes", "tell me how to cancel a run".
- [ ] These still classify as cancel, with the same scope as before the change: "stop", "cancel that", "okay stop", "please cancel the build", "Cancel RR-400", "uh, actually stop that", "scratch that", "never mind", and "write the ticket. Stop the build." (second sentence).
- [ ] These still split into two items as before: "open Chrome and click the Add project button", "fix the test and then run the suite".
- [ ] "stop the audio" / "stop talking" keep their speech-only handling.
- [ ] Every existing test in `rust/relay-intents` and `rust/relay-services` passes, and `cargo test` for those crates is reported in the run log.
- [ ] `docs/` text that describes voice-turn classification, if any names these rules, matches the new behaviour.
