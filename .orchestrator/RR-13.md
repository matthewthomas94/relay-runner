## Description

Today every behavioral rule about the Relay stack lives in `CLAUDE.md` at the root of the `relay-runner` repo. That file is **repo-scoped** — Claude Code only loads it when the working directory is `relay-runner`. So anyone who downloads the Relay Runner `.app`, installs it, and then opens Claude Code in their own project gets **zero** of these rules. Their Claude session will:

- Fall through to native `mcp__computer-use__*` for screen control because nothing told it to prefer `mcp__relay-actions__*`.
- Call `mcp__relay-actions__propose_action` expecting a confirmation gesture, and block for 30s until timeout.
- Re-derive the board-toggle hotkey from scratch every time, taking ~90s instead of the documented one-liner.
- Have no idea about the discuss → ticket → refine/promote → integrate orchestration workflow when invoking `/relay-dispatch`.
- Miss the 401 auto-recovery pattern that just got added.

The transfer vector is **MCP Server Instructions** — every MCP server can return an `instructions` string from its `initialize` response, and Claude Code surfaces those as durable rules at the top of every conversation that connects to that server (you've seen this for `computer-use`, `figma-remote`, and other MCPs). Mirroring the rules there means any Claude session that connects to `relay-actions-mcp` or `relay-orchestrator-mcp` gets the rules — regardless of project, regardless of CLAUDE.md presence.

Ship the rules via that vector, **and** introduce a single source of truth so CLAUDE.md and the MCP server instructions can never drift. Two files saying the same thing is one too many.

## Acceptance criteria

### Single source of truth

- Introduce a versioned, ordered set of behavioral-rule chunks at a stable path inside the repo — e.g. `services/instructions/` or `Sources/RelayInstructions/`. One markdown file per concern, named for what it covers. At minimum:
  - `relay-actions-vs-computer-use.md` — never use `mcp__computer-use__*` when `mcp__relay-actions__*` covers it.
  - `propose-action.md` — don't call `propose_action`; ask via chat if uncertain.
  - `board-hotkey.md` — the `osascript control+option` chord (gated on `/tmp/voice_bridge.sock`).
  - `look-at-screen-intent.md` — voice "look at my screen" → fire `mcp__relay-actions__screenshot` immediately.
  - `orchestration-workflow.md` — discuss → write tickets → refine/promote → integrate.
  - `recovery-401-auth.md` — auto-recover by opening Terminal + `claude` + `/login`.
  - `naming.md` — RelayActions vs ActionGlow (renamed in RR-9) vs RelayVision (the *new* observation namespace from RR-10).
- Each chunk is plain markdown — no Swift, no codegen artifacts. They are the canonical source.

### MCP server instructions wired up

- `Sources/relay-actions-mcp/` returns an `instructions` payload from its `initialize` response that **concatenates** the relevant chunks: `relay-actions-vs-computer-use.md`, `propose-action.md`, `board-hotkey.md`, `look-at-screen-intent.md`, `naming.md`. Use a small Swift load-at-build-time mechanism so the chunks ship inside the binary (resource bundle, Swift literal, or build-script-generated constant — pick what fits Package.swift cleanly).
- `Sources/relay-orchestrator-mcp/` returns an `instructions` payload concatenating: `orchestration-workflow.md`, `recovery-401-auth.md`, `naming.md`.
- Both servers' instructions are populated even when the binary is invoked outside the `relay-runner` repo — chunks are baked in, no filesystem dependency at runtime.
- After this ticket: a fresh `claude` session opened in `~/some-other-project` that connects to relay-actions-mcp shows the relay-actions rules in its MCP Server Instructions block at the top of the prompt. Verify manually.

### CLAUDE.md regenerated from the same source

- `CLAUDE.md` is no longer the canonical home of these rules — the chunks are. Either:
  - **Option A (preferred):** Add a build step / make target / script (e.g. `scripts/build-claude-md`) that concatenates all chunks into `CLAUDE.md`, with the "Where things live" + project-specific bits as a hand-edited preamble or postamble. Run it as part of the install path so checked-in `CLAUDE.md` stays in sync.
  - **Option B:** Keep `CLAUDE.md` hand-edited as it is, but add a CI/pre-commit check that diffs the relevant sections against the chunks and fails if they diverge.
- The current `CLAUDE.md` content for the "Always use the custom Relay stack", "Asking for permission", "Recovery patterns", "Naming notes", and "The orchestration workflow" sections becomes the seed content of the chunks (post-RR-9 / post-RR-10 wording — i.e. ActionGlow not RelayVision for the overlay, RelayVision for the new observation namespace).
- Add a short note near the top of `CLAUDE.md` explaining the new model: "Behavioral rules below are mirrored into `relay-actions-mcp` and `relay-orchestrator-mcp` so they ship to any Claude session that connects to those servers. Source of truth lives in `services/instructions/`."

## Notes

- This ticket depends on RR-9 (overlay rename to ActionGlow) and RR-10 (vision namespace split). If you start work before both have merged, you'd lift outdated content into the chunks. The auto-promotion will dispatch this ticket only when both predecessors land.
- The MCP Server Instructions surfaced to Claude have practical length budgets — they consume context. Don't lift the entire CLAUDE.md, only the behavioral rules. Skip the "Where things live" repo-specific paths section (it would be meaningless in someone else's project).
- The Swift MCP server SDK exposes the `initialize` response — see how the existing servers respond and add the `instructions` field. If the SDK doesn't currently surface that field, extending it is part of this ticket (or surface that gap and the orchestrator will adjust scope).
- Don't forget: the bundled `.app` ships with copies of these MCP servers. The DMG-build action handles propagation — just commit the changes here and they'll flow into the next build.
- The `Sources/relay-orchestrator-mcp/` module is the proxy MCP that exposes the orchestrator daemon's HTTP API as MCP tools (`dispatch_ticket`, `list_runs`, `get_run`, `cancel_run`). It's the right place for the workflow/recovery instructions because those rules govern how to *use* the orchestrator's MCP tools.
- The `Sources/relay-actions-mcp/` module is the right place for the screen-control rules because those rules govern how to *use* the actions tools and how they interact with native alternatives.
