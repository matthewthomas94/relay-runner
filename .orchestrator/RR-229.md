## Description

Replace version-pinned agent model choices with stable provider-family choices
that resolve to the newest available model at runtime. Relay Runner currently
hardcodes Codex model IDs such as `gpt-5.6-sol`, `gpt-5.5`, and `gpt-5.4`
across Swift configuration, Python services, messenger defaults, worker sizing,
launch validation, and tests. Every catalogue change therefore requires an app
release even when the user's intent has not changed.

For Codex, expose only the stable families **Sol**, **Terra**, and **Luna** in
Settings and onboarding. Persist the family rather than a numbered model ID,
then resolve it to the highest account-visible numeric version for that family
before launching a session or worker. The installed Codex CLI `0.146` app-server
protocol exposes `model/list`, including concrete model IDs, hidden/default
state, and supported reasoning efforts; use the provider-owned runtime
catalogue instead of maintaining a second static catalogue in Relay Runner.
Keep catalogue access and family/version parsing behind one shared resolver.

Claude already provides stable aliases. Keep **Best**, **Fable**, **Opus**,
**Sonnet**, and **Haiku** without pinning model numbers. Remove the ambiguous
user-facing **Default** model choice for both providers. Migrate existing
Codex `default` or generic numbered selections to Sol, existing suffixed Codex
models to their matching family, and Claude `default` to Best. These explicit
migration defaults are proposed so a saved configuration never silently
inherits an unknown provider default.

Use the same resolution path for the foreground orchestrator, configured
messenger family, inherited sub-agent defaults, and provider-neutral Codex
worker tiers. Codex worker tiers should map `fast` to Luna, `balanced` to Terra,
and `strong` to Sol before resolving the newest concrete version; the existing
Claude Haiku/Sonnet/Opus tier mapping remains stable. Do not redesign the ticket
sizing vocabulary.

Reasoning-effort choices must come from the resolved model's advertised
capabilities rather than a version-specific matrix. A provider-managed effort
may remain internally representable, but the UI must not present an unexplained
bare “Default”; show the concrete advertised default or explanatory provider
semantics.

## Acceptance criteria

- [ ] Codex Settings and onboarding show only Sol, Terra, and Luna model
      families, with no numeric versions or user-facing Default model option.
- [ ] Claude Settings and onboarding retain Best, Fable, Opus, Sonnet, and
      Haiku stable aliases, with no user-facing Default model option.
- [ ] A single Codex catalogue resolver uses the installed provider's
      account-visible `model/list` data and selects the highest numeric version
      matching the chosen family while excluding hidden or incompatible models.
- [ ] Fixture catalogues containing later versions such as `gpt-5.7-sol` and
      `gpt-6.0-terra` resolve correctly without changing an application model
      list or shipping a new Relay Runner build.
- [ ] If the selected family cannot be resolved, launch fails with an
      actionable visible error; it must not silently use the provider default,
      a different family, or a stale hardcoded version.
- [ ] Saved Codex family selections resolve consistently for foreground
      sessions, messenger sessions, inherited user-default workers, and
      fast/balanced/strong worker tiers; Claude continues to use its stable
      provider aliases across the same consumers.
- [ ] Existing configs migrate deterministically: Codex suffixed IDs preserve
      their family, Codex Default or generic numbered IDs become Sol, Claude
      Default becomes Best, and cross-provider values cannot leak.
- [ ] Effort options and validation derive from the resolved model catalogue,
      including newly advertised values, and the UI explains any
      provider-managed effort instead of showing an ambiguous bare Default.
- [ ] Runtime/status evidence records both the stable selected family and the
      resolved concrete model ID so launches remain auditable.
- [ ] Swift and Python tests cover catalogue refresh/fallback, semantic version
      ordering, unavailable families, config migration, Settings/onboarding,
      foreground launch flags, messenger resolution, worker tier resolution,
      and Codex/Claude provider parity.
- [ ] Static numbered Codex model allowlists and duplicated version-specific
      effort matrices are removed from production paths; model catalogue drift
      no longer requires a Relay Runner app update.
