## Description

Relay Runner can reach a misleading state where the Python voice bridge process and `/tmp/voice_bridge.sock` are alive, but the agent-side `/relay-bridge` consumer loop is not running. In that state the app may still treat the session as active, the user can speak, and voice input can be accepted by the bridge, but Codex/Claude does not consume `/tmp/voice_cmd_ready`.

This happened after the agent stopped its polling loop while leaving the bridge daemon alive. The next spoken messages were not seen by the agent. A healthy voice session needs both sides: the bridge daemon and an active consumer heartbeat.

Harden the app/bridge/session lifecycle so this state is detected quickly and recovered or surfaced accurately. Do not rely on the user noticing missing responses.

## Acceptance criteria

- [x] Reproduce or simulate a bridge daemon that is alive with `/tmp/voice_bridge.sock` present but no active agent consumer loop touching `/tmp/voice_bridge_heartbeat`.
- [x] Relay Runner no longer treats a missing or stale consumer heartbeat as a healthy active session once the modern heartbeat protocol should exist.
- [x] If a voice command is pending in `/tmp/voice_cmd_ready` and the consumer is absent, the app surfaces or recovers deterministically instead of silently letting messages sit unread.
- [x] The recovery behavior preserves compatibility for both Codex and Claude relay-bridge sessions.
- [x] Existing old-session fallback behavior, if still needed, is documented with a bounded grace period rather than indefinite "benefit of doubt."
- [x] Add targeted tests or logging around the bridge-consumer liveness decision.
