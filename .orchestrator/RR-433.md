## Description

The pairing confirmation in Relay Runner Settings offers the toggle "Only from my home network and Tailscale" (`Sources/relay-runner/Settings/RelayRemoteSettingsTab.swift`, line 171). When it is on, `RelayRemotePairing` passes `RelayRemoteHostInfo.networkRanges()` as `fromRanges` (`Sources/relay-runner/Remote/RelayRemotePairing.swift`, line 210) and `RelayRemoteAuthorizedKeys` writes them as a `from="..."` option on the device's line in `~/.ssh/authorized_keys` (`Sources/relay-runner/Remote/RelayRemoteAuthorizedKeys.swift`, line 107).

`networkRanges()` (`Sources/relay-runner/Remote/RelayRemoteHost.swift`, line 167) is built from `ipv4Interfaces()` (line 180), which enumerates `AF_INET` interfaces only (line 189), plus the Tailscale ranges `100.64.0.0/10` and `fd7a:115c:a1e0::/48`. No IPv6 home-network range is included: neither the link-local prefix `fe80::/10` nor the LAN's unique-local or global IPv6 prefixes.

On the home network the phone does not arrive over IPv4. `MacEndpointResolver.candidates()` (`ios/RelayRemoteKit/Sources/RelayRemoteKit/Discovery.swift`, line 17) tries the Bonjour `_ssh._tcp` service first, and `NWConnection` resolves it to the Mac's IPv6 link-local address. During the RR-428 device checks on 2026-10-25, `lsof` on the Mac showed every SSH session from the paired iPhone arriving from the phone's `fe80::/10` address at the Mac's `fe80::/10` address, never from the LAN IPv4 address. sshd skips an authorized key whose `from=` list does not match the client address, so with the toggle on the phone's key is refused on the home path.

The phone cannot recover from that refusal. `RemoteSession.openChannel()` (`ios/RelayRemoteKit/Sources/RelayRemoteKit/RemoteSession.swift`, line 275) iterates the endpoint candidates but rethrows any failure whose `isTerminal` is true (line 284), and `RemoteFailure.authenticationRejected` is terminal (`ios/RelayRemoteKit/Sources/RelayRemoteKit/RemoteFailure.swift`, line 28; raised from `ios/RelayRemoteKit/Sources/RelayRemoteKit/HostKeyPinning.swift`, line 54). The stored LAN IPv4 address, which would match the `from=` list, is never tried, and the user sees the device-key-rejected failure while at home, the opposite of what the toggle promises.

The pairing accepted on 2026-10-25 had the toggle off, so nothing is broken today. The defect is that the restriction cannot be enabled without losing home-network connectivity on an IPv6-capable LAN, which describes every current Apple network.

Required behavior:

- With the toggle on, a connection from the home network is accepted whether the phone arrives over IPv4, an IPv6 link-local address or the LAN's IPv6 prefix, and a connection from an address outside the home network and Tailscale is still refused.
- Decide how to get there and record the choice in the run log. Options, which may be combined: (a) extend `networkRanges()` to enumerate `AF_INET6` interfaces as well and emit the link-local and LAN IPv6 prefixes in a form sshd's `from=` matcher accepts; check how sshd on macOS renders a link-local client address (it carries a `%<interface>` scope id, and OpenSSH's address comparison in `addr.c` includes the scope id, so a bare `fe80::/10` pattern may not match) and keep the Tailscale IPv6 prefix; (b) make the phone continue to the next candidate when one endpoint rejects authentication and surface `authenticationRejected` as terminal only once every candidate has rejected it, so a key limited to IPv4 ranges still works through the stored LAN address; (c) prefer IPv4 for Bonjour-resolved endpoints on the phone.
- Whatever is chosen, `RelayRemoteAuthorizedKeys.parse` (line 185) must keep reporting `restrictedToNetwork` correctly for the new line format, and the Relay Remote spec (`docs/specs/relay-remote.md` where it exists on the target branch) plus `ios/README.md` must state precisely what "home network" means for the restriction and what the phone does when one address is refused.

Do not modify the user's real `~/.ssh/authorized_keys` or system sshd configuration while verifying. A throwaway non-root `sshd` on a high port with its own config, host key and authorized_keys file, reached at `fe80::1%lo0`, is enough to observe `from=` matching for a link-local client.
