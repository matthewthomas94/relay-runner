## Description

Make RR-325 safely resumable after two defects were discovered during verification-blocked reconciliation.

First, `scripts/speech-latency-report.py` currently groups playback by command identity without retaining or enforcing the utterance's authority and lifecycle role. The mounted 2026-08-22 sample for command sequence 10 therefore correlated a non-authoritative Messenger handoff (`authoritative: false`, `kind: handoff`) with the provider acknowledgement and reported 3,365.099 milliseconds. RR-325 requires the retained authoritative final, and duplicate detection concerns authoritative effects; a handoff must neither become the latency sample nor invalidate one valid authoritative final.

Second, canonical RR-325 preserves historical run 36, while the current live ledger's run 36 belongs to RR-338. The existing `reconcile_preserved_run` path correctly refuses to overwrite that row, but `resume_verification_blocked(run_id: 36)` cannot safely target RR-325. Add the narrowest daemon-owned recovery path that gives RR-325 an unambiguous canonical run link while preserving its historical run/attempt audit evidence and leaving RR-338's row unchanged. Do not silently rewrite or delete either history, dispatch verification, progress dependencies, or claim mounted UAT as part of the repair.

## Acceptance criteria

- [ ] The speech latency reporter retains the playback utterance's authority, kind, source, lifecycle role, command identity, play-request identity, and utterance identity when selecting mounted samples.
- [ ] A regression with one non-authoritative Messenger handoff and one authoritative final for the same acknowledged command produces exactly one latency sample from the authoritative final; a handoff-only command produces no sample.
- [ ] Duplicate authoritative playback identities fail closed, while non-authoritative conversational playback does not count as a duplicate authoritative effect.
- [ ] Documentation states the exact mounted RR-325 sample contract and distinguishes process evidence from human audible attestation.
- [ ] A clean committed `verification_blocked` ticket whose historical `run_id` collides with another ticket's live ledger row can be recovered through an explicit, idempotent daemon/MCP action that leaves the existing row byte-for-byte unchanged and records the old and replacement identities in canonical audit evidence.
- [ ] The collision recovery fails closed for dirty ticket evidence, nonterminal tickets, mismatched repositories, missing historical run-log evidence, and repeated or ambiguous recovery attempts.
- [ ] After collision recovery, the ordinary explicit resume path resolves RR-325 rather than RR-338; recovery itself does not resume, dispatch, progress dependencies, or represent external verification as passed.
- [ ] Focused speech reporter, dispatch, queue-drain, Program status, reconciliation, and MCP tests pass for both ordinary missing-row recovery and the new occupied-ID case.
