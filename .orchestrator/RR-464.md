## Description

Spoken replies from the foreground session and from background sessions are handled by `services/speech_coordinator.py` (the single speech gateway, 1,556 lines) and shown on the notch by `TranscriptionPill` (reply pill plus stacked cards). The user reports, on 2026-11-06, that replies regularly get dropped when several arrive close together, from one session or from several, and that the handling is "kind of terrible". The requested behaviour is a single bottleneck queue:

1. Every final reply enters one FIFO, whatever session it came from.
2. When a reply has been played, it leaves the queue and the next one plays (auto-play) or waits for Play (manual).
3. A reply that has not been played stays queued until the user listens to it or skips it. Nothing else removes it.
4. The notch keeps showing the stack while anything is queued: up to three cards visible, even when five are queued, with the count available.

What drops replies today (read at commit 0d212a6a):

- `SpeechCoordinator.submit` (around line 606): when the incoming intent is from a newer command than the current one (`_newer_command`), it sets `replace_committed` and calls `self._backlog.clear()`. That wipes every queued reply, including unplayed finals from other sessions. This is the main cause.
- `interrupt(command_key)` (around line 755): a newer command marks the committed and playing intents stale and drops every backlog intent whose `command_key` differs and whose `freshness_scope` is not `work`. Dropped finals are only kept as replay history, which holds `REPLAY_HISTORY_LIMIT` items, so older ones vanish.
- `_drop_obsolete_backlog` (around line 1462) replaces queued `handoff`/`progress` intents of the same command with its later superseding intent. This one is correct and should stay: a progress line is obsolete once the final for that command arrives.
- `TranscriptionPill.stackCards` holds two views, so `setStackDepth` is capped at 2 regardless of how many replies wait. The depth comes from `AppState.sessionReplyBadges` summed (`AppState.swift:283`), which counts unread background replies, not the coordinator's queue.

Required behaviour:

- Finals (`kind` in the final/reply set; confirm the exact kinds from `SUPERSEDING_KINDS` and the intent kinds in the module) are never removed from the backlog by another intent arriving. Only `handoff`/`progress` of the same `command_key`, and a fallback replaced by its real final (RR-460), may be replaced.
- A newer command still interrupts current playback if that is today's barge-in behaviour, but the interrupted final goes back to the head of the queue as unplayed unless the user skipped it; queued finals from other commands are untouched. Keep `freshness_scope == "work"` semantics for progress items.
- Order is arrival order across sessions. Do not reorder by session or focus; a focus switch or wheel stop does not advance or drop (the module already states this for replay, extend it to the queue).
- Played means playback completed, or the phone acknowledged playback when a remote sink is active (`_submit_remote_locked`, the phone's `speech_audio` acks). Partial playback that the user stopped keeps the item queued; `skip`/`cancel` removes the current item only; `stop`/`pause` keeps it. `play` resumes the head of the queue. Replay keeps working on the last played item.
- Queue depth is bounded only by a generous safety cap (for example 50) with a diagnostic when hit; below that nothing is dropped.
- The notch stack shows `min(queued, 3)` cards (`TranscriptionPill.stackCards` becomes three, with the existing fan-out motion extended to the third card per the RelayMotion rules) and exposes the true queued count for the badge path. Drive the depth from the coordinator's queue, not from `sessionReplyBadges` alone; keep the per-session badge counts as they are for the Workspace and the wheel.
- Phone parity: when Relay Remote owns playback, the same FIFO applies and the phone's queue (RR-458 `SpeechPlaybackQueue`) receives items in the same order with one ack each; a disconnect returns unplayed items to the Mac queue.
- Diagnostics: every drop or replacement already emits `_diagnostic(...)`; after this change a `replaced` diagnostic must name the same `command_key`, and there must be no `interrupted` diagnostic for a final that was merely queued behind a newer command.

Record the exact rules as a table in `docs/architecture.md` next to the TTS worker paragraph (around line 40), and the tests mirror that table.
