## Description

Introduce a persistent per-project or per-session orchestrator that starts with a Relay Runner bridge/session and remains available while that session is active.

This is the foundation for RR-127. The current system treats the foreground Codex/Claude session as the orchestrator and the daemon as a worker dispatcher. That assumption appears in `services/command_actions.py`, `services/voice_bridge.py`, `services/orchestrator.py`, `docs/orchestrator.md`, `AGENTS.md`, and generated Relay skills. This ticket should add the lifecycle primitive without yet changing every downstream behavior.

The persistent orchestrator should be event-driven and durable enough to receive commands, expose state, and survive idle periods without continuously spending model tokens. It must have provider-parity handling for Codex and Claude or document deliberate provider differences.

## Acceptance criteria

- [x] Define where the persistent orchestrator lives: process, run record, state file/database row, or managed session.
- [x] Starting `/relay-bridge` or Start Session for a project ensures the orchestrator is started or reused for that project/session.
- [x] The orchestrator lifecycle handles project switching, bridge stop, daemon restart, stale sessions, and provider changes.
- [x] The orchestrator exposes heartbeat/readable state so the PM can tell whether it is idle, planning, awaiting workers, reviewing, blocked, or failed.
- [x] The lifecycle does not require continuous token spend while idle.
- [x] Codex and Claude startup/auth/model differences are handled or explicitly documented.
- [x] Add focused tests or harness coverage for start, reuse, heartbeat, stop, and project switch behavior.
