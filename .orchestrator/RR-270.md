## Description

Run a time-boxed product and architecture spike for a revised Relay artifact model: every registered project repository keeps its own canonical `.orchestrator/` folder, and durable tickets and ticket lifecycle updates are committed to that project repository and synchronized through its user-controlled GitHub remote. Relay Runner must not require an app-owned central artifact repository, a parent repository containing all projects, repository nesting, or submodules.

Treat Workspace as a logical collection of explicitly registered repositories, not as a filesystem root. Through a Codex-style Add project flow in the Workspace UI, the user must be able to select Git repositories from unrelated locations anywhere they can access on the Mac. Relay must operate on each repository in place without moving, copying, nesting, or requiring it to be a descendant of the folder used to open Workspace. Registration must persist across relaunches, and removing a project from Workspace must unregister it without deleting or modifying the repository.

Define one fixed, Relay-owned application-support home in the standard macOS location for app-global files such as the project registry, persistent filesystem-access grants, Program/Graphify data, indexes, caches, daemon state, and other non-project configuration. Relay Runner must create and locate this home automatically: the user must not choose, browse for, or reopen a Workspace folder to use Workspace. Opening Workspace should load the persisted project registry directly, with an empty state when no projects are registered. A filesystem browser should appear only as part of adding or creating a project. The spike must specify the directory layout, ownership, backup and fresh-install behavior, migration from current workspace-root assumptions, and recovery from missing or corrupt app-global state. This application-support home must not become a parent directory for projects, a Git repository the user has to manage, or a second canonical writable store for project tickets that can diverge from each repository's `.orchestrator/` history.

Define an explicit scope-selection contract before Relay creates project work or performs a project mutation. The user must be able to choose an existing registered repository, create and register a new project repository, or identify work that is not yet attached to a project. Follow-up turns may inherit a confirmed thread scope until redirected, but filesystem location or terminal working directory alone must not silently determine ticket ownership. Resolve how intentionally unscoped work is handled without reintroducing a second canonical ticket store that can diverge from repo-local `.orchestrator/` state.

Design the repo-local ticket lifecycle from authoring through archival. All durable ticket content and lifecycle changes must have Git history and be eligible for synchronization to the project’s GitHub remote, while the locally materialized `.orchestrator/` working set should contain only tickets with relevant activity in the most recent 30 days. Define the age anchor, active-work exemptions, transition timing, on-demand restoration, offline behavior, deletion semantics, and user-visible states. Preserve older tickets remotely and make them discoverable and recoverable without requiring every historical ticket to remain in the current working tree.

The spike must confront the difference between working-tree file count, Git object/history size, Relay indexes or databases, attachments, and other local caches. Compare concrete Git-compatible strategies for keeping the 30-day working set bounded—for example archival commits, dedicated refs or branches, shallow or filtered synchronization, and generated local indexes—and recommend one canonical, non-divergent model. The recommendation must explain commit granularity, allowlisted staging, fetch/rebase/push ordering, a single-writer boundary, multi-device conflicts, retries, recovery, no-force-push behavior, and coexistence with ordinary project source changes.

Map the current repo-local `.orchestrator` source of truth, workspace-folder and child-repository discovery, project registry, path and stable-identity handling, macOS persistent folder access, Program/Graphify data, worker ticket snapshots and attachments, run audit history, fresh-install preservation, workspace activation, and existing repositories that may not yet have a usable GitHub remote. Define privacy and size boundaries for tickets, secrets, logs, caches, indexes, attachments, raw audio, and sensitive transcripts; remote storage must not be treated as unlimited or automatically safe merely because a repository is private.

The spike must end with a recommended target architecture, repository layout, scope-selection state machine, retention and synchronization state machines, migration plan, verification strategy, phased implementation tickets, and documented rejection reasons. It must not implement the migration, create or modify GitHub repositories, change routing, archive existing tickets, or alter production synchronization behavior.

## Acceptance criteria

- [x] The current dependencies on working directory, workspace roots, active-project resolution, repo-local `.orchestrator` ownership, Program/Graphify data, worker materialization, and fresh-install preservation are mapped with concrete code and data boundaries.
- [x] The target topology keeps each registered project’s canonical `.orchestrator/` inside that project repository and commits durable ticket content and lifecycle changes to that repository, without an app-owned central artifact repository, parent-repository requirement, nesting, or submodules.
- [x] Workspace is specified as a logical registry that can contain explicitly added repositories from unrelated filesystem locations; no repository must live beneath a shared Workspace folder or be moved, copied, nested, or rewritten when added.
- [x] The target architecture defines one automatically managed Relay Runner application-support home in the standard macOS location for app-global configuration and state, including its exact layout, ownership boundaries, backup and fresh-install behavior, migration path, and corruption recovery.
- [x] The user can open Workspace without choosing, browsing for, or reopening a Workspace folder; Relay loads the persisted project registry directly and presents an empty Add project state when the registry has no projects.
- [x] Folder browsing is limited to the Add/create project flow. The app-owned support home is never presented as a Workspace root, never contains or relocates registered project repositories, and never becomes a second canonical writable ticket store alongside project-local `.orchestrator/` history.
- [x] The Workspace UI includes a Codex-style Add project flow that validates a selected Git repository, prevents duplicate registration of the same repository identity, surfaces the resolved path before confirmation, and makes no recursive child-repository discovery a prerequisite.
- [x] Registered paths and the filesystem authorization needed to reopen them persist across app relaunches; the design covers moved, renamed, deleted, disconnected-volume, permission-revoked, symlinked, bare, and worktree-backed repositories with clear recovery behavior.
- [x] Removing a project from Workspace only unregisters it and releases Relay-owned access state; it never deletes the repository, its `.orchestrator/` folder, Git history, remote, or project files.
- [x] The work-scope state machine covers an existing registered repository, creating and registering a new project repository, and intentionally unscoped work, including confirmation, follow-up inheritance, redirection, cancellation, unavailable projects, and unresolved-scope behavior.
- [x] The interaction design specifies equivalent UI and voice behavior for choosing scope and avoids silently inferring ownership from terminal cwd while limiting repeated prompts inside an already confirmed work thread.
- [x] A precise 30-day local-materialization policy defines the age anchor, time-zone and boundary behavior, active or blocked ticket exemptions, archival timing, offline handling, deletion semantics, and how a restored ticket becomes locally active again.
- [x] Older tickets remain durably represented in the project’s remote Git history and are discoverable, inspectable, and restorable on demand without keeping every historical ticket file in the normal `.orchestrator/` working set.
- [x] The report separately measures or estimates working-tree ticket count, `.git` object/history size, Relay database or index size, attachments, and caches; it does not claim local bloat is solved by removing files from the current tree if full Git history is still cloned locally.
- [x] At least two viable Git-compatible retention/materialization strategies are compared, with one recommended canonical model and explicit rejection reasons; no bidirectional mirror or second writable ticket source may diverge from project Git history.
- [x] The Git synchronization state machine covers ticket-only commit granularity, allowlisted staging, project-source isolation, remote bootstrap or missing-remote behavior, fetch/rebase/push ordering, local-only and offline operation, multi-device conflicts, retries, status reporting, recovery, and prohibition of force-push.
- [x] The worker contract explains how dispatch, worktrees, review, dependencies, attachments, run logs, merge auditing, archival, and restoration function when tickets remain owned by each project repository.
- [x] Migration covers existing `.orchestrator` trees, attachments, run audit history, Program/Graphify records, open and historical tickets, repositories without GitHub remotes, and rollback without silently losing ticket provenance.
- [x] Privacy and storage policy distinguishes Git-suitable ticket text and small assets from secrets, caches, indexes, transient run state, large binaries, raw audio, and sensitive transcripts, and validates the recommendation against documented GitHub limits rather than assuming unlimited storage.
- [x] The recommendation documents equivalent Codex and Claude behavior and any intentional provider-specific differences in session routing, authentication, or execution context.
- [x] The final report includes repository and data-flow diagrams, product tradeoffs, migration phases, test fixtures for age and sync edge cases, manual recovery scenarios, and cold-start follow-up tickets, while making no production changes in this spike.
