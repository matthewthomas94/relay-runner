## Description

Run a time-boxed product and architecture spike to remove any implicit requirement that Relay Runner own, live above, or be launched from a parent folder containing the user’s project repositories. Design an app-owned Relay artifact repository that is independent of every project checkout and can use a user-controlled private GitHub repository as its synchronization and history layer. Project repositories must remain independent peers: Relay may reference and operate against them after an explicit user choice, but the artifact repository must never contain, nest, submodule, or automatically stage their source files.

Define an explicit scope-selection contract for each new work thread before Relay creates project work or performs a project mutation. The user must be able to choose an existing registered repository, create a new project/repository, or declare the work out-of-project. Follow-up turns may inherit the confirmed thread scope until the user redirects it, but filesystem location or terminal working directory alone must not silently determine ownership. Specify the UI and voice behavior for unresolved, unavailable, moved, newly created, and intentionally general work.

Design the artifact repository’s canonical information model. It should organize Relay-generated tickets, attachments, decisions, research, specifications, session summaries, and future note-taker transcripts or notes by stable project ID, new-project intent, or a general/out-of-project scope. Project identity must survive different local paths and devices. Define how out-of-project prototypes can remain general or later be promoted into a project without losing provenance.

Map the current repo-local `.orchestrator` source of truth, project registry, Graphify/program data, worker ticket snapshots and attachments, run audit history, fresh-install preservation, and workspace activation behavior. Recommend a migration to one canonical artifact source of truth; do not propose a bidirectional ticket mirror that can diverge. Explain how workers receive the ticket and attachments they need while project branches remain free of canonical Relay artifacts unless an explicit export is requested.

Specify a local-first Git synchronization state machine for the artifact repository: bootstrap or connect a private remote, clone, commit granularity, a single-writer boundary, allowlisted staging, offline operation, fetch/rebase/push behavior, multi-device conflicts, retries, user-visible sync state, recovery, and a no-force-push policy. Define privacy, retention, deletion, repository-access, encryption, and large-file boundaries for transcripts, small attachments, raw audio, secrets, logs, caches, indexes, and ephemeral run state. A private GitHub repository is still third-party storage, so sensitive data handling and any client-side encryption requirement must be explicit.

The spike must end with a recommended target architecture, data layout, project-context state machine, migration plan, phased implementation tickets, and documented rejection reasons. It must not implement the migration, create a GitHub repository, change project routing, move existing tickets, or build note-taking functionality.

## Acceptance criteria

- [ ] The current dependencies on working directory, workspace roots, active-project resolution, repo-local `.orchestrator` ownership, Program/Graphify data, worker materialization, and fresh-install preservation are mapped with concrete code and data boundaries.
- [ ] A target topology is documented in which the Relay artifact repository is app-owned and independent of all project repositories, with no parent-repository, nesting, submodule, or automatic project-source staging requirement.
- [ ] The work-scope state machine covers an existing registered repository, creating a new project/repository, and out-of-project work, including explicit confirmation, follow-up inheritance, redirection, cancellation, and unresolved-scope behavior.
- [ ] The interaction design specifies equivalent UI and voice prompts for choosing scope and explains how to avoid silently inferring ownership from the terminal cwd while limiting repeated prompts inside an already confirmed work thread.
- [ ] The canonical artifact schema covers stable project identity across devices and paths plus tickets, attachments, decisions, research, specifications, session summaries, future transcripts/notes, new-project intents, and general artifacts.
- [ ] The design explains how general artifacts and prototypes can remain out-of-project or later be promoted into a project without losing stable IDs, history, links, or provenance.
- [ ] A single source-of-truth decision and migration plan addresses existing repo-local tickets, attachments, run audit history, Program/Graphify records, and worker ticket snapshots without introducing a divergent two-way mirror.
- [ ] The worker contract explains how dispatch, worktrees, review, dependencies, attachments, run logs, and merge auditing function when canonical tickets live outside project repositories.
- [ ] The Git synchronization state machine covers private-remote bootstrap, local-only and offline operation, allowlisted commits, fetch/rebase/push ordering, multi-device conflicts, retries, status reporting, recovery, and prohibition of force-push or project-source staging.
- [ ] Artifact classification and policy distinguish Git-suitable text and small assets from secrets, caches, indexes, transient run state, large binaries, raw audio, and sensitive transcripts, including retention, deletion, repository access, and client-side encryption decisions.
- [ ] The recommendation documents equivalent Codex and Claude behavior and any intentional provider-specific differences in session routing, authentication, or execution context.
- [ ] The final report includes a recommended repository layout, component and data-flow diagrams, product tradeoffs, migration phases, verification strategy, and cold-start follow-up tickets, while making no production changes in this spike.
