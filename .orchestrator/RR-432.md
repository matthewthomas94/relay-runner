## Description

Implementation workers finish by posting one structured outcome to `POST /v1/runs/<run_id>/outcome` (route in `services/orchestrator.py` near line 12505, handled by `submit_worker_outcome` at line 9369 and `ArtifactLifecycleCoordinator.submit_outcome` in `services/artifact_lifecycle.py`). The outcome is immutable: a second post with a different payload is rejected with "run <id> already submitted a different immutable outcome" (`artifact_lifecycle.py`, line 386). At exit, `validate_worker_completion` (line 436) fails the run when the recorded `source_commit` is not the worker's HEAD.

The worker-facing template `services/orchestrator_artifact_workflow.md` tells the worker to post exactly one outcome, and its sample code uses `urllib.request.urlopen(request, timeout=30)` (line 56). Outcome handling can take longer than 30 seconds because the daemon publishes to the artifact branch, so the client times out while the server records the outcome. The worker then believes nothing was submitted, fixes something and commits again, every later post is rejected, and at exit the run is marked Failed although the branch holds complete work.

Observed on 2026-10-24 in relay-runner: RR-427 runs 252 and 254 both ended with "exit=0 but ticket incomplete: structured outcome source_commit does not match worker HEAD". In run 254 the first post timed out client-side, the daemon recorded `source_commit` 9460701b, the worker amended its commit to move the new tests from `Tests/` to `tests/` (HEAD cbe3436d), and all later posts returned 400. The reviewer never saw the finished branch. The retry, run 256, then failed with "worker snapshot destination already exists" because the failed run's workspace still held its `.orchestrator` snapshot, and the cleanup after that deleted the `relay/rr-427` branch, so the completed commit survived only because a human pinned it under a backup ref.

Required behavior: a lost response must not turn a finished run into a failure. Decide and implement one of: acknowledge the post quickly and finish publication asynchronously so a short client timeout cannot fire; or make the post idempotent and let a still-running worker supersede its own outcome once, before exit, with a newer `source_commit` that contains the recorded one; or let the worker read back the recorded outcome and have the completion check accept a HEAD that differs only by commits made before the recorded post was acknowledged. Whichever is chosen, update the worker-facing templates with a long client timeout, a "query the run before retrying" step and an explicit rule never to amend or commit after posting, and make sure a failed run's leftover workspace snapshot cannot block its retry.

## Acceptance criteria

- [ ] A test simulates a post whose response is lost after the daemon recorded it, followed by a new commit and a second post from the same live run; the run completes successfully, or the second post is rejected with a response that tells the worker exactly how to recover and the completion check then passes.
- [ ] A post for a run that has already exited, or from a different run, is still rejected.
- [ ] A retry dispatched after a Failed run does not fail with "worker snapshot destination already exists"; the stale snapshot is cleaned or replaced (test with a fixture workspace).
- [ ] `services/orchestrator_artifact_workflow.md` and any other worker-facing template, for Codex and Claude alike, carry the longer timeout, the query-before-retry step and the no-amend-after-post rule.
- [ ] Existing lifecycle and completion tests pass.
