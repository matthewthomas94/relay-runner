## Description

Relay speaks each Kokoro sentence chunk by spawning a brand-new `afplay` process (`services/tts_worker.py`, `_play_wav` around lines 772–831: `["afplay", wav_path]` plus `-r <rate>`), and interrupts speech by `proc.terminate()` / `proc.kill()` (lines ~644–648 and ~1356–1360). Between sentences the built-in speaker device is torn down and re-created by CoreAudio.

Measured on macOS 27.0.1 (MacBook Pro M4, 2026-10-28, Relay Runner 0.4.82):

- `coreaudiod` logged **9 "Audio IO Overload … possibly due to client timeout" events** in 48 h; **all 9 fell within 1.8 s of a Relay sentence start** (afplay session start), none near other activity. An IO overload is a missed render deadline and is audible as a click/dropout in *all* audio playing at that moment.
- In one busy hour: **34 afplay cold starts** and **48 `BuiltInSpeakerDevice` IO work-loop restarts** (`HALS_IOContext_Legacy_Impl::IOWorkLoopInit`).
- Each afplay start also re-initialises spatialisation, the time-stretcher and converters, and each natural end logs `HALS_ClientConnection … Error while ending transport` (benign for afplay, but it shows the device is being torn down per sentence).

Goal: one long-lived playback path per session so the speaker device stays running across a reply, sentence boundaries are seamless, and interruption fades instead of hard-cutting.

Design is the worker's call, but it must not spawn a process per sentence. Reasonable options:

1. A persistent output in the Swift app (e.g. `AVAudioEngine` + `AVAudioPlayerNode`, or an `AudioQueue`) fed PCM chunks by the Python TTS worker over the existing IPC. `Sources/relay-runner/Settings/VoicePreviewController.swift` already uses `AVAudioPlayer` and is a reference for the app side.
2. A single persistent Python-side player process that stays alive for the session and receives file paths / PCM over a pipe.

Preserve existing behaviour:

- `[tts] rate` (currently 1.3) must remain a time-stretch (tempo change without pitch shift), as `afplay -r` does today — not a resample.
- Sentence-level queueing and ordering in `tts_worker.py` (`_sentence_chunks`, `_speak_chunks`) and the `speech_coordinator.py` contract (`play()`, `played_coverage`, waiting-pill publication).
- Stop / replace / cancel (`__TTS_STOP__`, `__INTERRUPT__`, `__CANCEL__`) must take effect within 100 ms and apply a ≥10 ms fade-out instead of killing mid-buffer.
- The chime (`_chime`, currently also afplay) may stay on afplay or move to the new player.
- Observability: the `afplay_started` speech event consumed by `speech_coordinator.py` and `provider_turn_fault_harness.py` must keep firing (renaming is fine if all consumers are updated).

External verification: some checks need the live app, physical device changes, listening, or a long soak. Run what you can from the worktree without installing, releasing or restarting the running app. If only those checks remain, finish as `verification_blocked`, naming each remaining check in `verification_blocker` and how to run it in `verification_resume`.

## Acceptance criteria

- [ ] No `afplay` process is spawned for speech playback (`pgrep afplay` is empty while Relay is speaking; chime excepted if left on afplay).
- [ ] During a scripted 30-sentence continuous reply, `/usr/bin/log show --last 10m --predicate 'process == "coreaudiod" AND eventMessage CONTAINS "Audio IO Overload thread"'` reports 0 events attributable to the run, and `… eventMessage CONTAINS "IOWorkLoopInit" AND eventMessage CONTAINS "BuiltInSpeakerDevice"` reports ≤ 1 per reply (device stays up across sentences). Record before/after counts in the run log.
- [ ] Interrupting mid-sentence fades out: an automated test asserts the final ≥10 ms of emitted PCM ramps to near-zero, and stop latency ≤ 100 ms.
- [ ] Playback rate still behaves as a tempo change (a 10 s utterance at rate 1.3 plays in ~7.7 s with unchanged pitch; test with a known tone file).
- [ ] Existing TTS / speech-coordinator tests pass; new unit tests cover queueing, interruption and the observability event.
- [ ] Codex and Claude sessions behave identically (no provider-specific code path).
- [ ] Document the new speech pipeline in the relevant docs page.
- [ ] Commit source changes only and submit for independent review/merge; do not install, release, or restart the running app.
