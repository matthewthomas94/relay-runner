## Description

Make the foreground LLM session an orchestrator by product contract, not just by prompt convention.

Any substantive Relay command that asks for project work should resolve to an explicit action and a ticket before implementation starts. The active Codex or Claude session should shape, create, edit, or dispatch tickets; worker/sub-agent runs should perform the actual implementation. This gives every meaningful command an audit trail and prevents the foreground session from quietly doing untracked project work.

Define the command/action model in the smallest useful way. A command may create a new ticket, update an existing ticket, dispatch a ready ticket, steer/cancel a pending action, or be classified as an internal control action. Bridge controls such as TTS stop, replay, and interrupt should remain control actions rather than work tickets, but they should be explicit in code/tests so "no ticket" is a deliberate exception.

Provider parity matters. Codex and Claude should expose the same orchestration contract, even if their launch commands or interruption mechanics differ.

## Acceptance criteria

- [ ] Substantive voice or text commands that request repo/project work are represented as explicit command actions before implementation begins.
- [ ] Each substantive work action is linked to a ticket id, either by creating a new `.orchestrator/<id>.md` ticket or by attaching to an existing ticket.
- [ ] The foreground Codex/Claude session does not perform substantive implementation work directly unless the command is explicitly classified as a non-work/control action or the user explicitly asks for inline work.
- [ ] The user-facing response names the ticket/action outcome, such as created ticket, edited ticket, dispatched worker, or waiting on a target-project choice.
- [ ] Internal controls such as `__TTS_STOP__`, `__PLAY__`, `__REPLAY__`, `__INTERRUPT__`, and `__CANCEL__` are documented and tested as intentional no-ticket control actions.
- [ ] Codex and Claude generated relay/orchestration instructions describe the same orchestrator-only behavior and provider-specific differences, if any.
- [ ] Tests cover command-to-ticket creation, existing-ticket update/dispatch, and no-ticket control actions.
