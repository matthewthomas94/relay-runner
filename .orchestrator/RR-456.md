## Description

The phone can only attach to a session that is already running (`docs/specs/relay-remote.md:32`). The Python server (`services/relay_remote.py`) and `/tmp/relay_remote.sock` exist only while a Relay session's voice bridge is running, so with no session the phone's SSH channel through `relay-remote-shell` has nothing to talk to. The user wants: pick a registered project on the phone, start its session, attach, and stop it, as long as the Mac is awake and Relay Runner is running.

Design (builds on the Remote mode work in RR-454, which adds the frame plumbing pattern):

1. **App-owned session-control socket.** Relay Runner.app listens on a new Unix socket (for example `/tmp/relay_session_control.sock`, created with the same ownership and permission model as the Relay Actions socket) while the app runs, independent of any session. It answers a minimal line protocol: `list_projects`, `start {project_id}`, `stop`, `state`. It is implemented in Swift inside the app using `ProjectRegistryV2Service.projects()` (`Sources/relay-runner/Board/ProjectRegistration.swift:359`), `AppState.newSession(workingDirectory:…)` (`App/AppState.swift:2664`, the same path the Workspace Start button uses via `ProgramBoardOverlayController.startSession`), and `AppState.endSession()` (:1337). Only paired devices reach it, because the only client is `relay-remote-shell` invoked by the device's forced `command=` key.
2. **Shell routing.** `Sources/relay-remote-shell/main.swift` connects to `/tmp/relay_remote.sock` when present (today's behaviour). When it is absent it connects to the session-control socket instead and emits a `session_state` frame so the phone knows there is no session but the app is reachable. When neither socket exists it emits `session_state` with `app_running: false`. SSH failing altogether remains "Mac unreachable" on the phone.
3. **Protocol.** Phone-to-Mac `session_command` with `action: list_projects | start | stop | state`, optional `project_id`, and `client_id` for dedup. Mac-to-phone `session_state` with `app_running`, `session: none | starting | ready | failed`, `project_id`, `project_name`, optional `projects: [{project_id, display_name, availability}]`, optional `error`. Protocol changes go in `Sources/RelayRemoteProtocol/Frames.swift` with the Python twin `services/relay_remote_protocol.py` kept identical, new golden vectors under `tests/RelayRemoteProtocolTests/Vectors/`, and `RelayRemoteProtocol.version` left at 1 because both decoders ignore unknown keys; an unknown frame *type* is rejected by the Python server and logged by the phone, so bump the version only if an older peer would misbehave, and say why in the run log.
4. **Lifecycle.** `start` with a session already running for another project is refused with an error that names the running project (no implicit switching in this ticket). `stop` ends the session through `endSession()`. After `start` returns `ready`, the Python server comes up and the phone reconnects to it automatically (the existing reconnect loop), carrying its Remote mode in `hello`. Starting uses the Mac's current defaults for provider, model and effort; selection from the phone is deferred by decision. The daemon's voice-command authority model is unchanged: a session started from the phone behaves like one started from the Mac.
5. **Phone.** On the current main screen: a project picker fed by `list_projects`, Start/Stop controls with the `session_state` reflected (app not running / no session / starting / ready / failed), and automatic attach when the state becomes ready. A later ticket moves this into the Workspace header.
6. **Spec.** Update `docs/specs/relay-remote.md` (lines 32 and 197) to describe remote session start and stop and the new socket.

Tests: Swift unit tests for the socket handler's command parsing and its calls into registry/AppState through injected closures; `RelayRemoteShellTests` for the socket fallback order and emitted `session_state`; Python/Swift codec vectors; kit tests for the picker's state machine; the existing `GeneralSessionStartupTests` still pass.

Physical-device checks cannot run in the worker environment. Cover behaviour with the kit, app, Python and Swift unit tests plus the existing loopback tests, and name the manual iPhone check for the user in the run log; do not mark acceptance that needs the phone as verified.

## Acceptance criteria

- [ ] With the app running and no session, the shell connects to the session-control socket and the phone receives `session_state {app_running: true, session: none, projects: […]}` (shell and app tests with a fake socket).
- [ ] With neither socket present the phone receives `session_state {app_running: false}` (shell test).
- [ ] `start {project_id}` calls the same session-start path as the Workspace button with that project's path and reports `starting` then `ready` or `failed`; `stop` calls `endSession()`; a start while another project's session runs is refused with its name (app tests through injected handlers).
- [ ] After `ready` the phone reconnects to the voice-bridge socket without user action and the session accepts a typed request (kit loopback test with a scripted Mac).
- [ ] Spec lines updated; protocol vectors round-trip in both codecs; all Swift, kit and Python suites pass; run log names the manual iPhone check.
