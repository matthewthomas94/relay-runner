## Description

**Observed (2026-10-17).** The user asked the foreground PM to "execute all tickets from 404 to 409". RR-406 has `depends_on: ["RR-404", "RR-405"]`. The PM dispatched the five tickets with no dependencies through `dispatch_ticket` and left RR-406 in `backlog`. It was relying on `backlog → ready` auto-progression once both predecessors merged. The user expects that a ticket they asked to run, but which still waits on dependencies, sits in the **Queued** lane (`status: ready`). The board already renders that state as "Waiting" / "waiting on RR-404, RR-405". To get there, the PM had to call the raw `POST /v1/artifacts/tickets/write` endpoint because no tool queues a ticket.

**Root causes**

1. `services/instructions/orchestration-workflow.md`, step 3, tells the PM: "The first ticket of a chain is the only one you promote — its dependents auto-promote as each predecessor completes." So a dependent the user explicitly asked to run stays in Backlog.
2. `Daemon.dispatch()` in `services/orchestrator.py` (around line 7847) never checks `depends_on`. Only the ready-sweeper (`_sweep_ready_tickets_locked`) and queue drain call `_all_dependencies_done`. A manual `dispatch_ticket` on a dependency-gated ticket would start a worker immediately, on a base that lacks its predecessors' code. The PM's only execution tool, `dispatch_ticket`, therefore can't express "run this once its dependencies are done".

**Fix**

1. **Daemon.** In `dispatch()`, once the ticket has loaded and the existing validation and voice-authorization checks pass, evaluate `_all_dependencies_done`. This must include archived dependencies, as the sweeper does. If any dependency is not `done`:
   - create no run, worktree or branch;
   - if the ticket is in `backlog`, move it to `ready` through the canonical writer. Use the artifact lifecycle writer when `artifact_lifecycle` is enabled, and the existing ticket-file path otherwise. Leave a ticket already in `ready` unchanged;
   - return a structured result such as `{"queued": true, "already_active": false, "run": null, "waiting_on": ["RR-404", "RR-405"]}`.

   This applies to every dispatch source. Do not add a force or override flag. The existing sweeper and dependency progression dispatch the ticket once its predecessors reach `done`, and that behaviour must not change.
2. **MCP proxy.** Update the `dispatch_ticket` description in `Sources/relay-orchestrator-mcp/Tools.swift` so it states that dependency-gated tickets are queued, not started. Make sure the proxy passes the queued result through without treating a `null` run as an error.
3. **Instructions.** In `services/instructions/orchestration-workflow.md`, replace the "first ticket of a chain" rule. When the user asks to execute a set of tickets, the PM calls `dispatch_ticket` for every requested ticket. Ones that are gated on dependencies land in Queued with the waiting marker and start automatically when their predecessors are done. Dependents the user did not ask to run still auto-promote from Backlog as today. Qualify "moving a refined ticket into `ready` starts `dispatch_ticket`" with "once its dependencies are done". Make the same qualification in `services/instructions/compact/relay-orchestrator.md`, keeping it under the 2048-character limit. Then run `scripts/build-instructions` to regenerate `CLAUDE.md`, `AGENTS.md`, `Sources/relay-orchestrator-mcp/Instructions.generated.swift` and `scripts/relay-bridge`. Do not hand-edit generated blocks.
4. **Spec.** Update `docs/specs/orchestrator-tickets.md` (status transitions and the auto-dispatch section) and `docs/orchestrator.md` if it describes manual dispatch, so they state that a manual dispatch of a dependency-gated ticket queues it.
