## Description

When a TTS message is generated and the user cancels or dismisses it before actually listening to it, the next Replay action should replay that canceled-but-unheard message. Today Replay appears to fall back to the last message that was already listened to, which loses the most recent assistant response the user intentionally deferred.

Investigate the TTS replay state in `services/tts_worker.py`, plus any relevant cancel/replay plumbing in `services/voice_bridge.py` and the menu-bar Replay command. Preserve the existing behavior where Replay repeats the last listened message when there is no newer unheard message waiting.

## Acceptance criteria

- Reproduce the bug with a focused manual flow or automated test: receive a new TTS message, cancel/dismiss it before playback is heard, then invoke Replay.
- Replay after canceling an unheard message plays that same most recent unheard message, not the older last-listened message.
- Replay still plays the last listened message when there is no newer canceled/unheard message.
- The fix does not reintroduce the cancel loop where `__INTERRUPT__` causes the assistant to speak again.
- Add focused regression coverage around the TTS worker replay/cancel state if the existing test setup supports it; otherwise document the manual verification steps in the run log.
