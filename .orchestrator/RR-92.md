## Description

Large pieces of work often get split into several tickets, but not every ticket in the set should dispatch at the same time. Some tickets are known, refined, and intended to run next, but must wait for predecessor tickets to finish first to avoid worktree collisions or sequencing problems.

The board should represent that state more accurately. Tickets that are ready for development but blocked by explicit `depends_on` predecessors should be able to live in the active queue of known work, rather than being pushed back into Backlog. Backlog should remain the place for unrefined or not-yet-actionable ideas; the queued work column should include work the orchestrator already understands and intends to dispatch once dependencies clear.

The current "Ready" or "Ready for Dev" label may no longer be the right product language. "Queued" better communicates work that is known, sequenced, and waiting to be picked up, including work that cannot dispatch until dependencies clear. This ticket should evaluate and, if the product decision holds, rename the user-facing column and related copy to "Queued" while preserving or deliberately migrating the underlying on-disk `status: ready` schema.

This needs to reconcile with the current rule that moving a ticket to Ready for Dev triggers dispatch. A dependency-gated queued ticket should not launch a worker until all dependencies are done. Instead, it should visibly wait on those dependencies and then dispatch automatically when the dependency chain clears.

Provider parity matters. The queued/dependency-gated behavior should be provider-neutral for Codex and Claude workers, with provider-specific launch details remaining outside the board-state model.

## Acceptance criteria

- [ ] The user-facing board language uses "Queued" for the known/ready-to-dispatch lane, or the implementation documents a clear reason to keep "Ready" after evaluating the rename.
- [ ] If the on-disk `status: ready` enum is preserved, the code clearly maps that schema value to the user-facing "Queued" label without breaking existing tickets.
- [ ] If the on-disk enum is migrated, backwards compatibility and existing ticket files are handled deliberately.
- [ ] A ticket with `status: ready` and unsatisfied `depends_on` predecessors can remain visible in the queued lane without being dispatched immediately.
- [ ] Project Board and Program Board clearly mark dependency-gated queued tickets as waiting, including which predecessor ticket or tickets are blocking them.
- [ ] Moving or saving a ticket into the queued lane with unsatisfied dependencies does not produce a failed dispatch error or move the ticket back to Backlog.
- [ ] When all dependencies become `done`, the queued ticket dispatches through the existing worker path without requiring the user to move it again.
- [ ] Backlog remains reserved for unrefined or not-yet-actionable work; dependency-gated but otherwise refined work is not hidden there by default.
- [ ] Codex and Claude workers use the same dependency-gated Ready behavior, with any provider-specific limitation documented if one exists.
- [ ] Add tests covering ready-with-unsatisfied-dependencies, dependency completion auto-dispatch, and board rendering for the waiting state.
