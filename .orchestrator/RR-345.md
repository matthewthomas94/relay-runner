## Description

Prevent read-only information queries from becoming project mutations merely because they mention words associated with work or refer to tickets. A question whose desired output is an answer or evidence should remain in the foreground PM and may use bounded read-only inspection without creating, editing, or dispatching a ticket.

The observed failure was a release-history question about RR-325 through RR-343. Both the original question and the clarification that it meant a release rather than a build were classified as `create_ticket`, because command classification treats a bare occurrence of `build` as work regardless of whether it is a noun, historical context, or part of an interrogative sentence. When a normalized ticket ID is present, an unmatched question can also fall through to `update_ticket`. Intent arbitration then correctly queues the incorrectly labeled action as a repository mutation.

Use this decision boundary:

- An **information query** requests an answer, explanation, status, history, comparison, or evidence and does not authorize a durable state change. Handle it inline with no new ticket.
- **Project work** requires positive intent to change durable state or create a durable deliverable. Work nouns, historical verbs, and ticket references are context, not mutation authority.
- A **mixed query and mutation** must be split into ordered intents or clarified. Answering the query must not silently authorize the conditional mutation.
- Complexity alone must not silently promote a query into a ticket. A sustained read-only investigation becomes a tracked spike only when the user explicitly asks to queue, delegate, or track it, or affirmatively accepts that proposed escalation.

Preserve the existing foreground handling for screen observation, direct computer actions, session operations, speech controls, and explicit orchestration corrections.

## Acceptance criteria

- [ ] The exact disfluent release-history question and its “release, not build” clarification classify as non-mutating information queries, with `requires_ticket: false`, no repository mutation claim, and a `continue_current` disposition.
- [ ] Interrogative and epistemic forms such as “Was there a build?”, “Which release included these tickets?”, “Did we ship this?”, “Why did the build fail?”, and “Can you tell me whether RR-325 is done?” never create or update tickets solely because they contain work words or ticket IDs.
- [ ] Positive mutation requests such as “Build the release”, “Can you build a release?”, “Update RR-325”, and “Dispatch RR-325” retain their existing create, update, and dispatch behavior.
- [ ] Ticket IDs are treated as references rather than mutation authority: read-only ticket questions use a non-mutating inspection/query path, while updates require explicit change intent.
- [ ] Mixed requests such as “Is there a release, and if not, build one” are split into ordered query/work intents or produce one concise clarification; the query clause alone cannot authorize the work clause.
- [ ] Query results do not automatically create follow-up tickets. Escalation to a tracked spike requires explicit user tracking/delegation intent or affirmative acceptance after the PM proposes it.
- [ ] End-to-end voice metadata proves information queries produce no visible ticket file, no counter change, no dispatch, and no project mutation authorization for both Codex and Claude.
- [ ] Existing direct-action, inline-session-operation, cancellation, interruption, pending-work, orchestration-correction, and ordinary project-work regressions continue to pass.
