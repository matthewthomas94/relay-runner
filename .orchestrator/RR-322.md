## Description

Investigate whether Relay Runner should launch a separate, read-only self-healing
observer when the active orchestration path repeatedly fails or enters a degraded
state. The observer should diagnose the incident from outside the affected
session, identify whether the condition is likely to recur, and produce a
durable report with refined follow-up proposals for the Relay Runner project.

The spike must define safe activation and termination rules, process and
credential isolation, an allowlisted diagnostic boundary, and ownership of any
recovery action. It must not assume that an autonomous source-code fix is safe;
recommend whether remediation should remain ticketed, require foreground PM
authorization, or be limited to reversible runtime recovery.

## Acceptance criteria

- [ ] Define observable conditions that distinguish a transient failure, a stalled session, and a recurring degraded state before the observer starts.
- [ ] Compare viable observer architectures, including a separate process and a daemon-owned recovery lane, with explicit lifecycle and resource bounds.
- [ ] Specify which diagnostics the observer may read and which project, credential, conversation, desktop, and external data remain unavailable.
- [ ] Define how the observer correlates evidence across the app, daemon, bridge, messenger, provider, and worker without taking over foreground reply ownership.
- [ ] Define which reversible runtime recovery actions, if any, can run automatically and which actions require foreground PM or user authorization.
- [ ] Specify a durable structured report and refined follow-up proposal path for likely recurring failures without allowing the observer to edit source or canonical tickets directly.
- [ ] Evaluate Codex and Claude parity, including provider-specific failure and recovery signals.
- [ ] Deliver an evidence-backed recommendation, risks, unresolved questions, and implementation tickets if the design is viable.
