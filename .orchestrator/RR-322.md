## Description

Investigate whether Relay Runner should launch a separate, read-only self-healing
observer when the active orchestration path repeatedly fails or enters a degraded
state. The observer should diagnose the incident from outside the affected
session, identify whether the condition is likely to recur, and produce a
durable report with refined follow-up proposals for the Relay Runner project.

The spike must define safe activation and termination rules, process and
credential isolation, an allowlisted diagnostic boundary, and ownership of any
recovery action. It must not assume that an autonomous source-code fix is safe;
recommend whether remediation should remain ticketed, require foreground PM
authorization, or be limited to reversible runtime recovery.

## Acceptance criteria

- [ ] Define observable conditions that distinguish a transient failure, a stalled session, and a recurring degraded state before the observer starts.
- [ ] Compare viable observer architectures, including a separate process and a daemon-owned recovery lane, with explicit lifecycle and resource bounds.
- [ ] Specify which diagnostics the observer may read and which project, credential, conversation, desktop, and external data remain unavailable.
- [ ] Define how the observer correlates evidence across the app, daemon, bridge, messenger, provider, and worker without taking over foreground reply ownership.
- [ ] Define which reversible runtime recovery actions, if any, can run automatically and which actions require foreground PM or user authorization.
- [ ] Specify a durable structured report and refined follow-up proposal path for likely recurring failures without allowing the observer to edit source or canonical tickets directly.
- [ ] Evaluate Codex and Claude parity, including provider-specific failure and recovery signals.
- [ ] Deliver an evidence-backed recommendation, risks, unresolved questions, and implementation tickets if the design is viable.

## Spike report

- **Run:** 1 (attempt 1)
- **Provider:** codex

**Conclusions**

- The design is viable as a hybrid: component-local sensors classify incidents, while Relay Runner.app launches a one-shot sandboxed observer process. A daemon-owned lane is simpler for worker/run incidents but shares the daemon’s failure domain and cannot diagnose daemon loss (`services/orchestrator.py:4112-4191`; `Sources/relay-runner/App/AppState.swift:1489-1862`).
- Classify a transient failure as one symptom that clears within its native grace or one successful built-in recovery. Classify a stall as a hard liveness breach persisting through two post-grace samples or one failed recovery. Classify recurring degradation as the same sanitized fingerprint three times in 30 minutes, two failed recoveries in 10 minutes, recurrence across app sessions, or simultaneous hard failures in two components. Launch the observer only for recurring degradation or a stalled accepted command after recovery failure (`ProcessManager.swift:31-38,299-378`; `orchestrator.py:136,
- Prefer a deterministic, provider-free XPC helper over another Codex or Claude agent. Run one incident at a time with a two-item pending cap, 120-second wall limit, 30-second CPU budget, 256-MiB memory ceiling, 10-MiB/500-event input cap, and 15-minute fingerprint cooldown. Stop on report completion, deadline, explicit session/update/reset shutdown, or 60 seconds of restored stability. The parent should capture stdout and atomically persist it, leaving the observer without filesystem write access (`services/sidecar_lane.py:134-231`).
- Do not use the existing provider sidecar as the tertiary observer: it starts authenticated provider CLIs, permits public web access, inherits the bridge process environment, and reports through messenger callbacks. Those properties enlarge credential, network, reply-ownership, and correlated-failure risk (`services/sidecar_lane.py:35-132`; `services/messenger.py:300-403,635-788`; `.orchestrator/RR-321.md`).
- The observer may receive only a sanitized snapshot: allowlisted support events; component/PID liveness booleans; marker ages; orchestrator-session state; run state/attempt/exit code; worker log size/mtime; recovery-attempt outcomes; provider label; and opaque incident/run identities. It must not receive repositories, tickets, Git content/remotes, credentials or Keychain access, provider configuration, process environments/arguments, conversations, prompts, transcripts, audio, screenshots, desktop permissions, raw logs, external services, or network access (`docs/support-diagnostics.md`; `docs/
- Correlation needs a v2 event envelope shared by app, daemon, bridge, messenger, provider, and worker: app session, incident, correlation/event ID, component instance, actor role, provider, recovery generation, opaque command/run ID, phase, outcome, timestamp, and parent event. The current journal supplies app-session/incident/correlation IDs but has no messenger/worker process categories and records few runtime recovery events, so full correlation is not implementable from current evidence alone (`services/support_diagnostics.py:17-120`).
- The observer must have actor role `observer`, no foreground gate/session/reply variables, no TTS or messenger-output channel, and no authority to claim commands. It returns evidence and proposed actions only; the foreground PM remains the sole conversational and project authority. This follows the existing messenger authority boundary and the ownership defect documented by RR-321 (`services/messenger.py:100-132`; `.orchestrator/RR-321.md`).
- Automatic healing should remain with existing owners and be limited to one idempotent, reversible action: the app may relaunch a missing bridge while preserving exact command identity; a messenger backend may restart on its next event; the daemon may mark dead workers Stalled, restore dead review ownership to AwaitingReview, or use its existing capped retry path. The observer must not add retries, kill a live foreground provider, change configuration/auth, reset state, edit source, or edit tickets (`ProcessManager.swift:556-699`; `orchestrator.py:4969-5157,5450-5480`).
- Foreground PM authorization is required to cancel active work, explicitly redispatch after circuit opening, change provider/model/configuration, accept follow-up proposals, or perform ambiguous runtime recovery. User authorization is required for authentication, permission changes, reinstall/reset, destructive state changes, messages, pushes, releases, or deployment. Source remediation must always become a reviewed backlog ticket; never an observer-authored fix (`services/fresh_install.py:264-322`; `services/followup_tickets.py`; `orchestrator.py:7969-8178`).
- Persist reports in an app-owned `observer_reports.db`, retaining unresolved incidents and pruning terminal reports after 30 days or a 20-MiB global cap. Each report should include schema/build, incident interval, trigger/classification, fingerprint/count/window, component observations, evidence event IDs, correlation gaps, recovery attempts/owners/outcomes, likely-cause category and confidence, recurrence likelihood, risks, redaction count, unresolved questions, and refined ticket proposals. The app—not the observer—writes the record (`Sources/relay-runner/Diagnostics/RelayDiagnostics.swift:34
- Route report proposals through an incident-origin variant of the existing follow-up proposal review flow. Proposals remain editable drafts; only PM/user acceptance selects a registered target project and commits a Backlog ticket with provenance, without auto-dispatch. This already exists for spike-origin proposals and is the safest canonical-ticket boundary (`services/followup_tickets.py`; `services/orchestrator.py:7934-8178`; `docs/orchestrator.md:63`).
- Codex and Claude should share detection thresholds, report schema, recovery ownership, and normalized health vocabulary. Adapters may map Codex app-server RPC/`turn/completed` status and Claude stream-json `result`/`is_error` plus process exits into the common envelope. Neither provider’s native session ID, command flags, model names, or raw error output should become authority or unsanitized report data (`services/messenger.py:403-582,699-800`; `docs/specs/program-manager-mvp.md:75-90`).

**Evidence**

- `Sources/relay-runner/App/AppState.swift:1489-1862` - The app samples bridge health every three seconds, applies explicit keep/wait/recover/reap states, suppresses recovery during updates or explicit stops, and rate-limits recovery with a 15-second cooldown.
- `Sources/relay-runner/Process/ProcessManager.swift:31-38,299-699` - Current bridge signals include a 10-second pending-command timeout, 30-second heartbeat threshold, process/socket/context checks, and an exact-identity capture/replay recovery script.
- `services/orchestrator.py:126-136,2107-2367` - Foreground orchestrator sessions use provider-neutral lifecycle states and become stale after a 30-second heartbeat expiry.
- `services/orchestrator.py:1746-2030,4640-4820` - Run supervision distinguishes dead ownership from live-but-unchanged work; health compares activity, Git state, commit, and log metadata, and emits an advisory warning without terminating a live worker.
- `tests/test_orchestrator_supervision.py:11-141` - Codex and Claude worker tests explicitly require health checks to warn without imposing a wall-clock deadline and verify equivalent progress/stall messages.
- `services/orchestrator.py:202-204,5450-5480; tests/test_orchestrator_dispatch.py:850-890` - Automatic worker recovery already has a 30-second backoff, five-attempt cap, and deterministic-failure circuit behavior; exhaustion requires explicit redispatch.
- `services/sidecar_lane.py:35-231; tests/test_sidecar_lane.py:31-143` - The current sidecar is single-flight and bounded, but it invokes Codex or Claude with web tools and sends lifecycle/final callbacks into the active voice path, making it unsuitable as an isolated incident observer.
- `services/support_diagnostics.py:17-153; docs/support-diagnostics.md` - The local journal provides strict allowlisting, redaction, owner-only storage, seven-day/5-MiB retention, and cross-process correlation IDs, while excluding transcripts, repositories, credentials, provider output, screenshots, worker logs, and crash reports.
- `Sources/relay-runner/Terminal/EmbeddedTerminal.swift:80-233,2380-2450` - Provider readiness already emits shared started/ready/failed events for Codex and Claude with correlation IDs and bounded exit/error attributes.
- `services/messenger.py:300-800` - Codex exposes app-server RPC timeouts, process exit, and `turn/completed` status/error; Claude exposes stream-json result, `is_error`, session ID, timeout, and process exit. These can be normalized without storing provider output.
- `.orchestrator/RR-105.md; .orchestrator/RR-116.md; .orchestrator/RR-122.md; .orchestrator/RR-140.md` - Git-tracked incident history shows repeated bridge-loss and silent-delivery failures followed by a false-positive recovery regression, supporting recurrence detection while warning against reacting to a single weak signal.
- `services/followup_tickets.py; services/orchestrator.py:7934-8178` - Relay already persists sanitized proposal drafts and requires individual review, explicit registered target ownership, canonical commit, Backlog status, provenance, and no automatic dispatch.

**Uncertainties**

- The proposed recurrence thresholds and resource budgets are starting values; the snapshot contains no production incident-frequency or observer-cost distribution with which to tune them.
- A one-shot app-launched XPC observer cannot run during a total app crash. The safer initial behavior is post-relaunch analysis of the bounded journal; an always-on launchd observer would require a separate privacy, update, and lifecycle review.
- Current support telemetry does not record messenger and worker as journal process categories and does not capture all watchdog/recovery decisions, so a v2 envelope must land before the observer can correlate every required component reliably.
- The snapshot does not establish a portable mechanism for enforcing a 256-MiB resident-memory ceiling on the proposed macOS helper; packaging and enforcement need a focused prototype.
- Sanitized recurrence fingerprints can over-group distinct incidents or split one defect across changing error codes/builds. Reports must expose the fingerprint inputs and confidence rather than claim certainty.
- Provider authentication, rate-limit, and misconfiguration errors are not yet mapped comprehensively into the common health vocabulary; raw provider text cannot be used as a durable classifier without an allowlisted adapter.
