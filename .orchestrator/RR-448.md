## Description

Relay Runner's background services are Python: 68 files and about 61,500 lines in `services/`, plus about 50,000 lines of tests in `tests/test_*.py`. The largest are `orchestrator.py` (13k lines, the daemon), `voice_bridge.py` (6k), the artifact store/lifecycle/sync/migration/retention modules (about 10k together), `messenger.py` (2.4k), `tts_worker.py` and `speech_coordinator.py` (1.4k each), `speech_player.py` (new in RR-438) and `relay_completion_hook.py`. The app itself is Swift (SwiftPM, `Sources/`).

The user wants to know what porting these services to Rust would gain, what it would cost, and what it would need. They do not want a port started yet. Produce a decision-ready recommendation.

Known context to build on (do not re-measure; spikes cannot run commands):

- Packaging today: the daemon runs under Homebrew Python 3.13 (`/opt/homebrew/...`). `SharedSupport/setup-venv.sh` creates a venv and pip-installs `services/requirements.txt`, which brings in `kokoro_onnx`, `numpy` and onnxruntime for TTS. `scripts/relay-bridge` already has a `RELOCATABLE_PYTHON_DIR` path. Audio and permission prompts are attributed to `Python`, not Relay Runner.
- Performance: on 2026-10-29, with a session active and no speech, the installed daemon used 19% CPU and the app 6.8% over 10 minutes. RR-440 found that most of this was design (polling on the wrong tab, rebuilding the program graph, a new SQLite connection per call, rewriting unchanged queue items), not interpreter speed. RR-440's second attempt is in progress.
- Reliability: recent bugs included runtime type errors (`dataclasses.replace` TypeError in `voice_bridge._resolve_voice_work_items`) and lock and thread coordination in the daemon.
- Real-time audio: `speech_player.py` drives a CoreAudio AudioQueue from Python (RR-438).

Questions to answer:

3. **Language choice per component.** Compare Rust and Swift for the daemon, TTS inference (Kokoro ONNX via the `ort` crate, Swift ONNX Runtime or Core ML, plus phonemisation such as espeak-ng over a C interface), the real-time speech player, and short-lived helpers. 4. **Benefits versus costs.** For each component, rate the gain in packaging, reliability, real-time behaviour, startup and steady-state cost, against port effort and regression risk. Say plainly where a port would not help, for example where cost is architectural.

### Overall recommendation

**Port to Rust in stages, with a go/no-go gate after the speech engine and the hooks.** The first three stages are worth doing on their own and are low regret. The voice bridge and daemon ports are only justified by removing Python from the install entirely and by compile-time types; they will not fix CPU cost, which RR-440 and RR-449 showed is architectural.

Two findings change the order the ticket assumed:

1. **The Python suite cannot be the contract test.** 86 of 97 `tests/test_*.py` files import the services in-process, 52 files use `mock.patch` (722 lines), and no test starts the daemon or `voice_bridge.py` as a process. Only the `fresh_install_cli.py` end-to-end case (`tests/test_fresh_install.py:552`) would run unchanged against a Rust binary. Black-box contract suites must be written first, against the Python implementation, and they are a large part of the cost.
2. **The speech stack has a licence problem today.** The running bridge loads `espeakng_loader/libespeak-ng.dylib` (GPL-3.0) and uses `phonemizer-fork` 3.3.2 (GPL), pulled in by `kokoro-onnx`. `THIRD_PARTY_NOTICES.md:37-52` lists only ONNX Runtime and kokoro-onnx, and the project is MIT. The Rust port is the natural point to fix this with a non-GPL phonemiser; it should be disclosed now regardless.

### 2. Packaging: is a bundled Python enough?

It would remove the "user must have Python" dependency and nothing else. `scripts/relay-bridge:2211-2334` can already install python-build-standalone when no interpreter is found. Measured on this Mac: Homebrew Python 85 MB, the venv's site-packages 216 MB (onnxruntime 74 MB, numpy 34 MB, espeak-ng 20 MB), against a 52 MB app bundle. Bundling would roughly sextuple the download, require signing every `.so` and `.dylib` under the hardened runtime, keep the GPL libraries, keep audio and prompts attributed to `Python`, and leave two things it does not touch:

- the hooks run under `/usr/bin/python3`, which on a clean macOS is a stub that prompts for the Xcode Command Line Tools;
- first launch still creates a venv and runs `pip install` (`relay-bridge:2335-2495`).

Native binaries follow a precedent already in the bundle: `agent-desktop` is a 3.6 MB Rust binary, pinned by SHA-256 (`scripts/fetch-agent-desktop.sh:19-25`) and signed in the helper loop of `scripts/build-dmg.sh:369-446` with `--options runtime` and no entitlements. Builds are arm64 only.

Keep bundled Python as the fallback if the port is stopped at the gate: once the speech engine is native, the remaining Python is standard-library only, so a bundled interpreter with no site-packages would be about 60 MB and need no `pip`.

### 5. Staged plan

Every stage keeps the interfaces in section 1 byte-compatible, ships behind a switch that falls back to the Python implementation for at least one release, and is accepted by a black-box contract suite that passes against both implementations.

| Stage | Work | Rough effort | Rollback | No-go |
|---|---|---|---|---|
| 0 | Cargo workspace, build, signing and CI integration; licence disclosure fix. | Days | Remove one build step | Signed Rust helper fails hardened-runtime or notarisation checks |
| 1 | Contract suite for the hook and reply helper, then `relay-hook` in Rust for both providers together. | 1 to 2 weeks | Hook command line reverts to Python | Cannot match broker SQLite behaviour under concurrent access |
| 2 | Rust Kokoro prototype with measurements and audio samples; split speech into its own process behind a written protocol (still Python); then the Rust speech engine. | 3 to 5 weeks | Bridge launches the Python speech process | User rejects voice quality; first-audio latency or real-time factor worse than Python; `ort` unstable on macOS |
| **Gate** | Measure install size, first-run time, memory, hook latency and defect rate after stages 1 and 2. Decide: continue, or stop and bundle a standard-library-only Python. | Days | n/a | n/a |
| 3 | Contract suite for the bridge, then the bridge, messenger, intent inbox and Relay Remote in Rust. | 6 to 10 weeks | Launch script selects the Python bridge | Contract suite cannot reach meaningful coverage of preemption behaviour |
| 4 | Contract suite for the 76 routes and artifact refs, then the daemon in Rust, artifact stack first as a library with byte-identical git output. | 3 to 5 months | LaunchAgent runs the Python daemon; databases stay schema-compatible | Byte-identical artifact commits cannot be achieved |
| 5 | CLIs and install helpers; remove the venv, `pip` and Python discovery from `relay-bridge`. | 1 to 2 weeks | Not reversible; do last | Any earlier stage still on fallback |

Efforts assume agent workers with review and are estimates from line counts and coupling, not measurements.

### 6. Provider parity

No stage changes what Codex and Claude sessions see, provided these move together in one release each:

- **Hooks:** Codex's `-c hooks.*` TOML and Claude's `--settings` JSON (`ProcessManager.swift:2358-2404`) must switch to the Rust binary in the same change, including Claude's extra SessionStart and StopFailure events, the Claude `prompt_id` stand-in for `turn_id` (`relay_completion_hook.py:472-484`), both transcript token parsers (`:128-172`) and Codex native-id discovery (`:1528-1612`).
- **Reply helper:** the instruction text that names `/usr/bin/python3 "$RELAY_REPLY_HELPER"` (`ProcessManager.swift:2130`, `scripts/relay-bridge:820,1131`) is shared by both providers.
- **Messenger backends:** Codex JSON-RPC app-server and Claude stream-json (`messenger.py:419-1110`) port together in stage 3.
- **Workers:** both command lines in `_agent_command` (`orchestrator.py:4520-4618`) port together in stage 4.

### Uncertainties and recommended next steps

These need a measurement or a prototype and are not guessed here:

- Voice quality and unknown-word behaviour of `misaki-rs` against today's espeak-ng path. Needs the user to listen to samples.
- Real-time factor, first-audio latency and resident memory of `ort` on Apple silicon against onnxruntime 1.28 in Python, and whether the CoreML provider helps.
- Whether a signed Rust binary that links ONNX Runtime passes hardened-runtime and notarisation checks, and its size.
- Hook latency today (interpreter start plus imports) and after.
- Whether the GPL exposure of the current release needs more than a notices update; that is a legal judgement, not an engineering one.
