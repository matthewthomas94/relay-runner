## Description

Relay Runner's background services are Python: 68 files and about 61,500 lines in `services/`, plus about 50,000 lines of tests in `tests/test_*.py`. The largest are `orchestrator.py` (13k lines, the daemon), `voice_bridge.py` (6k), the artifact store/lifecycle/sync/migration/retention modules (about 10k together), `messenger.py` (2.4k), `tts_worker.py` and `speech_coordinator.py` (1.4k each), `speech_player.py` (new in RR-438) and `relay_completion_hook.py`. The app itself is Swift (SwiftPM, `Sources/`).

The user wants to know what porting these services to Rust would gain, what it would cost, and what it would need. They do not want a port started yet. Produce a decision-ready recommendation.

Known context to build on (do not re-measure; spikes cannot run commands):

- Packaging today: the daemon runs under Homebrew Python 3.13 (`/opt/homebrew/...`). `SharedSupport/setup-venv.sh` creates a venv and pip-installs `services/requirements.txt`, which brings in `kokoro_onnx`, `numpy` and onnxruntime for TTS. `scripts/relay-bridge` already has a `RELOCATABLE_PYTHON_DIR` path. Audio and permission prompts are attributed to `Python`, not Relay Runner.
- Performance: on 2026-10-29, with a session active and no speech, the installed daemon used 19% CPU and the app 6.8% over 10 minutes. RR-440 found that most of this was design (polling on the wrong tab, rebuilding the program graph, a new SQLite connection per call, rewriting unchanged queue items), not interpreter speed. RR-440's second attempt is in progress.
- Reliability: recent bugs included runtime type errors (`dataclasses.replace` TypeError in `voice_bridge._resolve_voice_work_items`) and lock and thread coordination in the daemon.
- Real-time audio: `speech_player.py` drives a CoreAudio AudioQueue from Python (RR-438).

Questions to answer:

1. **Inventory.** Group every module into components (daemon and artifact stack, voice bridge and messenger, TTS and speech player, short-lived helpers and hooks, continuity, notes and other). For each component give its runtime shape (long-lived or per-invocation), third-party dependencies, and external interfaces: the daemon HTTP API, FIFOs and Unix sockets, SQLite schemas, ticket/artifact files and git refs, CLI entry points, environment variables, and the hooks the Swift app and provider CLIs call.
2. **Packaging first.** Would a bundled relocatable Python (the existing `RELOCATABLE_PYTHON_DIR` route) solve the install-dependency problem on its own? Cover bundle size, signing and notarisation of an embedded interpreter, native wheels such as onnxruntime, and permission attribution. Compare that with native binaries.
3. **Language choice per component.** Compare Rust and Swift for the daemon, TTS inference (Kokoro ONNX via the `ort` crate, Swift ONNX Runtime or Core ML, plus phonemisation such as espeak-ng over a C interface), the real-time speech player, and short-lived helpers. Cover build and signing integration with SwiftPM and `scripts/build-dmg.sh`, test strategy, and how well coding agents work in each language here.
4. **Benefits versus costs.** For each component, rate the gain in packaging, reliability, real-time behaviour, startup and steady-state cost, against port effort and regression risk. Say plainly where a port would not help, for example where cost is architectural.
5. **Staged plan.** Give an order of stages that keeps every interface in point 1 stable, with Python suites kept as black-box contract tests against each new binary, rollback per stage, rough effort per stage, and explicit no-go conditions.
6. **Provider parity.** Confirm that no stage changes behaviour that Codex and Claude sessions see differently, and name any provider-specific hooks that must move together.

Cite repository evidence by path and line. Pin any public repository evidence (crates, ONNX/Kokoro projects, espeak-ng) to a full commit SHA, and report research-access failures explicitly.
