## Description

Fix the installed Start Session path so an embedded Codex or Claude process
remains interactive until the user, provider, or app explicitly ends it.

The 2026-07-30 installed build was verified to match packaged `main` at
`4ece979` and to contain RR-255. Despite that, diagnostic attempt
`8015a2a9-d39a-405b-9aba-1f85aa49cb63` recorded bridge socket readiness,
provider spawn, and interactive readiness at `09:37:10Z`, followed by a clean
provider exit (`exit 0`) at `09:37:11Z`. The mounted terminal visibly rendered
the Codex TUI before Relay Runner changed to `Session exited (0)`.

Current readiness logic schedules `running` after any provider output observed
after the `provider_spawn` marker. That proves bytes reached SwiftTerm but not
that the PTY/provider lifetime is stable. Determine why the live provider
receives EOF, loses its PTY, or otherwise exits, and correct the ownership
boundary rather than merely delaying or suppressing the exit state.

## Acceptance criteria

- [ ] A deterministic regression test reproduces a provider that renders interactive output and then exits cleanly immediately after apparent readiness.
- [ ] Start Session keeps the embedded provider and its controlling PTY alive until an explicit provider, user, or app-owned termination.
- [ ] Interactive readiness is based on a stable provider condition; arbitrary post-spawn output alone cannot turn a startup failure into a successful running session.
- [ ] A clean exit during the startup/readiness grace period is shown as an actionable launch failure with the exact lifecycle stage, rather than the ambiguous `Session exited (0)` state.
- [ ] Bridge cleanup occurs for failed starts without stopping a healthy bridge for a genuinely running session.
- [ ] Lifecycle diagnostics remain owner-only, privacy-safe, and emit an unambiguous ordered launch, readiness, and termination sequence.
- [ ] Codex and Claude launch paths have equivalent lifetime, diagnostics, retry, and cleanup coverage; intentional CLI-specific differences are documented.
- [ ] Focused Swift tests cover real `LocalProcess`/PTY behavior or the nearest deterministic integration boundary, not only an in-memory phase model.
- [ ] A packaged app smoke test confirms an embedded session remains interactive and accepts input after the former one-second failure window.
