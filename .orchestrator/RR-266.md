## Description

Automatically compact every embedded pseudo-terminal provider session when its active context reaches 150,000 tokens. The trigger must be non-interactive and must use the provider's native active-context accounting for the current conversation. Do not infer usage from rendered terminal text, scrollback size, transcript length, or cumulative input/output billing totals.

Observe usage independently for each embedded Codex and Claude session. When a session reaches the threshold, schedule one provider-native compaction at the next safe idle boundary, after the current provider turn and any in-flight input have settled. Compaction must not interrupt generation, race user typing or voice delivery, inject duplicate commands, or become visible as ordinary user-authored work.

Track the compaction lifecycle explicitly so repeated usage updates, relaunches, completion hooks, and terminal refreshes cannot fire the same threshold crossing more than once. Re-arm only after successful compaction has reduced the active context below the threshold, allowing a long-lived session to compact again at a later crossing. A failed or unconfirmed attempt must remain recoverable without a retry storm or a permanently disabled session.

Provide equivalent automatic behavior for Codex and Claude while isolating their native accounting fields, compaction commands, acknowledgements, and failure modes behind the existing provider boundary. Preserve normal manual compaction and ordinary interactive terminal behavior.

Implementation decision: use one fixed Claude auto-compaction configuration sized for the smallest supported native context window, currently Haiku 4.5 at 200,000 tokens. Apply that same Haiku-compatible configuration to every supported Claude alias; do not add model detection, a per-model window table, or model-specific threshold branches. Derive the fixed constants from Claude's actual window-cap, output-reserve, and percentage calculation so the effective trigger is 150,000 active-context tokens even when the configured window is capped at Haiku's limit. Verify the effective runtime boundary rather than merely checking emitted environment strings.

## Acceptance criteria

- [ ] Each embedded provider session uses provider-native active-context usage for its current conversation; terminal text, scrollback, transcript length, and cumulative billing totals are never used as the trigger.
- [ ] Reaching 150,000 active-context tokens schedules automatic compaction without prompting the user or requiring an interactive confirmation.
- [ ] A threshold crossing never interrupts active generation, queued voice delivery, or user input; the provider-native compaction command runs only at a verified safe idle boundary.
- [ ] Usage and compaction state are isolated per embedded pseudo-terminal session, so concurrent sessions cannot trigger, suppress, or re-arm one another.
- [ ] Repeated usage events, completion hooks, redraws, relaunch recovery, and duplicate idle notifications produce at most one compaction attempt for a single threshold crossing.
- [ ] Successful compaction is confirmed from provider-native state, reduces active context below the threshold, and re-arms the session for a later crossing.
- [ ] Failed, timed-out, or unconfirmed compaction remains retryable at a later safe boundary with bounded backoff and cannot create a retry storm or permanently disarm the session.
- [ ] Manual compaction and ordinary terminal commands retain their existing behavior and do not corrupt the automatic trigger state.
- [ ] Claude uses one fixed configuration derived from the Haiku 4.5 200,000-token limit for every supported Claude alias; the implementation contains no model detection, per-model window lookup, or model-specific threshold branch.
- [ ] The fixed Claude constants produce an effective 150,000-token trigger after the provider's real window cap, output reserve, and percentage calculation for both Haiku-capped and larger-window aliases.
- [ ] Codex and Claude embedded sessions provide the same 150,000-token automatic-compaction contract; provider-specific accounting fields, commands, acknowledgements, and limitations are explicitly covered.
- [ ] Diagnostics record provider, session identity, native active-context value, threshold state, idle-boundary decision, attempt, confirmation, and failure reason without logging terminal contents or raw conversation text.
- [ ] Focused tests cover below-threshold updates, the exact crossing, Haiku-capped and larger-window Claude aliases, repeated updates, busy-to-idle deferral, user-input races, successful re-arm, failure recovery, relaunch recovery, concurrent sessions, manual compaction, and Codex/Claude parity; relevant Swift and service tests plus git diff --check pass.
