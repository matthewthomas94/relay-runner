## Description

Investigate and fix the current regression where editing a ticket from the Workspace GUI does not work. Editing was previously added for Program Board tickets in RR-82 and later moved from lane cards into the opened ticket detail view in RR-246, so begin with an installed-app reproduction and identify the exact failing boundary rather than replacing the editor wholesale.

Trace the full interaction: selecting a ticket, invoking Edit from ticket detail, receiving keyboard focus, changing fields, validating the draft, committing through `ProgramBoardTicketEditor`, writing to the correct project authority, refreshing the board, and retaining the selected ticket. Cover both project-filtered and all-project Workspace contexts and the storage modes the current product supports. A save must update only the selected ticket in its owning project and preserve frontmatter/body fields the GUI does not edit.

The current controller catches save errors, writes only an `NSLog` entry, then closes the editor and refreshes. Do not allow a failed save to look successful. Keep the editor open with the user's draft intact and show a concise actionable error. Preserve the intentional safety behavior for missing/stale tickets, project-scope mismatches, invalid status transitions, and `ready` auto-dispatch; do not weaken validation merely to make the UI appear responsive.

## Acceptance criteria

- [ ] A mounted installed-app reproduction records the exact current failure: whether Edit cannot open, fields cannot receive input, Save is disabled or inert, persistence fails, the modal closes despite failure, or the board refresh hides a successful write.
- [ ] An editable ticket can be opened from its detail view, every supported field can receive keyboard and pointer input, and Cancel closes without writing while preserving the original ticket.
- [ ] Saving valid changes updates exactly the selected owning project's ticket through the configured canonical storage path, preserves unedited frontmatter/body content and attachments, and does not modify another project or ticket.
- [ ] Successful saves dismiss the editor only after persistence succeeds, refresh the card/detail exactly once, retain a coherent selection, and visibly show the updated values without requiring app relaunch or manual file editing.
- [ ] Failed saves keep the editor open, preserve the complete draft, and present a concise actionable GUI error. The failure is also logged without raw ticket-private content, but `NSLog` alone is not the user-visible error path.
- [ ] Project-filtered and all-project views route edits to the same owning project; missing identity, stale/deleted files, unavailable projects, scope-token mismatch, malformed tickets, and concurrent external edits fail safely without recreating or overwriting a phantom ticket.
- [ ] Backlog and other non-dispatching edits do not start workers. A deliberate successful transition into `ready` triggers the existing dispatch sweep exactly once, while a failed save or canceled edit never dispatches.
- [ ] Title, priority, status, execution mode, description, acceptance criteria, worker-sizing metadata, dependency metadata, run/verification fields, unknown compatible frontmatter, and image attachments retain their intended editable or preserve-only behavior.
- [ ] Keyboard focus, tab order, text selection, scrolling, Return/escape behavior, VoiceOver labels, modal dismissal, and pointer hit testing work in the actual AppKit overlay panel rather than only in isolated SwiftUI previews.
- [ ] Focused tests reproduce the failing boundary and cover successful persistence, visible failure retention, owning-project routing, refresh/selection behavior, stale and malformed files, concurrent changes, attachment preservation, and ready-dispatch exact-once behavior.
- [ ] Relevant Swift suites pass, and a fresh built/installed app completes manual edit/save/cancel/error checks in both project-filtered and all-project Workspace contexts without modifying unrelated source or ticket files.
- [ ] The run log identifies the root cause and regression point relative to RR-82/RR-246, lists the minimal files changed, records automated and mounted evidence, and documents any intentional edit restrictions that remain.
