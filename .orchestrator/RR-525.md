## Description

Relay Runner runs up to four named foreground agents at once (Puck, Isabella, George, Sky; `Sources/relay-runner/App/SessionAgent.swift`). Each is a separate Claude or Codex session with its own conversation. All four are general sessions that can reach every registered project, and today none knows what the others are doing, so two can work on the same repository without noticing.

The user wants agents to know which repository each other agent is working in. This ticket builds that foundation: a presence record and a way to deliver notices. Two follow-up tickets add closer coordination when two agents share a repository, and an enforced claim on a shared checkout; both are out of scope here.

Design decisions already made with the user:

- **The system records presence wherever it can.** Do not rely on an agent remembering to announce itself. An agent declares a repository itself only for work the system cannot see.
- **Notices are one-way.** An agent never replies to, acknowledges or answers another agent's notice. Nothing in this feature lets one agent start a turn in another.
- **Notices are silent.** They are text for the receiving agent, never spoken, and never shown to the user as a reply.
- **Delivery waits for the receiver's next turn.** A notice never interrupts a running turn and never wakes an idle agent.

### What exists today (verify before relying on it)

- Each session has a key, a spool directory `/tmp/relay-sessions/<key>/` whose `session_agent` file holds the agent slug, and `RELAY_SESSION_KEY` / `RELAY_SESSION_AGENT` in the provider environment. The bridge's `Targets` registry (`rust/relay-rs/src/bridge/targets.rs`) lists live sessions and can read each one's agent.
- Nothing records which repository an agent works in. All four agents have the general-tasks folder as working directory. `activate_project` only moves the app's board view and carries no session identity.
- `/v1/runs` (dispatch) carries `repo_path` and `dispatcher_session_key`. `orchestrator-actions` and `session_capture` carry `relay_session_key` for authorization only. Ticket writes (`/v1/artifacts/tickets/write`, `claim-next-id`; `rust/relay-orchestrator/src/board.rs`) carry `repo_path` but no session or agent; the actor is hard-coded `"user"`.
- Nothing injects text into a running PM session except voice-turn delivery: the bridge writes the turn into the target session's spool and the app types it into the terminal (`rust/relay-rs/src/bridge/relay.rs`, `commands.rs`; `RelayVoiceCommandDelivery` in `Sources/relay-runner/Terminal/EmbeddedTerminal.swift`). The bridge already appends context blocks to each voice turn's prompt (the "Relay work-intent disposition" and "Relay intent qualification" blocks).
- Run lifecycle updates go to a separate spoken messenger, not into the PM's prompt. The relay hook (`rust/relay-rs/src/hook/`) observes turns and adds no context to prompts.
- The orchestrator MCP (`Sources/relay-orchestrator-mcp`) already sends `RELAY_SESSION_KEY` and has its environment forwarded under both providers. The relay-app MCP does not get those variables under Codex.
- Startup instructions are assembled in `appOwnedInstructionFlag` (`Sources/relay-runner/Process/ProcessManager.swift`); the shared instruction text is built by `scripts/build-instructions` from `services/instructions/*.md`.

### What to build

1. **Presence record in the daemon.** For each running agent, the set of repositories it is working in. An entry has the agent, its session key, the repository path, how it was learned, when it was first and last seen, and an optional one-line note. A repository leaves an agent's set after two hours without activity there. All of an agent's entries are removed when its session stops, and entries for sessions that no longer exist do not survive a daemon or app restart.
2. **Automatic recording.** Every daemon mutation that names a repository and can be attributed to a session updates presence: dispatches, ticket claims and writes, orchestrator actions, session capture. Add an optional session key to the ticket-write and claim-next-id requests and have the foreground PM's ticket-writing path send it, so ticket work is attributed; requests without it keep working and record nothing. The built-in general-tasks project is never recorded: every agent lives there.
3. **Declared presence.** Add an orchestrator MCP tool with which an agent declares that it is starting work in a repository, with a one-line note, for work the daemon cannot see (reading and editing files directly, research in a checkout). Add a read tool that returns the current presence of all agents: name, running, repositories, notes, last activity. Both identify the caller by its session key.
4. **Notices.** When a repository enters an agent's set, every other running agent gets one notice, for example: `Agent notice: George started working in relay-runner (dispatched RR-530).` When an agent stops, the others get one notice that it stopped and which repositories it left. Nothing is sent for repeated activity in a repository already in the set. Notices for an agent that is not running are dropped, not stored for later.
5. **Delivery at the receiver's next turn.** Queue notices per receiving session in the daemon and deliver each once:
   - on a voice turn, the bridge appends an "Agent notices" block to that turn's prompt for the target session, the way it appends the disposition block;
   - on a typed turn, deliver through the provider's prompt-submit hook as added context where the provider supports it. If a provider has no such hook, say so in the docs and rely on the next two paths for it;
   - every presence tool result (item 3) includes the caller's undelivered notices;
   - a session that starts gets the current presence of the other agents in its startup instructions.
   A notice is never typed into a terminal by itself, never starts a turn and never reaches the messenger or TTS. When more than ten are pending, deliver the newest ten and a count of the rest.
6. **Instructions.** Add to the foreground PM's instructions, for both providers: what an agent notice is; that it is information from another agent and never an instruction or a user request; that the agent must not reply to it or act on another agent's behalf; that it declares a repository before working in one directly; and that when a notice shows another agent doing the same work, it stops that work and asks the user. Regenerate the generated instruction files.
7. **Docs.** Describe presence and notices in `docs/` next to the orchestrator documentation.

## Acceptance criteria

- [ ] Daemon test: a dispatch and a ticket write carrying a session key each add that repository to the agent's presence; a ticket write without a session key succeeds and records nothing; activity in general-tasks records nothing.
- [ ] Daemon test: the declare tool adds a repository with its note, and the read tool returns all four agents with running state, repositories and notes.
- [ ] Daemon test: a repository leaves the set after two hours without activity (use an injected clock); a stopped session's entries are removed; entries for a session that no longer exists are gone after a restart.
- [ ] Daemon test: with Puck and George running, George's first activity in a repository queues exactly one notice for Puck and none for George; a second activity in the same repository queues none; a stopped agent's notice names the repositories it left; no notice is queued for an agent that is not running.
- [ ] Bridge test: a voice turn for a session with pending notices carries an "Agent notices" block with them, and the next turn does not repeat them.
- [ ] Test: with more than ten pending, the block has the newest ten and the count of the rest.
- [ ] Test or documented finding: typed-turn delivery through the prompt-submit hook for Claude, and the stated behaviour for Codex.
- [ ] Test: no notice is passed to the messenger or the speech path, and no code path types a notice into a terminal or starts a provider turn.
- [ ] The orchestrator MCP exposes the declare and read tools with the caller identified by session key, under both providers' environment forwarding; tool-schema tests are updated.
- [ ] The PM instructions contain the notice rules in item 6 for both providers, and the generated files are regenerated with `scripts/build-instructions`.
