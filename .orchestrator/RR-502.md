## Description

Follow-up from the RR-501 spike (run 380); read its findings in RR-501 before starting.

On macOS, check three things and give a go/no-go for each:

1. Do the Claude and Codex CLIs keep their tool subprocesses in the provider's process group, so `setsid` plus `killpg` would reach them?
2. Can the daemon read argv and environment of same-user processes through `KERN_PROCARGS2`?
3. Is `ps -o lstart` stable enough to pair with a pid as a process identity?

Use only throwaway processes the experiment starts itself. Stop all of them before finishing.

**Conclusions**

- Q1 (setsid+killpg reaches tool subprocesses): NO-GO as the only cleanup mechanism. Codex shell-tool children call setsid() themselves and Codex MCP servers get their own group, so killpg(provider pgid) misses both. For Claude nothing public or local shows its Bash-tool children share the provider's group, so that is unverified.
- Q1 detail: the interactive provider needs no setsid. SwiftTerm forks it with forkpty, so it is already session and group leader (pid == pgid == sid) and killpg(pid) is available now. Adding setsid would fail with EPERM. Treat killpg as a free first step, not as proof that descendants are gone.
- Q2 (argv/env via KERN_PROCARGS2): argv is a GO for same-user processes. Env is a CONDITIONAL GO. XNU omits env strings when the target is cs_restricted, unless SIP allows it or the caller holds a private Apple entitlement the daemon cannot have. A present tag proves ownership. A missing tag proves nothing, so it must never authorize or veto a kill.
- Q2 caveat: whether Claude, Codex and the system tools they spawn count as cs_restricted was not tested, so env-tag coverage is unknown. The existing parser in ProcessManager.swift drops empty argv entries and stops after argv, so env parsing needs a new, length-correct parser. Codex defaults to inheriting the full environment; Claude's env scrub is opt-in.
- Q3 (ps -o lstart as identity): CONDITIONAL GO. lstart is p_starttime.tv_sec only, printed with localtime and %c. That gives 1-second resolution and output that depends on the caller's TZ and locale. The launcher records it inside the provider env and Swift re-reads it from the app, so a TZ or LANG difference can give a false mismatch. A mismatch fails safe (no signal) but leaks the process.
- Q3 recommendation: pair pid with the binary start time (tv_sec + tv_usec) plus uid, read via sysctl KERN_PROC_PID or proc_pidinfo. AssistantManagedProviderProcess.swift already reads p_starttime this way. Keep the ps text only as a display or compatibility field.
- setsid side effects on providers: none visible on the current paths. Headless workers already run under setsid with piped stdin and file output, and Codex's own shell tool calls setsid and falls back to setpgid on EPERM. On the interactive PTY path setsid is an EPERM no-op. Only a setsid wrapper placed before the PTY would break things: the terminal would no longer be the controlling terminal, so Ctrl-C/SIGWINCH/SIGHUP would not arrive. This is POSIX reasoning, not a live run.
- Process hygiene: this spike started no processes and made no changes, so none is left running. No shell tool was available, so the throwaway-process experiments in the ticket were not run. The answers rest on source, public documentation and repo code, and the gaps are listed as uncertainties.

**Recommended next steps**

- For RR-503/RR-505, do not rely on setsid+killpg alone. Use killpg(provider pid) as a best-effort first step on the interactive path, since pid == pgid already. Do not call setsid on the PTY-launched provider.
- Then do a descendant sweep. Enumerate the provider's descendants by parent pid, and also match any process whose KERN_PROCARGS2 env holds the per-launch tag. Signal only on a positive match with an identity check, and never because a tag is missing.
- Replace ps-text identity with (pid, uid, start time as tv_sec+tv_usec) from sysctl or proc_pidinfo for new work. Keep the old lstart string readable for stored bindings, and treat a mismatch as stale (no signal).
- Write a Rust integration test that starts only throwaway children (sleep, sh -c with a nested setsid child, a python3 child) and checks four things: pgid/sid after forkpty, whether killpg reaches a nested setsid child, whether KERN_PROCARGS2 returns env for a platform binary versus a user-compiled binary, and whether lstart text changes under a different TZ and LANG. The test must kill and reap everything it starts, and a reviewer can run it.
- Capture one live Claude and one live Codex tool-call tree (ps -o pid,ppid,pgid,sess) as a separate, user-independent check if a machine with the CLIs is available. If it is not, keep Claude and Codex handling identical and sweep-based.
