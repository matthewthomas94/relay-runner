## Description

Display attached ticket images inside the Workspace ticket detail panel.

The attachment pipeline already copies image files into
`.orchestrator/attachments/<TICKET_ID>/`, records Markdown image references,
and extracts their relative paths. The detail panel currently presents those
paths as plain text, so users can confirm only the filename rather than see the
design or evidence they attached. RR-211 is a current reproduction: its image
exists and parses correctly, but the ticket detail does not render it.

Replace the filename-only Images section with an inline visual preview that
resolves each attachment relative to the owning project's `.orchestrator`
directory. Keep the implementation limited to safe local ticket attachments;
do not turn the ticket body into a general remote or arbitrary-file image
loader.

## Acceptance criteria

- [ ] Opening a ticket with a valid image attachment shows the image itself in the Images section rather than only its relative path.
- [ ] The preview preserves aspect ratio, stays within the existing detail-panel width, and remains usable inside the current vertical scroll view.
- [ ] Multiple attachments render in ticket order without overlapping, clipping, or making the metadata and acceptance criteria unreachable.
- [ ] Relative attachment paths resolve against the exact owning project's `.orchestrator` directory in both single-project and Program Workspace routes.
- [ ] Absolute paths, remote URLs, parent-directory traversal, symlink escapes, and paths outside `.orchestrator/attachments/<TICKET_ID>/` are not loaded.
- [ ] Missing, unreadable, or corrupt images show a compact failure state with the filename while the rest of the ticket remains usable.
- [ ] The existing create/edit attachment flow, Markdown references, dispatch snapshots, and worker attachment access remain unchanged.
- [ ] Image previews expose useful accessibility labels derived from the attachment filename and do not interfere with keyboard scrolling or ticket actions.
- [ ] RR-211's committed screenshot is visible when its detail panel is reopened after refresh.
- [ ] Automated tests cover valid PNG/JPEG rendering inputs, multiple images, missing and corrupt files, path traversal rejection, project scoping, and attachment ordering.
- [ ] Visual verification covers representative portrait, landscape, and high-resolution screenshots at supported Workspace sizes.
