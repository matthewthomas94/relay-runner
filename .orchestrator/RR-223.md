## Description

Relay Runner repeatedly shows `I handled that Relay voice turn, but the provider did not send a spoken final reply` while the integrated provider terminal visibly reports that the same foreground turn is still working. The warning therefore claims the turn was handled and has no final before the provider has reached a terminal state. A normal response may still arrive later, leaving the user with a false failure message and no trustworthy indication of whether Relay is waiting, failed, or complete.

Treat this as a live regression of RR-211. The missing-final fallback must be armed only for the exact acknowledged provider turn and must not fire while that turn is active, while prompt delivery is still being acknowledged or recovered, or while a valid response is pending routing. Anchor any bounded grace period to an actual provider terminal event rather than command claim, PTY submit attempt, or elapsed foreground work time.

The full supplied screenshot is not attached because it contains unrelated terminal and application content. Its relevant evidence is the fallback warning visible in the response pill while the matching Codex terminal simultaneously shows `Working (24s • esc to interrupt)`.

RR-217 and RR-222 are dependencies because they correct the overlapping response-preview and input-acknowledgement state machines. This ticket must verify the combined event ordering after both land rather than introducing a competing workaround.

## Acceptance criteria

- [ ] Reproduce the false missing-final warning while the matching provider turn remains active in the current installed/package-equivalent app.
- [ ] Relay never emits the missing-final warning while the correlated provider turn is active, prompt delivery is unacknowledged or recovering, or a nonempty current response is pending routing.
- [ ] A fallback grace period starts only after an acknowledged terminal provider event that produced no usable final, not at command receipt, claim publication, PTY write, submit attempt, or provider-turn start.
- [ ] Long-running turns, tool calls, context compaction, foreground orchestration, and worker dispatch can exceed the old timeout without producing a false warning.
- [ ] A late but valid current final cancels any pending fallback and is delivered exactly once; a warning cannot overwrite the final or remain as stale pill content.
- [ ] Explicit orchestrator replies and completion-hook recovery continue to deduplicate one another for the exact Relay sequence and id.
- [ ] Interrupted, failed, empty-final, bridge-unavailable, and genuinely completed-without-final turns still produce at most one bounded and accurate recovery message.
- [ ] Newer-intent preemption prevents a stale turn's fallback from appearing over a newer command or response.
- [ ] Sanitized diagnostics identify warning eligibility, deferral, cancellation, and emission with provider turn state and Relay sequence/id but no raw prompt or response content.
- [ ] Codex and Claude pass equivalent active-turn, delayed-final, empty-final, interruption, stale-turn, and exact-once regression tests using their provider-specific terminal signals.
- [ ] A manual installed-app smoke test confirms the warning cannot appear while the terminal still shows the provider working.
