## Description

Add a PM update mode that keeps the user informed after work has been handed to the orchestrator and workers.

In the RR-127 model, the PM is stakeholder/user management. After dispatch, it should fetch state from the persistent orchestrator, worker runs, board files, and program status surfaces, then provide timely TTS/notch/chat updates. It should not wait for worker-to-PM push messages or block fresh user instructions while summarizing current work.

This touches PM-frontstage status events, voice bridge TTS/notch behavior, program status surfaces, and likely tests around preemption/stale commands.

## Acceptance criteria

- [ ] Define when PM update mode starts and stops for a voice session.
- [ ] The PM can fetch orchestrator and worker state directly from durable status sources.
- [ ] The PM emits concise, user-safe status updates at relevant intervals or on meaningful events.
- [ ] Status updates do not include hidden reasoning, raw transcripts, raw tool logs, or unbounded metadata.
- [ ] New user instructions during update mode still fan out to the orchestrator and do not block status fetching.
- [ ] TTS/notch updates honor Relay stale-command metadata and do not speak stale work.
- [ ] Add tests for update cadence, event-triggered summaries, fresh-command interruption, and status privacy.
