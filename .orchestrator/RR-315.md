## Description

The Registry V2 **Add existing project** flow currently rejects a user-selected directory when it is not already a Git worktree and surfaces a low-level `project path is not a Git worktree` failure. Treat the explicit folder selection as authorization to make that existing project Relay-ready: initialize Git in the selected directory, then continue the normal validation, duplicate detection, access-grant, registration, active-selection, and Workspace refresh flow.

Keep the mutation boundary narrow. Automatic `git init` applies only to the explicit **Add existing project** action. Passive discovery, bridge/session routing, Relay Actions activation, and other generic project/workspace resolution must continue to refuse non-Git folders rather than mutating them. Existing repositories, nested selections that already resolve to a containing worktree, bare repositories, and Relay-created worker worktrees must retain their current validation and identity behavior.

Initialization should match Relay's Create Project convention (`main` as the initial branch), create no commit, stage no user files, and preserve every pre-existing file. If Git initialization fails, do not write a registry entry or access grant; surface a concise actionable project-update error instead of the current generic not-a-worktree wording. Update user-facing documentation or generated orchestration guidance only where it describes this explicit Add Existing behavior; do not weaken the refusal contract for passive activation.

## Acceptance criteria

- [ ] Selecting an ordinary existing non-Git directory through **Add existing project** runs Git initialization in that exact directory and then registers and selects it without requiring a retry.
- [ ] The initialized repository uses `main` as its initial branch, has no initial commit, stages no existing files, and preserves all existing directory contents.
- [ ] Selecting an existing repository or a directory inside one does not reinitialize or otherwise alter its Git metadata, and existing duplicate, bare-repository, user-worktree, and Relay-worker-worktree protections remain intact.
- [ ] An initialization failure leaves the registry and access-grant state unchanged and surfaces concise actionable UI copy that names the initialization failure.
- [ ] Passive workspace discovery, session/bridge routing, and programmatic activation still do not run `git init` for non-Git folders.
- [ ] The Add Existing operation remains off the main actor and resumes the Workspace/Settings surface through the existing success and failure paths.
- [ ] Focused tests cover successful non-Git initialization and registration, preservation/no staging/no commit, existing-repository behavior, initialization failure cleanup, and the unchanged passive-activation refusal boundary.
- [ ] The full relevant Swift test suite passes.
