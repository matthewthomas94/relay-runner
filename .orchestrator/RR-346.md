## Description

Restore the Messenger as Relay Runner's immediate, lightweight conversational intermediary between the user and the foreground PM. The persistent Messenger exists so the user receives a fast, natural response while the heavier PM is queued, reasoning, authoring tickets, dispatching workers, or waiting for a safe provider boundary. It must not inherit foreground-PM latency or remain silent until authoritative work completes.

For every eligible user turn, submit the turn to the already-running lightweight Messenger concurrently with foreground orchestration. The Messenger should promptly produce a short semantic response that reflects the user's actual meaning: affirm the request or concern, answer ordinary low-risk conversation when authorized, and set an honest expectation for what the PM will do next. A deterministic receipt such as a fixed "got it" is not an acceptable substitute for model understanding.

The Messenger must also continue translating public PM and worker lifecycle context into useful user-facing updates without inventing work state or gaining tools, ticketing, dispatch, repository-write, or authoritative-decision powers. Diagnose the present regression across command receipt, Messenger fanout, provider turn start, first semantic output, speech arbitration, TTS enqueue, and playback. Remove any unnecessary dependency on PM command delivery, classification, terminal safe-boundary waits, completion, or another foreground turn.

Treat this as a regression of the architecture established by RR-161 and the multi-message lifecycle preserved by RR-263. Preserve stale-command suppression, interruption and barge-in, privacy boundaries, semantic deduplication, authoritative outcome delivery, exact-once playback, and equivalent Codex and Claude behavior.

## Acceptance criteria

- [ ] A deterministic regression reproduces the current delayed or missing Messenger response and identifies which measured stage is responsible: user-turn receipt, Messenger submission, lightweight provider start, first semantic output, speech arbitration, TTS enqueue, or playback.
- [ ] Every eligible user turn is offered to the persistent Messenger immediately and concurrently; this path does not await foreground-PM delivery, classification, ticketing, terminal safe-boundary availability, reasoning, or completion.
- [ ] The first Messenger response is generated by the configured lightweight model and contains a concise, safe gist or affirmation specific to the user's meaning. A fixed, templated, or randomly varied generic acknowledgement does not satisfy the healthy path.
- [ ] For task-like turns, the Messenger confirms what it understood and sets an honest expectation that the PM will return with a plan, clarification, status, or result without claiming that unperformed work has started or finished.
- [ ] For ordinary conversational turns within its authority, the Messenger can respond directly without a foreground-PM handoff delay; project mutations and authoritative project claims remain PM-owned.
- [ ] Public PM reasoning summaries, clarification needs, worker lifecycle events, blockers, and outcomes remain available for concise Messenger updates so the user can understand and steer the PM without reading the terminal.
- [ ] Privacy-safe timing telemetry correlates the exact Relay command sequence and ID across receipt, Messenger submit/start/output, TTS enqueue, and playback, and makes PM-caused or provider-caused latency distinguishable without logging raw transcript or response text.
- [ ] In an installed healthy-session UAT sample of at least ten eligible turns, at least nine begin a semantically specific visible response within two seconds of final transcript receipt and audible playback within three seconds; any provider/network outlier is labeled with stage timing rather than silently attributed to the PM.
- [ ] Messenger process failure or provider unavailability produces a prompt, truthful degraded-state indication and preserves foreground command delivery; it does not create prolonged unexplained silence or substitute a canned semantic claim.
- [ ] A prompt Messenger acknowledgement never suppresses a later substantive PM result, blocker, or critical decision request, while semantically redundant same-phase speech remains deduplicated.
- [ ] Superseded, interrupted, canceled, and stale Messenger output cannot speak or update the current user turn; rapid consecutive turns retain command-scoped ordering and barge-in behavior.
- [ ] Codex and Claude use equivalent lightweight Messenger behavior and latency instrumentation, with provider-specific process/protocol differences and any live-auth verification limitation documented.
- [ ] Focused Python and Swift tests cover parallel fanout, PM-busy and terminal-safe-boundary scenarios, contextual acknowledgement quality, timing telemetry, failure fallback, semantic arbitration, stale turns, interruption, TTS playback, and both supported providers; a mounted signed-app voice check validates the human-visible and audible experience.
