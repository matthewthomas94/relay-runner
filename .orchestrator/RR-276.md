## Description

Add an explicit execution mode for research and discovery tickets that need an agent to investigate a bounded question without implying an implementation change. Ticket creation and editing should distinguish ordinary implementation work from a spike while preserving the existing implementation behavior as the default for all current tickets.

A spike run must not create or check out a `relay/<ticket>` implementation branch, produce a source-code commit, or enter the implementation review-and-merge path. It may use a disposable detached checkout or another isolated read-only view when needed, but source and board mutations from the spike worker must fail closed. The daemon remains responsible for lifecycle, cancellation, retries, cleanup, and a durable result linked to the ticket and run.

Completed spike findings must be inspectable from Workspace and usable by the foreground PM without exposing raw provider transcripts. Define a safe ticket-only completion path or equivalent canonical persistence mechanism so a successful spike can reach Done without pretending that an implementation branch was merged. Keep dependency progression explicit: completion of a research ticket must not dispatch downstream implementation work unless those tickets were already refined and authorized for dispatch.

## Acceptance criteria

- [ ] The ticket schema and parser support an explicit spike execution mode alongside the existing implementation mode; legacy tickets without the field retain current implementation semantics.
- [ ] Workspace ticket creation and editing clearly expose the execution mode and explain that a spike is research-only and branchless before the ticket can be saved or promoted.
- [ ] Foreground PM ticket authoring can create a refined spike ticket directly without encoding raw voice transcripts or provider-specific launch details in visible prose.
- [ ] Dispatching a spike creates a daemon-tracked run without creating or checking out a `relay/<ticket>` branch and without scheduling an implementation review/merge worker.
- [ ] Any temporary repository view used by a spike is detached, isolated, read-only, and cleaned up after success, failure, cancellation, timeout, or app restart.
- [ ] A spike worker receives a bounded research question, allowed evidence sources, non-mutation rules, and a structured result contract; attempted source, ticket, Git-ref, desktop, or external side-effect mutations fail closed and are reported.
- [ ] Successful spike findings are stored durably with ticket/run provenance and are visible in Workspace as a concise report containing conclusions, evidence, uncertainties, and recommended next steps without raw chain-of-thought or transcript content.
- [ ] A successful spike can reach the Done lane through a canonical daemon-owned result path that does not claim an implementation merge; failures and incomplete spikes remain visibly retryable with their exact cause.
- [ ] Cancellation, retry, stale-command authorization, queue-drain reconciliation, dependencies, and app restart recovery distinguish branchless spike runs from implementation runs without losing accepted work.
- [ ] The default Ready behavior remains unchanged for implementation tickets, and choosing spike mode cannot silently weaken mutation isolation for an implementation worker.
- [ ] Codex and Claude exercise equivalent branchless spike behavior, lifecycle states, privacy boundaries, and cleanup, with intentional provider-specific sandbox differences documented.
- [ ] Focused daemon and Swift tests verify schema compatibility, ticket editor behavior, absence of worker branches, mutation rejection, durable result rendering, cancellation/retry, dependency behavior, and cleanup.
- [ ] Documentation describes when to use a spike, its non-implementation guarantees, how it completes, and how its findings can be turned into separately reviewed backlog tickets.
