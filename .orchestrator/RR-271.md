## Description

Fix the silent delay between a valid double-tap Option playback gesture and audible speech for an authoritative Relay response. The current path publishes the final response preview and arms waiting playback before `MessengerRuntime` has completed a second model call and submitted the matching final `SpeechIntent`. If Option is pressed during that interval, `SpeechCoordinator.play()` retains `_play_requested`, but no state or diagnostic acknowledges the accepted gesture. The overlay remains at Response ready until `TTSWorker.play()` later emits Preparing speech. Only then can Kokoro first-sentence realization add its own delay; four recent warm-session samples measured 0.514, 2.477, 1.078, and 1.192 seconds from final intent proposal to audio start (1.135-second median).

Make the first valid Option gesture visibly acknowledged immediately even when the authoritative speech intent has not materialized. Keep the visible state truthful until speaking, cancellation, failure, or supersession, and do not require a second gesture. Remove the authoritative final's extra LLM completion from the critical playback path: final speech must not wait for `MessengerRuntime.backend.ask` after the provider-visible response is already available. Use the authoritative final text directly or a bounded deterministic local transformation; preserve concise natural speech without making another provider request a prerequisite for TTS enqueue.

Add privacy-safe end-to-end timing diagnostics for Option detection, FIFO `__PLAY__` receipt, retained-play latch, matching intent commit, TTS preparing, first WAV readiness, and `afplay` start. Diagnostics must carry correlation metadata and durations but never response or transcript text. Preserve exact-once authoritative playback, stale-command rejection, older-handoff suppression, replay, cancel/skip behavior, speculation, completion-hook deduplication, background shortcut delivery, and Codex/Claude parity. Verify the actual mounted Relay Runner path in addition to focused unit tests.

## Acceptance criteria

- [ ] A valid double-tap Option for a visible current response produces deterministic visual acknowledgement within 250 ms in the mounted app, including when the matching final speech intent is not yet committed.
- [ ] The acknowledgement remains truthful through the retained wait and transitions to Playing, Response cancelled, or an explicit failure/supersession outcome without reverting to an unexplained idle Response ready state.
- [ ] A first Option gesture received before final-intent commit is retained and starts that exact authoritative final once it is playable; it never requires a second gesture and never plays an older handoff.
- [ ] Authoritative final playback no longer waits for a second provider or messenger LLM completion after the provider-visible final text exists; the TTS intent is queued directly from that text or a bounded deterministic local transformation.
- [ ] Privacy-safe diagnostics measure Option detection, FIFO play receipt, retained-play latch, intent commit, Preparing speech, first WAV readiness, and audio-process start using command and utterance correlation without recording transcript or response text.
- [ ] A repeatable warm-session benchmark reports end-to-end Option-to-first-audio latency and its stage breakdown; representative authoritative finals meet a 3-second p95 first-audio budget on the supported Apple Silicon test machine, while acknowledgement remains within 250 ms.
- [ ] Duplicate play gestures, stale or superseded responses, cancellation, replay, notification chime/speculation races, completion-hook deduplication, and background Option delivery retain exact-once and freshness behavior.
- [ ] Focused Python coverage includes speech coordinator, messenger, voice bridge, and TTS worker paths; focused Swift coverage includes Option gesture delivery and preparing/playing acknowledgement state transitions.
- [ ] A mounted installed-app smoke test confirms one prompt, one prompt double-tap Option, immediate feedback, and one authoritative spoken response for both a speech-ready response and an early gesture during retained playback.
- [ ] Codex and Claude sessions receive equivalent acknowledgement, authoritative-final selection, cancellation, diagnostics, and latency behavior; any unavoidable provider-specific completion-hook handling is documented.
