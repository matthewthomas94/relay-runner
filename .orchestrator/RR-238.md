## Description

Fix a race in app-owned Relay voice sessions that can process one user command
twice. The observed failure occurred when command sequence N+1 arrived while
the provider was still completing sequence N:

1. Swift correctly left N+1 pending because a provider turn was active.
2. The active provider turn independently noticed the newer
   `/tmp/voice_command_state.json` value and handled N+1 before it had been
   claimed.
3. When sequence N finished, Swift claimed and injected the still-pending N+1
   command as a new provider turn.
4. The provider therefore produced two nearly identical replies for one user
   command.

Delivery-event timestamps confirmed that the first N+1 reply began before its
`claimed` and `prompt_write` events. This was duplicate command consumption,
not merely replay of one TTS result. Besides repeated speech, the race could
duplicate ticket edits, worker dispatches, or other actions.

The conflicting ownership rules currently span
`ProcessManager.appOwnedRelayInstructions` in
`Sources/relay-runner/Process/ProcessManager.swift` and
`RelayVoiceCommandDelivery.providerReadyForNextCommand()` in
`Sources/relay-runner/Terminal/EmbeddedTerminal.swift`. The first tells an
active turn that sees newer state to stop stale work and handle the newest
intent, while the second deliberately retains the same command for later
claim and injection until the active provider turn ends.

Establish one authoritative owner for every app-owned command. The smallest
safe behavior is for an active stale turn to use newer sequence metadata only
to stop its stale follow-up work and end silently; it must not answer or act
on the new command until Swift atomically claims and injects that command as
the next provider turn. A formal atomic adoption handshake is also acceptable
if it transfers the pending command, claimed metadata, provider-turn
correlation, completion hook, and messenger/TTS authority together so Swift
cannot inject the command again.

Preserve newest-intent-wins behavior and stale-action protection. Preserve the
special immediate handling of `__INTERRUPT__`, normal active-provider
deferral, submit acknowledgement and retry behavior, and the manual
`relay-bridge` path's atomic checkpoint semantics. Apply equivalent
exactly-once behavior to Codex and Claude app-owned sessions.

## Acceptance criteria

- [ ] Add a deterministic regression test in which sequence N is active when
      sequence N+1 becomes ready. For both Codex and Claude app-owned session
      paths, N+1 has exactly one authoritative handling, provider prompt, and
      user-visible final reply.
- [ ] If the implementation ends the stale N turn silently, verify that it
      performs no N+1 action or final reply, N+1 remains pending while the
      provider is active, and Swift claims and injects N+1 exactly once after
      the provider becomes inactive.
- [ ] If the implementation adopts N+1 into the active turn, make that
      adoption atomic: remove the ready command, advance claimed metadata,
      transfer provider-turn and completion ownership, and prevent any later
      Swift injection of N+1.
- [ ] `/tmp/voice_cmd_claimed.json` advances only when a provider turn truly
      owns the command. `/tmp/voice_cmd_ready` and its metadata cannot remain
      replayable after a provider begins handling the same sequence.
- [ ] After a newer sequence exists, the stale command cannot create or edit
      a ticket, dispatch a worker, perform another external action, or emit a
      user-visible final reply.
- [ ] Explicit final delivery, the provider completion hook, the persistent
      messenger, and TTS collectively emit or speak the latest command's
      outcome once.
- [ ] Regression coverage preserves immediate `__INTERRUPT__` delivery,
      normal active-turn deferral, rapid supersession of pending commands,
      provider acknowledgement, and submit retry behavior.
- [ ] Codex and Claude receive equivalent exactly-once semantics, with any
      provider-specific turn-detection differences documented and tested.
- [ ] The manual `relay-bridge` atomic claim/checkpoint flow continues to
      consume steered commands once and is not weakened by the app-owned fix.
- [ ] Sanitized delivery diagnostics distinguish defer, claim, adoption if
      implemented, injection, and completion without recording raw voice
      text, terminal input, or secrets.
- [ ] Relevant Swift and Python voice-delivery, provider-turn, messenger, and
      completion-hook tests pass.
