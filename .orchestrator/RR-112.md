## Description

Evolve the existing notch status surface so Relay Runner uses the MacBook Pro notch area as a small dynamic-island style session indicator, matching the latest design screenshots in `~/Downloads`:

- `Session active - Not working.png`
- `Session active - Working.png`
- `Session active - Listening.png`
- `Session active - Playing.png`

The physical notch outline shown in the design is only an illustrative alignment guide and must not be drawn by the app.

The right-side notch cap should render a discrete dot-matrix glyph, not the current tray icon or a smooth gradient orb. The final states are:

- Not working: compact neutral/white 2x2 dot glyph.
- Working: compact neutral/white 2x2 dot glyph plus an optional black capsule extending left from the notch.
- Listening: orange dot-matrix activity glyph, with the lower listening/voice surface using the matching orange dot-field treatment.
- Playing: blue/purple dot-matrix activity glyph, with the lower playback surface using the matching blue/purple dot-field treatment.

For the working state, use the reasoning/progress updates Codex or Claude writes to the terminal but does not send to TTS as the notch capsule content. The capsule needs concise summarized status text rather than raw long messages or transcripts. Examples: `Reading code`, `Editing files`, `Running tests`, `Moving ticket`, `Waiting dependency`.

The existing `NotchStatusController`, `NotchActivityLabelPlanner`, `AppState.syncNotchActivitySurface`, `OverlayController`, and related tests are likely touch points. Keep the state names user-facing as not working, working, listening, and playing; do not expose a recording state in the notch UI even if lower-level STT internals still use recording terminology.

Assumption to confirm before implementation: the `Listening` screenshot's lower card still says `Recording - Press Caps Lock again to send`, but the intended user-facing notch state is `Listening`.

## Acceptance criteria

- [ ] The notch status cap renders a dot-matrix glyph matching the four final screenshots rather than the existing tray icon/gradient treatment.
- [ ] Not working and working use the compact neutral/white glyph state.
- [ ] Listening uses the orange glyph state and keeps the lower voice/listening surface visually aligned with the orange dot-field treatment.
- [ ] Playing uses the blue/purple glyph state and keeps the lower playback surface visually aligned with the blue/purple dot-field treatment.
- [ ] Working can show concise non-TTS reasoning/progress status in the left notch capsule, summarized to fit the available space without showing transcripts or raw long terminal text.
- [ ] The app never renders the white physical-notch outline from the design.
- [ ] The notch UI uses user-facing statuses `Not working`, `Working`, `Listening`, and `Playing`; any internal `recording` naming is mapped to `Listening`.
- [ ] Existing non-notched and multi-display placement behavior remains intact.
- [ ] Tests cover glyph/state mapping, activity-label summarization, and placement for both the right-side cap and left-side capsule.
- [ ] Provider parity is explicit: Codex and Claude progress/reasoning activity surfaces should use the same summarized notch-status behavior unless a provider cannot expose equivalent activity.
