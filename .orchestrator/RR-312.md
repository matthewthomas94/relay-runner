## Description

Repair the Workspace support-bundle export path after a remote Relay Runner 0.4.41 build 45 test appeared to crash immediately after exporting incident `inc-fda6cd599a82`. The exported archive is valid, but it ends before the reported termination and intentionally excludes native crash reports, so do not claim that the bundle proves the crash cause.

The current UI action synchronously snapshots and decodes every journal file, serializes the timeline, launches `ditto`, and waits for it to exit on the main thread. The reported incident had 647 journal files and 1,313 events because the workspace daemon was restarting continuously. Move the expensive work off the UI thread, make output publication atomic, and retain enough allowlisted lifecycle evidence to distinguish success, failure, cancellation, and an interrupted export without adding raw logs or crash reports to the bundle.

## Acceptance criteria

- [ ] The save panel remains on the main actor, but journal snapshotting, validation, timeline serialization, and archive creation run off the main thread without blocking Workspace interaction.
- [ ] The UI presents one clear in-progress export state, prevents duplicate concurrent exports, and reports completion or failure back on the main actor without retaining the controller or touching deallocated UI.
- [ ] Export records a stable allowlisted attempt identifier and `diagnostics_export` started event before snapshotting, then a terminal ready, failed, or canceled outcome; an interrupted attempt remains diagnosable on the next launch without copying native crash reports into the support archive.
- [ ] Archive creation uses a unique staging destination and atomic final publication, preserves an existing destination unless replacement succeeds, and removes abandoned staging data after success or failure.
- [ ] Cross-process journal writers remain safe and bounded while an export is in progress; no long-running archive process holds the journal lock.
- [ ] A stress regression with at least 650 source files, 1,300 events, and a concurrent writer proves the main actor remains responsive, the archive validates, duplicate export is rejected, and failure cleanup is complete.
- [ ] Obtain and inspect the matching native crash or termination evidence when available, record the verified cause separately from the main-thread defect, and verify the corrected signed app no longer terminates during the same remote export flow.
- [ ] Privacy tests continue to exclude transcripts, prompts, repository paths/content, credentials, worker logs, screenshots, raw stderr, full temporary directories, and native crash reports from the archive.

## Verification plan

Add focused concurrency, lifecycle, atomic-output, cleanup, and privacy tests around `ProgramBoardOverlayController` and `RelayDiagnostics`. Exercise a large synthetic cross-process journal while periodically servicing a main-actor probe, inject `ditto` failure and interruption, then repeat the user-visible export in a signed build. Treat the reported crash as unconfirmed until the matching macOS crash or termination record is correlated.

## Reported evidence

- Relay Runner 0.4.41 build 45 on macOS 26.6.1 produced a valid bundle at 2026-08-12T07:30:34Z with 647 source files, 1,313 events, and zero writer-reported redactions.
- The last exported event is a shell setup start at 2026-08-12T07:30:10Z. There is no export-started event because the current code records only the terminal outcome after archive creation, and there is no post-export crash evidence by design.
- Source inspection confirms `exportSupportBundle()` calls synchronous `createSupportBundle(at:)` from the UI path; that method uses `queue.sync`, reads all journals, builds the complete timeline in memory, runs `/usr/bin/ditto`, and calls `waitUntilExit()`.
