## Description

Change the review and merge workflow so the foreground orchestrator does not directly review and merge an implementation worker's branch after that worker finishes a ticket. Instead, when an implementation worker completes, the foreground orchestrator should hand off the completed worker branch to a new review/merge sub-agent.

The review/merge sub-agent should inspect the completed worker's changes, run the appropriate verification, decide whether the branch is acceptable, and merge it into the working branch when it passes. The foreground orchestrator remains responsible for reporting status to the user and preserving the same project/command metadata guarantees, but the substantive review and merge work moves into the follow-up worker.

The implementation should preserve provider parity: Codex and Claude sessions should follow the same review/merge handoff model, with only documented provider-specific command, permission, or model differences.

## Acceptance criteria

- [ ] The documented orchestration workflow says completed implementation workers are reviewed and merged by a dedicated follow-up review/merge worker, not directly by the foreground orchestrator.
- [ ] The runtime workflow can create or dispatch a review/merge worker after an implementation worker finishes, carrying enough context to identify the original ticket, worker branch, target branch, and verification expectations.
- [ ] The review/merge worker can report success, failure, and required follow-up in a way the foreground orchestrator can summarize to the user.
- [ ] The merge path preserves the ticket lifecycle and board behavior, including publishing `done` only after the worker branch has been accepted and merged.
- [ ] Provider-facing behavior is considered for both Codex and Claude, with intentional differences documented in code, workflow docs, or user-facing status text.
- [ ] Tests or documented manual verification cover successful review/merge, review failure, merge conflict, and provider-specific launch handling.
