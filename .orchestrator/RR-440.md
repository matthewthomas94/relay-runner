## Description

Two processes burn CPU while Relay is idle, which heats the machine, drains battery, and raises the chance of CoreAudio "client timeout" overloads (audible clicks) during speech.

Measured on macOS 27.0.1 (MacBook Pro M4, 24 GB, 2026-10-28, Relay Runner 0.4.82):

1. **relay-runner (Swift app):** macOS wrote five `cpu_resource.diag` reports between 2026-10-25 and 2026-10-28 (`/Library/Logs/DiagnosticReports/relay-runner_*.cpu_resource.diag`). The latest: **90 s CPU over 114 s (79% average), exceeding the 50%-over-180 s limit**. The heaviest stack is the main thread inside the SwiftUI/AppKit event loop (`RelayRunnerApp.$main → NSApplicationMain → _DPSNextEvent …`), i.e. UI work, not audio.
2. **`services/orchestrator.py`:** sits at **40–60% CPU continuously** with no workers running (sampled three times over 3 s; `voice_bridge.py` is ~4% by comparison). Load average on the host was ~5.5 with 6 GB of swap in use.

Goal: profile both, find the root causes, and fix them without changing behaviour.

- For the app: use Instruments (Time Profiler) or `sample relay-runner` during an idle session to find the view-invalidation storm, timer, or polling loop; fix the top offenders (e.g. move polling to event-driven updates, throttle re-renders, avoid per-tick `@Published` churn).
- For the daemon: find the busy loop (likely tight polling of files, sockets, or the run ledger); replace with `select`/`kqueue`/file-watching or a sane sleep interval; make sure no thread spins when idle.

External verification: some checks need the live app, physical device changes, listening, or a long soak. Run what you can from the worktree without installing, releasing or restarting the running app. If only those checks remain, finish as `verification_blocked`, naming each remaining check in `verification_blocker` and how to run it in `verification_resume`.
