## Description

Relay Runner can leave processes running after the work that started them has ended, and nothing removes them. The user wants a clean-up step that runs when a session starts (or while it starts up) and deals with anything still running that should not be.

The case that prompted this, found on 15 November 2026: four Python daemons were still running days after their worker finished. Each was `python .../orchestrator/workspaces/relay-runner-bd315711-rr-485/services/orchestrator.py --config /private/var/folders/...` — a test daemon started from the RR-485 worker's workspace with a temporary config. Three dated from 11 November and one from 13 November. They were killed by hand. They were not the real daemon, which the LaunchAgent runs (now the Rust `relay-orchestrator` binary since RR-500).

This is a read-only spike. Work out what a safe, automatic clean-up should cover and how it should decide what is safe to stop. Do not implement it.

Questions to answer:

1. **Inventory.** Which kinds of process does Relay Runner start, directly or through workers, reviewers, spikes and tests? Cover at least: orchestrator daemons (Rust and Python), the voice bridge, messenger and provider CLI processes (Claude and Codex), MCP servers, worker and reviewer provider processes, test daemons and servers that workers start in their workspaces, and build or dev-server processes. For each, say what starts it, what is meant to stop it, and how it can outlive its owner.
2. **Other leftovers.** Besides processes, what else is left behind that the same step should consider: worker worktrees and `relay/<id>` branches for finished runs, temporary config and socket files, per-session spool directories under `/tmp/relay-sessions`, stale lock or pid files?
3. **Identification.** How can a leftover be told apart from something still in use, without false positives? Consider the run ledger (a process whose run is terminal), the process's working directory or command line pointing into a workspace of a finished run, parent process and process group, start time, and listening ports. State which signals are reliable and which are not.
4. **Where it runs.** Compare running the clean-up at app launch, at Start Session, when a run ends (the daemon stopping its own worker's process group), and periodically. Recommend one or a combination, and say which component should own it (the app, the daemon, or the `scripts/relay-orchestrator` launcher).
5. **Prevention.** Can the leak be stopped at the source, for example by running each worker in its own process group or session and killing the group when the run ends? Say how that compares with cleaning up afterwards.
6. **Safety.** What must never be killed (the live daemon, the active session's provider and bridge, a running worker, anything the user started themselves)? Should the step act silently, report what it stopped, or ask first? Both Claude and Codex paths must be covered equally.

## Acceptance criteria

- The report lists every kind of Relay-started process and leftover found, each with file and line evidence for where it is started and where, if anywhere, it is stopped.
- The report explains, with evidence from the code, how the RR-485 test daemons could outlive their run.

**Conclusions**

- RR-485 root cause: the Rust worker path signals only the provider's direct pid (worker.rs:464) and starts it with no process group or session (worker.rs:553-586). Whatever the provider's tools start survives the run. No code at run end, daemon start or in the app looks for those processes afterwards.
- The RR-485 test daemons also escaped by design. The contract harness starts them with start_new_session=True, a from-scratch env and a tmp cwd, and stops them only from inside the test process. A kill, timeout or cancel of that process skips cleanup, and the daemon has no parent-death exit. Killing the worker's group would not have reached them.
- Inventory: launchd daemon (Rust; Python only as rollback); worker and reviewer provider CLIs (Claude, Codex); test daemons, servers and dev servers that workers start (untracked, the real leak); voice bridge (launchd/nohup, detached); speech service (self-reaps); messenger and catalog providers (bridge children); MCP servers (provider children); embedded provider PTY (app).
- Identification rule, Tier 1 (safe to stop): same uid, no controlling TTY, not in the daemon's or app's ancestry or any live run's group, AND positive ownership. Ownership means argv or exe path under a workspace_path whose latest run for that ticket is terminal (match with trailing '/'), or env tag RELAY_RUN_ID of a terminal run. The process must predate the run's end and the run must have ended more than a grace period ago.
- Reliable signals: terminal run state with ended_at; recorded pid plus lstart identity; process group of a worker the daemon spawned; env tag set by the daemon; argv/exe path inside a workspace. Unreliable: cwd (RR-485 daemons had a tmp cwd), ppid==1 (launchd services too), listening port (port 0), pgrep -f name patterns, bare kill(pid,0), and env tags when the env is cleared.
- Where the rule is wrong: a user runs a dev server from a finished worktree; a retry reuses the per-ticket workspace path, so any non-terminal run for that ticket must veto; a run awaiting review or kept for external verification; pid reuse; unreadable argv. Path-only matches are Tier 2: report, never auto-stop.
- Where it runs: the daemon owns it. (1) Run end: killpg survivors when the provider exits. (2) Daemon start, after ledger reconcile, plus a slow periodic tick, because the LaunchAgent daemon lives for days. (3) The app asks the daemon at Start Session, non-blocking, beside the bridge/provider cleanup it already does there.
- Alternatives rejected: app launch only (rare, no run ledger, daemon may be down); Start Session only (leaks persist until a session starts, app has no ledger); launcher script (it exec()s into the daemon, uses pgrep -f patterns that already match test daemons, has no ledger); periodic only (no deterministic path for the common case).
- Prevention is feasible and should be the primary fix. Spawn worker and reviewer providers with process_group(0) or setsid (precedents: general_work.rs:1116, metadata.rs:275) and killpg SIGTERM then SIGKILL on cancel, shutdown and after the provider exits. It is deterministic and covers Claude and Codex alike.
- Prevention does not cover: descendants that call setsid/setpgid themselves (the RR-485 harness; possibly the CLIs' tool runners), a daemon crash or SIGKILL, or leftovers that already exist. So keep a sweep as the backstop, with pgid plus lstart identity recorded per run and an env tag RELAY_RUN_ID for escapees that inherit env.
- Never kill: the live daemon (launchd job pid, own pid, ancestors); any process in a non-terminal run's group; a live session's provider or PTY; the voice bridge with its speech and messenger children; MCP servers whose provider is live; the app; other users' processes; TTY-attached user processes; anything whose identity cannot be read (leave it and report).
- Behaviour: SIGTERM, grace, SIGKILL on a verified group or pid only. Ship report-only first, then auto-stop Tier 1 with a log line and lifecycle trace event, and a config switch off/report/stop. Tier 2 is shown, never auto-stopped. Asking first for everything would go unanswered. Claude and Codex share start_process, Proc and AssistantManagedProviderProcess, and tests must exercise both fakes.

**Evidence**

- `rust/relay-orchestrator/src/worker.rs:453-497, 553-586, 1412` - Worker and reviewer providers (Claude and Codex) start through start_process: Command::new with no process_group, setsid or pre_exec. signal() is libc::kill(child.id()); terminate is SIGTERM then SIGKILL on that one pid. Descendants (tests, servers, daemons) are never signalled.
- `rust/relay-orchestrator/src/execution.rs:1522-1530; daemon.rs:926-931; worker.rs:1069-1099` - Shutdown and cancel call the same direct-pid kill. At run end the worker only reaps the provider. for_each_line reads until the stdout pipe closes, so a grandchild holding the pipe could keep the run Running after the provider exits (inferred, not reproduced).
- `rust/relay-store/src/runs.rs:105-114, 457-497; rust/relay-orchestrator/src/daemon.rs:824-855` - The ledger keeps one pid per run (the provider). process_is_alive is kill(pid,0) with no identity check. Startup reconcile marks runs Stalled and SIGTERMs a spike's recorded pid with no start-time check (runs.rs:472-477), so a reused pid could be hit. No startup step looks for processes outside the ledger.
- `tests/contract/orchestrator_contract_support.py:231-255, 318-353, 370-388` - RR-485 mechanism: Sandbox runs [python, <workspace>/services/orchestrator.py, --config <mkdtemp>/config.toml] with start_new_session=True, cwd = tmp root, env built from scratch. Cleanup is addCleanup(self.stop) and killpg in the test process, so a killed test run leaves the daemon. No getppid watchdog exists in orchestrator.py or the Rust daemon.
- `rust/relay-services/src/general_work.rs:984-1060, 1116-1124; notes/metadata.rs:275,331` - In-tree precedents: the General worker uses setsid, records pid plus `ps lstart` identity and kills with killpg SIGTERM then SIGKILL. Note-metadata workers use process_group(0) and killpg. The orchestrator's own worker path does neither.
- `Sources/relay-runner/Process/AssistantManagedProviderProcess.swift:6-35; App/AppState.swift:2874-2893, 2918-2921, 2954-2969` - Start Session already reconciles bindings, stops previous providers of non-live contexts only when pid, lstart, uid and pgid match (stale or unknown identity is not signalled), and calls killBridge() when no session is live. It is provider-neutral, so Claude and Codex are treated alike. Embedded PTY ends via session.end().
- `Sources/relay-runner/Process/ProcessManager.swift:901, 913, 940, 960-969, 983-1020` - Voice bridge: killBridge sends shutdown, then SIGTERM to the pid in /tmp/voice_bridge.pid after a command-line check (RR-403), then removes fifos, sockets and pid files. Watchdog recovery relaunches via launchctl submit or a nohup fallback and kills stray bridges by pattern for this uid. It is detached by design and outlives the app.
- `rust/relay-rs/src/messenger/claude.rs:327-339; codex.rs:430-439; relay-services/src/providers/process.rs:52-95; catalog.rs:247-255; subscription.rs:307-329` - Claude and Codex messengers, the Codex app-server catalog probe and the Claude subscription probe run as piped children. Drop and shutdown kill the direct child only, with no group. They leak only if the bridge is SIGKILLed; the children then see stdin EOF (assumed, untested).
- `rust/relay-rs/src/bridge/speech_client.rs:595-609, 767-781; rust/relay-speech/src/main.rs:181-241; service.rs:843-844` - The speech service is spawned by the bridge, which removes a stale socket first and stops it with SIGTERM or kill. The service exits by itself when getppid() changes, the only parent-death watchdog found in the repo.
- `Sources/relay-orchestrator-mcp/Server.swift:57-78; Sources/relay-runner/Onboarding/ParentOnboardingTracker.swift:6` - MCP servers (orchestrator, actions, vision, desktop, app) are stdio children the provider spawns per session. They loop on stdin and exit on EOF, so they follow the provider. Relay never starts them directly; leak risk is low.
- `rust/relay-orchestrator/src/execution.rs:75-113, 431, 506-507, 990-992, 1210-1211, 1496-1510; worker.rs:1159-1169` - Worktree and relay/<id> branch are removed on merge, review retry, cancel with prune, close-out and for spikes. Failed, Stalled, MergeConflict and integration-blocked runs keep theirs deliberately (worker.rs:1163-1167) and nothing garbage-collects them. Workspace paths are per ticket and reused on redispatch.
- `VoiceSessionSpool.swift:21,113-116; EmbeddedSessionRegistry.swift:98-113; scripts/relay-orchestrator:69,355-360,540-550` - Other leftovers: /tmp/relay-sessions/<key> is removed per session and on quit, but no sweep of the root, so a crash leaves dirs. The port file is removed only on uninstall. The launcher's DAEMON_PROCESS_PATTERN matches services/orchestrator[.]py, so test daemons look like the real daemon. The launcher exec()s the daemon, so it can't supervise anything.

**Uncertainties**

- No ps output or run log for the RR-485 incident was available. The mechanism is inferred from the harness and orchestrator code and the ticket text, not observed.
- There was no shell, so ps, lsof and launchctl were not run. Whether macOS lets the daemon read another same-uid process's argv and env (KERN_PROCARGS2) and whether lstart is stable enough as identity are untested.
- Unknown whether the Claude and Codex CLIs run tool commands in their own process group or session. If they do, a worker-group killpg misses those, and setsid on the provider might change CLI behaviour. This needs an experiment.
- Local Git history was not available (no Git tool). I cannot say why the worker path never used process groups, or whether the RR-485 worktree still existed when the daemons were found.
- The Python worker Popen (services/orchestrator.py:4755-4763) was only partly read and is being removed by RR-487. general.rs:419-461 and continuity/agent.rs spawns were not read in detail. I assumed the same no-group pattern.
- Whether Failed or Stalled worktrees should be kept indefinitely is a product decision. I found no retention policy in code or docs.
- The pipe-hold hazard (a grandchild keeping the run Running by holding stdout) and the claim that messenger children exit after the bridge is SIGKILLed are read from code, not reproduced.
- The exact set of run states that veto a sweep (ACTIVE_STATES and review states) was not enumerated; implement it from the store constants.
- Spike workflow: the result schema caps each list at 12 items and about 600 characters, so per-process file:line evidence had to be grouped. Run 378 failed on those limits. Nothing else misbehaved.

**Recommended next steps**

- Small experiment first: on macOS check (a) whether Claude and Codex keep tool subprocesses in the provider's group, (b) reading same-uid argv/env via KERN_PROCARGS2, (c) lstart stability. Output: go/no-go for setsid and an env tag.
- Ticket: give worker and reviewer providers their own process group (worker.rs start_process); signal and terminate use killpg; killpg survivors as soon as the provider exits, before waiting for pipe EOF. Tests use fake claude and codex providers that leave a background child.
- Ticket: record pgid and lstart identity with the pid in the runs table at spawn. Use it in process_is_alive and run_abandoned, fix the unverified SIGTERM in reconcile_on_startup (runs.rs:472-477), and killpg verified workers of a previous daemon at startup.
- Ticket: tag worker env with RELAY_RUN_ID and RELAY_WORKSPACE via the start_process overrides (worker.rs:569-571), as the sweep key for escapees that inherit env.
- Ticket: report-only leftover scanner in the daemon, exposed at GET /v1/maintenance/leftovers, with Tier 1 and Tier 2 reasons. Unit tests on synthetic process tables: rr-48 vs rr-485 prefix, reused workspace, TTY process, unreadable argv, live-run veto.
- Ticket: auto-stop Tier 1 at daemon start (after reconcile_on_startup) and every ~15 minutes. SIGTERM, grace, SIGKILL on verified targets; log and lifecycle trace event; config switch off, report or stop.
- Ticket: the app calls the daemon sweep at Start Session (AppState.swift ~2918), non-blocking, and shows a one-line summary. At app launch, remove /tmp/relay-sessions/<key> dirs with no live session in the registry.
- Ticket: make the contract Sandbox self-reaping: record its pgid in a temp registry, reap stale entries on the next harness start, sweep old relay-orch-contract-* tmp roots, and consider a parent-liveness exit for the test daemon.
- Ticket: launcher fixes: narrow DAEMON_PROCESS_PATTERN (scripts/relay-orchestrator:69) to the launchd job's pid so status ignores test daemons; remove the stale port file on clean daemon exit.
- Ticket (needs decision): worktree and relay/<id> branch GC for Failed, Stalled and Canceled runs older than N days using remove_worktree and delete_branch, report-only by default.
- Open decisions for the user: (a) default of report-only vs auto-stop; (b) whether Tier 2 path-only matches may ever auto-stop; (c) retention days for failed worktrees; (d) accept setsid on providers if the experiment shows CLI side effects; (e) how to notify the user of stops.
