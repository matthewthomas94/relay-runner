## Description

Relay Runner can leave processes running after the work that started them has ended, and nothing removes them. The user wants a clean-up step that runs when a session starts (or while it starts up) and deals with anything still running that should not be.

The case that prompted this, found on 15 November 2026: four Python daemons were still running days after their worker finished. Each was `python .../orchestrator/workspaces/relay-runner-bd315711-rr-485/services/orchestrator.py --config /private/var/folders/...` — a test daemon started from the RR-485 worker's workspace with a temporary config. Three dated from 11 November and one from 13 November. They were killed by hand. They were not the real daemon, which the LaunchAgent runs (now the Rust `relay-orchestrator` binary since RR-500).

This is a read-only spike. Work out what a safe, automatic clean-up should cover and how it should decide what is safe to stop. Do not implement it.

Questions to answer:

1. **Inventory.** Which kinds of process does Relay Runner start, directly or through workers, reviewers, spikes and tests? Cover at least: orchestrator daemons (Rust and Python), the voice bridge, messenger and provider CLI processes (Claude and Codex), MCP servers, worker and reviewer provider processes, test daemons and servers that workers start in their workspaces, and build or dev-server processes. For each, say what starts it, what is meant to stop it, and how it can outlive its owner.
2. **Other leftovers.** Besides processes, what else is left behind that the same step should consider: worker worktrees and `relay/<id>` branches for finished runs, temporary config and socket files, per-session spool directories under `/tmp/relay-sessions`, stale lock or pid files?
3. **Identification.** How can a leftover be told apart from something still in use, without false positives? Consider the run ledger (a process whose run is terminal), the process's working directory or command line pointing into a workspace of a finished run, parent process and process group, start time, and listening ports. State which signals are reliable and which are not.
4. **Where it runs.** Compare running the clean-up at app launch, at Start Session, when a run ends (the daemon stopping its own worker's process group), and periodically. Recommend one or a combination, and say which component should own it (the app, the daemon, or the `scripts/relay-orchestrator` launcher).
5. **Prevention.** Can the leak be stopped at the source, for example by running each worker in its own process group or session and killing the group when the run ends? Say how that compares with cleaning up afterwards.
6. **Safety.** What must never be killed (the live daemon, the active session's provider and bridge, a running worker, anything the user started themselves)? Should the step act silently, report what it stopped, or ask first? Both Claude and Codex paths must be covered equally.

## Acceptance criteria

- The report lists every kind of Relay-started process and leftover found, each with file and line evidence for where it is started and where, if anywhere, it is stopped.
- The report explains, with evidence from the code, how the RR-485 test daemons could outlive their run.
- The report gives a rule for identifying leftovers and names the cases where that rule would be wrong.
- The report recommends when the clean-up runs and which component owns it, with the alternatives considered and why they were rejected.
- The report states whether prevention at the source is feasible and what it would not cover.
- The report ends with a short list of proposed implementation tickets, each small enough to hand to a worker, with any open decisions for the user called out.
