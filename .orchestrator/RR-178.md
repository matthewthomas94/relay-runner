## Description

Replace the RR-177 borderless onboarding panel with an onboarding mode embedded directly in Relay Runner's existing Settings tab. The supplied screenshot is the failure reference:

- `/var/folders/xs/qtmf4y_s3_l3dd6b_2mxjj4c0000gn/T/TemporaryItems/NSIRD_screencaptureui_pjcgqZ/Screenshot 2026-07-20 at 6.24.22 am.png`

The screenshot shows `OnboardingNotchSurfaceController` presenting the Coding Agent step as a separate floating panel over the Workspace Settings tab. Removing the old title bar was not sufficient: Relay Runner still owns two independently managed windows. Delete that product behavior rather than restyling or repositioning the panel.

The walkthrough must become a transient detail mode of the existing Settings surface. Keep the Workspace navigation strip and Settings sidebar visible. While setup is active, render the current walkthrough step inside the same Settings detail plane that ordinarily renders Status, using its available width and scrolling behavior. The Settings header, separators, content padding, footer/action placement, typography, colors, focus/hover behavior, corner treatment, and accessibility conventions are the visual authority. Reuse shared Settings components (`SettingsStack`, `SettingsSection`, `SettingsRow`, `SettingsActionButton`, `SettingsDivider`, Settings typography and surface colors) rather than reproducing the current onboarding card/window chrome inside the detail pane.

Fresh automatic onboarding keeps the existing Workspace pull-down/typewriter introduction. At handoff, open the Workspace on the Settings tab and enter embedded walkthrough mode at the resolved initial step. Simplified/resumed onboarding and missing-permission recovery must use the same route. `Re-run Setup Walkthrough…` from Status must replace the Status detail in place; it must not open, activate, or require dismissal of another window. Finishing, skipping, or cancelling the walkthrough clears embedded mode and returns the same host to the normal Status detail. If setup is invoked from the standalone macOS Settings scene, it must render inline in that existing Settings scene or route the user to Workspace Settings without leaving a second onboarding window behind.

Refactor `OnboardingController` away from ownership of `OnboardingSurfaceControlling`, `OnboardingNotchSurfaceController`, `OnboardingNotchPanel`, separate activation-policy changes, and independent key-window/close lifecycle. Use an observable presentation state or a small injected Settings/Workspace presenter so `AppState`, `ProgramBoardOverlayController`, and `WorkspaceSettingsPanel` can open Settings and host one `OnboardingView` instance. Preserve controller testability and all first-run sentinel/resume behavior. Do not create a hidden or transparent onboarding `NSPanel` as an implementation shortcut.

Adapt `OnboardingView` for the embedded host. Remove fixed 520×620 outer-window assumptions and duplicate background/card/footer chrome. Each step must fit the Settings detail maximum width, scroll naturally, and use the shared Settings hierarchy. The step title/progress should integrate with the Settings detail header; primary and secondary actions should integrate with the Settings footer/action style. Avoid nested modal-looking cards like the failure screenshot.

During a native microphone prompt or Settings-backed Accessibility/Input Monitoring/Screen Recording flow, keep the existing compact notch status and RR-177 permission companion behavior. The embedded walkthrough may temporarily present its waiting state or yield focus while macOS surfaces are active, but it must never create another Relay Runner window. When a request ends without a grant, recover into the same embedded Settings walkthrough with retry/skip/settings controls. Preserve the native drag payload, companion tile, cursor animation, permission polling, and teardown behavior from RR-177.

There are six unrelated, pre-existing unstaged Settings styling edits in the source worktree. Do not discard, rewrite, stage, or commit those source-worktree edits from the worker. Build this ticket in its isolated branch against committed code, reuse public Settings components rather than depending on the unstaged identifier rename, and let the foreground orchestrator verify the merged change together with those edits afterward.
