## Description

The board's "In progress" column ([Ticket.swift:27](Sources/relay-runner/Board/Ticket.swift:27) — `case inProgress = "in_progress"`) exists structurally but is permanently empty in practice. The board reads ticket-file frontmatter to decide column placement, and that frontmatter only changes at well-defined human / worker checkpoints (`backlog → ready` by human, `ready → done` by worker on commit). The orchestrator daemon, meanwhile, knows the live run state (`Claimed`, `Running`, `Succeeded`, `Failed`, `Stalled`, `Canceled` — see `mcp__relay-orchestrator__list_runs`), but never surfaces it to the board. Net effect: a ticket sits in "Ready" the whole time a worker is grinding on it, and only appears in "Done" once the human merges the worker's branch.

Bridge the gap. The daemon should publish ephemeral run state to a runs-index file, the board should overlay that state on top of the ticket files, and tickets should visibly move into "In progress" the moment a worker is dispatched. Status pills should distinguish `Running` vs. `Stalled` vs. `Failed` vs. `Succeeded — awaiting merge`. The ticket files themselves remain untouched by this ticket — they stay the source of truth for "stable" state and stay human-editable without write contention.

## Acceptance criteria

- **Daemon writes a runs-index file** at a stable path under the existing daemon-owned tree (e.g. `~/Library/Application Support/relay-runner/orchestrator/runs.json`). One entry per active or recently-completed run. Each entry includes at minimum: `ticket_id`, `repo_path`, `run_id`, `state` (matching the existing enum), `started_at`, `ended_at` (nullable), `last_error` (nullable), `workspace_path`, `branch`.
- The file is updated **synchronously on every state transition** (Claimed, Running, Succeeded, Failed, Stalled, Canceled). No polling lag — when the daemon updates internal state, the file is rewritten in the same code path.
- Completed entries (Succeeded / Failed / Canceled) stay in the file for at least 5 minutes after `ended_at`, then are pruned by the daemon. This window covers the typical merge gap so the board can surface "Succeeded — awaiting merge" pills without flicker.
- **Board reads the runs file** alongside the ticket files when it refreshes. For each ticket whose `id` matches an active or recently-completed run, the board:
  - Visually places the ticket in the "In progress" column if `state` is `Claimed`, `Running`, or `Stalled` — *overriding* the ticket file's `status:` for placement purposes.
  - Visually places the ticket in the "Done" column if `state` is `Succeeded` AND the ticket file still says `ready` (i.e. the worker finished but the human hasn't merged yet) — with a distinct pill (e.g. "Awaiting merge").
  - Renders a small status pill on the card itself reflecting `state` (`Running`, `Stalled`, `Failed`, `Awaiting merge`, etc.). Use distinct colors so `Failed` and `Stalled` read at a glance.
- Board picks up runs-file changes within ~1s (file-system watcher preferred over polling; if polling, ≤1s interval).
- When a runs-file entry is removed (post-prune) and no active run exists for a ticket, the board falls back to rendering position from the ticket file's `status:` only.
- The currently-dispatched run (`RR-9`, run #1) should be visible in "In progress" with a `Running` pill the moment this change ships, assuming the run is still active. (If the reviewer runs this test against a fresh dispatch instead, that's fine.)
- No regression in drag-to-promote behavior. Dragging a ticket from `ready` to `inProgress` manually should still work — the daemon's override only applies *additionally*, never blocks human edits.
- Manual verification: dispatch a ticket, watch the board — ticket moves to "In progress" within ~1s, pill reads `Running`. Worker finishes, ticket moves to "Done" with `Awaiting merge` pill. Merge the branch into main → ticket file's status updates to `done` → pill disappears (entry pruned eventually, or immediately if you can detect the merge).
- Don't touch the bundled `.app`'s scripts — DMG-build action is the source of truth.
- Commit message references RR-11.

## Notes

- Daemon code lives in `services/orchestrator.py`. The existing run-state machine is the source of truth for transitions — wire the file-write off the same transition function so they can't drift.
- Board controller lives in `Sources/relay-runner/Board/`. The likely insertion point is wherever `BoardOverlayController` currently scans the `.orchestrator/` directory (probably `OrchestratorClient.swift`) — extend it to also read the runs file and merge the two views.
- This ticket is foundational for RR-12 (live activity chip). RR-12 extends the runs-index entry shape with an `activity` field and a render path on the board card.
- `mcp__relay-orchestrator__list_runs` already returns essentially the data we need — that MCP tool can stay the network-API view, while the runs-index file is the local-filesystem view consumed by the board. Don't replace one with the other.
