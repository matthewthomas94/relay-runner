## Description

Create a self-contained HTML architecture diagram at `docs/relay-runner-architecture.html` that explains how Relay Runner works end to end. It should serve as a concise developer and product onboarding artifact: visually clear enough to understand at a glance, with short supporting explanations for the important authority and lifecycle boundaries.

Ground the diagram in the current repository rather than an idealized design. Show the user/app entry points, app-owned voice bridge, concurrent delivery to the persistent tool-free messenger and authoritative foreground orchestrator/PM, command classification, Relay Actions and Relay Vision tool paths with ActionGlow feedback, local `.orchestrator/` board state, daemon dispatch into isolated worker worktrees, review/merge publication, dependency progression, and the return path for public traces and the authoritative final reply. Make newest-intent seq/id checks and the rule that raw voice captures do not become visible ticket prose understandable without overwhelming the main flow.

Use one coherent visual system with labeled arrows, a legend, and clear role boundaries. Prefer a strong static diagram with lightweight progressive enhancement over a framework or build step. The page must work when opened directly from the repository without network access or external assets. Include concise links or references to the relevant in-repo source and documentation files so readers can go deeper.

## Acceptance criteria

- [ ] `docs/relay-runner-architecture.html` opens directly via `file://` and has no CDN, font, image, framework, or other network dependency.
- [ ] The primary diagram distinguishes the user/app shell, voice bridge, tool-free messenger, authoritative orchestrator/PM, local board/daemon, implementation worker, and review/merge worker, with labeled direction of control and public response flow.
- [ ] The diagram accurately shows a voice turn reaching the messenger and foreground orchestrator concurrently while preserving the foreground orchestrator as the authority for actions, tickets, dispatch, and final outcomes.
- [ ] Direct-action flow covers Relay Actions for manipulation, Relay Vision for observation, and automatic ActionGlow feedback without presenting the messenger as tool-capable.
- [ ] Ticket flow covers refined `.orchestrator/` files, `backlog -> ready -> in_progress -> done`, ready-triggered dispatch, isolated `relay/<id>` worktrees, follow-up review/merge, and dependency auto-progression.
- [ ] Newest-intent seq/id preemption and the separation between private raw voice metadata and user-safe visible ticket prose are represented clearly.
- [ ] Codex and Claude are presented with equivalent supported foreground and worker roles; any intentional provider-specific transport details are labeled as implementation differences, not architectural authority differences.
- [ ] The page is legible at common desktop and narrow/mobile widths, uses semantic HTML, maintains useful contrast, does not rely on color alone, and respects reduced-motion preferences for any animation.
- [ ] A compact legend and in-repo source map link to the most relevant current files, including `AGENTS.md`, `docs/orchestrator.md`, `services/voice_bridge.py`, `services/messenger.py`, `services/orchestrator.py`, and the Relay Actions/Vision specs.
- [ ] Visual browser checks at desktop and narrow widths show no clipping, overlapping labels, broken links, or console errors; `git diff --check` passes.
