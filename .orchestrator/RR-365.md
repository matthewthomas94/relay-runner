## Description

Add a continuous local meeting transcription path inside the existing macOS app, reusing suitable FluidAudio/Parakeet components while separating its destination and lifecycle from STTEngine voice commands. The recorder produces document content and runs without starting Codex, Claude, the voice bridge, the messenger or a title/summary model.

Retain microphone plus computer/meeting audio in the implementation scope. Establish a documented source matrix against Relay Runner's current supported OS/hardware and select the smallest capture implementation supported by the evidence in RR-359. Do not silently ship a mic-only interpretation, raise the app OS floor, or promise every device combination. Resolve ordinary API/engine choices in implementation; report a concrete limitation or necessary product tradeoff if the supported baseline cannot meet the scope.

Use ordered segment identities and audio time ranges to reconcile changing partial hypotheses and final text. The current TranscriptAccumulator removes text found anywhere in earlier text; that behavior alone is not proof of meeting fidelity. Genuine repetitions and a later repeated sentence must survive. Use local STT readiness/error handling and existing model terms; no new foundation-model, title-generation or summary prerequisite.

Foreground work sessions and note-taking are mutually exclusive. Start Note Taker ends the existing foreground work session through its established End Session lifecycle, waits for bridge/audio/TTS/UI ownership to be released, and then begins local note capture. Start Session from either recording or paused note mode stops capture, drains the accepted final tail and durably saves the same note to its original project before launching the requested work session. These explicit start actions authorize the switch without a second confirmation. A save or teardown failure blocks the destination mode and preserves recovery state; remote sync alone does not block a locally saved switch. Unrelated daemon worker runs are unaffected.

One authoritative transition owner serializes mode changes and rejects stale callbacks. Snapshot the destination project when the start action is accepted while retaining the source note's original project. Repeat clicks, project changes, start failures and delayed teardown must never leave both foreground modes active or misfile a note.

Within note mode, actual Caps Lock ON pauses capture and OFF resumes the same note. Paused speech from every source is excluded from both retained audio and later transcription; preserve already accepted content and the pre-pause tail. Pause does not finalize, allocate a new ID or launch an agent. Read the actual key state at startup, so Caps Lock already ON starts paused before accepting audio. Route the key exclusively to the active mode; paused notes still own note mode. Synchronize rapid/repeated changes and restore ordinary work-mode key behavior after teardown.

## Run log

- **Run 136** — retry requested: Review requested retry: RR-365 needs follow-up before merge. The checkpoint/replay path is not lossless or idempotent: a later successful final window removes every pending descriptor through its end, including audio from an earlier failed transcription; replay ignores nextWindowSequenceByEpoch, clears buffered samples when the epoch changes, and starts from a retained chunk's raw start, so boundary-crossing chunks can re-emit committed audio and pending audio from earlier epochs can be lost. Add regression tests for failed-window-then-success, a checkpoint with a chunk crossing an owned-window boundary, and multiple pending epochs. Also establish a shared monotonic/PTS-based note timeline for microphone and system audio; current per-source accepted-sample counters timestamp a delayed system-audio start at 0 and cannot correctly align simultaneous local/remote speech.
- **Run 138** — retry requested: Review requested retry: Review found a blocking capture-ingress and teardown gap. MeetingNoteCaptureSession creates an untracked Task for every audio frame, so a slow accepted-audio sink can build an unbounded task/mailbox backlog, and pause/stop has no barrier to drain frames already emitted by an adapter before the producer changes state. Also, handle(.failed) removes a source from activeSources while stopSources stops only active sources, so a running ScreenCaptureKit stream that reports an unsupported format can be skipped during teardown. Use a bounded, tracked ingress/drain path, always stop every started adapter, and add regressions for burst input with a slow sink, pre-boundary tail draining, and post-start capture failure teardown.
