## Description

Add an opt-in, developer-only diagnostic channel that lets a separate local
observer agent monitor the Codex or Claude CLI hosted inside Relay Runner's
embedded SwiftTerm.

The current installed app starts the embedded provider as a child process, but
Relay Runner's stdout and stderr are `/dev/null`, the provider's stdout exists
only on the SwiftTerm PTY, and the provider's stderr is `/dev/null`. Once text
scrolls away there is no app-owned, session-scoped record that another local
Codex session can reliably discover or correlate.

When a private developer marker exists under Relay Runner's Application
Support directory, each new embedded session should publish:

1. A stable, atomically updated JSON manifest containing a schema version,
   provider, child PID, working directory, start time, lifecycle state, and
   the absolute path to the current terminal transcript.
2. A bounded transcript containing the bytes received from the child PTY and
   rendered into SwiftTerm.

Keep this facility internal. Do not add a settings control, onboarding copy,
menu item, notification, or other user-facing surface. Logging must be disabled
when the marker is absent. Store diagnostics in a private directory, use
owner-only file permissions, rotate or truncate transcripts to a documented
small bound, and make every logging failure non-fatal to the terminal session.

Do not separately record keyboard input, voice injection payloads, process
arguments, developer instructions, environment values, or configuration
secrets. The PTY transcript can inherently contain content that the provider
renders or echoes, so its private permissions and bounded retention are part
of the feature contract.

The separate personal `relay-runner-monitor` skill will own process discovery,
provider-native trace correlation, Relay Vision checks, log following, and
issue summaries. It must work for any capable local observer agent rather than
assuming the observer is Codex Desktop. Do not ship that skill or add product
UI for it in this ticket.

## Acceptance criteria

- [ ] With the developer marker absent, starting and using an embedded Codex
      or Claude session creates no new diagnostic manifest or transcript.
- [ ] With the marker present, a new embedded session creates a deterministic
      current-session manifest with schema version, provider, child PID,
      working directory, start timestamp, running state, and an absolute
      transcript path.
- [ ] Bytes received from the PTY are appended to the current transcript
      without delaying or changing the bytes fed to SwiftTerm.
- [ ] Exit and explicit termination paths update the manifest lifecycle state
      and exit information where available.
- [ ] The diagnostics directory and files are owner-only, transcript storage
      is bounded with deterministic rotation/truncation, and a logging or
      permissions failure never prevents the embedded provider from starting,
      rendering output, accepting input, or terminating.
- [ ] Direct terminal input, voice delivery payloads, launch arguments,
      developer instructions, environment values, and config contents are not
      independently written to diagnostics.
- [ ] The implementation adds no user-facing settings, onboarding, menu, or
      notification surface.
- [ ] Focused tests cover disabled/enabled behavior, manifest contents,
      transcript writes and retention, lifecycle updates, non-fatal I/O
      failures, and both Codex and Claude labels.
- [ ] The full `swift test` suite passes.
