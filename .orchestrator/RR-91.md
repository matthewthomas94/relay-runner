## Description

The permission onboarding diagram currently uses generic placeholders such as App 1, App 2, and App 3 to explain which apps need to appear in the macOS privacy permission window. That makes the instruction less concrete than it needs to be.

Replace the placeholders with the actual app targets required for the current setup path. For example, if Codex and Terminal need a permission grant, the diagram should preview Codex and Terminal by name/icon and show the permission switches in the on state. Claude setup should do the equivalent for Claude and Terminal, and any detected additional parent apps should be represented without falling back to generic labels.

Provider parity matters. Codex and Claude should see equivalent goal-state previews, with provider-specific app names/icons coming from the existing permission target model rather than separate hardcoded flows.

## Acceptance criteria

- [ ] The permission onboarding diagram is generated from the current required permission target list instead of generic App 1/App 2/App 3 placeholders.
- [ ] Codex setup previews Codex and Terminal when those are the required targets; Claude setup previews Claude and Terminal when those are the required targets.
- [ ] The diagram shows the destination permission switches in the on/enabled goal state for the displayed apps.
- [ ] One, two, three, and more-than-three app target sets render without label overlap, clipping, or layout jumps.
- [ ] Missing app icons use a readable fallback that still names the actual app instead of reverting to generic placeholder labels.
- [ ] Provider parity is explicit in tests or verification notes for Codex and Claude permission onboarding.
