## Description

Fix a live installed-app regression where one interrupted Relay Runner response is retained for replay, reappears under the generic `Double tap Option to play` presentation, and is then experienced as the same Relay message being sent twice. Preserve the useful RR-279 behavior that stopping an active playback attempt does not destroy an otherwise eligible replay target, but stop presenting that retained history as a newly delivered response.

The issue was reproduced on installed Relay Runner 0.4.45 (build 49) in a Codex session. The RR-301 completion shown in the response pill was authored once, accepted once, and queued once as one `authoritative_final_direct` utterance. One bridge and one speech coordinator were live, and the fast-messenger handoff for the command was interrupted before playback. The first physical Option gesture started the authoritative final at 21:57:43 AEST. Playback stopped before terminal `played` at 21:57:58, after which the coordinator deliberately retained the stopped utterance and the overlay returned it to `messageWaiting`. A later physical Option gesture at 22:06:31 created a new `replacement_policy: replay` intent linked to the original utterance and started the same response again. The speech journal therefore proves a replay, not a second provider final or duplicate bridge delivery, while also reproducing the user-visible false-duplicate experience.

The current behavior spans `SpeechCoordinator.stop_playback`, stopped-attempt retention in `_observe_worker`, `TTSWorker.publish_replay_retained`, and the Swift `StateMachine` transition from `replay_retained` through `.cancelled(.tts)` back to `.messageWaiting`. The UI does not carry or render the distinction between a newly delivered response, an interrupted response retained in history, and an explicit replay attempt. It also does not record why the first attempt stopped, so a deliberate Control stop, recording barge-in, newer command, and actual message cancellation cannot be evaluated independently in the reproduction evidence.

Implement one authoritative delivery-versus-replay presentation contract. A newly accepted response may enter the normal message-waiting state once. Stopping its audio may retain it for a later explicit replay without publishing it again as new delivery. If replay remains available, label and present it unmistakably as replay of the previous response, and ensure a newer user turn does not make stale retained text reappear over current work. Keep the coordinator as the source of truth; do not add an overlay-only replay cache, disable Option replay, discard every stopped message, or weaken current-command freshness.

## Acceptance criteria

- [x] A deterministic regression reproduces the verified sequence: one current authoritative final is proposed, accepted, and queued once; first Option playback starts; playback stops before `played`; the target remains eligible; and a later Option gesture creates a linked replay. The pre-fix assertion demonstrates that the retained response is presented like a newly delivered message.
- [x] Delivery identity and replay identity are explicit across the speech coordinator, TTS state event, and Swift state machine. One original response can produce multiple playback attempts without any replay attempt being counted or rendered as a second original delivery.
- [x] A newly accepted response enters the ordinary `messageWaiting` presentation at most once. Repeated identical preview datagrams, preparing/speaking transitions, stopped-attempt callbacks, and retained-history updates are idempotent and cannot restart the fresh-message entrance or reset the body as though new content arrived.
- [x] Stopping playback retains the eligible target required by RR-279, but the overlay does not return it to the generic `Double tap Option to play` state as a fresh Relay response. Any visible retained affordance says that it will replay the previous response and does not use new-delivery language or animation.
- [x] The stop reason is recorded and applied explicitly. A deliberate playback stop may retain a replay target; a recording or newer-turn barge-in must not resurface stale text over the new turn; actual cancellation, revocation, replacement, or supersession must continue to invalidate the target.
- [x] With a current pending response, the first valid Option gesture starts that response once. With no pending response and one eligible retained target, an explicit replay gesture starts one linked replay from the beginning. Duplicate gestures cannot create overlapping replay attempts or more than one managed audio process.
- [x] Replay lifecycle evidence includes the original utterance identity, the replay utterance identity, `replay_of`, stop reason, presentation mode, and terminal state. A stopped initial attempt is not reported as `played`, and a successful later replay reaches `started` and `played` exactly once.
- [x] A new current Relay command or response supersedes the retained replay presentation immediately. Stale, unscoped, privacy-ineligible, failed, canceled, non-replayable, or provider-session-mismatched speech cannot reappear or replay.
- [x] Existing RR-274 and RR-279 guarantees remain intact: completed current speech is replayable on the first valid Option gesture; mid-message stop does not destroy an eligible target; replay begins from the start; Queue and Auto modes retain correct ownership; and one Control gesture stops the active attempt without automatic audio restart.
- [x] The contract is provider-neutral. Equivalent authenticated Codex and Claude finals produce the same original-delivery, stop, retained-replay, and explicit-replay behavior despite provider-specific completion signals.
- [x] Privacy-safe diagnostics record command and utterance identities, playback attempt, replay relationship, stop reason, presentation transition, and decision without response text, prompts, transcripts, repo content, or secrets.
- [x] Focused Python tests cover original delivery, duplicate preview publication, initial-play stop, explicit replay, replay stop, repeated Option gestures, stop reasons, Queue/Auto modes, freshness, supersession, and exact-once process cleanup. Focused Swift tests cover idempotent same-preview handling, distinct replay copy/state, canceled-to-retained transitions, newer-turn replacement, and Option/Control ordering.
- [ ] A fresh installed build passes a mounted physical-gesture smoke in foreground and background: receive one response, play it, stop it mid-message, verify it is not presented as a second new reply, explicitly replay it once, and observe `started` then terminal `played`. Exercise both Codex and Claude or record the exact environment blocker without claiming unperformed parity.
