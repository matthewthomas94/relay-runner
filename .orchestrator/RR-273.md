## Description

Implement the target architecture selected by the completed RR-270 spike and documented in `docs/investigations/RR-270-repo-local-retention-and-scope.md`. That report is the design authority for topology, invariants, state machines, privacy boundaries, migration, and verification. This ticket translates the recommendation into a durable delivery item; it does not reopen the architecture decision.

Relay Runner should open Workspace from an automatically managed app-global home at `~/Library/Application Support/relay-runner/`, without asking the user to choose or reopen a Workspace folder. That home owns the logical project registry, persistent access-grant references, run and orchestration databases, Graphify and search projections, caches, locks, migration journals, and ephemeral worker worktrees. It must never become a parent directory for registered projects or a second canonical writable ticket store. Filesystem browsing belongs only to Add/Create project flows.

Each registered project's durable Relay artifacts remain owned by that Git repository. The canonical writable store is the Relay-owned `refs/heads/relay/artifacts` ref, synchronized only to an explicitly selected existing remote. The repo-root `.orchestrator/` directory is a bounded, write-through materialization of that ref, not an independent authority or a normal source-branch payload. A single project artifact writer must use typed, allowlisted operations, a private Git index, immutable event IDs, and compare-and-swap ref updates without changing the user's source branch, index, staged files, dirty files, remotes, or ordinary unpushed commits.

Delivery must be phased rather than attempted in one worker run. Before any implementation phase is promoted to `ready`, split or refine it into a cold-start child ticket with its own bounded acceptance criteria, dependency metadata, worker sizing, rollback boundary, and verification plan. Preserve compatibility behind per-project opt-in until migration and installed-product release gates pass.

## Delivery phases

1. Stable registry and app-home ownership: add schema-versioned registry-v2 records, immutable project IDs, atomic backup/quarantine recovery, Keychain-backed persistent access grants, duplicate detection, and unavailable-project recovery without mutating repositories during registration.
2. Explicit Workspace and thread scope: replace workspace-root opening with registry-backed empty/project states, Add/Create/Remove project UI, and provider-neutral confirmed thread scopes. Cwd may suggest a project but must never confirm ownership.
3. Project artifact Git store: implement the orphan `relay/artifacts` ref, typed allowlisted writer, private-index Git plumbing, compare-and-swap updates, idempotent event IDs, attachment gates, crash recovery, and repo-root materialization.
4. Remote synchronization and conflicts: add explicit remote selection, local-only mode, exact-ref fetch, rebase of unpublished Relay-only commits, normal fast-forward push, bounded retry, conflict handling, and fail-closed local-ahead behavior. Never force-push or automatically publish ordinary source commits.
5. Thirty-day retention and restoration: add precise activity timestamps and exemptions, deterministic archive catalog updates, atomic archive/restore commits, historical discovery, archived dependency handling, recoverable deletion, and honest working-tree/Git/database/index/cache metrics.
6. Worker and reviewer lifecycle split: snapshot artifact input for workers, keep worker source commits separate from ticket lifecycle publication, and commit canonical done/dependency transitions only after review merge success. Preserve bounded run summaries, attachments, retries, raw-log policy, and snapshot leases.
7. Program and Graphify ownership migration: export project-scoped capture-only records to the artifact ref, make Graphify/search rebuildable projections, and retain only genuinely app-global cross-project data in application support.
8. Guarded migration, rollback, and fresh-install recovery: add preflight manifests, writer freeze, artifact bootstrap, optional first remote push, explicit source cleanup, materialization cutover, run/capture mapping, journaled resume, rollback, and supported reinstall validation that never deletes project repositories.
9. Installed-product verification and staged rollout: exercise two-device, offline, permissions, archive/restore, dirty-source isolation, Codex/Claude, failure-injection, fresh-install, and mounted Workspace UI scenarios; roll out per-project opt-in first, then new-project defaults, then legacy migration after evidence supports it.

## Acceptance criteria

- [ ] The RR-270 report remains the traceable design authority, and each implementation change links back to the relevant report section and delivery phase.
- [ ] The nine phases above are represented by bounded child tickets before implementation begins; dependencies enforce the ordering and parallelism documented by RR-270, and the parent ticket is not dispatched as one monolithic implementation run.
- [ ] Workspace opens directly from Relay Runner's fixed application-support home and persisted registry with no Workspace-folder picker; only Add/Create project flows browse for filesystem locations.
- [ ] Registration uses stable project identity and persistent macOS access grants, supports the recovery cases in RR-270, and Add/Remove never moves, nests, deletes, or silently rewrites a user repository.
- [ ] A confirmed project scope is required for ticket creation, dispatch, archive, restore, sync, and other project mutations; cwd and filesystem proximity are suggestions only, and Codex and Claude receive equivalent scope semantics.
- [ ] Each project's durable artifacts are canonical on `refs/heads/relay/artifacts`; the repo-root `.orchestrator/` tree is a verifiable materialization, and app-global databases or caches cannot become a divergent writable authority.
- [ ] Artifact writes use a private index, strict path allowlist, immutable event IDs, single-writer serialization, and compare-and-swap ref updates without altering the user's source branch, index, dirty worktree, remotes, or ordinary commits.
- [ ] Remote sync is explicit, local-first, offline-capable, retryable, conflict-aware, and fail-closed when safe publication cannot be proven; it never force-pushes or automatically publishes ordinary local source commits.
- [ ] The 30-day materialization, archive catalog, historical inspection, restore, delete, active-work exemptions, attachment/privacy limits, and storage accounting match RR-270's specified policies and edge cases.
- [ ] Worker dispatch, review, merge, dependencies, run summaries, attachments, retries, and archival operate against project-owned artifacts without tracking ticket lifecycle files on source worker branches.
- [ ] Project-scoped Program/Graphify captures survive loss of derived app-global indexes, while raw logs, secrets, caches, large binaries, raw audio, and sensitive transcripts remain outside Git according to the report's classification.
- [ ] Migration is journaled, resumable, previewable, and reversible; normal reinstall preserves app support, destructive reset is recoverable, and no migration or reset deletes or rewrites registered repositories without an explicit reviewed operation.
- [ ] Automated fixtures and manual recovery scenarios cover age boundaries, archive/restore, multi-device conflicts, local-ahead source commits, dirty/staged worktrees, permissions, missing remotes, provider parity, crash recovery, and rollback.
- [ ] Installed-product validation passes on a signed fresh build before default enablement, and rollout proceeds through per-project opt-in, new-project default, then evidence-gated legacy migration.
- [ ] Documentation records final data ownership, state machines, operational recovery, privacy limits, intentional Codex/Claude differences, and rejection reasons for any deviation from RR-270.
