## Description

In a healthy Relay session, a voice command recorded while the foreground provider is busy can remain pending until that turn yields. If the user toggles Caps Lock again before the pending command is claimed, Relay Runner cancels the new recording and shows `Voice command waiting`, describing the active listener as if it were unavailable. The foreground turn and bridge can both be healthy; the user is nevertheless blocked from correcting or superseding the pending instruction.

Treat this as normal busy-turn steering rather than a listener failure. Keep the existing newest-intent contract: a newly completed utterance may atomically supersede the older unclaimed command, and stale work must stop at its next checkpoint. When the provider yields, deliver the latest command exactly once. Reserve recovery/error messaging for a genuinely missing or timed-out consumer, and use a passive queued/steering status while the session is healthy.

## Acceptance criteria

- [ ] With a healthy Codex or Claude foreground turn active and one unclaimed voice command pending, Caps Lock can start and complete another recording.
- [ ] The newer completed utterance receives newer Relay metadata and atomically supersedes the older unclaimed command; the older command is never delivered later.
- [ ] Newest-intent checkpoints observe the new sequence promptly and prevent stale follow-up ticket edits, dispatches, external actions, and replies.
- [ ] A healthy busy turn does not show wording that says the active listener is missing or requires a new session.
- [ ] The UI presents pending delivery as a passive queued/steering state and makes replacement semantics understandable without blocking voice capture.
- [ ] When the provider becomes available, exactly one copy of the latest command is claimed and submitted.
- [ ] Genuine missing-consumer and delivery-timeout cases still trigger the existing bounded recovery and failure surfaces.
- [ ] Automated Swift and Python tests cover busy-turn replacement, stale suppression, exact-once delivery, timeout recovery, and Codex/Claude parity.
