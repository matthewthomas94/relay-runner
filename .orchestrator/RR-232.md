## Description

Prevent acknowledgments, status questions, and other non-superseding voice
turns from silently canceling project actions the user has already authorized.

Relay Runner currently uses one newest-intent `relay_command_seq` and
`relay_command_id` for two distinct responsibilities:

- deciding which conversational reply, trace, and TTS output is current; and
- authorizing pending ticket edits, dispatches, and other project mutations.

`services/voice_bridge.py` advances `/tmp/voice_command_state.json` for every
completed utterance in `_begin_relay_command`, before the utterance is
classified. `services/orchestrator.py` then requires an exact match to that
single latest seq/id in `_validate_relay_command`. Consequently, a brief
conversational acknowledgment arriving after the foreground PM accepts a
dispatch request but before the dispatch call reaches the daemon makes the
authorized request stale. A multi-ticket request can also stop before its
first action or partway through the batch.

Separate conversational freshness from mutation authorization, or introduce
an equivalently explicit supersession relationship. A later turn should revoke
an outstanding action only when it actually cancels, redirects, or replaces
that action. Acknowledgments, status checks, and additive conversation may
become the latest reply/TTS turn without erasing previously authorized bounded
work.

Keep the safety properties from RR-52 and RR-106: explicit interruption,
cancellation, and redirection must stop not-yet-started stale mutations at the
next checkpoint; stale replies and TTS must not speak over newer intent; and
already-completed actions must be reported honestly. Do not solve this with
only a hard-coded list of acknowledgment phrases. The command relationship and
authorization state must be explicit, testable, and provider-neutral.

## Acceptance criteria

- [ ] Model conversational freshness separately from authorization for
      pending project mutations, with a documented contract for
      acknowledgment, inspection/status, additive, replacement, redirect,
      interrupt, and cancel turns.
- [ ] A refined dispatch request followed by a non-superseding acknowledgment
      before the daemon call still starts the authorized run exactly once.
- [ ] A status question received while an authorized action is pending can be
      answered without silently canceling that action.
- [ ] A genuinely newer cancel, interrupt, redirect, or replacement revokes
      not-yet-started actions from the older command before any mutation.
- [ ] The daemon continues to reject arbitrary expired, mismatched, replayed,
      or revoked authorization; the change does not weaken stale-action safety
      into trusting any older seq/id.
- [ ] Multiple actions authorized by one turn, including a multi-ticket
      dispatch, are durably registered as one bounded plan or otherwise have
      deterministic continuation semantics. A later real supersession cannot
      produce an unexplained partial batch.
- [ ] If some actions completed before a real supersession, Relay Runner
      reports exactly which actions started and which were canceled rather
      than claiming the whole batch succeeded or failed.
- [ ] Conversational output still follows newest-turn rules: stale
      acknowledgments, traces, fallback completions, and TTS remain suppressed
      even when an older authorized project action is allowed to continue.
- [ ] Foreground instructions and daemon validation use the same semantics for
      Codex and Claude, with any unavoidable delivery difference documented.
- [ ] Automated race tests reproduce an acknowledgment arriving immediately
      before a dispatch, a status question during a pending action, a true
      redirect before mutation, and a true redirect partway through a
      multi-action request.
- [ ] Existing voice preemption, completion-hook, orchestrator dispatch,
      command lifecycle, replay/recovery, and TTS suppression suites pass.
- [ ] A live app smoke test verifies both paths: an acknowledgment no longer
      cancels an accepted dispatch, while an explicit cancellation still does.
