## Description

Switch the note-taker from live transcription to "record now, transcribe after Stop". This is the final MVP step and uses RR-404 (`MeetingCompressedAudioRecorder`) and RR-405 (the offline batch transcription path).

The goal is to keep Relay Runner as lean as possible while a note is being taken:

- no ASR model resident;
- no windowed inference;
- no partial hypotheses;
- no raw Float32 chunk files;
- no per-chunk checkpoint rewrites.

Then transcribe once after Stop, save the note, and delete the audio.

### While recording

- **Capture behaviour is unchanged.** `MeetingNoteCaptureSession` keeps owning the adapters, ingress, pause and resume, interruption, source restart and capture generations, with the same barriers.
- **Accepted audio goes to the recorder.** Each `MeetingAcceptedAudio` chunk goes to the RR-404 recorder instead of `MeetingNoteRecoveryStore.persistAudio`. The producer, or a slimmed recorder-only stage, still assigns the timeline and timing epochs. It runs no ASR, submits no windows and emits no revisions. `FluidAudioMeetingTranscriber.prepare` is not called. Producer checkpoints are written only at state boundaries (start, pause, resume, interruption, stop), not on every chunk.
- **The note is still created at start.** Creating the note stays as it is today. The 15 s canonical checkpoint loop does not run while recording, because there is no transcript to publish yet. Pause and resume still persist the journal state they need for recovery.
- **The recorder is finalized at pause and stop.**

### On Stop

1. Run the existing stop barrier, then finalize the recorder.
2. Run the RR-405 batch transcription over each source's recording.
3. While ASR runs, the coordinator shows a visible transcribing state. The notch and `AppState` label (currently "Saving notes" for `.stopping`) read **Transcribing notes**. They switch to **Saving notes** for the artifact write.
4. Publish the complete note through the existing journaled, idempotent checkpoint path with `recordingState: completed`. Segment shape and `speaker` attribution stay as today. This final save is what triggers the existing RR-377 background title and summary job (`services/note_metadata.py`), so the summary is generated once, from the full transcript.
5. Only after the completed note is saved locally (a writer `pending` sync state still counts as saved), delete the recording and the session directory.
6. The note-to-work transition keeps waiting for this whole Stop, transcription included. Background transcription is out of scope for this MVP.

### Failure and recovery

- **Keep the audio on failure.** If transcription fails (for example the model is unavailable) or the local save fails, keep the recording and journal. Show the existing interrupted or recovery presentation. Never delete audio before the completed note is saved.
- **Build relaunch offers without starting anything.** On relaunch, build offers from the journals and recordings without loading the model, opening the microphone or starting capture. Map the existing resolutions:
  - `finalize`: transcribe the retained recording, publish and delete.
  - `recoverPaused`: reopen the same note paused on its existing recording. A later explicit resume appends new epochs, and the eventual Stop transcribes everything.
  - `discardIncompleteTail`: delete the recording and complete the note with whatever canonical segments already exist, possibly none, without crashing.
- **Legacy offers.** `pendingAudioChunkCount` or its replacement reflects recorded segments. A recovery journal left by the previous version, with raw `.f32` chunks, must still finalize by feeding its chunks to the RR-405 path.
- **Remove only what this change orphans,** for example per-chunk Float32 persistence for new sessions and unused partial-hypothesis plumbing. Leave unrelated code alone.
- **Update docs.** Update `docs/specs/project-note-capture.md`, and `docs/specs/project-notes.md` if it is affected. Cover the new capture, durability and recovery contract:
  - the "zero unpersisted audio" rule is replaced by "at most one open segment, 30 s or less per source, lost on a hard crash";
  - the new budget;
  - no live partials;
  - transcription after Stop;
  - audio deletion and backup exclusion.

### Decisions taken for this MVP (override before promoting if wrong)

- AAC `.m4a` at about 32 kbps, 16 kHz mono, with one track per source (microphone and system audio kept separate for speaker attribution).
- A hard crash can lose at most about 30 s of open-segment audio per source.
- The model loads only after Stop, so a first-ever note may wait for a model download at the end.
- Audio is deleted after a successful save and kept for recovery after any failure.
- Stop blocks until transcription and saving finish.

## Acceptance criteria

- [ ] Coordinator test with fake capture and fake transcriber: during recording, `prepare` and `transcribe` are never called, no revisions are emitted, no per-chunk checkpoint or `.f32` writes happen, and the recorder receives every accepted chunk for each source.
- [ ] Stop goes through the transcribing state to `saved`. The notch and `AppState` show "Transcribing notes" while ASR runs and "Saving notes" during the write. The completed note's segments carry the same IDs, timings and speaker attribution the live path produced for the same synthetic input.
- [ ] After a successful save, the session's recording directory and journal no longer exist.
- [ ] After an injected transcription failure, or an injected local-save failure, the recording and journal remain and a recovery offer is listed.
- [ ] Recovery `finalize` transcribes the retained recording and completes the note. `recoverPaused` followed by resume and Stop yields a transcript covering audio from before and after the restart. `discardIncompleteTail` deletes the audio and completes without error.
- [ ] Building recovery offers neither prepares the model nor starts capture.
- [ ] A fixture recovery journal in the previous raw-Float32 format finalizes successfully.
- [ ] Pause, resume, interruption and source-restart tests are updated and pass. The full `swift build` and `swift test` pass. `OnboardingIntroTests` is known to flake under CPU load; if it does, rerun it in isolation before treating it as a failure.
- [ ] The specs describe the new contract, and no remaining text claims live partials or zero unpersisted audio.
- [ ] No summary is requested while recording. Until Stop, every writer call (create, plus pause and resume state updates) carries zero transcript segments, so the RR-377 job takes its empty-note path with no provider call. A coordinator test asserts the zero-segment writes. A daemon test in `tests/test_note_metadata.py` covers an empty create, then state-only checkpoints, then one completed checkpoint with transcript text. It asserts no provider call before the completed save and exactly one after it.
- [ ] No audio samples or transcript text are written to logs or diagnostics, or sent to any provider other than through the existing RR-377 summary job after the completed save.
