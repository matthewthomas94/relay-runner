## Description

The Relay Remote iPhone design has a chat per agent (Puck, Isabella, George, Sky): the user picks an agent's tab, talks or types to that agent, and hears and reads that agent's replies. Each agent tab shows a live status glyph. RR-532 added the wire fields and left stubs on the Mac. This ticket makes them real.

**Today:** a remote utterance is delivered to whichever voice target is focused on the Mac (`rust/relay-rs/src/remote/server.rs` → `RemoteItem` in `rust/relay-rs/src/bridge/remote_link.rs` → the focused target in `rust/relay-rs/src/bridge/targets.rs`). Replies sent to the phone carry no agent. `session_state` reports only which agents are running. Starting a session from the phone needs a project id (`Sources/relay-runner/Remote/RelaySessionControl.swift`).

**Wanted**

1. **Addressed delivery.** An `utterance` with `agent` set is delivered to that agent's session, whichever agent is focused on the Mac, without stealing the desktop's focus for local microphone input any longer than the delivery needs. An utterance without `agent` behaves as today. A `control` with `agent` (stop, replay, cancel) acts on that agent's speech.
2. **Tagged replies.** `accepted`, `speech`, `speech_audio`, `speech_control` and `status` frames sent to the phone carry the agent they belong to, including replies from an agent that is in the background on the Mac. A reply reaches the phone when its request came from the phone or when Remote mode routes speech to the phone, as the spec already defines; this ticket adds the tag, not new routing rules.
3. **Per-agent state.** `session_state.agents` reports, for each of the four agents: `running`; a `state` of `off`, `starting`, `ready`, `working`, `listening` or `playing`, taken from the same source that drives the desktop notch glyph (`Sources/relay-runner/Overlay/NotchStatusController.swift`); and `working_on`, the agent card's "Currently working on" text when there is one. Pushed to connected phones when any of it changes, without flooding (coalesce rapid changes).
4. **Start without a project.** `session_command` `start` with an `agent` and no `project_id` starts that agent in the built-in general-tasks context, exactly as the desktop's Start Session does by default.
5. **Message to start.** An utterance addressed to an agent that is not running starts that agent (as in point 4) and is delivered once the agent is ready. The phone sees `starting`, then `ready`, then the normal `accepted`.

## Acceptance criteria

- [ ] With two agents running and agent A focused on the Mac, an utterance addressed to agent B is answered by B, and the `accepted` and `speech` frames for it carry B's slug. The Mac's focused target for local microphone input is A afterwards.
- [ ] An utterance with no `agent` is delivered exactly as before; existing bridge and remote tests pass unchanged.
- [ ] A `control` stop addressed to an agent stops that agent's reply on the phone and does not stop another agent's.
- [ ] `session_state.agents` lists all four agents with the right `running` and `state` values as an agent goes through off → starting → ready → working → playing → ready, and updates are pushed without a poll.
- [ ] `start` with an agent and no project starts that agent in general-tasks; `start` with a project still works.
- [ ] An utterance addressed to a stopped agent starts it and is delivered once, not dropped and not duplicated (covers a phone reconnect during the start).
- [ ] Remote utterances keep their `input_source`, `device_id`, command sequence and mutation-authorisation behaviour. An addressed utterance is authorised against the target agent's session, not the focused one.
- [ ] `docs/specs/relay-remote.md` describes addressed delivery, the state values and their source, and message-to-start.
- [ ] `swift build`, `swift test` and `cargo test` pass, with new tests for each criterion above that can be tested without a phone.
