## Description

The note-taker is moving from live transcription to "record now, transcribe after Stop" (MVP chain RR-404 → RR-406, with RR-405 in parallel). Today `MeetingTranscriptProducer` runs FluidAudio/Parakeet windowed ASR (6 s windows, 2 s partial refreshes) while capture runs. `MeetingNoteRecoveryStore` also persists every accepted chunk as raw Float32 `.f32` files, about 64 KB/s per source. Both are heavier than the user wants during note-taking.

This ticket adds **only the recording and storage component**. It is not wired into `MeetingNoteCaptureSession` or `MeetingNoteCoordinator`; RR-406 does that. The existing live path must behave exactly as before after this merges.

Add `MeetingCompressedAudioRecorder`, an actor, under `Sources/relay-runner/Notes/`:

- **Input** is the existing `MeetingAcceptedAudio`: descriptor plus 16 kHz mono Float32 samples. The descriptor already carries `sourceID`, `timingEpochID`, `startSample` and `startMilliseconds` on the shared host-monotonic timeline. Do not invent a second timeline.
- **Encoding.** Use AAC-LC in `.m4a` via AVFoundation (`AVAudioFile` with AAC settings is fine): 16 kHz, mono, target about 32 kbps. Keep one track per `MeetingAudioSourceID` and never mix microphone and system audio. Speaker attribution later relies on `sourceID`.
- **Rolling segments for crash safety.** A plain `.m4a` is unreadable if the process dies before it is finalized. Rotate to a new file:
  - at every new timing epoch;
  - at least every 30 s per source (a named constant);
  - and finalize on rotation, `finishAll()` (pause or stop) and close.

  Keep an atomic JSON manifest per session, rewritten after each segment closes. Each entry records the source, epoch ID, timeline start sample, exact recorded sample count and an opaque file name. A hard crash may lose at most the open segment for each source.
- **Reading back.** Decode in timeline order per source as an async sequence or iterator of `MeetingAcceptedAudio` chunks with a bounded maximum chunk size. Peak memory must not grow with meeting length. Trim AAC priming and padding so each segment's decoded sample count equals the manifest count, padding or trimming the last few samples if the decoder differs. Descriptors must reproduce the original epoch and timeline positions.
- **Storage.** Put recordings inside the existing per-session recovery directory owned by `MeetingNoteRecoveryStore` (`~/Library/Application Support/Relay Runner/Note Recovery/session-*/`), in a `recording/` subdirectory:
  - directories 0700, files 0600;
  - opaque file names;
  - `URLResourceValues.isExcludedFromBackup = true`.

  Add the minimal store API needed to resolve and remove that directory. `removeSession` must also remove the recording.
- **Budget.** Enforce a per-session byte budget. The default must hold at least 4 hours of two-source audio at the chosen bitrate, with the arithmetic in a code comment. Exceeding it throws a typed error before writing past the budget.
- **Privacy.** Never log audio samples or file contents. Log only cause codes and counters, under the existing `notes` logger category.

## Acceptance criteria

- [ ] Round-trip test with synthetic two-source audio across at least 3 epochs (including a pause gap) and at least 2 rotations per source. Decoded per-source sample counts equal the input counts, and every decoded chunk's timeline start is within 50 ms of the original.
- [ ] The decoded signal is non-silent and matches the synthetic input within a threshold stated in the test, for example correlation or RMS error on a speech-band tone sweep.
- [ ] Abrupt-termination test: with one segment left open and never finalized, the manifest loads and every closed segment decodes. The open segment is reported as lost without throwing.
- [ ] Storage test: the recording lives under the session's Note Recovery directory with 0700/0600 permissions and is excluded from backup. `removeSession` deletes it completely.
- [ ] Budget test: exceeding a small configured budget throws the typed error and writes no further bytes. The default budget's hours-at-bitrate arithmetic is documented.
- [ ] The reader never returns more than the configured maximum chunk size, so no API returns a whole-source buffer.
- [ ] A test asserts measured encoded size is at most 20 MB per hour per source.
- [ ] No production code path calls the recorder yet. Existing `MeetingTranscriptProducerTests` and `MeetingNoteCoordinatorTests` pass unchanged, and `swift build` succeeds.
