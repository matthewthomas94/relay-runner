## Description

Fix the Workspace board regression where the visible card under the pointer is
not the card that receives a drag. This occurs across the board: mouse down on
any visible Backlog ticket, then drag toward Queued, and a different card can
become the drag source. RR-263, RR-176, RR-175, and RR-174 are observed
examples, not a position-specific reproduction. The defect is not primarily a
drop-target error: the wrong card identity is selected at pointer-down.

Hover and cursor feedback on ticket cards is absent, delayed, or intermittent,
while hover on project-folder controls can still work. This confirms that the
panel receives pointer events and narrows the failure to the mounted card
routing and hover ownership inside scrollable lanes. Interaction is also
visibly laggy on populated boards.

RR-254, RR-259, and RR-260 added targeted card routing and lifecycle fixes but
did not resolve the installed behavior. Perform an end-to-end mounted
investigation before changing code. Preserve the intent of custom card routing,
but remove the repeated whole-hierarchy routing and feedback path that lets
the rendered card, hit-tested card, and captured card disagree.

Likely implementation direction: derive a stable, ordered document-space hit
index from mounted card event views during layout; use it consistently for
hover and mouse-down; capture the exact selected event view through mouse-up;
and avoid publishing every card-frame update into shared board state during
pointer movement. Confirm the final design against real mounted geometry rather
than assuming this hypothesis is complete.

## Acceptance criteria

- [ ] A mounted regression fails on current main by pointer-down/dragging multiple visible Backlog cards and observing a different card selected as the source.
- [ ] Pointer-down on every tested visible card preserves that exact item identity through drag and a drop into Queued; no gesture can move a different card.
- [ ] Hover and cursor feedback appears immediately on the exact visible card under the pointer without click, scroll, refocus, or tab switch.
- [ ] First, middle, and last visible cards route correctly before and after scrolling, snapshot refresh, prepend, reorder, variable-height layout, scope change, and tab transition.
- [ ] The solution uses one authoritative mounted-card identity path for hover, mouse-down, drag capture, and mouse-up; it does not add another position-specific exception.
- [ ] Pointer movement does not repeatedly recurse through the full mounted card hierarchy or trigger board-wide frame/state feedback for every card; include a focused responsiveness measurement on a populated Done lane.
- [ ] Click selection, scrolling, non-draggable cards, folder controls, column controls, valid and invalid drop indicators, drag cancellation, and panel dismissal keep their existing behavior.
- [ ] Tests exercise the actual NSApplication to BoardOverlayPanel to scroll-document path. Isolated helper or synthetic geometry tests alone are insufficient.
- [ ] Focused Workspace board tests, the RR-237 board benchmark, and relevant Swift package tests pass; retain prior RR-254, RR-259, and RR-260 coverage.
- [ ] After review and install, perform a human smoke check on the populated Workspace board, or record the precise macOS permission blocker.
