## Description

Spec: `docs/specs/relay-remote.md` (Relay Remote: iOS voice over SSH), committed as `2a64cc0d` on branch `claude/ios-relay-ssh-tcp-spec-ddb8f2`. The spec is not on `main` yet; if the file is missing from your worktree, read it with `git show 2a64cc0d:docs/specs/relay-remote.md`. Read these sections first: Architecture, Pairing and trust, Verified upstream inputs, Open questions.

Relay Remote carries text frames between a native iOS app and the user's Mac over one persistent SSH connection to the Mac's own OpenSSH server; there is no relay server. The spec assumes one `exec` channel running the forced command `relay-remote-shell --device <device_id>` with NDJSON over the channel's stdin and stdout, and names a `direct-tcpip` forward to the bridge socket as the fallback. Settle that choice before the iOS transport (RR-428) and the helper (RR-425) are built.

Answer these questions by reading source and documentation only (swift-nio-ssh, swift-nio-transport-services, Citadel, Apple's background execution and network documentation). Pin every citation to a commit SHA or a dated document.

1. Can a swift-nio-ssh client open an `exec` channel with a writable stdin and no PTY, and keep it open as a long-lived bidirectional stream? Name the channel type, request, and handler types involved.
2. Which delegate or hook validates the server host key against a key pinned at pairing, and what does it receive (key type, raw bytes, fingerprint)?
3. Can the public half of `NIOSSHPrivateKey(secureEnclaveP256Key:)` be exported in `ecdsa-sha2-nistp256` authorized_keys format so the Mac can install it, and what is the fallback on a device without a Secure Enclave?
4. Does Citadel (the higher-level client built on swift-nio-ssh) add anything Relay Remote needs (exec with stdin, forwarding, reconnection) or only cost?
5. What does the `direct-tcpip` fallback cost compared with `exec`: extra `sshd` options (`AllowTcpForwarding`, `AllowStreamLocalForwarding`), interaction with `restrict` in `authorized_keys`, and client complexity?

Also list the iOS channel edge cases RR-428 must test: suspension and resume, network path changes (Wi-Fi to cellular), keepalive intervals that survive NAT timeouts, and what the app can rely on while in the background.

This is read-only research: do not write prototype code into the repository.

**Conclusions**

- RECOMMENDATION: use `exec` as the primary channel, running forced command `relay-remote-shell --device <device_id>`. Reasons: swift-nio-ssh supports exec with no PTY; `command=` binds device_id to the key server-side; `restrict,command="..."` locks down everything else; helper lifetime equals channel lifetime. Keep `direct-tcpip` as a documented fallback only (cost in Q5).
- Q1 (yes): `NIOSSHHandler.createChannel(_:channelType:_:)` defaults to `SSHChannelType.session`. In the initializer, add a handler, set `allowRemoteHalfClosure`, and send `SSHChannelRequestEvent.ExecRequest(command:wantReply:)` as a user outbound event; send no `PseudoTerminalRequest`. Replies: `ChannelSuccessEvent`/`ChannelFailureEvent`. Stdin is outbound `SSHChannelData(.channel)`; stdout inbound `.channel`; stderr `.stdErr`; `ExitStatus`/`ExitSignal` are inbound events. The channel stays open until close, EOF or parent shutdown. Evidence: swift-nio-ssh 149f32ff ExecHandler.swift.
- Q2: the hook is `NIOSSHClientServerAuthenticationDelegate.validateHostKey(hostKey: NIOSSHPublicKey, validationCompletePromise:)`, supplied as `SSHClientConfiguration.serverAuthDelegate`. Succeed the promise to trust, fail it to abort. It receives only an opaque Hashable `NIOSSHPublicKey`: no fingerprint, and no public key-type or raw-byte accessor. To pin: build the pinned key with `NIOSSHPublicKey(openSSHPublicKey:)` and compare with `==`. For a displayable SHA-256 fingerprint, use `String(openSSHPublicKey:)`, base64-decode the blob and hash it.
- Q3 (yes): `NIOSSHPrivateKey(secureEnclaveP256Key:)` exists under `#if canImport(Darwin)` (added in 4ebb6ea7, 2020-05-05). `.publicKey` gives a `NIOSSHPublicKey`, and `String(openSSHPublicKey:)` renders `ecdsa-sha2-nistp256 <base64>` (blob is "nistp256" plus the x963 point), which is usable in authorized_keys as-is. Persist the key via `dataRepresentation`. When `SecureEnclave.isAvailable` is false, fall back to a software `NIOSSHPrivateKey(p256Key:)` or `ed25519Key:` kept in the Keychain and exported the same way.
- Q4: Citadel mostly adds cost. It has stdin-writable no-PTY exec (`SSHClient.withExec` with `TTYStdinWriter`), `.directTCPIP`, `SSHHostKeyValidator`, and `SSHReconnectMode` (immediate retry, no backoff, no state resume). But: its Package.swift depends on the fork `Wellz26/swift-nio-ssh`, not Apple's; it uses BSD-socket `ClientBootstrap`, so no Network.framework path events, and no TCP keepalive; Secure Enclave auth needs `.custom` delegate. Use swift-nio-ssh directly over NIOTS. Evidence: Citadel ae8562f8 (2026-04-04).
- Q5: `direct-tcpip` costs more. sshd: `AllowTcpForwarding` (default yes, `local` suffices) plus per-key `restrict,port-forwarding,permitopen="127.0.0.1:<port>"`. `command=` does not apply to forwards, so the forced command and device_id binding are lost and the bridge must authenticate devices itself. Unix-socket forwarding (`AllowStreamLocalForwarding`, `direct-streamlocal@openssh.com`) is unavailable: `SSHChannelType` has only `.session`, `.directTCPIP`, `.forwardedTCPIP`, so the bridge needs a loopback TCP listener. Client code is similarly simple.
- KEEPALIVE: swift-nio-ssh 149f32ff has no public API for a client to send `keepalive@openssh.com`; only `sendTCPForwardingRequest` is public. It answers unknown inbound global requests with failure, so server `ClientAliveInterval` should still work. Client liveness needs NDJSON ping/pong frames (natural with exec) plus TCP keepalive via `NWProtocolTCP.Options` (`enableKeepalive`, `keepaliveIdle`, `keepaliveInterval`, `keepaliveCount`) given to `NIOTSConnectionBootstrap.tcpOptions(_:)`. Prefer NIOTS (f85ed684): it fires PathChanged, BetterPathAvailable, ViabilityUpdate.
- RR-428 edge cases, lifecycle: (1) background then suspend: Apple gives about 5s in the background callback, then suspension, and a bounded `beginBackgroundTask` window; no page promises TCP survives suspension, so assume the socket is lost; (2) resume onto a dead socket: detect via write error, `tcpShutdown`, missed pong or path change, then reconnect and resume frames; (3) sshd `ClientAlive*` reaps the helper while suspended; (4) no background delivery without a declared background mode; (5) relaunch with persisted SE key and pinned host key; (6) locked device and Keychain/SE access.
- RR-428 edge cases, network: (1) Wi-Fi to cellular and back: Apple DTS (forum 746449, Feb 2024) says Network framework does not drop unviable TCP connections and a new connection is needed after an interface change; test that PathChanged, ViabilityUpdate or BetterPathAvailable forces teardown and reconnect without waiting for a timeout; (2) airplane mode and `.waiting` states; (3) silent NAT drop: verify ping timeout and keepalive values hold the mapping; (4) Mac sleep, IP change, sshd restart; (5) half-open in both directions; (6) reconnect backoff, one connection per device.
- RR-428 edge cases, channel semantics: (1) ExecRequest rejected, or forced command missing or crashing; (2) ExitStatus or ExitSignal arriving with data pending; (3) remote half-close: `allowRemoteHalfClosure` default promotes EOF to full close, so set it deliberately; (4) parent close surfacing as `NIOSSHError.tcpShutdown`, writes failing with `ChannelError.eof`, no silent frame loss; (5) backpressure via `isWritable`; (6) NDJSON framing across packets, max line length, stderr kept out; (7) host-key mismatch aborts before auth; (8) key revoked on the Mac; (9) duplicate device_id connect.

- Read the spec with `git show 2a64cc0d:docs/specs/relay-remote.md` in an environment with Git. Reconcile this report with its Open questions and Verified upstream inputs, and correct the report if the spec's assumptions differ.
- Run a throwaway prototype outside this repo (separate ticket): swift-nio-ssh over `NIOTSConnectionBootstrap` against macOS sshd. Cover SE-key auth, the `validateHostKey` pin, a no-PTY exec stream held 30+ minutes, and `tcpOptions` keepalive. Pin swift-nio-ssh and NIOTS by revision (149f32ff, f85ed684) or release tag.
- Define the RR-428 frame contract: NDJSON frames with session id and sequence numbers so a reconnect can resume, plus `ping`/`pong` frames. Treat the SSH connection as disposable; reconnect on foreground, PathChanged or ViabilityUpdate, and a missed pong.
- Measure NAT and idle timeouts on real Wi-Fi and cellular, then set `keepaliveIdle`, `keepaliveInterval`, the app ping period, and sshd `ClientAliveInterval` and `ClientAliveCountMax`. Decide whether `withMultipath` is worth testing; it needs server support, so it is probably out of scope.
- Decide the foreground-only versus background-mode policy with the product owner. Voice features may need an audio background mode; Apple's background-mode review rules were not researched here.
- Write a one-page `direct-tcpip` fallback note (loopback TCP bridge listener, `permitopen`, bridge-level device auth). Use it only if the exec prototype hits a blocker such as an sshd or helper-spawn constraint.
- Pin swift-nio-ssh and swift-nio-transport-services by revision in `ios/`, and review pins on every update.
