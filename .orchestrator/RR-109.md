## Description

Fix the ready-ticket dispatch path so a ticket with a succeeded worker branch awaiting merge is not repeatedly redispatched from the main worktree just because its `done` ticket update has not been merged yet.

`RR-108` exposed the bug: run 10 succeeded and the worker branch marked the ticket `done`, but the main worktree still had `status: ready` and `run_id: null`, so later sweeps/manual dispatch attempts created extra runs that exited with validation errors such as "ticket run_id is 10, expected 14". The same pattern can spam failed runs, confuse Program Board status, and waste worker quota.

Preserve the intended retry behavior: a genuinely failed or canceled run may still be retried intentionally, but a succeeded run awaiting merge should be treated as already claimed until it is merged, canceled, or explicitly reset by the user.

Likely touch points:

- `services/orchestrator.py`
- `services/program_status.py`
- `Sources/relay-runner/Board/ProgramBoardStatus.swift`
- Python dispatch/sweeper tests
- Swift Program Board status tests if visible status text changes

## Acceptance criteria

- [ ] Ready-ticket sweeps do not dispatch a ticket that already has a succeeded run awaiting merge for the same repo and ticket id.
- [ ] Direct `dispatch_ticket` reports an actionable already-awaiting-merge response instead of creating another run for a ticket with a succeeded unmerged worker branch.
- [ ] Failed, canceled, and explicitly reset tickets retain a deliberate retry path.
- [ ] Program Board or status output makes the waiting-for-merge state clear enough that users do not expect another worker to start.
- [ ] Regression tests cover a ready ticket with `run_id: null` on main plus a succeeded worker branch/run record, and verify no duplicate run is created.
- [ ] Provider parity is explicit: Codex and Claude runs share the same duplicate-dispatch guard.
