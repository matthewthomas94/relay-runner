## Description

Relay Runner supports multiple agent providers, especially Codex and Claude. The user wants a standing product/engineering rule: when we add a feature for one LLM provider, we must explicitly consider and support the equivalent experience for the other supported providers unless there is a deliberate documented exception.

Make this rule durable in the repo so future humans and agents do not treat Codex-only or Claude-only behavior as the default. This should be written into the project guidance that agents read before working, and into any nearby workflow docs or ticket/review guidance that shape implementation work.

The intent is not to force identical implementation for every provider. The intent is parity of user experience:

- Codex-specific work should ask what the Claude path does.
- Claude-specific work should ask what the Codex path does.
- Provider differences, flags, auth paths, model names, and permissions may differ, but those differences should be handled intentionally.
- If a provider cannot support a feature, the limitation should be visible in the ticket, implementation notes, or user-facing behavior.

Likely places to inspect:

- `AGENTS.md` for top-level project guidance.
- `services/orchestrator_workflow.md` for worker instructions.
- `docs/specs/` for any relevant feature/ticket/review guidance.
- Existing settings/launch code comments if a small local note would prevent future provider-specific drift.

## Acceptance criteria

- [ ] Project guidance includes a clear provider-parity rule covering Codex and Claude.
- [ ] Worker/sub-agent instructions include the same rule or link to it, so dispatched agents see it before implementing tickets.
- [ ] The rule explicitly says that new provider-facing features must consider all supported providers, not just the provider named in the immediate request.
- [ ] The rule allows intentional provider-specific differences, but requires them to be documented in the ticket or implementation notes.
- [ ] Any existing ticket/review guidance that defines "ready" or acceptance criteria is updated to encourage provider-specific acceptance checks when relevant.
- [ ] No runtime behavior changes are made unless a tiny comment or naming adjustment is necessary to make the guidance discoverable.
- [ ] Validation includes a grep/readback showing the provider-parity language exists in the files future agents will actually read.
