## Description

The user reproduced the bug from RR-516 on their own company-managed work laptop, with a fresh install of v0.7.0, and collected a diagnostic report. RR-516 added diagnostics and a fallback from code reading alone. This ticket uses the real evidence to find and fix the root cause. Start from main after RR-516 merges and build on what it added.

### Evidence from the report (2026-11-16, macOS 27 / Darwin 27, Apple silicon)

Reproduction:
- Relay state, provider integrations, the voice model and the TCC grants for `com.relayrunner.app` (Microphone, Accessibility, ListenEvent, ScreenCapture, AppleEvents) were reset first.
- The v0.7.0 DMG was downloaded with `gh`, so it had no quarantine flag and no Gatekeeper first-launch check.
- The app was launched **from the mounted DMG** (pid 5348, 18:49:04) and ran onboarding through the permissions steps. It then **copied itself to /Applications and quit** (18:49:46, "Relay Runner will copy itself to Applications and launch").
- The /Applications copy (pid 11681, 18:49:48) **resumed onboarding at the tutorial step** "Turn caps lock on & say hi" (resume state `tutorialRecording`). Caps Lock presses did nothing.
- A later launch (pid 35075, 19:00:53) resumed at the same step, and Caps Lock still did nothing. No crashes.

tccd preflight answers for Relay Runner (authValue: 2 allowed, 1 unknown, 0 denied; authReason: 2 user consent, 4 system set, 5 service policy, 6 MDM policy):
- DMG instance at 18:49:08: Accessibility, ListenEvent and ScreenCapture all 1/5 (unknown), Microphone 1/0.
- During permissions:
  - 18:49:10 Accessibility 2/6 (MDM policy). Probably a non-preflight check, possibly Microsoft DLP's query.
  - 18:49:23 Microphone 2/2.
  - 18:49:34 Accessibility 2/4.
  - 18:49:38 ScreenCapture **0/5 (denied)**.
- /Applications copy at 18:49:48, and again at 19:00:53: Accessibility, ListenEvent and ScreenCapture **2/4 (allowed, "system set")**, Microphone 2/2. The app's defaults also cache all four as granted.
- In System Settings, Relay Runner is **not listed under Input Monitoring**. The user couldn't find Relay Runner under Accessibility either. This macOS version's Privacy list has a "Device Control and Data Access" pane instead of an "Accessibility" row, and Relay Runner wasn't there. Microphone is listed and on. No toggle is greyed out or managed.

So preflight says allowed, but nothing in Settings shows a grant. That points to the app trusting preflight results that don't reflect a usable grant, possibly carried over in an odd way from the DMG copy to the /Applications copy.

Logs:
- The process is named `relay-runner`. 7,287 lines were captured from it during the repro, and **none** mention Caps Lock, `flagsChanged`, key events or `[CapsLockGesture] monitor active`. Yet `CapsLockGesture` logs `monitor active identity=modifier-local` through NSLog whenever its local monitor installs, and the STT model was prepared at launch (`[com.relay-runner:STTModelPreparation] Prepared phonon-2 ... 20 files verified`, 19:00:54.9). Either the gesture/STT engine was never constructed on this resume path, or NSLog lines aren't reaching the unified log. Determine which.
- The windows created were only OverlayPanel, PerimeterPanel, NotchStatusPanel, BoardOverlayPanel and status-bar windows.

Environment:
- Intune-managed (DEP, user-approved MDM). Its PPPC profiles grant Accessibility, AppleEvents, ScreenCapture and Full Disk Access **only to Microsoft components**; none mention Relay Runner, ListenEvent or PostEvent.
- Microsoft Defender, the Intune agent and Microsoft DLP are running. The DLP daemon queries Accessibility for Relay Runner at each launch.
- One keyboard layout (Australian). Caps Lock isn't remapped, `AppleCapsLockSwitchesInputSource` is unset, `UserKeyMapping` is null, and there are no key remappers.
- The app is Developer ID-signed (team QK9K4AQRNH) and not notarised.

**Update from the user (2026-11-16): permission ruled out as the sole cause.** With Relay Runner switched **on** under Device Control and Data Access (Accessibility) and the app reopened, Caps Lock still does nothing in the tutorial. Treat hypothesis 1 (the gesture/STT never starts on the resumed tutorial path) and the window/monitor delivery path as the primary suspects. Hypothesis 2 is secondary.

**Update 2 from the user (2026-11-16), now the leading theory.** After skipping onboarding (writing `.onboarded`), **double-tap Shift also does nothing** on the managed laptop, so no global key monitor gets events anywhere, not just in the tutorial. That happens with Accessibility (Device Control and Data Access) switched on and the app relaunched. On the developer's own Mac, where everything works, the app's cached permissions include `com.relayrunner.lastKnownPermission.inputMonitoring = granted`, a leftover from older builds that still requested it. The fresh install never requests Input Monitoring (`PermissionKind.guidedSetupOrder` is microphone, accessibility, screenRecording; the doc comment assumes Accessibility covers global hotkeys), and the laptop's Input Monitoring list doesn't include Relay Runner. **Most likely root cause: on macOS 27 the NSEvent global `flagsChanged`/`keyDown` monitors need Input Monitoring (kTCCServiceListenEvent), and Accessibility no longer covers them.** Required change: guided setup always requests Input Monitoring (before Accessibility), Caps Lock and the hotkeys depend on it, and its status is verified by actually receiving an event. Update the doc comment, setup copy and tests. Keep Accessibility for computer control.

**Update 3 from the user (2026-11-16), which supersedes "Update 2" as the leading theory.** A few minutes after relaunching with Accessibility on, and **without adding Input Monitoring**, key monitoring started working on its own. The Workspace popped open by itself. Since then double-tap Shift toggles it, and Caps Lock registers: with no session running it shows the "no session" pill. So the grant was valid but **became usable only minutes after it was switched on and the app relaunched**, and `CapsLockGesture`'s 1-second global-monitor retry picked it up then. Meanwhile onboarding showed the tutorial with Caps Lock silently dead. That is how the friend and the user both got stuck. The spontaneous Workspace open probably came from queued or replayed shift events, or onboarding's workspace handoff, once the monitor attached; check which. A follow-up log report (`~/Desktop/relay-hotkey-followup.md` on the laptop) will give exact times and will be added here if it arrives.

Required behaviour, keeping the Input Monitoring request from Update 2 as belt and braces:
- The tutorial's Caps Lock step (and any hotkey-dependent step) doesn't start until the global key monitor is actually attached. Until then it shows a clear waiting state ("Waiting for macOS to apply the permission. This can take a minute."), with Open Settings and a click-to-record fallback.
- The global monitor retry and the step's state are linked, so the step advances automatically the moment the monitor attaches.
- No spontaneous Workspace open when the monitor attaches late.

**Update 4 from the follow-up log report (2026-11-16 19:23), which supersedes Updates 2 and 3. This is the leading theory.**
- tccd answered **the same for every launch from 18:49:48 on**: Accessibility, ListenEvent and ScreenCapture allowed (2/4), Microphone 2/2. That held before and after the user switched Accessibility on in Settings, and **no TCC record changed**. Permission timing is ruled out.
- Hotkeys and Caps Lock never worked in any launch while onboarding was in progress (19:12:49, 19:13:34, 19:17:57–19:18:27, all resumed at `tutorialRecording`). They worked in **the first launch where `.onboarded` existed** (pid 51105, 19:19:30; `.onboarded` was written in the same second). In that launch, window 130f (probably the Workspace's post-onboarding auto-open) showed at 19:19:35 and was hidden at 19:19:56 by the user's double-tap Shift. The user's "it opened on its own" was that auto-open. Input Monitoring was still not listed. Caps Lock records speech in that launch.
- **Conclusion: while onboarding is incomplete or resumed (`com.relayrunner.onboarding.resume.step = tutorialRecording`, especially after the DMG to /Applications self-relocation), the key monitors are not running or not receiving events. The tutorial needs Caps Lock to advance, so it deadlocks.** Permissions don't fix it.
- Code pointers: `AppState` launch (~1124–1140) calls `startOverlay`, `startAwareness` depending on `launchPlan(for: microphone)`, then `onboarding.showIfNeeded()`. `prepareOnboardingTutorialSpeech` (~3258) starts awareness only if `sttEngine == nil && microphone == .granted`, then sets `tutorialActive` and calls `syncCommandCaptureOwnership()`. Check what in the onboarding or tutorial state stops `CapsLockGesture` and `BoardHotkeyGesture` getting events: capture ownership, `allowsAppShellAccess`, `tutorialActive` gating, the resume path skipping `prepareOnboardingTutorialSpeech`, or the onboarding window or panel swallowing `flagsChanged`.
- The diagnostics the gesture prints are lost: the report found they go to stderr/`/dev/null` and never reach the unified log. Fixing the logging criterion is essential.
- Updates 2 and 3 stay as defensive work (request Input Monitoring; the tutorial waits visibly until key events actually arrive), but the root-cause fix is the onboarding deadlock above.

### Hypotheses to confirm or rule out, most likely first

1. **Resume after self-relocation skips starting STT/the gesture.** The relaunched /Applications copy resumes at `tutorialRecording` without whatever earlier step normally calls `startConfiguredSTT` (`AppState.swift` ~1243) or creates the `CapsLockGesture` (`STTEngine` init via `makeGesture`). Check every path that starts STT against an onboarding resume at each tutorial step.
2. **Preflight says yes, but the global monitor gets nothing.** `NSEvent.addGlobalMonitorForEvents(.flagsChanged)` needs a real Accessibility/Input Monitoring grant. If onboarding's surface is a non-activating panel that never becomes key, the local monitor never sees Caps Lock either. Check whether the tutorial step's window can be key. Check whether the permission steps passed on a cached or preflight "granted" (2/4 "system set") that doesn't match a visible grant, and whether onboarding should verify a grant by actually receiving an event. On macOS 27 the Accessibility row seems to have been renamed or moved; check that the app's System Settings deep links still open the right pane.
3. **Logging gap.** Make the gesture and STT start diagnostics reach the unified log under the app's subsystem (os `Logger`, public strings, no key contents), so a report like this shows them.

### Fix

Fix the root cause(s) you confirm. At minimum:
- Every resume into a tutorial step that needs speech starts STT and the gesture.
- Onboarding doesn't pass a permission step on a preflight result alone when it can verify the grant directly (for key monitoring, an actual received event or a positive check). When verification fails, it says so and links to the right pane on this macOS version.
