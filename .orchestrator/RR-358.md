## Description

Investigate and plan a full native iOS Relay Runner experience that remotely controls sessions executing on the user's Mac. The phone owns its native interface and speech input/output; the Mac remains authoritative for projects, sessions, agents, files, tools, tickets, and execution. This is broader than a voice remote: preserve the core session-management and work-management experience of the current macOS app, adapted to phone interaction.

The deliverable is an evidence-backed architecture and a set of cold-start-ready implementation-ticket drafts, with dependencies, interface contracts, ownership boundaries, and parallel execution waves. This ticket authorizes planning only. Do not implement the app, change source, create child board cards directly, dispatch implementation workers, provision networking, or modify the installed application. Return the designated structured spike report; the daemon persists it and the foreground PM turns reviewed recommendations into canonical backlog tickets.

### Product scope to decompose

1. Native iOS app shell: pairing with and selecting a Mac host, selecting a project, session list and current-session state, phone-appropriate navigation, configuration, connection status, and errors. Inventory relevant macOS controls and distinguish shared models/services from platform-specific UI; do not assume existing macOS views can simply be reused.
2. Session lifecycle: start, resume/attach, switch, interrupt, and stop remote sessions; choose supported provider, model, and effort; handle agent prompts and approvals. Specify both Codex and Claude behavior and keep host credentials on the host.
3. Terminal and conversation: live terminal output, typed input, control keys, resizing, scrollback/history, public progress and final responses, and clear distinction between terminal transport and structured session events.
4. Phone voice: native STT and TTS, push-to-talk, speech playback/replay and interruption, audio routing including AirPods, transcript presentation, and handoff between Mac and phone microphone/speaker ownership. Separate stopping speech, interrupting a turn, canceling scoped work, and stopping a session. Evaluate foreground, locked-phone, and background modes explicitly; do not assume continuous background operation.
5. Work management: view and manage the project board and ticket details, author/refine tickets, dispatch workers, inspect progress, failures, diffs/results and verification evidence, and perform supported review/integration actions. Preserve ready-means-dispatch semantics, artifact-backed ticket authority, PM/worker boundaries, and project scoping.
6. Remote connectivity: evaluate private Tailscale/HTTPS connectivity as a first transport, an authenticated Mac session gateway and bidirectional streaming, device pairing/revocation, host availability, and whether a later integrated connection experience warrants a separate phase. Treat the transport choice as a recommendation to validate, not an existing implemented capability. Cover least-privilege endpoints and avoid exposing unrestricted local daemon administration.
7. Continuity and concurrency: sessions survive phone disconnects and UI closure, reconnect restores state and missed output, stable command/event identities prevent duplicate execution, and Mac plus phone interactions follow one authoritative ordering and scoped cancellation contract. Identify current coupling to app windows/embedded terminal/bridge lifetime and the host changes necessary to remove it safely.
8. Mobile notifications and host constraints: meaningful completion/failure/input-needed notifications, privacy of previews, offline/sleep/locked-host behavior, desktop permission constraints, and optional Relay Vision snapshots/Relay Actions controls where useful. Explicitly phase visual remote interaction; full video desktop streaming is not a default requirement.
9. Delivery and validation: native iOS target/build structure, shared Swift code boundaries where justified, supported OS/device/language assumptions, signing and distribution prerequisites, test strategy, compatibility/version negotiation, macOS regression coverage, rollout, and physical-device UAT.

## Product decisions from the user (2026-11-03)

Treat these as settled inputs, not open questions. Plan around them and flag only genuine conflicts with evidence.

1. **Remote mode is an explicit switch on the phone.** On: the phone is the primary driver and owns microphone and speaker for the turn; the Mac stays quiet. Off: everything routes back through the Mac even while the phone remains connected. Today ownership flips implicitly on connect; make it deliberate and visible on both devices.
2. **Three destinations, reached from a gooey-style menu**: Home, Workspace, Settings. The visual reference is the `liquid-gooey` React library at https://libraries.dev/gooey.html (round buttons that merge like liquid; morph/move/melt/bend). Build the look natively in SwiftUI (blur plus alpha-threshold canvas); do not depend on the React package. No side menu, no tab bar.
3. **Home is the talk screen.** It carries the agent card from the Mac's Settings (voice name, state label such as Standing by / Listening / Speaking, and the dot-blob particle field reacting to state) as the backdrop. One exchange at a time: the message sent and the reply received, previous exchanges reviewable but not stacked as a chat. Push to talk or type.
4. **Workspace**: a project dropdown at the top, a start/stop-session control beside it, and the board for that project only, one lane per screen with horizontal swipe between Backlog, Queued, In Progress and Done (Jira mobile style). Ticket detail, dispatch and review actions preserve ready-means-dispatch and PM/worker boundaries.
5. **A single shared control strip** on Home and Workspace: send, play/replay last reply, stop speech, cancel current turn. **Interrupt is not a button**: starting to talk interrupts playback, as on the Mac. The current phone app has a bug where push to talk does not reliably stop playback; the plan must include its fix.
6. **Settings on the phone mirrors the Mac's pages** (which settings are editable remotely is a planning output; the Mac remains authoritative and credentials stay on the host).
7. **Session control from the phone**: list registered projects, start a session for a project using the Mac's current defaults (provider/model/effort selection from the phone is deferred), attach to a running one, stop it. Distinguish "Relay Runner app not running" from "no session" in the UI. The Mac must be awake; there is no wake-on-demand. Turning Remote mode on should engage the Mac's Keep Awake.
8. **The Mac's voice on the phone (spec change).** The user does not want Apple's voice on the phone. Decision: the Mac synthesises with its configured voice (Kokoro/custom voice) and streams the audio to the phone over the existing channel, per sentence as it is synthesised (Opus or AAC, roughly 3 KB/s). This deliberately retires the "no audio on the wire" non-goal in docs/specs/relay-remote.md for Mac-to-phone speech; phone-to-Mac remains text. The plan must measure first-audio latency against today's text path on Wi-Fi, Tailscale and cellular, and keep a text fallback.
9. **Playback mode setting on the phone**: auto-play (default, matches the Mac) or play on demand.
10. **Touch controls mirror the Mac's keyboard/modifier functionality**; nothing depends on a keyboard.

Already shipped and verified on a real iPhone (2026-11-03): pairing by QR, SSH key transport with the home-network/Tailscale restriction, typed requests, lock/unlock resume, reconnect over Tailscale on cellular, push-to-talk speech with spoken replies on the phone (RR-428, RR-429, RR-433). Implementation tickets already on the board for the decided pieces, to be referenced rather than re-proposed: RR-454 (Remote mode switch, ownership and Keep Awake), RR-455 (push to talk interrupts playback), RR-456 (project list and start/attach/stop session from the phone via an app-owned control socket), RR-457 (Mac voice streamed to the phone: protocol and Mac side), RR-458 (phone playback with auto-play or play-on-demand). Plan the rest around them: the gooey navigation shell, Home with the agent card, the swipeable single-lane Workspace board with ticket actions, Settings mirroring, and the ordering/continuity contracts they all share.

The phone maps Stop to stop and Cancel to cancel, so its Cancel button does not cancel the current turn.
