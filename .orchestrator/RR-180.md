## Description

Reliably deliver both foreground provider replies and asynchronous worker
outcomes through the active Relay messenger, without relying on the user to
notice terminal text or ask for status.

Run 272 exposed the gap: `RR-179` stopped as failed/incomplete because its manual
verification remained, but the user received no spoken outcome. The Relay
bridge process and both bridge/state sockets were present when the run ended, so
this was not caused by an inactive bridge. The orchestrator emitted the
`run-failed` trace through `_notify_state` to `/tmp/voice_state.sock`, which can
update Relay Runner's visual state. The active `MessengerRuntime`, however,
receives lifecycle context through `voice_bridge.emit_orchestration_trace` or
the bridge control/FIFO path. The daemon's asynchronous terminal event therefore
never reached the component responsible for contextual speech.

A following voice turn exposed the same user-visible failure on the foreground
path: the provider produced the correct final response in the integrated
terminal, but no `__ORCHESTRATOR_REPLY__` envelope reached the bridge, so Relay
Runner did not speak it. The active bridge cannot currently recover when a
provider finishes a claimed voice turn without emitting that manual control
message. Prompt instructions remain useful, but delivery of the primary product
response must not depend solely on perfect model compliance.

Harden both routes. A claimed voice turn that completes with a provider final
must yield one authoritative messenger reply tagged to the current command,
whether the provider emitted the control envelope itself or the app-managed
session needs to recover the final through a deterministic completion path.
Typed/non-Relay turns must remain terminal-only. Explicit envelopes remain the
preferred authoritative route and must not be duplicated by fallback delivery.

Worker outcomes must likewise reach both the deterministic visual surface and
the active tool-free messenger. Cover at least awaiting review,
failed/incomplete, canceled, review failure/retry, and merged/done outcomes. The
spoken copy must describe the real state: an implementation that still needs
manual verification is not "done," while a merged ticket may be announced as
complete.

This path is asynchronous and is not owned by the Relay command that originally
dispatched the worker. A newer voice command must not silently discard a later
worker outcome. If no bridge/messenger is active at transition time, retain a
bounded durable pending outcome and deliver or otherwise surface it once when an
eligible session resumes. Do not replay the same outcome after reconnects,
polling, daemon restarts, or repeated status reads.

Keep public messages concise and sanitized. Never forward raw worker logs,
commands, transcript text, hidden reasoning, secrets, or exception dumps to the
messenger or visual status stream.

## Acceptance criteria

- [ ] A provider final produced for an exact claimed Relay voice turn is delivered once through the messenger with the authoritative `relay_command_seq` and `relay_command_id`, without requiring the user to read terminal output.
- [ ] An explicit current `__ORCHESTRATOR_REPLY__` remains authoritative and is spoken once; any app-managed fallback detects that delivery and does not repeat it.
- [ ] If a Codex or Claude provider turn finishes without the control envelope, the app-managed session deterministically recovers or reports the missing foreground reply instead of silently completing with no Relay response.
- [ ] Recovered foreground replies obey newest-intent checks and are never spoken for a superseded voice command; ordinary typed turns are not routed into Relay speech.
- [ ] With an active Relay bridge and messenger, a worker entering awaiting-review, failed/incomplete, canceled, review-retry/failure, or merged/done produces one proactive user-facing lifecycle announcement without a new user turn.
- [ ] The same lifecycle transition continues to update the existing visual notch/Workspace status; adding speech does not replace or regress `StateEventBus` delivery.
- [ ] Announcement semantics match the authoritative run/ticket state: awaiting review is not completion, failed/incomplete identifies that attention is needed, and only an accepted merge is announced as done.
- [ ] Asynchronous worker outcomes are not rejected as stale merely because a newer Relay voice command exists; command-scoped replies and ticket mutations retain their current newest-intent guards.
- [ ] If the bridge or messenger is unavailable at transition time, a bounded durable record preserves the latest unannounced terminal outcome and surfaces it exactly once when an eligible session resumes.
- [ ] Reconnects, daemon/app restarts, repeated run polling, Workspace refreshes, and duplicate state callbacks do not speak the same lifecycle transition more than once.
- [ ] Multiple workers finishing near-simultaneously are queued or summarized without losing outcomes, interrupting the user's current command response incorrectly, or producing overlapping TTS.
- [ ] Public lifecycle payloads contain only sanitized ticket id, run id, state, and concise action guidance; raw logs, commands, transcripts, prompts, hidden reasoning, and secrets are excluded.
- [ ] Codex and Claude active sessions receive equivalent announcements through the shared bridge/messenger contract.
- [ ] Focused tests reproduce the run-272 routing gap, prove active-messenger delivery plus visual delivery, cover bridge-unavailable recovery and deduplication, and distinguish awaiting-review, failed/incomplete, and merged/done copy.
- [ ] Relevant Python and Swift test suites pass, including voice-bridge preemption, PM frontstage traces, orchestrator worker lifecycle, messenger delivery, and `StateEventBus` behavior.
