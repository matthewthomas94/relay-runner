## Description

Change the orchestrator and board lifecycle so tickets do not appear in Done until the worker result has been reviewed and merged into the source branch.

The current behavior can surface a completed worker as `done` before review/merge, or otherwise make awaiting-review work look indistinguishable from merged Done work. That makes the board overstate completion and can imply dependents are safe to progress before the human/orchestrator has accepted the worker branch.

Desired lifecycle:

- Worker claim still moves the source ticket into `in_progress` with the active `run_id`.
- Worker completion should produce an awaiting-review/run-succeeded state without publishing source-branch `status: done`.
- The ticket may still be marked `done` inside the worker branch/run log as implementation evidence, but that state must not become visible on the source Workspace/board until review accepts and merges the branch.
- Review accept/merge is the publication point for `done`.
- Merge conflicts, retries, failures, and cancellations must not leave the source ticket incorrectly in Done.

Update code, tests, and documentation/spec text that still describes "Done with awaiting merge" as acceptable source-board behavior.

## Acceptance criteria

- [ ] A running worker keeps the source ticket visible as `in_progress` or the equivalent active/awaiting-review board state, not `done`.
- [ ] A worker that succeeds and awaits review does not make the source Workspace/board place the ticket in Done before `review_run(decision=accept)` merges the worker branch.
- [ ] `review_run(decision=accept)` remains the only path that publishes the worker branch's `status: done` ticket update into the source branch.
- [ ] `review_run(decision=retry)`, failed runs, canceled runs, stalled runs, and merge conflicts do not publish `done` to the source ticket.
- [ ] Dependency progression only treats a predecessor as done after accepted merge publication, not merely after worker success/awaiting review.
- [ ] Board/program status copy distinguishes awaiting-review work from merged Done work without using a Done column placement for unmerged results.
- [ ] Existing provider behavior stays equivalent for Codex and Claude workers.
- [ ] Python orchestrator tests cover worker success awaiting review, accept merge, retry, failure/cancel, merge conflict, and dependency progression.
- [ ] Swift board/status tests cover the user-visible lane/status projection where practical.
- [ ] Relevant docs/specs are updated so they no longer describe unmerged worker success as Done.
