## Description

The user set Relay Runner up on a friend's MacBook today, a fresh install of the current release. At the tutorial step that asks the user to press Caps Lock to start speaking, Caps Lock did nothing: every press failed to start recording, so the friend was stuck. On the user's own machine it works. Nothing else is known about the friend's Mac (keyboard layout, language, permissions).

Relevant code: `Sources/relay-runner/STT/CapsLockGesture.swift` (NSEvent `flagsChanged` monitors), `Sources/relay-runner/Onboarding/OnboardingSessionControlsTutorial.swift` (`RecordingGate`), `OnboardingController.swift` / `OnboardingView.swift` tutorial steps, and the permission steps before them.

Investigate, in order, and state which of these the code can and can't rule out:
- **Permissions.** A global `flagsChanged` monitor sees nothing when Accessibility / Input Monitoring isn't granted, or is granted to a different binary. Can onboarding reach the tutorial without the permission the gesture needs actually being live, for example granted but not effective until relaunch? Is microphone permission checked before the recording gate?
- **Caps Lock owned by macOS.** With more than one input source, macOS defaults to "Use Caps Lock to switch to and from ABC", which takes short presses. Caps Lock may also be remapped under Keyboard > Modifier Keys. Can the app detect either (e.g. `com.apple.HIToolbox` / `AppleCapsLockSwitchesInputSource`, `hidutil property --get UserKeyMapping`)?
- **Monitor lifecycle.** Is the gesture monitor installed and armed when the tutorial step appears? Look for generation or ordering bugs (`monitorGeneration`), a recording gate waiting on a state that never comes, and the tutorial starting before the speech/STT stack is ready (`prepareTutorialSpeech`).

Added later by the user: the tutorial step may not have appeared at all for the friend ("it just didn't appear, or the Caps Lock just wasn't working"). Treat "the tutorial's recording step never showed" as a second possible failure and check what can stop it appearing: a permission or readiness gate never passing, a step that silently fails to render, or a resume state that skips it.

A further lead: both laptops are company-managed Macs with the same MDM. An MDM privacy (PPPC/TCC) profile can deny Input Monitoring or Accessibility in a way the user can't override in System Settings, so a global `flagsChanged` monitor would get nothing. Check whether the app can detect that the permission is effectively denied, not merely un-prompted, and make sure onboarding says so instead of waiting forever.

Then fix what you find, and add these regardless of cause:
- If the tutorial's recording step sees no recording start within a few seconds of a Caps Lock press, or no Caps Lock event at all, it shows a short reason (permission missing, Caps Lock switches input source, etc.) with a one-click fix, for example opening the right System Settings pane. That hand-off goes through RR-514's hide-the-workspace helper if RR-514 has merged by then.
- Recording can also be started by clicking a button on that step, so the tutorial can always be completed.
- Log enough (no key contents) that a future report like this can be diagnosed from the app's logs.
