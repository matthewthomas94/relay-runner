## Description

The current voice bridge recovery fixes have not prevented repeated silent failures after a Codex job completes or the terminal-side listener hangs for too long. In this failure mode the Relay Runner app is still running and accepts voice input, but the command is effectively sent into the void because the terminal-side bridge no longer hands it to Codex.

Add an app-side recovery path for missing terminal responses. When Relay Runner sends a voice command to the active Codex session and does not receive the expected bridge/terminal acknowledgement or response within a bounded timeout, the app should recover the same session instead of dropping the command.

The intended behavior is:

- detect that the active terminal-side bridge is not responding;
- refire the bridge startup path for the same terminal/Codex instance where possible;
- preserve the pending voice command and its metadata;
- resend the command after recovery so Codex receives it once;
- avoid creating duplicate visible tickets or duplicate command effects if the original command eventually arrives late.

This should be treated as the fallback recovery path because previous daemon-survival fixes have not been reliable enough. The app should make failed delivery visible rather than allowing voice commands to disappear silently.

## Acceptance criteria

- [ ] Relay Runner detects when a sent voice command has not produced the expected terminal/bridge acknowledgement within a documented timeout.
- [ ] On timeout, Relay Runner attempts to restart or refire the bridge path for the same active Codex session without requiring the user to manually start a new session.
- [ ] The original voice command payload and Relay metadata are preserved across recovery and resent after the bridge is ready.
- [ ] Replayed commands keep newest-intent and stale-action semantics: a superseding newer command must prevent stale replay side effects.
- [ ] Late delivery of the original command does not cause duplicate ticket creation, duplicate dispatch, duplicate TTS, or duplicate command execution.
- [ ] Recovery failure is surfaced in the app/notch instead of silently accepting more voice input into a broken bridge.
- [ ] The behavior is provider-aware: Codex recovery is implemented first, and Claude parity or any intentional provider difference is documented.
- [ ] Add regression coverage for timeout detection, successful replay, stale replay suppression, duplicate suppression, and recovery failure surfacing.
