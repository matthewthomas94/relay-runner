## Description

Change Relay Runner message handling so every incoming Relay message can steer the active conversation immediately, even when the previous spoken request is still being executed.

The current voice-loop shape can behave like a serial queue: the agent handles the first message, finishes its response, then ingests the next one. The desired product behavior is that a new Relay message becomes active user intent as soon as it arrives. If the user redirects, interrupts, or refines the task, the active agent should stop following stale instructions and continue from the newest instruction.

Define and implement a safe preemption policy. Reversible or not-yet-started work can be canceled or redirected. Already-completed actions should be reported honestly. High-stakes or irreversible actions should not be newly started from stale instructions after a newer Relay message arrives.

Provider parity matters. Codex and Claude should get equivalent message-steering semantics, even if the integration points for interrupting or updating an active run differ by provider.

## Acceptance criteria

- [ ] A Relay message received during active execution is surfaced to the active agent promptly instead of waiting for the prior request to finish.
- [ ] Newest user intent supersedes stale instructions for future work in the active run.
- [ ] Stale TTS or response output is canceled, replaced, or clearly prevented from speaking over the newer instruction.
- [ ] The implementation defines what happens to in-flight shell commands, MCP calls, and high-stakes actions when a newer Relay message arrives.
- [ ] Codex and Claude integrations have equivalent steering behavior or documented provider-specific limitations.
- [ ] Tests or a deterministic harness cover two rapid Relay messages where the second message redirects the first before completion.
- [ ] Regression coverage ensures ordinary single-message voice sessions still work.
