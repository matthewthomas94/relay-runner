## Description

Phone side of the Mac-voice decision; RR-457 defines the `speech_audio` frames and the `audio` flag on `Speech`. The phone must play the Mac's own voice instead of `AVSpeechSynthesizer`, and the user wants a playback-mode setting: **auto-play** (default, matches the Mac) or **play on demand**.

Today `SpeechPlaybackQueue` (`ios/RelayRemoteKit/Sources/RelayRemoteKit/SpeechPlayback.swift:26`) plays text frames in seq order through the `SpeechSynthesizing` protocol, honours `speech_control`, and acks exactly once per seq after playback (`flushAcks`, :170). The Mac pops its realization on the first ack, so acks must still be sent only when a frame is played (or deliberately skipped).

Work:

1. **Audio assembly.** The queue collects `speech_audio` parts per seq, plays them in part order as they arrive (streaming playback with `AVAudioEngine`/`AVAudioPlayerNode` or sequential `AVAudioPlayer` per part with gapless scheduling), and treats the text frame as the unit for acks. If a `speech` frame says `audio: true` but no part arrives within a short wait (start at 1.5 s, configurable), fall back to synthesising the text locally and log it; if `audio: false`, synthesise as today.
2. **Playback mode setting** on the phone, persisted, default auto-play. In play-on-demand mode frames queue unplayed, the UI shows the latest reply with a Play control, and the `played` ack is sent only when the user plays it. Stop, replay and cancel behave the same in both modes. Starting to talk still interrupts (RR-455).
3. **Agent state.** Expose playback state (idle, buffering, playing) from the queue so the UI's state label and blob can follow it; the current main screen shows the label.
4. **Audio session.** Keep the existing `AudioSessionController` behaviour for lock-screen and background playback; streamed audio must survive a lock during a reply and resume correctly after reconnect without playing a frame twice (reuse the resume rules the queue already has).
5. **Tests** in `RelayRemoteKitTests/SpeechPlayback` with a fake audio player and fake synthesiser: parts assembled in order, out-of-order part arrival, fallback after the wait, ack exactly once per seq after playback in auto mode, ack deferred until Play in on-demand mode, stop/skip during streaming, and resume after a `welcome` with lower `serverSeq`.

Physical-device checks cannot run in the worker environment. Cover behaviour with the kit, app, Python and Swift unit tests plus the existing loopback tests, and name the manual iPhone check for the user in the run log; do not mark acceptance that needs the phone as verified.

## Acceptance criteria

- [ ] Streamed `speech_audio` parts play in order through the injected player and the seq is acked once after playback; text-only frames still use the synthesiser (tests).
- [ ] Missing audio falls back to local synthesis after the configured wait and is logged (test).
- [ ] Play-on-demand defers both playback and the ack until the user plays; auto-play behaves as today (tests).
- [ ] Stop, skip and interrupt during streamed playback stop the player and leave the reply replayable (tests).
- [ ] Reconnect replay does not play any seq twice (test).
- [ ] Kit and app tests pass; run log names the manual iPhone check (hear Puck, not the Apple voice; lock the phone mid-reply; switch modes).
