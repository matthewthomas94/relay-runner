## Description

The orchestrator daemon's dependency-progression code path (the bit that auto-flips a `backlog` ticket to `ready` when its predecessor lands in `done`) is silently broken. Every time a Succeeded worker completes, the daemon's error log shows:

```
[orchestrator] dep-progression error for RR-9: No module named 'tickets'
[orchestrator] dep-progression error for RR-11: No module named 'tickets'
```

The error originates at `services/orchestrator.py:674` inside `_progress_dependents`:

```python
from tickets import scan_repo, write as write_ticket, all_deps_done
```

This is a lazy import inside the function. `tickets.py` lives in the same directory as `orchestrator.py` (`services/`), so when the daemon is launched as `python services/orchestrator.py`, `sys.path[0]` is that directory and the import should succeed. Something in the daemon's launch path (likely the bundled `.app` invocation) is causing the module to be unfindable in the worker-completion thread context.

Concrete impact (observed twice this session): tickets with `depends_on:` predecessors do NOT auto-promote when those predecessors complete, so the orchestrator has to manually flip them from `backlog` to `ready` and call `dispatch_ticket` to keep the chain moving. The whole point of dependency declarations is undermined.

## Acceptance criteria

- The dep-progression import succeeds at runtime — no `No module named 'tickets'` errors in `/tmp/relay_orchestrator.err` after a Succeeded run completes.
- Verification: dispatch a ticket pair where ticket B has `depends_on: [A]` and both are in `backlog`. Move A to `ready` and dispatch. When A succeeds and is merged to main, B should auto-promote from `backlog` to `ready` and be dispatched by the daemon **without** any manual intervention. The daemon log should show a dispatch line for B shortly after A's completion, with no dep-progression error.
- Pick the right fix mechanism:
  - **Option A:** Move the import to module top (`from tickets import ...` at the top of `orchestrator.py`). Verify no circular-import regression at startup.
  - **Option B:** Use an absolute path import via `importlib.util.spec_from_file_location` referencing the file's actual filesystem location (resolved relative to `Path(__file__).parent`). More robust against weird launch contexts.
  - **Option C:** Make `services/` a proper package (add `__init__.py`) and use `from .tickets import ...`. Lowest-magic fix, but requires verifying nothing else in the daemon assumes a script-style invocation.
  - The reviewer should pick whichever has the lowest risk and best matches how the project structures Python modules elsewhere — but document the reasoning briefly in the commit message.
- No regression in the daemon's other code paths. `swift build` and a manual smoke test (dispatch any ticket and watch it complete normally) should still work.
- Don't touch the bundled `.app`'s scripts — DMG-build action is the source of truth.
- Commit message references RR-14.
