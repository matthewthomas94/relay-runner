## Description

Whenever a Relay Runner project has tickets in Queued or In progress, it should maintain a durable queue-drain goal and continue orchestrating until every actionable ticket is genuinely integrated. Tickets may enter one after another while the goal is active; they must join the same rolling drain cycle rather than being left for a later manual `continue`. The goal must not stop at dispatch, worker success, or `AwaitingReview`: implementation workers must finish, review/merge workers must accept the changes, and each ticket must be published as `done` on the target source branch.

The core liveness invariant is that every Queued or In progress ticket has one of:

- a live implementation or review/merge worker with current heartbeat/activity;
- a durable scheduled next action that will claim available capacity within a bounded time;
- an explicit unresolved dependency that automatically wakes the ticket when its predecessor is merged; or
- a visible actionable blocker with an owner and required next step.

A ticket must never sit in Queued or In progress because a sweeper, review callback, retry, or provider turn silently stopped. Detect stale ownership and recover it once through an idempotent path; bounded retry exhaustion must become a visible blocker rather than an arbitrary loop.

Build this on the existing ready sweeper, dependency progression, automatic review-worker handoff, and merge-only Done publication. The rolling goal is the missing persistence, liveness, and terminal-condition layer. Codex sessions should use the supported Codex/ChatGPT goal lifecycle. Claude sessions should use a verified native equivalent when the installed Claude surface exposes one; otherwise Relay Runner must provide equivalent durable queue-drain semantics rather than inventing or depending on a nonexistent Claude API.

The goal should survive ordinary foreground turns, idle periods, Relay session recovery, and app/daemon restarts without requiring the user to say `continue`. Progress should be event-driven or use bounded monitoring rather than consuming model tokens in a tight polling loop. New tickets entering Queued or In progress while a drain is active become members of that drain. After a verified quiescence window with no remaining actionable, reviewing, retrying, or conflicted tickets, the provider goal may complete. A ticket queued after completion should automatically start a new drain goal.

Completion means all tickets observed in the drain have accepted review evidence, their worker changes are merged into the intended target branch, their source ticket files are `done`, and no run remains active, awaiting review, retrying, stale, or conflicted. Dependency-blocked tickets keep the goal in a visible waiting state and automatically resume when their dependencies merge. Only verified quiescence should mark the provider goal complete and emit the final outcome. Do not add an automatic release, build, install, push, or deployment after completion; the requested terminal action is the reviewed merge itself.

## Acceptance criteria

- [ ] The first ticket entering Queued or In progress creates one idempotent drain record with a stable ID, repository, target branch, provider, observed ticket IDs, and durable goal state.
- [ ] Tickets entering Queued or In progress while the drain is active join it automatically; unrelated Backlog tickets remain out of scope unless they are required predecessors or the user queues them.
- [ ] A ticket queued after a completed drain automatically starts a new drain without requiring a foreground `continue`.
- [ ] Codex uses its supported create/read/update goal lifecycle so the foreground goal remains active until the rolling drain terminal condition is met.
- [ ] Claude uses its verified equivalent goal capability when available; if none exists in the installed Claude surface, Relay Runner supplies equivalent durable continuation and completion semantics and documents the provider difference.
- [ ] The goal survives provider turn completion, idle time, voice-session recovery, Relay Runner relaunch, and orchestrator-daemon restart without a manual `continue`.
- [ ] Every Queued or In progress ticket exposes a live worker, a bounded scheduled next action, a specific unresolved dependency, or an actionable blocker; no ticket can remain in those lanes with an ownerless or unexplained state.
- [ ] Eligible tickets dispatch automatically subject to configured concurrency; capacity-waiting tickets expose their durable reason and wake automatically when a slot opens.
- [ ] Dependency-gated tickets name their unresolved predecessors, keep the drain visibly waiting, and progress automatically when those predecessors are reviewed and merged.
- [ ] Every successful implementation run automatically receives the existing independent review/merge worker, and accepted work merges through the daemon path.
- [ ] Stale claimed/running/reviewing ownership is detected from durable heartbeat/activity, recovered idempotently, and never left spinning in an arbitrary retry loop.
- [ ] Worker failure, incomplete verification, review rejection, and retryable review-worker failure follow a bounded retry path without completing the drain early or duplicating effects.
- [ ] Merge conflicts, exhausted retries, cancellation, missing authority, broken dependencies, and other non-automatic decisions leave the drain durably blocked or canceled with the affected ticket/run, owner, and required next action.
- [ ] The drain cannot complete while any observed ticket is ready/in progress, any observed run is active/awaiting review/retrying/stale/conflicted, any dependency could still progress, or any accepted worker commit is absent from the target branch.
- [ ] Completion requires a documented quiescence window, then verifies that every observed source ticket is `done`, every accepted change is reachable from the target branch, every worktree/throwaway branch is pruned according to policy, and no observed run remains unfinished.
- [ ] Relay Runner emits concise, deduplicated drain progress and one final completion outcome without exposing raw transcripts, hidden reasoning, or unbounded worker logs.
- [ ] New user commands can inspect, steer, cancel, or extend the rolling drain without weakening newest-intent safeguards or losing durable liveness state.
- [ ] Monitoring is event-driven or bounded and does not keep Codex or Claude spending tokens merely to poll unchanged state.
- [ ] Automated tests cover tickets arriving sequentially, multi-ticket success, dependencies, capacity waits, concurrent workers, stale ownership, review retry, worker failure, merge conflict, restart/resume, cancellation, idempotent recovery, quiescence races, false-completion prevention, and Codex/Claude parity.
- [ ] Documentation states the queue liveness invariant and distinguishes active, scheduled, dependency-waiting, blocked, awaiting review, accepted merge, canceled, and truly complete states, with no implied post-merge release/deploy action.
