## Description

The Relay PM/backstage loop still has two rough edges that make orchestration feel unreliable:

1. When a voice conversation settles into a concrete ticket request, the backstage ticket authoring path can still create a vague visible ticket with a title/body like "Write ticket also orchestrator was meant review" instead of refined, cold-start-safe work.
2. A completed worker run can sit in `AwaitingReview` without an obvious PM follow-through, while the project board may still appear to show the original ticket in backlog if the source ticket was dispatched manually.

Tighten the command-action flow so visible tickets are created from refined, user-safe PM context and acceptance criteria, not from lossy raw-command summaries. Also make completed worker review states hard to miss: when a run reaches `AwaitingReview`, the PM/frontstage and board/status surfaces should make the next action clear within a bounded interval.

This should preserve the existing private raw Relay metadata model: raw transcripts remain private command metadata, while visible tickets contain refined implementation summaries.

## Acceptance criteria

- [ ] Backstage-created visible tickets include a specific title, description, and acceptance criteria derived from PM-refined context rather than a vague raw-command summary.
- [ ] A voice command that asks to turn an ongoing conversation into a ticket has access to enough sanitized conversation context to produce a cold-start-safe ticket.
- [ ] Raw Relay transcripts, hidden reasoning, tool logs, and shell output remain out of visible `.orchestrator/*.md` tickets.
- [ ] The PM/frontstage reports a clear user-facing outcome when a ticket is created, refined, dispatched, blocked, or waiting for review.
- [ ] Runs that enter `AwaitingReview` surface a clear review/merge next step in board/status feedback without appearing like untouched backlog work.
- [ ] Manual dispatches from backlog are covered: a review-pending run still appears as review-pending work until accepted or retried.
- [ ] Provider parity is covered for Codex and Claude command-action prompts and review-follow-through behavior.
- [ ] Add regression coverage for generic-ticket prevention, sanitized context handoff, review-pending status surfacing, and manual-dispatch review placement.
