## Description

Research and recommend the backing architecture for Relay Runner's Graphify layer when indexing many local repos.

The user explicitly does not want a "grep harder" approach. Compare a pragmatic SQLite-only MVP against richer options such as SQLite plus Kuzu, Tree-sitter-based structural indexing, SCIP-style code intelligence, and optional vector/hybrid retrieval. Use primary sources where current technical claims matter.

The output should be an implementation-ready research note in the repo, with a recommendation for the MVP and clear deferrals for post-MVP work.

Provider parity matters indirectly: the graph/indexing layer should support program visibility for Codex and Claude worker runs without assuming either provider owns the data model.

## Acceptance criteria

- [ ] A new research document compares at least three architecture options for Graphify/indexing.
- [ ] The comparison includes storage, query model, incremental update strategy, expected local complexity, and macOS app integration impact.
- [ ] The recommendation identifies the MVP backend and explains why it is sufficient.
- [ ] The note distinguishes Graphify Core program graph data from deeper code/symbol indexing.
- [ ] The note proposes measurable spike criteria: cold index time, incremental update time, query latency, disk footprint, and implementation complexity.
- [ ] The note includes source links for external technical claims.
- [ ] Provider-neutral run/ticket data is explicitly accounted for.
- [ ] The worker runs an appropriate lightweight verification command for docs-only changes or explains why none is needed.
