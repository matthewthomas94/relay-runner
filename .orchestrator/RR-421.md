## Description

Spec: `docs/specs/relay-remote.md` (Relay Remote: iOS voice over SSH), committed as `2a64cc0d` on branch `claude/ios-relay-ssh-tcp-spec-ddb8f2`. The iOS app keeps speech on the phone: on-device speech-to-text produces `utterance` frames, and on-device text-to-speech speaks the `speech` frames the Mac sends back; only text crosses the wire. The spec names two candidate stacks and does not pick one.

Compare them with public evidence pinned to a commit SHA or a dated document:

- FluidAudio on iOS: the STT models (Parakeet TDT v3, Parakeet EOU for end-of-utterance, Phonon-2), the TTS models (Kokoro, PocketTTS), minimum iOS version, on-device model sizes and download or caching behaviour, and what the project states about validation on iPhone hardware as opposed to macOS. Recommend the first-ship STT engine, TTS engine, and the resulting iOS deployment target (iOS 18 or iOS 26). Name the parity gaps between the phone path and the Mac path (the Mac uses FluidAudio for STT and Kokoro for TTS): different voices, different end-of-utterance behaviour, anything the phone cannot do.

**Conclusions**

- Recommended first-ship stack: STT = Apple SpeechAnalyzer/SpeechTranscriber, TTS = AVSpeechSynthesizer (Enhanced or Premium system voices), deployment target = iOS 26. Confidence is moderate. The reasons are that Apple manages the model outside the app, there is no model download for the app to ship, and Apple's engines are first-party on iPhone. FluidAudio's own README makes no explicit iPhone validation claim.
- The Mac's pinned FluidAudio revision 0b1f46289fe27d95b5e66ad8be46e64f5ee02ae7 does support iOS at the package level. Its Package.swift declares platforms macOS .v14 and iOS .v17, and the library product is separate from the macOS-only CLI. Phonon-2 needs iOS 18+ / macOS 15+, so FluidAudio on iOS would set an effective floor of iOS 18 if Phonon-2 were used. TDT v3 and Kokoro have no stated per-model OS floor.
- FluidAudio STT options: Parakeet TDT v3 (0.6B, 25 European languages, library default); Parakeet EOU (120M, English-only streaming with end-of-utterance detection); Phonon-2 (English-only, default encoder 321 MB, alternatives 176–470 MB). Only Phonon-2 has a published size. The README says 'CLI is available on macOS only. For iOS, use the library programmatically.' It makes no explicit claim that models were validated on iPhone hardware. The macOS evidence is a ~190x RTF on M4 Pro.
- FluidAudio TTS options: Kokoro (82M parameters, README says American English only in the TTS section but lists more languages in the highlights, so the two statements conflict) and PocketTTS (about 155M parameters, streaming, voice cloning, EN/DE/ES/FR/IT/PT). Neither has a published download size in the cited docs. Models auto-download from HuggingFace on first use, with an offline-mode flag and a custom registry option. The only documented cache path is a macOS-style path (~/.cache/fluidaudio/Models/kokoro/), and its iOS sandbox equivalent is unstated.
- Apple STT: SpeechAnalyzer/SpeechTranscriber is new in iOS 26. WWDC25 session 277 says it runs on-device, does not increase the app's download size, storage or runtime memory, and has model assets installed via AssetInventory with automatic system updates. It offers volatile results (provisional) and finalized results (stable), and finalizeAndFinishThroughEndOfInput() forces pending results to finalize. DictationTranscriber covers locales or devices SpeechTranscriber does not, using the same model and languages as on-device SFSpeechRecognizer.
- End-of-utterance: the WWDC25 session does not document automatic endpointing. Finalized results cover non-overlapping audio ranges, but how range boundaries are chosen is not specified. The phone path will probably need an app-side utterance boundary (a silence timer or push-to-talk plus explicit finalization). This is the largest behavioural risk of the Apple route. The Parakeet EOU model is the only candidate here that offers a model-level end-of-utterance signal, and it is English-only.
- Apple TTS: AVSpeechSynthesizer is the zero-download option. A developer-forum report says Default-quality voices sound much worse than Enhanced and Premium voices, and the app cannot detect or trigger Enhanced/Premium downloads (only the user can, via Settings). Voice sets can change at runtime (availableVoicesDidChangeNotification). Latency and iOS 26 quality changes were not found in public evidence.
- Parity gaps versus the Mac path (FluidAudio STT, Kokoro TTS): phone voices differ from Kokoro; end-of-utterance comes from app-side logic, not FluidAudio streaming; transcript punctuation and number formatting will differ from Parakeet/Phonon; language coverage follows Apple's supportedLocales (not listed in the cited material); first run depends on AssetInventory download and installed voices; no Kokoro custom/imported voices or cloning on the phone unless FluidAudio TTS is added later.
- Fallback if iOS 26 is too high a floor: iOS 18 with on-device SFSpeechRecognizer (requiresOnDeviceRecognition) for STT, plus AVSpeechSynthesizer. This was assessed only from general API knowledge, because the Apple reference pages did not render. Alternatively, use FluidAudio on iOS 18+ (Phonon-2 or Parakeet EOU for STT, Kokoro for TTS). That would give closer Mac parity but carries hundreds of MB of downloads and no stated iPhone validation.
