## Description

The final Relay Remote iPhone design (`docs/design/relay-remote-ios/README.md`) needs things the wire protocol cannot carry today. This ticket defines the contract and lands it everywhere it must agree, so that the Mac tickets and the iPhone tickets can then run in parallel against it. It adds no user-visible behaviour by itself.

**Today**

- The protocol (`Sources/RelayRemoteProtocol/Frames.swift`, Rust twin `rust/relay-rs/src/remote/protocol.rs`, spec `docs/specs/relay-remote.md`) has `utterance`, `control`, `speech`, `speech_audio`, `speech_control`, `accepted` and `status` frames with no agent identity. A remote utterance goes to whichever voice target is focused on the Mac (`RemoteItem` in `rust/relay-rs/src/bridge/remote_link.rs` has no agent field).
- `session_state` reports `active_agent` and `running_agents`, but no per-agent state (working, listening, playing back).
- `session_command` `start` requires a `project_id`.
- There are no frames for the Workspace ticket list or for reading and changing Mac settings. The spec lists choosing the model from the phone and push notifications as non-capabilities.

**Wanted: additive protocol changes** (optional fields and new frame types, so an older peer keeps working). Suggested shapes; you may refine names and details while reading the code, but the Swift and Rust codecs must stay identical and the spec must document exactly what ships:

1. **Agent addressing.** `utterance` and `control` gain an optional `agent` (`puck`, `isabella`, `george`, `sky`). `accepted`, `speech`, `speech_audio`, `speech_control` and `status` gain an optional `agent` naming the agent the frame belongs to. Absent means today's behaviour (the focused target).
2. **Per-agent state.** `session_state` gains `agents`: one entry per agent with `agent`, `running`, a `state` of `off`, `starting`, `ready`, `working`, `listening` or `playing`, and an optional short `working_on` string. It is pushed when any of these change.
3. **Start without a project.** `session_command` `start` accepts a missing `project_id`, meaning the built-in general-tasks context that the desktop's Start Session uses by default.
4. **Workspace feed.** A `workspace_command` (`list`) answered by a `workspace_state` carrying `projects` (`id`, `name`) and `tickets` (`id`, `title`, `status` of `in_progress`, `queued` or `backlog`, `project_id`, optional owning `agent`).
5. **Settings.** A `settings_command` (`get`, or `set` with only the keys to change) answered by a `settings_state` carrying the current values of speech speed, orchestrator provider, model, effort and sub-agent sizing, plus the allowed options for model, effort and sizing so the phone never hard-codes the catalogue, and an `error` when a `set` is refused.

**Work**

- Add the frames and fields to both codecs with shared golden vectors, as the existing frames have.
- Update `docs/specs/relay-remote.md`: the wire protocol, session control, and the non-capabilities paragraph (choosing the model from the phone is now in scope; push notifications stay out, replaced by local notifications while the app runs in the background).
- **Kit client API** (`ios/RelayRemoteKit`): `RemoteSession` (and `MacSessionStatus` or a sibling) can send an utterance and a control to a named agent, exposes received frames' agent, publishes per-agent state, and can request the workspace list and get and set settings. Cover each with tests against the scripted transport the kit tests already use.
- **Mac stubs.** Route the new commands to three new, separate handler files so the follow-up tickets do not collide: one for agent routing and state, one for the workspace feed, one for settings. Until those tickets land, each stub answers correctly formed but empty or "unsupported" replies (for example an `error` frame with a clear code, or a `settings_state` with an `error`), and `agent` on an utterance is accepted and ignored. Whether a command is served by the app's session-control socket (`RelaySessionControl.swift`, reached through `Sources/relay-remote-shell/main.swift`) or by the Rust bridge is your call; record the choice in the spec.

## Acceptance criteria

- [ ] The Swift and Rust codecs encode and decode every new frame and field, and both pass the same golden vectors, including vectors without the new optional fields.
- [ ] Frames from a peer that sends none of the new fields decode and behave exactly as before; the existing protocol, bridge and kit tests still pass unchanged.
- [ ] `docs/specs/relay-remote.md` documents every new frame and field, which side serves each command, and the updated non-capabilities.
- [ ] `RelayRemoteKit` exposes the client API described above, with tests for: sending to a named agent, receiving agent-tagged speech, per-agent state updates, a workspace list round trip, and settings get and set including a refused set.
- [ ] On the Mac, each new command reaches its own stub handler file and gets a well-formed reply; an utterance with `agent` set is delivered as it is today.
- [ ] `swift build`, `swift test`, `cargo test` (in `rust/relay-rs`) and `cd ios/RelayRemoteKit && swift test` pass.
