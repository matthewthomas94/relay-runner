## Description

Decision (2026-11-03): the user does not want Apple's voice on the phone. The Mac synthesises replies with its configured voice (Kokoro, or a custom voice through `ConversionClient`) and streams the audio to the phone per sentence as it is produced. This deliberately retires the "no audio on the wire" non-goal in `docs/specs/relay-remote.md` (lines 7, 21, 23, 30, 99, 116-117, 135-136, 183, 193, 197) for Mac-to-phone speech only; phone-to-Mac stays text. This ticket is the protocol plus Mac side; RR-458 is the phone side.

Today when a remote sink is active, `SpeechCoordinator._submit_remote_locked` (`services/speech_coordinator.py:1148`) sends a text `speech` frame and never touches Kokoro. `TTSWorker` (`services/tts_worker.py`) splits replies with `_sentence_chunks()` (:44), synthesises each chunk to a mono 16-bit WAV at Kokoro's sample rate (24 kHz) in `_synthesize_to_wav` (:815), and plays through `SpeechPlayer`. Every protocol line is capped at 64 KiB (`RelayRemoteProtocol.maxLineBytes`, the shell, `LineFramer`), so one second of raw PCM does not fit; audio must be compressed and chunked.

Work:

1. **Protocol.** New Mac-to-phone frame `speech_audio`: `seq` (the `seq` of the `speech` frame it voices), `part` (0-based), `parts` (total for that seq, or 0 while unknown with a final `last: true`), `format` (`aac` or `opus`), `sample_rate`, `data` (base64, at most 32 KiB per frame), plus the ordinary replay bookkeeping. Add `audio: Bool` to `Speech` so the phone knows audio will follow. Replay buffers must replay audio parts with their text frame. Protocol changes go in `Sources/RelayRemoteProtocol/Frames.swift` with the Python twin `services/relay_remote_protocol.py` kept identical, new golden vectors under `tests/RelayRemoteProtocolTests/Vectors/`, and `RelayRemoteProtocol.version` left at 1 because both decoders ignore unknown keys; an unknown frame *type* is rejected by the Python server and logged by the phone, so bump the version only if an older peer would misbehave, and say why in the run log.
2. **Synth-only path.** Add a coordinator route for remote sinks that enqueues the text to `TTSWorker` in a synthesise-only mode: per sentence chunk, synthesise (Kokoro or custom voice), encode, and hand the encoded bytes to the remote sink as `speech_audio` parts immediately, before the next chunk is synthesised. Do not open the Mac's `SpeechPlayer` or take a `VoiceAudioLease` in this mode. Preserve the existing text `speech` frame first so the phone can show text at once and fall back to its own voice if audio does not arrive. Stops (`new_turn`, `stop`, `stop_playback`, `skip`) cancel pending synthesis and still emit `speech_control`.
3. **Encoding.** Use macOS built-ins: AAC-LC at 48 kbps in an M4A/CAF container through AudioToolbox (via `afconvert` or `ExtAudioFile`), or Opus if the toolchain supports it; record the choice and measured bytes per second in the run log. Target about 3 to 6 KB/s. Chunks are split into parts of at most 32 KiB base64.
4. **Remote mode off** (RR-454): the Mac speaks locally and sends text only, as before. **Fallback:** if encoding fails, send the text frame with `audio: false`.
5. **Latency measurement.** Log, per reply, the time from coordinator submit to first `speech_audio` part emitted, and expose it in the existing diagnostics so the user can compare Wi-Fi, Tailscale and cellular later.
6. **Spec.** Update `docs/specs/relay-remote.md` at the lines above to describe Mac-to-phone audio, the fallback, and the unchanged text-only phone-to-Mac direction.

Tests: Python `tests/test_speech_coordinator_remote.py` and a new `tests/test_tts_worker_remote_audio.py` with a fake synthesiser and encoder covering per-sentence emission order, part splitting at the size cap, stop cancellation, replay of audio parts, and the fallback flag; codec vectors in both languages; `tests/test_relay_remote_loopback.py` extended to carry audio parts end to end.

Physical-device checks cannot run in the worker environment. Cover behaviour with the kit, app, Python and Swift unit tests plus the existing loopback tests, and name the manual iPhone check for the user in the run log; do not mark acceptance that needs the phone as verified. The worker cannot hear the result; a Python test that decodes an emitted M4A/Opus part back to PCM length is the proof of a valid encoding.

## Acceptance criteria

- [ ] With a remote sink active and Remote mode on, a reply produces one text `speech` frame with `audio: true` followed by `speech_audio` parts per sentence, in order, each at most 32 KiB of base64, and no Mac audio device is opened (Python tests with fakes).
- [ ] Stops cancel remaining synthesis and emit `speech_control`; replay after reconnect replays the text frame and its audio parts (Python tests).
- [ ] An emitted part decodes to valid audio with the expected duration (Python test using the real encoder on a short synthetic WAV).
- [ ] Encoding failure falls back to `audio: false` text frames (test).
- [ ] First-audio latency is logged per reply and surfaced in diagnostics (test asserts the log record).
- [ ] Spec updated; vectors round-trip in both codecs; Swift protocol tests, kit tests and the Python suite pass.
