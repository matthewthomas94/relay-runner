## Description

The validation/acknowledgement response that appears after the user sends a voice message currently arrives too soon and feels abrupt. The user likes the acknowledgement copy, but the visual timing is wrong: it can replace the recording/sent overlay before the send animation has had time to finish, and it snaps in instead of using the normal playback-style transition.

Adjust the post-send acknowledgement path so that after a recording is sent:

- the sent/recording completion animation is allowed to finish first;
- there is at least a short pause, roughly one second, before showing the acknowledgement;
- the acknowledgement enters using the same standard TTS/playback overlay transition behavior as normal playback responses;
- this visual delay does not delay command processing or actual TTS generation.

Likely touch points include `StateMachine.handleServiceEvent(source:newState:text:autoDismiss:)`, `OverlayController.applyState(_:)`, acknowledgement timers/dismissal, and `StateMachineAcknowledgementTests`.

## Acceptance criteria

- [ ] When a bridge acknowledgement arrives immediately after `.sent`, it is visually deferred until the sent/recording completion animation has finished plus about one second.
- [ ] The acknowledgement uses the normal TTS/playback overlay transition path rather than snapping directly over the recording/sent pill.
- [ ] If a substantive TTS `message_waiting`, `preparing`, or `speaking` state arrives before the delayed acknowledgement is displayed, the stale acknowledgement is suppressed.
- [ ] The delay affects only presentation timing; it must not delay command execution, worker dispatch, TTS generation, or other backend state handling.
- [ ] Existing acknowledgement behavior still works when the acknowledgement is not racing a just-sent recording.
- [ ] Tests cover an acknowledgement received during `.sent`, the delayed presentation, suppression when a substantive TTS response arrives first, and normal acknowledgement dismissal.
