## Description

Relay Runner can write a voice command into the integrated provider terminal, emit Return, and record a successful `submit` delivery event even though the provider leaves the text sitting unsent in its composer. From the user's perspective, the command appears in the terminal but Relay never receives it as a new turn, so requested actions such as queueing tickets do not happen and later commands may accumulate without a trustworthy delivery state.

Treat this as a live regression of RR-163 and RR-211. A PTY write is only a submission attempt; successful delivery requires an acknowledgement that the corresponding provider turn actually started. Tie that acknowledgement to the exact Relay command sequence and id without exposing raw command text. If acknowledgement does not arrive within a bounded interval, recover safely by retrying submission or restoring the composer/session state without executing the same command twice.

The supplied screenshot is not attached because it includes unrelated terminal and application content. Its relevant evidence is that two complete Relay prompts remained visible in the Codex composer with the cursor active, while sanitized delivery diagnostics recorded `prompt_write`, `claim_published`, and `submit` for those commands. The diagnostics therefore prove bytes were emitted, not that the provider accepted a turn.

## Acceptance criteria

- [ ] Relay distinguishes a submission attempt from a provider-acknowledged turn and does not report successful delivery solely because prompt and Return bytes were written to the PTY.
- [ ] A Codex command is acknowledged only after the corresponding user turn begins; the equivalent provider-specific acknowledgement is implemented for Claude.
- [ ] The acknowledgement is correlated with the exact Relay command sequence and id, and duplicate or stale acknowledgements cannot complete a newer command.
- [ ] If Return is emitted but the composer remains active and no provider turn starts, Relay detects the missing acknowledgement within a bounded timeout and retries or recovers automatically.
- [ ] Recovery is idempotent: a command that actually started cannot be executed a second time because its acknowledgement was delayed or temporarily unreadable.
- [ ] Back-to-back commands never concatenate, overwrite one another, or remain silently typed in the composer; each is either queued, submitting, recovering, acknowledged, or visibly failed.
- [ ] Newest-intent and busy-turn behavior remains correct when a newer voice command arrives during acknowledgement or recovery.
- [ ] Sanitized diagnostics record submission attempts, acknowledgements, timeout/retry/recovery outcomes, and exact sequence/id metadata without storing raw transcript text.
- [ ] Automated tests reproduce the escaped failure where prompt and Return writes succeed but the provider composer stays active, then verify recovery and exact-once execution.
- [ ] Regression coverage exercises both Codex and Claude delivery paths, consecutive commands, delayed acknowledgements, provider restart, and the installed/package-equivalent app.
- [ ] A manual installed-app smoke test confirms that a voice command visibly starts a provider turn and cannot remain silently unsent in the terminal composer.
