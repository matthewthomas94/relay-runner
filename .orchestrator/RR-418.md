## Description

In an artifact-enabled project, the Relay Runner app can write a ticket file straight into the projected `.orchestrator/` folder instead of going through the daemon's artifact writer. The daemon then sees a projection that no longer matches `materialization.json` and refuses every lifecycle action with "materialized .orchestrator was edited manually; use explicit Save/import". There is no import API, so the project stays stuck until someone re-materializes by hand.

Observed on 2026-10-19 with RR-416: runs 240 and 241 both failed at dispatch for this reason. The stray file's frontmatter (unquoted `id`, `order: 0`, the exact field order) matches `TicketWriter.render` in `Sources/relay-runner/Board/TicketWriter.swift`, so the app wrote it, not the daemon. Both stray writes landed within seconds of a forced re-materialization.

Likely mechanism: `TicketWriter.save` and `TicketWriter.delete` pick the artifact writer only when `BoardProjectConfig.usesArtifactWriter(forRepoAt:)` can read and parse `.orchestrator/config.toml`. Otherwise they silently fall back to a raw file write. `ArtifactStore._materialize` (`services/artifact_store.py`) swaps the whole folder with two `os.replace` calls, so `config.toml` is briefly missing. Any save in that window, or with an unreadable or partly written config, goes down the raw-write path. The app's file watcher firing on the swap may be what triggers that save (board drop, retry or editor save via `ProgramBoardStatus.swift` `ProgramBoardTicketMover.move` and the other `TicketWriter.save` callers). Confirm the exact trigger as part of this ticket.

Fix: make the app fail closed. Decide whether a project is artifact-managed from durable state that the projection swap can't hide, such as the registry-v2 project record or a cached decision for the project, not only the projected config. When that state says artifact-managed, or the answer can't be determined, never write or delete projected ticket files directly; surface a retryable save error instead. Non-artifact (schema 1) projects keep their direct write path unchanged.

## Acceptance criteria

- [ ] Reproduce in a test: with an artifact-enabled project whose `.orchestrator/config.toml` is temporarily missing or unparseable, `TicketWriter.save` and `TicketWriter.delete` do not touch files under `.orchestrator/` and report a retryable error.
- [ ] Artifact-managed detection survives the materialization swap. It is based on durable project state, with a test showing the decision stays "artifact-managed" while `config.toml` is absent.
- [ ] Schema-1 / non-artifact projects still save and delete via direct file writes. Existing TicketWriter and board tests pass.
- [ ] Identify and document (in the run log) which app path triggered the stray RR-416 writes, and confirm it now routes through the daemon or fails closed.
- [ ] Board drop to `ready`, editor save and delete in an artifact-enabled project still go through `/v1/artifacts/tickets/write` and `/v1/artifacts/tickets/delete`, with no regressions in dispatch-on-drop.
- [ ] Full Swift test suite passes, plus a signed build in the worker worktree. Do not install, touch /Applications, or restart the running app or daemon.

## Out of scope

- A daemon-side Save/import API for recovering a manually edited projection. Note it in the run log if it looks worthwhile.
- Changing how `ArtifactStore._materialize` swaps directories, unless the app-side fix alone proves insufficient.
