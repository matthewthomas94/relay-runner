## Description

With several project sessions open (RR-394/395/398), the only way to choose which session voice goes to is to open the Workspace and click a session tab. Add a global hotkey so the user can switch the voice target without opening the Workspace:

- **Shift+Right** focuses the next open session tab.
- **Shift+Left** focuses the previous one.
- The cycle wraps around at both ends.

**Order and switching.** Cycle in the same order the Workspace shows its tabs, which is `AppState.workspaceSessionTabs` (built from `sessionRegistry.liveContextIDs`; see `Sources/relay-runner/App/AppState.swift` around line 1220). Count only live sessions. Switch through the existing `AppState.focusSessionTab(contextID:)` (around line 1263), which leads to `syncVoiceFocus` stamping `sttEngine.voiceTargetSessionKey`. Do not add a second routing path. With zero or one live session the hotkey does nothing.

**Notch feedback.** After a switch, the notch briefly names the new target, for example **Switched to · vial-qmk** (the old name may also appear, e.g. "relay-runner → vial-qmk"). It then returns to its normal state. The next recording then shows **Listening · vial-qmk** through the existing `listeningVoiceTargetName` path. Add the transient label through `NotchVisualLabelAllowlist` / `NotchActivityLabelPlanner` in `Sources/relay-runner/Overlay/NotchStatusController.swift`, following RelayMotion swap rules (the old label exits, then the new one enters). Repeated presses update the label without stacking animations.

**While recording or playing:**

- A recording keeps the session it was stamped with when it started (`recordingVoiceTargetSessionKey` in `STTEngine.swift` around line 274). A switch during a recording applies to the next recording, and the notch should make that clear rather than imply the current utterance moved.
- If `focusSessionTab` defers or refuses a switch under the existing rules in `docs/specs/assistant-session-context.md` (for example unsubmitted terminal text, playback or outstanding approvals), show the outcome honestly, such as "Switch pending" or no change. Never show a switch that did not happen.

**Gesture detection.**

- Add a small testable gesture type next to `BoardHotkeyGesture` (`Sources/relay-runner/Board/BoardHotkeyGesture.swift`) or `NoteOptionGesture`.
- Feed it from the existing `CapsLockGesture` `.keyDown` monitor (around line 259). Only Shift may be held: no Command, Option or Control. Ignore key repeats, or rate-limit them.
- The arrow `keyDown` must still reach `boardHotkeyGesture.handleKeyDown()` so a Shift+Arrow never counts as a clean Shift tap. Holding Shift and pressing Left then Right must never toggle the board.
- Global key monitors here are passive `NSEvent.addGlobalMonitorForEvents` and cannot consume the event. That is accepted; see Decisions below.

**Out of scope.** Starting new sessions, closing sessions, reordering tabs, and changing which tab is shown in an already-open Workspace beyond what `focusSessionTab` already does. The behaviour is provider-neutral: Codex and Claude sessions switch the same way.

## Decisions

- **Text-selection conflict (decided by the user on 2026-10-17):** use Shift+Left/Right as specified, always active, through the existing passive local and global monitors, so it works whether or not Relay is frontmost. The frontmost app will also extend its text selection by one character on each press. The user accepted this as harmless. Do not add a `CGEvent` tap or an alternative chord in this ticket.

## Acceptance criteria

- [ ] Unit tests for the gesture type: Shift+Right gives next and Shift+Left gives previous. Any extra modifier (Command, Option or Control) gives nothing, plain arrows give nothing, and key repeats are ignored or rate-limited as chosen.
- [ ] AppState-level test with three live sessions: repeated Shift+Right visits all three in `workspaceSessionTabs` order and wraps to the first, Shift+Left wraps from the first to the last, and each step updates `sttEngine.voiceTargetSessionKey` to the newly focused session's spool key.
- [ ] With zero or one live session the hotkey changes nothing and shows no switch label.
- [ ] A switch during a recording leaves the in-flight recording's target unchanged, and the next recording uses the new target. Tests cover this.
- [ ] If the existing context-switch guards defer or refuse a switch, the notch never claims the switch happened. Tests cover this.
- [ ] Notch tests: after a switch, the planner shows the transient label naming the new project, then returns to the normal label. A following recording shows **Listening · <new project>**.
- [ ] `BoardHotkeyGestureTests` gains a case where holding Shift and pressing Left then Right never toggles the board. Existing gesture, notch and multi-session tests pass.
- [ ] The gesture vocabulary documents Shift+Left/Right, including that the keypress still reaches the frontmost app (passive monitor, not consumed): the `CapsLockGesture.swift` header comment, plus `docs/specs/assistant-session-context.md` if that spec lists hotkeys.
- [ ] `swift build` and `swift test` pass. `OnboardingIntroTests` is known to flake under CPU load; if it does, rerun it in isolation before treating it as a failure.
