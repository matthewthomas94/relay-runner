## Description

Fix the path where dismissing an automatic acknowledgement or TTS message can accidentally cancel the command the user just issued.

Observed live behavior: after a substantive voice command was claimed, a subsequent dismissal gesture produced `__INTERRUPT__`. The foreground relay instructions treated that interrupt as newest intent and dropped the already-intended project work. The user clarified that dismissing the automatic message was not meant to cancel the command.

Relevant code paths:

- `Sources/relay-runner/STT/CapsLockGesture.swift` maps double-tap Control to cancel when no confirmation is pending.
- `Sources/relay-runner/STT/STTEngine.swift` writes `__CANCEL__` for `.cancel` and can write `__INTERRUPT__` when a recording ends empty or a settled recording starts.
- `services/voice_bridge.py` publishes `__INTERRUPT__` as a foreground command, causing the relay loop to abandon stale work and suppress TTS.
- `tests/test_voice_bridge_preemption.py` covers the existing newest-intent semantics, but not the distinction between dismissing TTS and canceling an already-submitted command.

The fix should preserve intentional cancellation of active recording or active spoken output while preventing a TTS/ack dismissal from invalidating an already-submitted project command.

## Acceptance criteria

- [x] Dismissing an acknowledgement or queued/spoken TTS response stops playback/overlay feedback without publishing `__INTERRUPT__` as a newer Relay command.
- [x] Intentional cancellation of an active recording still prevents that recording from being submitted.
- [x] Intentional cancellation of active TTS still stops playback promptly.
- [x] A substantive command followed by TTS dismissal remains current for ticket creation, dispatch, and TTS metadata unless a real newer user command arrives.
- [x] Add Swift and/or Python regression coverage for the command-preservation behavior.
- [x] Provider parity is explicit: Codex and Claude relay sessions share the same dismissal semantics.
