## Description

Design and implement the next Relay Runner agent architecture where the main agent acts as a fast project-manager frontstage and a persistent orchestrator agent acts as the technical lead that owns project synthesis.

The desired model:

- when a Relay Runner session starts for a project, the main agent ensures an orchestrator agent is available and keeps it alive for the session or project;
- when the user gives a raw project-work instruction, the main agent immediately acknowledges the instruction and forwards the raw private command context to the orchestrator;
- the main agent should not do substantive solutioning for project work beyond fast acknowledgement, target/session routing, user-facing synthesis, and executing privileged frontstage actions;
- the orchestrator should synthesize the work, decide whether to create one ticket or many, author the ticket content, choose dependencies, and tell the main agent when workers should be dispatched;
- ticket writing is part of solutioning: the orchestrator should produce the ticket drafts/edits or exact ticket mutations, while the main agent applies them to the visible board and commits them as the user-facing/privileged actor;
- the main agent remains the user-facing status surface and should fetch status directly from board/run/program state instead of waiting for workers to push status updates;
- the orchestrator should expose readable state or events so the main agent can summarize what it is thinking/doing without blocking on ad hoc status requests;
- worker agents remain narrow executors, while the orchestrator coordinates planning, review, retry/fix decisions, and merge recommendations.

Keep the raw Relay command transcript private. Visible ticket content should contain refined, actionable architecture requirements rather than copied speech.

## Acceptance criteria

- [ ] Define the lifecycle for a persistent per-project or per-session orchestrator, including startup, reuse, project switching, and shutdown.
- [ ] Add or update the command-action flow so project-work instructions are acknowledged by the main agent and forwarded to the orchestrator with private command metadata.
- [ ] Specify and implement the structured contract by which the orchestrator authors ticket creations/edits and requests worker dispatches, review, retry, and merge actions from the main agent.
- [ ] Keep frontstage/privileged execution with the main agent: TTS, notch updates, applying orchestrator-authored visible ticket mutations, commits, dispatch calls carrying Relay stale-action metadata, and final user summaries.
- [ ] Let the main agent fetch status directly from board/run/program state and orchestrator-readable state, rather than requiring worker-to-main status pushes.
- [ ] Preserve provider parity for Codex and Claude, including startup commands, auth behavior, model/effort mapping, and stale-command handling.
- [ ] Treat internal controls such as stop listening, replay, cancel speech, and bridge recovery as frontstage actions that do not require orchestrator solutioning.
- [ ] Add deterministic tests or harness coverage for orchestrator startup/reuse, raw-command forwarding, dispatch-request handling, status fetching, and stale-command rejection.
- [ ] Document the full sequence with the PM frontstage, persistent orchestrator, worker fanout, review/merge, and user status loops.
