## Description

Design and implement the next Relay Runner agent architecture where the main agent acts as a fast project-manager frontstage and a persistent orchestrator agent acts as the technical lead that owns project synthesis.

The desired model:

- when a Relay Runner session starts for a project, the main agent ensures an orchestrator agent is available and keeps it alive for the session or project;
- when the user gives a raw project-work instruction, Relay Runner should fan out the raw private STT/instruction context to both the main agent and the already-running orchestrator in parallel;
- the PM acknowledgement/affirmation path should not block the orchestrator path, and the orchestrator path should not wait for the PM to finish interpreting or rewriting the command;
- the main agent should not do substantive solutioning for project work beyond fast acknowledgement, target/session routing, user-facing synthesis, and Relay/session control actions;
- the orchestrator should synthesize the work, decide whether to create one ticket or many, author the ticket content, choose dependencies, and tell the main agent when workers should be dispatched;
- ticket writing is part of solutioning: the persistent orchestrator should write or edit the visible `.orchestrator/RR-*.md` tickets through an orchestrator-owned path, not through the PM frontstage loop;
- after creating tickets, the orchestrator should send the main agent a worker-creation/dispatch request that names the ticket IDs, dependencies, sizing, and any context each worker needs;
- the main agent should create the requested worker sub-agents and automatically bind each worker to the orchestrator-created ticket it was requested for;
- the main agent should remain available for acknowledgement, clarification, and user/status management while the orchestrator performs ticket synthesis;
- the main agent remains the user-facing status surface and should fetch status directly from board/run/program state instead of waiting for workers to push status updates;
- after workers are dispatched, the main agent should enter an update mode where it continuously fetches relevant orchestrator and worker state and provides timely, useful status updates to the user;
- while in update mode, the main agent should continue accepting new user instructions and fan them out to the orchestrator without blocking on the existing worker graph;
- the orchestrator should expose readable state or events so the main agent can summarize what it is thinking/doing without blocking on ad hoc status requests;
- worker agents remain narrow executors and hand completed ticket work back to the orchestrator for review;
- the orchestrator should review completed tickets, request fixes/retries when needed, merge accepted work, and move accepted tickets to the board's `done` column.

Reference flow: FigJam board "RR-Loop" (`https://www.figma.com/board/N6eqwikO7VQdhQzUzSs44w/RR-Loop?node-id=0-1`) shows the user raw instruction, PM acknowledgement/status loop, orchestrator synthesis/tickets, PM worker dispatch, worker status, orchestrator review of completed tickets, merge to Git, and final status updates.

Keep the raw Relay command transcript private. Visible ticket content should contain refined, actionable architecture requirements rather than copied speech.

## Acceptance criteria

- [ ] Define the lifecycle for a persistent per-project or per-session orchestrator, including startup, reuse, project switching, and shutdown.
- [ ] Add or update the command-action flow so project-work instructions are broadcast to the main agent and orchestrator in parallel with private command metadata.
- [ ] Ensure PM acknowledgement/affirmation and orchestrator solutioning can proceed concurrently without the PM rewriting the user command first.
- [ ] Specify and implement the structured contract by which the orchestrator directly writes or edits visible tickets and requests worker dispatches, review, retry, and merge actions when needed.
- [ ] Worker-creation requests from the orchestrator include explicit ticket-to-worker assignment data so the PM can spawn worker sub-agents without re-solutioning the plan.
- [ ] Ensure the PM frontstage does not author, refine, apply, or commit ticket content while handling a user command; it should remain responsive to the user while the orchestrator performs that work.
- [ ] Keep user/session-facing execution with the main agent: acknowledgement, clarification, TTS, notch updates, status summaries, Relay stale-command checks, and dispatch calls when the orchestrator requests workers.
- [ ] Let the main agent fetch status directly from board/run/program state and orchestrator-readable state, rather than requiring worker-to-main status pushes.
- [ ] Add an update-mode loop where the PM periodically or event-reactively summarizes relevant orchestrator/worker progress to the user without blocking fresh instructions.
- [ ] New user instructions received during update mode are fanned out to the orchestrator promptly and do not require the PM to stop fetching/summarizing current work.
- [ ] Completed worker tickets route to the orchestrator for review, not to the PM for technical acceptance.
- [ ] The orchestrator can reject work for fixes/retries or accept it, merge it, and move the ticket to `done`.
- [ ] Preserve provider parity for Codex and Claude, including startup commands, auth behavior, model/effort mapping, and stale-command handling.
- [ ] Treat internal controls such as stop listening, replay, cancel speech, and bridge recovery as frontstage actions that do not require orchestrator solutioning.
- [ ] Add deterministic tests or harness coverage for orchestrator startup/reuse, raw-command forwarding, dispatch-request handling, status fetching, and stale-command rejection.
- [ ] Document the full sequence with the PM frontstage, persistent orchestrator, worker fanout, review/merge, and user status loops.
