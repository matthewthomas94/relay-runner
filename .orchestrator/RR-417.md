## Description

A ticket that merged its code as `verification_blocked` can't currently be closed as `done` once its external condition is met.

The current flow:

1. `resume_verification_blocked(run_id, reason, redispatch=True)` (`services/orchestrator.py`, around line 9685) moves the ticket back to `ready` with `run_state: verification_resumed` and dispatches a close-out worker.
2. The worker's only job is to confirm the condition and close the ticket. It usually has nothing to change, because the source change merged in the earlier run.
3. `_validate_outcome` (`services/artifact_lifecycle.py`, around lines 1132–1210) rejects every completed outcome whose `changed_paths` is empty ("structured outcome changed_paths is empty or exceeds its bound").
4. The worker can't submit an outcome, so the run fails with "exit=0 but ticket incomplete: worker did not submit a structured outcome".

RR-409 run 226 hit exactly this. The user had confirmed the fix in the installed app, and the worker re-ran the build and tests on `relay/rr-409`. The only way through would have been a throwaway commit, which the worker correctly refused to make.

### Required behaviour

Add a verification-only completion for resumed runs.

- **When it is allowed.** A completed outcome with an empty `changed_paths` is accepted only when all of these hold:
  - the run was dispatched from a ticket whose `run_state` is `verification_resumed`;
  - the ticket's earlier source merge is recorded;
  - the outcome carries no `verification_blocker` or `verification_resume`;
  - the outcome has at least one verification item.
- **Every other run is unchanged.** That includes ordinary implementation runs, verification-blocked outcomes and spikes. All of them keep the current non-empty rule and error.
- **What the daemon does with it.** There is no diff to integrate, so the daemon skips the source merge and the review/merge worker. It then:
  - publishes the ticket as `done`;
  - records a `## Run log` entry with the outcome summary and verification items;
  - progresses dependents as a normal `done` does.
- **What workers are told.** Update `services/orchestrator_workflow.md` so a verification-resume close-out worker submits this verification-only outcome when it has nothing to change. It must not make a placeholder commit.
- **Provider parity.** Codex and Claude workers use the same outcome schema and path.

Out of scope:
- closing a ticket from `resume_verification_blocked` with no worker;
- relaxing the rule for runs that were not resumed.

  - an empty-`changed_paths` completed outcome is accepted for a verification-resumed run whose source merge is recorded;
  - it is still rejected, with the existing error, for an ordinary run;
  - it is still rejected for a resumed run with no recorded merge;
  - it is still rejected for a `verification_blocked` outcome;
  - it is still rejected when there are no verification items.

  1. merge as `verification_blocked`;
  2. call `resume_verification_blocked` with redispatch;

  The ticket ends `done`, the Run log entry is written, no review/merge worker is dispatched, and a `backlog` dependent is promoted.
- [ ] The workflow prompt tells resumed close-out workers to use the verification-only outcome and not to make placeholder commits.
- [ ] `docs/orchestrator.md` describes the verification-only close-out.
- [ ] The existing artifact-lifecycle, verification and orchestrator test suites pass.
