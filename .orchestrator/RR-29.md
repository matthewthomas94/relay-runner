## Description

The user hit a recovery failure where Relay Runner stopped working and did not recover by quitting/restarting the voice bridge alone. Restarting the macOS Relay Runner app, then restarting the bridge, restored voice input. That means at least one app-side socket, FIFO, state-machine, TTS, STT, or watchdog state can get stuck in a way the bridge restart path does not fully reset.

Investigate why restarting `scripts/relay-bridge --relay` is insufficient in that state, and make bridge/app recovery robust enough that the user does not need to manually kill and relaunch the menu-bar app.

Likely areas to inspect:

- `services/voice_bridge.py` relay-mode socket/FIFO lifecycle.
- `scripts/relay-bridge` cleanup and startup path.
- `Sources/relay-runner/App/AppState.swift` bridge watchdog and session state.
- `Sources/relay-runner/Process/ProcessManager.swift` bridge liveness and orphan detection.
- STT/TTS state transitions that may survive bridge death.

## Acceptance criteria

- [x] Reconstruct the likely failure mode from logs and current bridge/app lifecycle code.
- [x] Identify whether the stuck state is caused by stale sockets/FIFOs, stale heartbeat/watchdog state, app-side socket clients, STT capture state, TTS FIFO readers, or launchd service state.
- [x] Bridge restart from the skill or `scripts/relay-bridge --relay` fully resets the recoverable state without requiring a Relay Runner app restart.
- [x] If app-side reset is required, expose a deterministic recovery action instead of relying on manual quit/relaunch.
- [x] Add targeted logging or tests where they make future diagnosis easier.
- [x] Verify by simulating bridge death/restart and confirming a new spoken command is delivered without restarting the app.

## Run log

- Inline orchestrator fix: identified stale bridge IPC as the likely recovery failure. The restart path cleaned the bridge socket and command files but could leave `/tmp/voice_in.fifo`, `/tmp/tts_in.fifo`, `/tmp/tts_control.sock`, and a heartbeat refresher behind; app restart repaired the STT FIFO because `FIFOWriter.ensureFifo` ran on app startup.
- Hardened recovery by making `services/voice_bridge.py` validate and repair FIFO paths, making `scripts/relay-bridge` and generated Codex/Claude skills clean the full runtime file set, and making `ProcessManager` kill stranded bridge processes even when the socket is gone.
- Verified with `bash -n scripts/relay-bridge`, `python3 -m py_compile services/voice_bridge.py`, focused Python unit tests, `swift build`, and `swift test`.
- Simulated the user-facing failure by replacing `/tmp/voice_in.fifo` with a regular file, restarting only the bridge, confirming the path became a FIFO again, and injecting `RR-29 bridge restart smoke`; the bridge delivered it to `/tmp/voice_cmd_ready` without restarting the Relay Runner app.
