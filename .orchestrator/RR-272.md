## Description

Fix a live regression in app-owned voice delivery where a valid voice command can remain silently queued behind terminal input state, then race a manually submitted provider turn, be declared undelivered, and still execute later.

Sanitized production evidence from one Codex session showed the command was received, classified, and queued immediately, but remained unclaimed for 73.9 seconds. The terminal delivery loop claimed it 6 milliseconds after a manually typed Codex turn started. Both acknowledgement attempts timed out, Relay cleared recovery state and published delivery failure after 4.2 seconds, yet Codex accepted the same voice command as steering 3.8 seconds after that failure. The next voice turn claimed in 29 milliseconds and acknowledged in 428 milliseconds after the manual Return had cleared the stuck condition. This proves STT and bridge publication were healthy; the split occurred between terminal-input deferral, typed-turn visibility, PTY submission acknowledgement, and late provider acceptance.

Treat this as a regression of RR-122, RR-163, RR-211, RR-218, RR-222, and RR-238. Replace the implicit collection of booleans and timeouts with one command-scoped transactional delivery state machine. It must distinguish at least: queued; intentionally blocked by a real terminal draft; manual terminal submission in flight; waiting for a safe provider boundary; prompt written; awaiting exact provider acknowledgement; acknowledged; recovering; superseded; and terminal failure. Every state transition must retain the exact Relay sequence and ID and have one authoritative owner.

Preserve genuine user drafts without letting a stale `RelayTerminalInputTracker` latch block voice indefinitely. A pending draft must produce immediate, passive feedback explaining that the voice command is queued until terminal input is submitted or cleared. A manual Return must establish a provider-turn barrier before the input tracker is considered safe for voice injection; do not treat the cleared byte counter as proof that the provider is idle. Either wait for the typed turn to finish or use a provider-specific atomic steering acknowledgement, but never inject speculatively into an unobserved active turn.

Make timeout and late-acceptance outcomes truthful and mutually exclusive. If the provider can still consume an injected prompt, Relay must not publish terminal delivery failure. If Relay publishes failure and permits retry, the original command must be provably unable to execute later. If a delayed exact acknowledgement arrives during recovery, reconcile it atomically and suppress duplicate retry, duplicate action, and false failure output. A terminal command may have exactly one final delivery outcome.

Add privacy-safe diagnostics and mounted validation. Record deferral reason, state, elapsed time, pending byte count rather than content, manual-submit barrier transitions, PTY attempts, exact provider acknowledgements, late-ack reconciliation, recovery, and final outcome. Never log typed prompt or voice text. Preserve newest-intent semantics, interruption, background voice input, exact-once ticket and external mutations, completion/TTS correlation, bridge recovery, normal typed terminal use, and Codex/Claude parity.

## Acceptance criteria

- [ ] A deterministic regression reproduces the observed sequence: a voice command waits, manual Return starts a typed provider turn, delivery claims on that boundary, both acknowledgement attempts time out, and the provider accepts the command after failure; the fixed path cannot reach both failed and handled outcomes.
- [ ] With an idle provider and no real terminal draft, a queued voice command is claimed within 500 ms p95 and starts one exactly correlated provider turn without manual terminal input.
- [ ] A genuine typed or pasted draft is never overwritten, concatenated with voice text, cleared, or submitted by voice delivery; Relay shows passive queued feedback within 250 ms that explains the terminal-input wait.
- [ ] Terminal-input deferral emits a sanitized durable diagnostic with sequence, ID, elapsed time, and pending byte count, and cannot remain silently blocked by stale tracker state indefinitely.
- [ ] Submitting or clearing a manual draft does not immediately expose an unsafe idle window: Relay establishes a manual-submit/provider-turn barrier before claiming or injecting the queued voice command.
- [ ] A queued voice command is delivered only after a verified safe provider boundary, or through a provider-specific atomic steering handshake that transfers exact command ownership and acknowledgement together.
- [ ] Provider acknowledgement is correlated to the exact Relay sequence and ID; a PTY write, Return byte, cleared input counter, or unrelated typed provider turn never counts as acknowledgement.
- [ ] Acknowledgement timeout, recovery, and late acceptance are reconciled transactionally: a command has exactly one terminal outcome and cannot be reported failed and then execute later.
- [ ] When failure is surfaced and user retry is permitted, the original prompt is provably retracted or quarantined so it cannot become delayed provider steering; otherwise Relay continues to show recovering or awaiting acknowledgement rather than a false terminal failure.
- [ ] Recovery never sends duplicate Return events into an unrelated active typed turn, duplicates a command, restarts a healthy provider unnecessarily, or requires the user to type a terminal message to wake delivery.
- [ ] Newest-intent replacement, explicit interruption, stale-action suppression, exactly-once tickets/dispatches/external effects, completion-hook correlation, messenger/TTS output, and background recording remain correct across every delivery state.
- [ ] Sanitized diagnostics distinguish draft deferral, manual submission, safe-boundary wait, prompt write, submit attempt, acknowledgement, timeout, retry, late acknowledgement, reconciliation, supersession, and final outcome without storing terminal or voice content.
- [ ] Focused Swift tests cover RelayTerminalInputTracker, RelayVoiceCommandDelivery, typed-turn barriers, delayed acknowledgement, retry, and installed-session lifecycle; focused Python tests cover provider-turn hooks, completion correlation, stale commands, and both app-owned providers.
- [ ] Mounted installed-app tests reproduce the exact voice-then-manual-Return incident and verify automatic recovery without a terminal kick, immediate truthful feedback, one provider execution, and one final outcome for both Codex and Claude or a documented provider-specific live-test limitation.
- [ ] The implementation documents why earlier RR-122/RR-163/RR-211/RR-218/RR-222/RR-238 safeguards did not compose safely and identifies one authoritative delivery state machine rather than adding an independent watchdog or another blind timeout.
