## Description

Run a time-boxed architecture spike to determine whether and how Relay Runner should support a user-supplied cloned voice while retaining the current Kokoro voice path as a safe fallback. Begin by confirming the intended cloning engine and terminology; Coqui/XTTS is a likely interpretation, but the investigation must verify the exact maintained project, version, license, and supported deployment model rather than assuming a product identity.

Map the current TTS configuration, synthesis, playback, packaging, update, and Settings boundaries. Compare viable local-first voice-cloning approaches using representative Relay prompts and measured evidence. Cover reference-audio requirements, voice quality and similarity, time to first audio, real-time factor, CPU/GPU and memory use, model/download size, Apple Silicon and supported macOS compatibility, offline behavior, maintenance risk, licensing and redistribution, and failure recovery.

Define the consent, privacy, and lifecycle contract for reference recordings and derived voice assets: users must affirm they have permission to clone the voice; Relay must make import, local storage, deletion, and any network transfer explicit; project repositories and ticket data must remain outside this asset lifecycle.

The spike may use disposable prototypes or benchmark scripts to validate feasibility, but it must not add production integration, alter the default George/Kokoro voice, ship a model, change the installer, or expose unfinished Settings controls. End with a recommended architecture or a documented no-go decision, including how fallback, selection, packaging, and provider parity would work. Create separate cold-start implementation tickets only after the evidence supports a direction.

## Acceptance criteria

- [ ] The intended cloning engine and terminology are confirmed, including the exact maintained project/version, license, redistribution terms, and whether Coqui/XTTS was the intended reference.
- [ ] The existing Relay Runner TTS path is mapped from Settings and persisted configuration through synthesis, speech coordination, playback, packaging, updates, and fallback behavior.
- [ ] At least two viable local-first approaches, or one viable approach plus a documented reason alternatives fail, are compared using the same representative Relay prompts and reference audio.
- [ ] On-device measurements cover voice quality and similarity, time to first audio, real-time factor, CPU/GPU use, peak memory, model/download size, offline operation, and supported macOS hardware.
- [ ] The investigation documents reference-audio requirements and an explicit consent, import, local-storage, deletion, and network-transfer contract for source recordings and derived voice assets.
- [ ] Licensing, model provenance, redistribution, maintenance, security, and release-packaging risks are evaluated before recommending any bundled or downloaded runtime.
- [ ] The recommended architecture explains voice selection, fallback to the current George/Kokoro path, asset lifecycle, error recovery, and equivalent Codex/Claude behavior.
- [ ] No production TTS integration, default-voice change, installer change, bundled model, or unfinished Settings UI is shipped as part of the spike.
- [ ] The final report records a go, no-go, or further-evidence decision with tradeoffs and rejection reasons; implementation tickets are created only if the recommendation is supported by evidence.
