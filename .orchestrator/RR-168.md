## Description

Redesign Relay Runner's Settings experience so it feels native to the unified Workspace and Terminal surfaces instead of a nested macOS preferences card. Keep every existing setting, config binding, save behavior, permission action, preview action, folder picker, installer action, and standalone Settings window functional. This is a visual hierarchy, information architecture, control-quality, and interaction polish pass, not a config-schema or feature expansion.

Use Relay Runner's current Workspace/Terminal shell as the source of truth: restrained dark neutrals, PP Mori/PP Telegraf typography, compact navigation, precise spacing, thin separators, and quiet hover/focus treatment. Purple is the Relay selection/focus/action accent. Orange is reserved for listening or recording state and must not be used for unsaved changes, permission warnings, focus, or generic attention inside Settings.

Linear is a reference for principles, not a component library to copy. Its current UI refresh emphasizes consistent headers/navigation, calmer scanning, a dimmer navigation rail, and a main content plane that carries the focus. Its redesigned settings emphasize simpler navigation and consolidated, easy-to-scan controls. Reference: https://linear.app/changelog/2026-03-12-ui-refresh and https://linear.app/changelog/2024-12-18-personalized-sidebar.

The intended composition is a settings workspace:

- The Workspace Settings tab is a full-height, edge-aligned surface within the existing shell, without a second floating rounded card or oversized shadow.
- A quiet left navigation rail uses single-line category rows, restrained icons, and a subtle selected/focused treatment. Remove per-row subtitles and selected chevrons; the detail header owns the category explanation.
- The content plane uses a readable, left-aligned maximum width rather than stretching controls across the full display.
- Section hierarchy comes from headings, spacing, and hairline separators. Do not wrap every section in a bordered rounded card and do not create nested cards.
- Settings rows share a consistent anatomy: label and optional description on the left, aligned control/action on the right. Long-form controls such as the workspace folder can use a purposeful stacked row.
- Supporting copy must remain comfortably readable in long sessions. Do not use the current 8–9 pt caption roles for explanatory settings text; use an appropriate 11–12 pt role without changing global typography used by unrelated surfaces.
- Native pickers, switches, sliders, fields, action buttons, status rows, and the voice preview control receive a restrained, consistent treatment and alignment. Preserve familiar macOS behavior and keyboard access.
- The sticky save area remains stable but is visually quiet when clean. A dirty draft uses purple emphasis and a clear primary Save action, never orange.
- The standalone Settings window shares the same system and remains usable at its fixed window size; adjust that size if the new hierarchy needs more breathing room.

Do not change the top-level Workspace/Terminal/Settings tabs, overlay sizing, configuration defaults, persistence format, or underlying service behavior. Do not add glass effects, decorative gradients, generic cyan focus rings, excessive focus rings, or animation that moves layout.

## Acceptance criteria

- [ ] Workspace Settings visually reads as part of the unified Workspace shell: full-height and edge-aligned, with no nested outer card, duplicate workspace border, or large floating shadow.
- [ ] The standalone Settings window and embedded Workspace Settings share the same layout/components and remain fully usable.
- [ ] The Settings navigation rail is visually quieter than the content plane and uses one-line labels, consistent icons, subtle hover/selection, no per-item subtitle, and no selected chevron.
- [ ] Category changes preserve keyboard navigation and VoiceOver labels. Keyboard focus is visible through a restrained purple fill/hairline treatment rather than the current generic cyan ring or an excessive system focus halo.
- [ ] Detail headers, section headings, labels, descriptions, and metadata have a clear typographic hierarchy using the existing PP Mori/PP Telegraf system. Explanatory copy renders at 11 pt or larger without globally inflating unrelated app typography.
- [ ] The detail content uses a readable maximum width and consistent vertical rhythm; labels and controls align predictably at normal Workspace and standalone-window sizes.
- [ ] Repeated bordered rounded `SettingsSection` cards are replaced by flatter groups whose hierarchy comes from spacing and hairline separators. No nested-card treatment remains.
- [ ] Pickers, switches, sliders, text fields, buttons, status indicators, and preview/install/permission actions have a coherent dark treatment and preserve their existing behavior.
- [ ] Purple is used for Settings selection, custom focus, dirty/save emphasis, and Relay-active affordances. Settings contains no orange styling for generic warnings, unsaved state, focus, or selection; denied/error states use red, success uses green, and idle uses muted neutral styling.
- [ ] The footer/save state is subdued and stable when clean, becomes clearly actionable when dirty, saves with the existing keyboard shortcut, and still updates when `appState.config` changes externally.
- [ ] Status, General, Speech-to-Text, Text-to-Speech, and Awareness retain every existing setting/action and continue to fit without clipping or unusable scrolling.
- [ ] Folder picker suspension/resume, voice preview progress/error, permission prompts, setup walkthrough, Relay Skills install/reinstall alert, conditional activation controls, and conditional sub-agent controls remain functional.
- [ ] No config schema, defaults, persistence, service behavior, provider behavior, or top-level Workspace navigation changes are introduced.
- [ ] Focused Settings layout/style tests cover navigation metadata/order, workspace versus window sizing, semantic color rules, readable typography roles, and clean/dirty save presentation decisions where those can be modeled deterministically.
- [ ] `swift test` and `git diff --check` pass.
