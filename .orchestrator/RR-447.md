## Description

After quitting and reopening Relay Runner with a saved session (macOS 27, Relay Runner 0.4.86 local build, Claude provider, 2026-10-28), voice turns stopped reaching the resumed provider session for about 13 minutes. The user's turns were transcribed and recorded but sat undelivered, and spoken replies failed.

Observed sequence (all times local, one session):

1. 22:29:52 app launched; the provider session resumed the saved conversation.
2. 22:30:34 to 22:36:17: the app watchdog restarted the voice bridge 6 times (`/tmp/voice_bridge.<timestamp>.log`, `reason=watchdog-recovery`). Most bridge logs end with `Persistent orchestrator heartbeat failed: timed out` (`services/voice_bridge.py:1543`) and `pending messenger outcome fetch failed: timed out`. Each restart was followed about 7 s later by a playback that paused microphone capture.
3. 22:31:38 voice command seq 60 was typed into the provider terminal and the provider **did receive and act on it**, but the delivery events show `acknowledgement_timeout` after 2.1 s, then `recovery_started`, then `recovery_blocked` 10 s later (`Sources/relay-runner/Terminal/EmbeddedTerminal.swift` `handleAcknowledgementTimeout` ~2628 and `scheduleRecoveryPoll` ~2654). The session's `voice_cmd_claimed.json` was never written, so the reply helper refused the provider's spoken reply with `claimed command unavailable`.
4. The intent inbox then reported `inbox_recovery_blocker` for seq 60 (`services/intent_inbox.py` `recovery_blocker` ~950, state `review_required`). Later turns (seq 61 at 22:44:29, seq 62 interrupt at 22:44:50) were recorded in `command-actions/events.jsonl` with `state=pending` but not delivered. The user saw no prompt explaining that voice was blocked.
5. Around 22:51 the blocker cleared (cause not established) and seq 61 and a new seq 63 were delivered together, about 7 minutes late.
6. The inbox state still lists a `pending` item from a previous session (seq 42, item 3, `queue_project_work`), carried across the relaunch.

Holding uncertain deliveries instead of replaying them is intended and must stay. The defects to find and fix:

- **False uncertainty:** a command the provider actually received was classed as unacknowledged, probably because the resumed provider's acknowledgement (claim write or provider turn event) did not fire or was not observed. Find why and make a received turn acknowledge reliably after resume.
- **Silent block:** while a recovery blocker holds the queue, the user gets no signal. Surface it in the notch or session UI with the existing compare-and-skip path (`skip_recovery_blocker`), and tell the messenger so it can say voice is paused.
- **Watchdog churn:** find why the bridge heartbeat timed out repeatedly after relaunch (provider busy resuming, app main thread busy, daemon slow) and stop the watchdog restarting a bridge that is alive but slow. Each restart also interrupts microphone capture.
- **Stale cross-session items:** pending items from an ended session should not carry into a new session's deliverable list.

External verification: checks that need the live app, real hardware, or a human run what you can from the worktree without installing, releasing, or restarting the running app. If only those checks remain, finish as `verification_blocked`, naming each remaining check in `verification_blocker` and how to run it in `verification_resume`.
