## Description

Fix the first-run onboarding runtime progress indicator shown under **Preparing Codex /** or **Preparing Claude /**. A user-observed v0.4.43 local build shows the linear bar fully filled while setup is still running, so it looks static and complete rather than communicating ongoing work.

Treat progress as an end-to-end setup contract. `VenvInstaller` launches the outer `relay-orchestrator --install` workflow, while the nested `relay-bridge` installer emits `RELAY_PROGRESS` markers and can currently reach `100` before the outer workflow has finished provider validation, daemon installation, health checks, or other readiness gates. A nested phase finishing must not make the onboarding bar appear complete while the parent process remains active.

Keep the indicator truthful and visibly alive:

- show indeterminate activity before the first reliable progress marker;
- advance determinate progress monotonically as meaningful phases complete;
- reserve the fully filled state for successful end-to-end readiness, immediately followed by the existing success treatment;
- if a remaining phase cannot be measured, communicate ongoing activity without fabricating percentages or resetting backwards;
- preserve retry, failure, cancellation, provider parity, and Reduce Motion behavior.

Prefer one explicit progress ownership/mapping contract over cosmetic looping animation. Do not introduce a timer that claims forward progress unrelated to real setup events.

## Acceptance criteria

- [ ] While the outer runtime installer is active, the onboarding linear indicator never renders at its fully completed value solely because a nested installer emitted `RELAY_PROGRESS:100`.
- [ ] The initial state visibly communicates indeterminate activity until a trustworthy determinate marker is received.
- [ ] Determinate progress advances monotonically through real setup phases and retains visible unfilled capacity until all selected-provider readiness checks succeed.
- [ ] Completion is owned by the outer process result: only a successful end-to-end install transitions to the existing success/checkmark state; failure never briefly presents a completed bar.
- [ ] Long or unmeasurable final phases continue to communicate activity without fake time-based percentages, backward jumps, or a static full bar.
- [ ] Retry starts from a fresh progress state and cannot inherit `100%` from the prior attempt.
- [ ] Codex and Claude paths use equivalent progress semantics, including their provider-specific CLI installation and validation phases.
- [ ] Reduce Motion retains clear status feedback without unnecessary looping spatial motion; accessibility exposes an accurate in-progress versus complete state.
- [ ] Focused tests reproduce the premature-full-bar case across chunked/multi-line output, verify nested `100` clamping/reservation, outer-process success/failure ownership, monotonicity, retry reset, and provider parity.
- [ ] Relevant Swift and script tests pass, and a packaged local build is ready for a first-run visual check confirming the bar visibly loads instead of appearing full from the start.
