## Description

Replace Relay Runner's misleading dirty-source merge failure with a recoverable integration-blocked lifecycle, and stop historical merge errors from remaining visible after a run ultimately succeeds.

Today `accept_worker_run` treats any nonempty `git status --porcelain` result as a `MergeConflict`, emits `run-failed`, and records only the generic message `source repo has uncommitted changes; refusing worker merge`. The completed and reviewed worker branch is preserved, but the board presents the condition as an implementation failure and gives the user no precise recovery path. If the run is later merged successfully, `RunsStore.update` cannot explicitly clear `last_error`, and the native board renders any retained error even for a terminal merged ticket. This leaves successful cards displaying obsolete red failures, as observed on RR-174, while current reviewed work such as RR-297 and RR-298 appears to have failed even though only integration is waiting.

Model a dirty canonical checkout as a nonfailure integration block. Preserve completed implementation, review evidence, the worker branch, and the worktree without redispatching or rerunning the implementation. Publish bounded repo-relative dirty paths and a clear next step. Once the checkout is clean, allow the existing reviewed run to resume through the daemon's normal merge path idempotently, including after daemon restart. Do not automatically stash, discard, overwrite, commit, or mix user-owned changes into a worker merge.

Prevent avoidable compute when the canonical checkout is already dirty before dispatch: keep the ready ticket queued without spawning a worker, expose that it is waiting for a clean integration target, and let normal queue reconciliation proceed when the checkout becomes clean. A checkout that becomes dirty only after a worker starts must still preserve the completed reviewed run and enter the same recoverable integration-blocked state.

## Acceptance criteria

- [ ] A dirty canonical checkout before dispatch does not spawn a worker; the ready ticket remains queued with a nonfailure waiting state and resumes through normal queue reconciliation after the checkout becomes clean.
- [ ] A checkout that becomes dirty after worker execution or review preserves the completed implementation commit, review evidence, worker branch, and worktree without requesting an implementation retry or rerunning verification.
- [ ] Dirty-source integration uses a distinct persisted lifecycle state rather than `MergeConflict`, `Failed`, or `run-failed`, and its lifecycle event, queue-drain item, Program Status response, and board placement remain consistent across daemon restart.
- [ ] The blocker reports a bounded, privacy-safe list of repo-relative tracked and untracked paths plus an actionable clean-checkout recovery step; it does not expose absolute paths or file contents.
- [ ] When the canonical checkout becomes clean, an explicit recheck or normal queue reconciliation can resume the existing reviewed run and merge it exactly once without creating a new implementation attempt.
- [ ] Successful merge clears obsolete `last_error` data in SQLite, the generated runs index, MCP/API responses, and native board models while preserving historical evidence in the run log or lifecycle history where appropriate.
- [ ] Merged or otherwise successful terminal tickets never render stale red error text; active failure and integration-blocked states continue to show their current actionable detail.
- [ ] No recovery path automatically stashes, commits, discards, overwrites, resets, or includes user-owned working-copy changes in the worker merge.
- [ ] Codex and Claude runs have identical dirty-source blocking, resume, persistence, and board behavior.
- [ ] Focused Python tests cover dirty-before-dispatch, dirty-after-review, clean-and-resume, restart recovery, idempotence, exact `last_error` clearing, bounded path reporting, and no worker redispatch; focused Swift tests cover placement, pills, and stale-error suppression for the new and terminal states.
