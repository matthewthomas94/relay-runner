## Description

Implement RR-273 delivery phase 1 using the RR-270 report sections `Application-support home` and `Registration, identity, and filesystem access` as the design authority. Add a schema-versioned registry-v2 under `~/Library/Application Support/relay-runner/`, immutable project IDs, atomic primary/backup writes, corrupt-primary quarantine and backup recovery, and Keychain-backed security-scoped bookmarks. Migrate existing path-based records without creating or changing any repository artifact during registration.

Registration must distinguish exact-path, file-resource, Git common-directory, and committed project-ID duplicates; retain moved, missing, disconnected-volume, stale-bookmark, symlink, bare-repository, and user-worktree recovery states. Only one primary local worktree may be active for a project ID, and Relay-created worker worktrees must be rejected. Removing a project unregisters app-owned state without editing, moving, nesting, or deleting the repository.

Keep compatibility behind a bounded registry-v2 opt-in or equivalent reversible read-path gate. This ticket does not implement the new Workspace UI, artifact Git ref, remote sync, or source-tree cutover.

## Acceptance criteria

- [x] Registry-v2 records have a schema version, immutable project ID, display name, selected/last-resolved paths, Git common-directory fingerprint, remote mode metadata, availability state, timestamps, and a Keychain bookmark reference without embedding bookmark bytes in JSON.
- [x] Writes are atomic and preserve a last-known-good backup; tests prove recovery from a corrupt primary, quarantine when both copies are unusable, and a valid empty-registry state after total app-state loss.
- [x] Legacy path-based records migrate deterministically and idempotently while registration validation makes no repository write, does not create `.orchestrator`, and does not alter Git refs, remotes, index, worktree, or source status.
- [x] Add/locate validation covers moved or renamed paths, symlinks, missing paths, disconnected volumes, stale or revoked grants, bare repositories, user worktrees, Relay worker worktrees, and duplicate path/common-dir/project-ID cases.
- [x] Bookmark bytes are stored and refreshed through the Keychain service/account contract from RR-270; stale access is surfaced for explicit regrant rather than silently dropping or changing project identity.
- [x] Remove releases app-owned access and clears only Relay-owned registry/cache state after confirmation; repository bytes, refs, remotes, materialized files, and history remain unchanged in automated fixtures.
- [x] Existing registry consumers keep working during the opt-in period, and targeted Swift tests plus the relevant full source suite pass without provider-specific project identity behavior.
- [x] Documentation links the implementation to RR-270 phase 1 and records registry ownership, recovery states, migration behavior, and intentional platform-only differences.

## Rollback boundary

Disabling registry-v2 restores the legacy read path from the preserved pre-migration record/backup. Rollback may remove only app-owned v2 registry and Keychain entries created by the migration; it must never mutate a registered repository.

## Verification plan

Use disposable repositories and volumes where possible to compare pre/post Git status, refs, remotes, index, and repository hashes. Exercise migration twice for idempotency, inject interrupted/corrupt writes, and verify Keychain grant refresh and unavailable-state recovery on an installed app before this foundation is used as the default.
