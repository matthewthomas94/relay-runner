## Description

The installed app can still expand the deferred-playback response pill with its playback hint but no response body. The text appears only after the user double-taps Option to start playback. This is the same user-visible failure RR-203 intended to fix, so treat it as a regression and diagnose the end-to-end event order in the current packaged app rather than assuming the earlier state-preservation change covers every completion route.

The response body must be visible as soon as a nonempty provider response becomes ready. Playback may change the pill's action and audio state, but it must never be the event that first populates text Relay Runner already received.

## Acceptance criteria

- [ ] Reproduce the blank waiting-pill body against the current installed/package-equivalent build with automatic playback disabled.
- [ ] A nonempty response is visible before the user presses or double-taps anything, including on the event ordering that currently reproduces the regression.
- [ ] Explicit orchestrator replies, completion-hook recovery replies, and ordinary conversation replies all preserve their response preview through waiting, preparing, speaking, cancellation, and idle transitions.
- [ ] Playback starts and updates state without being required to populate or recover the response body.
- [ ] Blank or stale events cannot overwrite a newer nonempty preview, and consecutive responses never reuse the preceding response body.
- [ ] Existing behavior remains correct when previews are disabled and when automatic playback is enabled.
- [ ] Codex and Claude sessions exhibit the same response-pill behavior.
- [ ] Python and Swift regression tests exercise the packaged event order that escaped RR-203, not only the isolated state-machine happy path.
