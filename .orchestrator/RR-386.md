## Description

Extend the existing Task / Action / Discussion contract in docs/intent-qualification-testing.md and services/command_actions.py to repository-independent work. Classify intent first, then use size, number of steps, durability, delegation and explicit tracking intent to decide whether executable general work needs a ticket. A long explanation or read-only exploration remains Discussion unless the user requests tracked research. Small bounded actions run in the foreground. Larger or explicitly tracked general tasks use an app-owned General work board and managed execution directories, never an unrelated source repository. The user should not need to create or select a repository to obtain task tracking. Keep the foreground PM authoritative and messenger tool-free.

## Acceptance criteria

- [x] Document an actionable matrix covering discussion/status, one-step general actions, substantial general tasks, explicitly tracked research, project implementation and mixed requests. Include examples and a reason for each ticket/no-ticket decision; elapsed research time alone never authorizes a ticket or execution.
- [x] Small authorized actions such as opening an app or creating a short local draft execute without a ticket. Substantial authorized work such as preparing a multi-file report receives a General ticket with acceptance criteria, lifecycle and run provenance.
- [x] General tickets persist in a dedicated daemon-owned app store under the central app data root, using canonical writers and globally distinguishable identities; project tickets continue to belong to their confirmed repository.
- [x] Support actual worker execution for ticketed general work in isolated per-task working directories. Define artifact review/completion without assuming every output is a source-code branch or requiring a user GitHub repository.
- [x] Both Codex and Claude can perform foreground general actions and tracked general work using the same classification, storage, cancellation and review contract; document any intentional provider-specific execution differences.
- [x] Discussion and backlog-only requests never execute. A Task or Action label does not grant external send, publish, purchase or delete authority; preserve ordered mixed intents and scoped cancellation.
- [x] Project mutation still resolves a specific project and validates its current scope. An unresolved project is clarified when needed rather than silently using the global store or a selected UI row.
- [x] Meaningful regressions and separately authorized live trials demonstrate general action, general tracked task, project task, discussion, no-dispatch, cancellation and failure recovery without changing unrelated boards.
