## Description

Prevent Relay voice sessions from speaking a follow-up that merely restates what the messenger or PM already said for the same user turn, while preserving the normal multi-message lifecycle of acknowledged work.

The desired interaction is not limited to one utterance per user turn. An actionable request should receive a prompt spoken acknowledgement from the messenger or PM that confirms the request was understood, states the intended next step, and sets the expectation that Relay will return with a result. The orchestrator may then speak again when it has advanced the interaction: it completed the work, reached a meaningful new status, encountered a blocker, or needs a critical decision or clarification from the user.

The current pipeline can play a fast messenger response and later play the authoritative provider completion under different deduplication keys. Exact text or event-key deduplication is insufficient because equivalent statements may use different wording. Conversely, blindly suppressing every later final would hide real outcomes, ticket IDs, errors, blockers, decisions, and next steps.

Add command-scoped lifecycle and semantic-coverage arbitration at the existing MessengerRuntime and SpeechCoordinator boundary. Track speech that actually played for the same relay command sequence and ID, including its lifecycle role and the user-visible facts it covered. When later provider or messenger content arrives, the existing synthesis path should choose an explicit realization: suppress a pure restatement, speak only the novel delta or a concise synthesis, or speak the full message when no prior coverage is usable. Fold the decision into the existing final-synthesis path rather than adding a second remote model round trip.

Use deterministic coordinator guardrails around any model-assisted comparison. An acknowledgement or task handoff never establishes coverage of a later result. A completed result, failure, blocker, or critical decision request must remain speakable even when some phrasing overlaps the acknowledgement; only the already-covered portion may be removed. For a non-action conversational turn already answered by the messenger, an equivalent provider final may be suppressed because it advances neither lifecycle state nor factual content.

Interrupted, canceled, queued, stale, failed, or superseded speech does not count as delivered coverage. If semantic arbitration is unavailable, times out, or returns malformed data, fail open by speaking the full authoritative final. Provider-visible output must remain in the terminal and messenger context even when a redundant TTS realization is suppressed. Preserve completion-hook correlation, freshness checks, diagnostics privacy, fallback behavior, and Codex/Claude parity.

## Acceptance criteria

- [ ] An actionable user turn receives one prompt spoken acknowledgement from the messenger or PM that confirms the accepted action, states the immediate next step, and promises a later result or decision request without claiming unperformed work.
- [ ] The system permits multiple spoken messages for one user turn when each advances the lifecycle or adds user-relevant information; it does not enforce a one-utterance-per-turn limit.
- [ ] After acknowledgement, an orchestrator follow-up is spoken when it reports a completed result, meaningful new progress, failure, blocker, or critical decision or clarification needed from the user.
- [ ] A later message that only paraphrases the acknowledgement or repeats its plan with no new lifecycle state or facts produces no additional TTS utterance.
- [ ] When a substantive result overlaps earlier wording, Relay preserves every novel fact, identifier, outcome, error, blocker, decision, and next step while omitting only the redundant portion.
- [ ] A task-like acknowledgement or handoff can never suppress a later substantive result merely because both contain similar framing.
- [ ] For a non-action conversational turn already answered by the messenger, a semantically equivalent provider final is suppressed while the provider-visible final remains available in the terminal.
- [ ] Only utterances that reached the played state count as coverage; queued, interrupted, canceled, stale, failed, and superseded utterances do not suppress later speech.
- [ ] Coverage state and lifecycle phase are isolated by relay command sequence and ID, are superseded correctly, and cannot leak across rapid turns or barge-in.
- [ ] Malformed, failed, or timed-out arbitration falls back to speaking the full authoritative final so a result or critical decision request is never silently lost.
- [ ] The realization decision and any delta are produced through the existing messenger final-synthesis path without a second remote model call dedicated only to comparison.
- [ ] Codex and Claude app-owned sessions behave equivalently across messenger acknowledgements, explicit replies, completion hooks, provider failure, and direct fallback; intentional provider differences are documented.
- [ ] Diagnostics expose command identity, lifecycle role, realization decision, and suppression reason without logging raw user transcripts or full reply bodies.
- [ ] Focused SpeechCoordinator, MessengerRuntime, voice-bridge preemption, completion-hook, and speech-event tests cover acknowledgement then result, acknowledgement then critical decision, redundant plan restatement, conversational duplicate, partial-overlap delta, interruption, stale turn, fallback, and provider parity; git diff --check passes.
