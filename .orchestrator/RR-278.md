## Description

Fix a live audio-capture regression where Relay Runner stops receiving usable microphone audio after the macOS input changes to another device. The current STT settings intentionally follow the system-default input, but the running AVAudioEngine capture graph is established only when STTEngine starts; after a device switch, later recordings can remain bound to the old route or otherwise stay silent until Relay Runner is quit and reopened.

Make the capture lifecycle follow valid system-default input changes without requiring an app restart, provider-session restart, or settings edit. Detect and coalesce the relevant Core Audio or AVAudioEngine route/configuration events, then rebuild the input tap, native format, converter, and engine state in a safe order on one owner. Preserve the loaded transcription model and ordinary gesture behavior where possible. If a route changes during an active recording, use one explicit fail-safe outcome: continue only when the capture is valid, otherwise cancel or end that recording once with a clear recoverable status; the next recording must use the new input.

Keep scope focused on resilient system-default migration rather than adding a manual device picker. Permission behavior and local transcription remain unchanged. Diagnostics may record privacy-safe device and route metadata, transition reason, and recovery outcome, but never captured audio or transcript content.

## Acceptance criteria

- [ ] A deterministic regression demonstrates an engine started on input A becoming unusable when the macOS default input changes to B, and the fix makes the next capture use B without quitting or reopening Relay Runner.
- [ ] Relay Runner observes the authoritative macOS default-input or audio-engine configuration changes needed for device selection, connection, disconnection, and replacement, and coalesces duplicate notifications into one bounded recovery.
- [ ] When idle, a valid input change rebuilds the audio input tap, native format, 16 kHz converter, and running capture graph promptly while preserving the already loaded STT model and existing gesture configuration.
- [ ] A device change during an active recording has one documented and user-visible outcome: valid capture may continue, otherwise the recording is canceled or ended exactly once and the next recording uses the new device; stale, silent, or mixed-route audio is not submitted as a successful command.
- [ ] Reconfiguration is serialized with start, stop, settings restart, recording-buffer ownership, and app teardown so taps are never installed or removed twice and late notifications cannot restart a stopped engine.
- [ ] Input format changes, including sample-rate and channel-count differences between devices, create a compatible converter or publish an actionable recoverable error instead of leaving the UI at Listening while no audio is captured.
- [ ] If no valid input is temporarily available, Relay Runner reports that state, remains responsive, and automatically recovers when a valid system-default input returns without requiring an app restart.
- [ ] Microphone permission semantics, local-only audio handling, activation gestures, VAD, ordered voice delivery, and the read-only System Default settings contract remain unchanged.
- [ ] Privacy-safe diagnostics identify the route transition and recovery result without recording audio samples, transcript text, or unrelated device details.
- [ ] Focused Swift tests cover idle switching, switching during recording, duplicate notifications, format changes, unplug and reconnect, temporary no-input failure, settings-triggered restart, and teardown races through injectable route and capture seams.
- [ ] A freshly built installed app passes a mounted smoke test that records successfully, switches between two representative macOS input devices, records successfully again, and switches back without relaunching Relay Runner; the run log records devices used, build identity, observed recovery timing, and results.
