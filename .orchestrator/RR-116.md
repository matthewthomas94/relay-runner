## Description

Relay bridge still does not survive after a Codex App job completes. The latest observed failure happened after the foreground session finished dispatching `RR-114` and `RR-115`: the final Codex response rendered in the app, but the active `/relay-bridge` session was gone afterward and had to be restarted manually.

This is a recurrence of a problem the user has now reported three times. `RR-74` previously claimed to fix bridge survival across local commits by keeping an already-observed bridge daemon alive when the consumer heartbeat goes stale, and the current test suite includes liveness/recovery tests such as `BridgeConsumerLivenessTests.testRelaySessionSurvivesCompletedCodexTurnWithBridgeContext`. Those tests are not catching the live Codex App completion failure.

Investigate the real post-completion lifecycle end to end:

- whether the foreground Codex App turn stops the relay loop before re-entering its wait state,
- whether the bridge daemon, launchctl job, socket, cwd/provider metadata, heartbeat pid, or TTS/control FIFOs are being cleaned up,
- whether the app watchdog/recovery path is using the wrong context or incorrectly marking the session dead,
- whether final-answer cleanup in the skill, app, or generated bridge scripts differs from the simulated tests,
- whether worker dispatch completion or Codex thread completion triggers service cleanup that should be suppressed for an active voice session.

Preserve intentional cleanup when the user explicitly stops listening, stops the session, quits Relay Runner, or Sparkle relaunches the app. Do not paper over the issue by merely restarting the bridge silently if the underlying ownership/cleanup contract is wrong.

## Acceptance criteria

- [ ] The exact root cause of bridge loss after Codex App job completion is identified with log/process/socket evidence, not guessed.
- [ ] A live `/relay-bridge` session remains usable after the foreground Codex App sends a final response for a normal job, including after ticket creation/commit/dispatch workflows.
- [ ] After job completion, the bridge re-enters a listening state and can claim the next spoken command without manually invoking `$relay-bridge` again.
- [ ] `/tmp/voice_bridge.sock`, `/tmp/voice_bridge.cwd`, `/tmp/voice_bridge.provider`, heartbeat behavior, TTS FIFO behavior, and the launchctl/direct daemon ownership model are all consistent with the intended active-session contract.
- [ ] Existing explicit cleanup still works when the user stops listening, ends the session, quits Relay Runner, or Sparkle relaunches for an update.
- [ ] Add or revise automated regression coverage so the current false confidence is removed; tests must model the real Codex App completion path closely enough to fail before the fix.
- [ ] Include a manual verification recipe: start `/relay-bridge`, run a foreground Codex job to final response, wait long enough for watchdog/heartbeat edge cases, speak a follow-up command, and confirm it is claimed without restarting the bridge.
- [ ] Provider parity is addressed for Codex and Claude, with any provider-specific lifecycle differences documented.
