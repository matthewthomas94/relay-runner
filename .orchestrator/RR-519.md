## Description

Today a running session holds up to nine PM tabs. They are anonymous and numbered by position ("Session 1", "S1"), closing one deletes its conversation, and only the first tab's conversation resumes on the next Start.

The user wants four fixed, named agents instead. Each agent is a permanent slot with its own conversation, so the user always knows what that agent was working on. Up to four run in parallel. This ticket is the foundation; four follow-up tickets (per-agent voice, the session wheel submenu, the start menus, per-agent work style) depend on it and are out of scope here.

### The agents

| Order | Name | Slug | Kokoro voice |
|---|---|---|---|
| 1 | Puck | `puck` | `am_puck` |
| 2 | Isabella | `isabella` | `bf_isabella` |
| 3 | George | `george` | `bm_george` |
| 4 | Sky | `sky` | `af_sky` |

Define them once in Swift (name, slug, voice id, order). The voice id is recorded here but not used for speech until the voice ticket.

### How it works today (starting points, verify before relying on them)

- `AppState.PMTab`, `pmTabIDs`, `sessionLabel`, `openPMTab`, `selectPMTab`, `removePMTab`, `discardPMTabs` in `Sources/relay-runner/App/AppState.swift` (around lines 1388-1490, 2913, 3056).
- A tab is a context suffix: `AssistantSessionContext.tab` in `Sources/relay-runner/Process/AssistantSessionStore.swift` gives `base#tab-<8 hex>`; the first tab has `tab == nil`. `openPMTab` mints a random tab id.
- Each tab's `Binding` (provider, `nativeSessionID` used to resume, transcript path and more) is persisted in `~/Library/Application Support/relay-runner/sessions/conversation-v1.json`.
- `removePMTab` ends the provider and calls `removeTab`, which deletes the binding and the tab's public history. `discardPMTabs` does the same for every extra tab when the session ends.
- `selectPMTab` on a tab whose provider exited calls `newSession(workingDirectory:tab:)`, which resumes from the binding's `launchableNativeSessionID`.
- The limit is `EmbeddedSessionRegistry.maxConcurrentSessions = 9` in `Sources/relay-runner/Terminal/EmbeddedSessionRegistry.swift`, checked again in AppState ("Nine tabs open").

### What to build

1. **Fixed identity.** Each agent has a stable tab identity derived from its slug, not a random id, so its binding is found again after a stop, after End Session, and after the app relaunches. Today's first-tab conversation (`tab == nil`) becomes Puck's, so the user's current conversation is not lost. Bindings left over from old random tab ids can be dropped.
2. **Limit of four.** At most four agents run at once, one per slot. Replace the nine-tab limit, its messages and its tests.
3. **Stop keeps the conversation.** Stopping an agent (the tab's x, Cmd-W, the wheel's x) ends its provider and keeps its binding. Ending the session, by End Session or by stopping the last running agent, keeps all four bindings. Nothing in this change deletes an agent's conversation.
4. **Start resumes.** Starting an agent that has a binding resumes that conversation, the way an exited tab is turned back on today. An agent with no binding starts a new conversation.
5. **Names everywhere.** Wherever a tab is named or numbered, show the agent's name: the terminal tab strip, the wheel's tab labels, notch messages (for example "Close Session 2" becomes "Stop Isabella"), VoiceOver labels, and the limit message. No "Session n" or "S n" remains.
6. **Agent parameter on the start calls.** `newSession` / `openPMTab` (or their replacements) take the agent to start. Until the wheel and start-menu tickets land, keep the existing controls working with these interim rules: an Add control ("+" in the tab strip, the wheel's Add tab, Cmd-T) starts the first agent in table order that is not running; every other start path (Start Session buttons, the wheel's Start session, `start_session`, Relay Remote, the Notetaker hand-off) starts the most recently active agent, or Puck if none has run.
7. **Publish the agent to the rest of the system.** The follow-up tickets rely on exactly this:
   - the provider process gets `RELAY_SESSION_AGENT=<slug>` in its environment, next to `RELAY_SESSION_KEY`;
   - the session's spool directory (`/tmp/relay-sessions/<session key>/`, see `VoiceSessionSpool.swift`) contains a file `session_agent` holding the slug and a newline, written before the provider starts;
   - `mcp__relay-app__app_status` lists the four agents with name, slug, whether each is running and which is active.
8. **Tell the agent its name.** The foreground PM's startup instructions state its agent name ("You are Puck in this session; the user may address you by that name"), for both providers.
9. **Text.** Update the provider instructions that say the session "can hold up to nine PM tabs" (source under `services/instructions/`, generated into `Sources/relay-orchestrator-mcp/Instructions.generated.swift`) and `docs/session-wheel.md` for the names and the limit.

A session whose base context is a project keeps working: the same four agents apply inside it, with conversations kept separately per context, as tab bindings are keyed today.
