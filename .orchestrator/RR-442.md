## Description

Today a session is bound to one project folder: its working directory, the provider CLI's directory permissions, and a single `RELAY_PROJECT_SCOPE_TOKEN` (`AppState.prepareSessionContext` in `Sources/relay-runner/App/AppState.swift:3085`; `ProjectRegistryV2Service.scopeToken(matching:)` in `Sources/relay-runner/Board/ProjectRegistration.swift`; registry at `~/Library/Application Support/relay-runner/projects/registry-v2.json`). Ticket writes and dispatches for another project are refused.

Target: one foreground session, started from the general project (its working folder stays the app-owned general-tasks folder), that can read and edit any registered project and author tickets or dispatch workers in any of them. Membership in the project registry, plus the user naming the project, is the authority; nothing outside the registry is reachable.

Work, in order:

1. Feasibility first: establish how each provider CLI grants access to additional directories at launch and while a session is running (a project registered mid-session must become reachable without a restart). Record the mechanism and limits per provider in `docs/providers.md`. If a provider cannot do this without weakening its sandbox, stop, report, and do not loosen isolation.
2. Launch the general session with access to every registered project path, for both providers, and extend access when a project is registered during the session.
3. Scope tokens: give the general session a token for every registered project at launch, and a way to obtain a token for a project registered mid-session (for example a Relay Actions or orchestrator tool that returns a token only for a registered project). The daemon endpoints and MCP tools already accept `project_scope_token` per call; keep validation unchanged.
4. Worker launches in `services/orchestrator.py` stay per repository and unchanged.
5. Tests: launch configuration includes every registered path for both providers; token issuance refuses paths outside the registry; existing scope validation tests pass.

External verification: checks that need the live app, real hardware, or a human run what you can from the worktree without installing, releasing, or restarting the running app. If only those checks remain, finish as `verification_blocked`, naming each remaining check in `verification_blocker` and how to run it in `verification_resume`.

## Acceptance criteria

- [ ] From a general session, reading a file in another registered project works without a permission prompt, for Claude and for Codex (manual check per provider recorded in the run log).
- [ ] From a general session, claiming and writing a ticket and dispatching it in another registered project succeed with the issued token; a path outside the registry is refused.
- [ ] A project registered during the session becomes reachable without restarting the session.
- [ ] `docs/providers.md` documents the per-provider directory-access mechanism and any intentional difference.
- [ ] Unit tests cover launch configuration, token issuance and refusal; existing suites pass.
- [ ] Commit source changes only and submit for independent review/merge; do not install, release, or restart the running app.
