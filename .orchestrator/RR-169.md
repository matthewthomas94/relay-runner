## Description

Add a restrained, coherent visual hover system to the unified Workspace board. The board already changes the pointer for many clickable surfaces, but project cards, ticket cards, and most compact actions remain visually static, so users cannot reliably tell what will respond before clicking.

This is an interaction-feedback pass for existing actions, not a new feature or board-layout redesign. Preserve the Workspace composition, ticket selection, editing, drag/drop, scrolling, project filtering, session controls, and provider behavior. Apply hover only to interactive surfaces; static lane panels, headings, metadata, and empty states must remain visually quiet.

Use the existing dark Workspace vocabulary and restrained motion:

- Neutral hover feedback should use a small increase in fill, border, icon, or text contrast. Purple remains reserved for selected, focused, active, and valid drop states. Orange remains reserved for listening or recording and must not appear in generic board hover styling.
- Project cards should gain a clear but quiet hover state. A selected project must remain visually stronger than hover, and an unavailable project must not present as interactive.
- Ticket cards should gain a clear hover state without changing layout. Selected ticket styling remains stronger. While a ticket is being dragged, drag opacity/preview/drop-target feedback takes precedence and hover styling must not flicker or lift the source card.
- Compact controls, including Select all, lane add, edit, detail actions, retry, close, save/cancel, and other board-local buttons, should share the same hover vocabulary rather than each inventing one.
- Cursor changes must remain balanced on enter, exit, disable, and disappearance. Disabled controls stay visually disabled and do not advertise an action.
- Motion should communicate state only, complete in roughly 150 ms with a non-bouncy ease-out curve, avoid animating layout properties, and respect Reduce Motion. Do not add decorative choreography, glass effects, gradients, or new focus rings.
- Keyboard focus should receive equivalent visible affordance on controls where SwiftUI focus can be modeled without reintroducing the excessive system focus halo removed elsewhere.

Prefer a small reusable interaction-state presentation or style layer that makes precedence deterministic instead of scattering unrelated opacity literals. Keep it scoped to the Workspace board unless an existing shared Workspace control already owns the relevant behavior.

## Acceptance criteria

- [ ] Every enabled clickable project card, ticket card, and board-local button has a visible hover response; static columns, headings, metadata, and empty states do not animate or suggest clickability.
- [ ] Project-card states resolve predictably: selected is strongest, hover is subordinate, disabled/unavailable never appears actionable, and pointer behavior matches the visual state.
- [ ] Ticket-card states resolve predictably: selected is stronger than hover, the dragged source suppresses hover treatment, and drag preview/drop-target feedback remains authoritative throughout drag/drop.
- [ ] Hover never changes measured layout or causes card, column, or modal content to jump. Any transform/opacity motion is subtle, completes in about 150 ms with a restrained ease-out curve, and is disabled or reduced when Reduce Motion is enabled.
- [ ] Board-local buttons use a consistent neutral hover fill/border/icon treatment. Disabled buttons remain muted, do not brighten on hover, and keep their existing help/accessibility behavior.
- [ ] Purple remains limited to selected/focused/active/valid-drop semantics. Generic hover introduces no orange; listening/recording and Relay Vision color semantics are unchanged.
- [ ] Existing ticket selection, project filtering, edit/create/delete/detail actions, session start/end, refresh/retry, modal save/cancel, scrolling, and drag/drop behavior are unchanged.
- [ ] Existing focus-ring suppression remains intact. Keyboard-focused interactive controls receive a restrained custom affordance where supported, without restoring excessive system focus halos.
- [ ] Hover-state precedence and presentation decisions are covered by deterministic tests where practical, including selected, disabled, dragging, and reduced-motion cases.
- [ ] Provider-facing behavior remains identical for Codex and Claude; no config, daemon, ticket-schema, or provider-launch behavior changes.
- [ ] `swift test` and `git diff --check` pass.
