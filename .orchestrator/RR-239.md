## Description

Restore the response pill's intended message-preview contract. When the
foreground provider supplies an authoritative final response, the expanded TTS
pill must show that response's actual content. It must not substitute a
messenger-generated wrapper or generic phrase such as a promise of a fresh or
fast answer. A response-bearing pill must never render with an empty body. If
the authoritative response has not arrived yet, the UI must remain in a compact
working state instead of expanding a blank pill.

The current path couples display and speech text. An authoritative final is
submitted to the persistent messenger, the messenger may synthesize different
spoken wording, and `services/voice_bridge.py` sends that wording through
`_queue_tts_text`. That function publishes the same string as the waiting
preview before queuing it for speech. As a result, the body rendered by the
Swift overlay can be messenger copy rather than the provider response the user
is waiting to read.

Separate the semantic response preview from the text selected for audio. For an
authoritative final, the display payload must retain the provider-visible final
response while the speech path may apply TTS-safe formatting or a concise
spoken rendering. Any spoken rendering must convey the actual outcome directly;
it must not degrade into a canned acknowledgement or content-free introduction.
User-turn acknowledgements and progress updates must not overwrite or masquerade
as the final response preview.

Preserve the nonblank and state-ordering guarantees delivered by RR-203 and
RR-217. This ticket must not solve the problem by introducing another fixed
fallback sentence, by waiting for playback to reveal the body, or by bypassing
newest-command and exactly-once delivery checks. RR-239 follows RR-238 because
that ticket establishes authoritative ownership for final replies on the same
messenger and completion path. The nonblank invariant applies regardless of a
persisted `message_preview` preference: retire, migrate, or reinterpret that
setting rather than allowing it to produce an empty response pill.

## Acceptance criteria

- [ ] Define an explicit provider-neutral payload contract that can carry
      authoritative display text separately from spoken text, including Relay
      command sequence and id metadata.
- [ ] No explicit reply, completion-hook recovery, messenger failure, silent
      messenger result, playback mode, event-ordering race, or legacy
      configuration can render an expanded response pill with a nil,
      whitespace-only, or otherwise empty body.
- [ ] Before an authoritative response is available, the UI remains in an
      appropriate compact processing state; it does not present an expanded
      response-ready pill without response content.
- [ ] When an authoritative foreground response is received, the waiting pill
      displays that response's substantive content before playback starts,
      even when the messenger produces a shorter or differently worded spoken
      rendering.
- [ ] TTS for an authoritative final conveys the actual outcome without canned
      lead-ins or content-free substitutes. Empty, silent, failed, or
      non-substantive messenger output falls back to the authoritative response
      rather than another generic sentence.
- [ ] A user-turn acknowledgement, reasoning summary, or worker lifecycle
      update cannot overwrite an already received authoritative final preview
      or remain presented as that command's final response.
- [ ] The implementation preserves readable response content through
      display-specific normalization while keeping Markdown removal and other
      speech-only cleanup from silently changing the visual preview.
- [ ] With deferred playback, the full response body is nonempty and visible in
      the expanded **Double tap Option to play** pill as soon as the final is
      available; pressing Option is never required to populate it.
- [ ] Preview text remains stable through waiting, preparing, speaking,
      cancellation, and idle transitions, and consecutive commands cannot
      reuse either the previous authoritative preview or its spoken rendering.
- [ ] Existing installations with `message_preview = false` are migrated or
      handled so every response-bearing pill still displays the response. The
      settings UI and configuration documentation no longer imply that a blank
      response body is a supported mode.
- [ ] Automatic-playback behavior remains intact after making the visible
      response body mandatory.
- [ ] Stale-command rejection, explicit-reply/completion-hook deduplication, and
      exactly-once final delivery remain intact after the payload split.
- [ ] Add Python regression coverage that supplies distinct authoritative,
      messenger, acknowledgement, and stale-command strings and verifies which
      text reaches the preview publisher and which reaches the TTS queue.
- [ ] Add Swift regression coverage for the resulting service-event order,
      including the blank-body races previously covered by RR-203 and RR-217.
- [ ] Verify equivalent behavior for Codex and Claude app-owned sessions,
      including explicit orchestrator replies and completion-hook recovery.
- [ ] Relevant messenger, voice-bridge, TTS-worker, and overlay state-machine
      test suites pass.
