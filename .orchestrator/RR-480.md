## Description

Background: RR-448 (done) scoped porting the Python services in `services/` to Rust. Read its `## Spike report` first; it holds the inventory, interface list, evidence and staged plan. Use `scripts/relay-ticket-history show RR-448` if the ticket has been archived.

In a Relay session the speech stack runs inside the voice bridge: `services/voice_bridge.py` (around lines 5903-5908) builds `TTSWorker` and wraps it in `SpeechCoordinator`, then reaches into them through attributes such as `speaking`, `playing`, `control_session`, `session_playback_states` and `queue_depth` (around lines 1051-1199). That coupling makes it impossible to replace speech without replacing the bridge. A standalone mode already exists for the tutorial (`tts_worker.py` reading stdin).

Still in Python, move speech into its own long-lived process and make the bridge a client of it:

- Write `docs/specs/speech-service-protocol.md`: the transport (a Unix stream socket with newline-delimited JSON is the expected choice), every request (speak intent with its metadata, stop, skip, pause, replay, play request, focus and session playback changes, remote synthesis for Relay Remote, shutdown), every event the service emits (state changes, playback started and finished per intent, queue depth, errors), ordering guarantees, and what happens when either side restarts.
- A new entry point, for example `services/speech_service.py`, that hosts `SpeechCoordinator`, `TTSWorker` and `SpeechPlayer` and serves that protocol. Existing external surfaces keep working unchanged: `/tmp/tts_control.sock`, state datagrams to `/tmp/voice_state.sock`, `/tmp/tts_in.fifo`, the `voice-audio.lock` lease, the tutorial stdin mode and `preview_voice.py`.
- The bridge starts, supervises and talks to the service through a small client, replacing every direct attribute access. A switch keeps the in-process path for one release as rollback.
- A black-box contract suite under `tests/contract/` that starts the service command from an environment variable (default: the Python service), with synthesis and audio output replaced by a documented test mode that the service itself provides (for example an environment variable that makes it render silence of a deterministic length and write playback events to a file instead of opening an audio device). The suite covers queueing in order, supersede and replace rules, barge-in, skip, replay history, pause and resume, the 50-item cap, stale intents, a remote synthesis request, and a service restart with queued speech.

Do not change what the user hears or when. RR-438, RR-464 and RR-465 fixed click, ordering and lost-reply bugs in this area; their tests must keep passing.

## Acceptance criteria

- [ ] `docs/specs/speech-service-protocol.md` describes every request and event, and the contract suite references it case by case.
- [ ] With the switch on, the bridge process no longer imports `kokoro_onnx`, `numpy` or `onnxruntime`; the run log shows the bridge's resident memory before and after.
- [ ] The contract suite passes against the Python service and imports nothing from `services/`.
- [ ] `python3 -m unittest discover -s tests` and `swift test` pass, including the speech coordinator, replay and bridge preemption suites.
- [ ] A live session check confirms replies are spoken, barge-in stops speech, and replay works; if this cannot be run on the worker machine the ticket ends `verification_blocked` naming the check.
