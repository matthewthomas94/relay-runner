## Description

The board already calls `dispatch_ticket` when a card lands in `ready`, but that event path is not enough as the only guarantee. A ticket can sit in `ready` without an agent if the app relaunches, the bridge reconnects, a filesystem/update event is missed, a user edits the ticket file directly, or the board/daemon loses the immediate dispatch call.

Add a product-side sweeper that continuously reconciles the active repo's `.orchestrator/` board and dispatches any ticket that is eligible in `ready` but not already active. This should make drag-to-ready feel immediate while also recovering stale ready tickets without requiring the user to manually notice and re-dispatch them.

Keep dispatch idempotent through the existing daemon chokepoint: the sweeper should ask for work often enough to feel live, but duplicate polls must not spawn duplicate workers for the same ticket.

## Acceptance criteria

- [x] A ticket that becomes `ready` via board drag or editor save is still dispatched immediately through the current event path.
- [x] A ticket already sitting in `ready` with `run_id: null` is discovered and dispatched automatically on the next sweeper pass.
- [x] The sweeper runs after relevant lifecycle boundaries such as app launch, board/project resolution, bridge reconnect, or orchestrator daemon restart.
- [x] The sweeper is idempotent: ready tickets with an active run, `in_progress` tickets, `done` tickets, canceled tickets, or tickets with unsatisfied `depends_on` do not spawn duplicate workers.
- [x] The behavior is provider-neutral and works for both Codex and Claude workers through the same orchestrator dispatch path.
- [x] Logs or run-state updates make it clear when a ready ticket was auto-dispatched by the sweeper versus by a direct board drag/save.
- [x] Focused tests or smoke coverage verify direct ready-transition dispatch, stale-ready recovery, and no duplicate dispatch for already-active tickets.
