## Description

RR-440 roughly halved idle CPU, but on 2026-10-29 the installed build of main 3c986b91 still missed its targets. The measurements were taken with a Claude session active, no speech, and 600 s windows:

| Workspace tab | relay-runner | orchestrator.py |
|---|---|---|
| Terminal | 4.43% | 11.49% |
| Work | 5.24% | 10.52% |
| Target | <= 3% | <= 2% |

Earlier figures: the first RR-440 fix measured 6.8% (app) and 19.1% (daemon); the previous build averaged about 15% and 38% over its lifetime. The user accepted RR-440 as is and asked for this follow-up.

Already fixed by RR-440 (do not redo): Workspace dashboard polling only on the Work tab; program-graph re-ingest only on change; one SQLite connection per store; drain writes only for changed items; ticket and artifact-head parse caching; and the run-list cache. Two stale queue drains were also cancelled by hand.

What is known about the rest: a native `sample` of the live daemon over 8 s showed its busiest thread active only about 3% of the time, mostly SQLite page reads. That suggests the 10-minute average comes from periodic bursts the short sample missed. Candidates to rule in or out include artifact sync and archive/retention passes, graphify ingestion, run-log capping, the app's 3 s bridge-watchdog ready sweep, the remaining queue drain reconcile (one active drain covers RR-428, RR-433 and RR-440), continuity checks, and per-request threads for app polls. Nothing has profiled the app's main thread yet.

Work:

1. **Daemon profiler.** Add an opt-in, in-process sampling profiler to the daemon, for example a thread that reads `sys._current_frames()` every 10-20 ms when an environment variable or config flag is set and writes collapsed stacks to a file. It must cost nothing when off. `py-spy` against a live process needs root on macOS, so do not depend on it.
2. **Reproduce realistically.** Run a sandbox daemon against copies of the live state in `~/Library/Application Support/relay-runner/orchestrator/` (runs.db, queue_drains.db, orchestrator.db and the others) and the 5 registered projects. Simulate the app's request pattern (the 3 s watchdog sweep and the Work-tab dashboard poll). Never touch the live files. Profile 10 minutes and rank CPU by source, including timer-driven bursts.
3. **App main thread.** Use `sample` on a relay-runner build (or the running app's pid, read-only) for 60 s each with the Workspace closed, on Terminal and on Work. Rank recurring main-thread work such as SwiftUI invalidations, timers, polling and overlay animation.
4. **Fix and prove.** Fix the top contributors in both processes and record before/after numbers against the same copied state.

External verification: checks that need the live app, real hardware, or a human run what you can from the worktree without installing, releasing, or restarting the running app. If only those checks remain, finish as `verification_blocked`, naming each remaining check in `verification_blocker` and how to run it in `verification_resume`.
