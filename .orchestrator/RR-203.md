## Description

Fix an intermittent response-presentation race in deferred-playback mode. The response pill often expands with the `Double tap Option to play` title while its response body is blank. The missing text then appears only after the user double-taps Option to start playback.

The response preview should be populated as soon as the response becomes available and the pill enters its waiting state. Starting playback may update the action hint and audio state, but it must not be the trigger that first makes already-received response text visible.

## Acceptance criteria

- [ ] With message previews enabled and automatic playback disabled, a completed response appears in the expanded waiting pill before the user presses or double-taps anything.
- [ ] The waiting pill never presents a full-size blank body when nonempty response text has already been received.
- [ ] Double-tapping Option starts playback and updates the pill state without being required to populate the response body.
- [ ] Event-ordering races between response delivery, `message_waiting`, TTS preparation, and playback do not replace a nonempty preview with an empty or stale value.
- [ ] Consecutive responses display their own text and do not briefly reuse or lose the preceding response preview.
- [ ] Existing behavior remains correct when message previews are disabled and when automatic playback is enabled.
- [ ] Codex and Claude sessions exhibit the same waiting-pill and playback behavior.
- [ ] Automated Python and Swift tests reproduce the empty-body ordering case and verify preview preservation through waiting, preparing, speaking, cancellation, and idle transitions.
