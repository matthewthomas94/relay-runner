## Description

Fix a live installed-app regression where Relay Runner keeps queued voice prompts behind a provider-turn safe-boundary after the foreground provider has already completed. Sanitized evidence from one Codex session showed a conversational command received and queued immediately, the foreground task completing about ten seconds later, and terminal delivery continuing to emit `safe_boundary_wait` with `deferral_reason: provider_turn` for roughly another 2 minutes 19 seconds. The command was not claimed until the wait had lasted about 148 seconds. Once the boundary finally cleared, the pending command and later queued turns drained serially without any implementation worker having been active.

The lifecycle records disagreed during the delay: the Relay-correlated turn had reached a terminal stale state, while a separate `origin: manual` provider-turn record remained active until immediately before delivery resumed. Diagnose whether that record is created by duplicate prompt-submit correlation, startup/session identity drift, or failure to close the correct manual record. Establish one authoritative identity and terminal transition for the actual foreground turn so an unrelated or orphaned record cannot make an idle terminal look busy indefinitely.

Treat this as a live regression of RR-238 and RR-272, especially RR-272's requirement that an idle provider with no real draft claim a queued command within 500 ms p95. Preserve the safety boundary for genuine typed or pasted terminal input. Do not inject voice into a real active manual turn, overwrite a draft, weaken newest-intent reply suppression, drop ordered inbox items, or allow a stale conversational turn to act on a newer unclaimed command.

## Acceptance criteria

- [ ] A deterministic regression reproduces the observed disagreement: the Relay-correlated foreground turn reaches a terminal state while a separate manual-origin record remains active and blocks the next queued voice command behind `safe_boundary_wait`.
- [ ] The root cause is identified at the exact lifecycle boundary, including why one provider prompt produced or retained records with different session/turn identity and why the real completion did not release delivery.
- [ ] Provider-turn activity used by `RelayVoiceCommandDelivery` is scoped to the actual live embedded provider session and cannot be held active by an orphaned, duplicate, stale, or unrelated manual record.
- [ ] A queued voice command is claimed within 500 ms p95 after the actual foreground provider turn reaches its terminal event when there is no genuine terminal draft or active manual turn.
- [ ] Rapid conversational turns received during an active turn remain ordered and drain one at a time immediately after verified safe boundaries; they do not require terminal typing, a new recording, app restart, or a blind timeout to make progress.
- [ ] A stale foreground turn still suppresses its user-visible reply when a newer command exists, then releases ownership so Relay Runner can claim and inject the ordered next item without adopting that newer item itself.
- [ ] Genuine typed and pasted drafts remain untouched, and a real manually submitted provider turn continues to block voice injection until its exact completion or an explicitly supported atomic steering handoff.
- [ ] Completion correlation is exact across prompt submit, Stop, StopFailure, process termination, session restart, and app teardown; duplicate or late events are idempotent and cannot leave an active lifecycle record behind.
- [ ] Privacy-safe diagnostics expose the active record's provider, origin, session/turn correlation, age, and release reason without storing prompt, transcript, response, or other terminal content.
- [ ] Focused Swift tests cover safe-boundary aggregation, stale/manual record disagreement, ordered drain timing, genuine manual-turn barriers, and session teardown; focused Python tests cover prompt-submit binding, completion correlation, duplicate events, and stale-current command races.
- [ ] Codex and Claude pass equivalent lifecycle and delivery tests using their provider-specific signals, with any intentional difference documented rather than hidden behind a shared timeout.
- [ ] A freshly built installed app passes a mounted smoke test beginning with an app-owned session-start command followed by several rapid conversational turns; durable evidence shows each prompt claimed promptly after the prior terminal event and no phantom active turn remains.
- [ ] The run log records the root cause, the minimal ownership-boundary repair, why RR-238/RR-272 coverage missed this startup or rapid-turn path, tests run, installed build identity, and mounted timing evidence.
