## Description

Design a permanent, provider-neutral repair for Relay voice commands that appear dropped because terminal delivery remains blocked after the real foreground provider turn is idle. In the captured incident, the durable inbox retained the command and eventually delivered it exactly once, but delivery waited about 182 seconds behind `safe_boundary_wait` with `deferral_reason=provider_turn`. The blocking active record belonged to a separate Messenger-owned provider process rather than the embedded foreground session. That child inherited the foreground `RELAY_PROVIDER_SESSION_ID`, allowing its lifecycle hook to publish a foreign manual-turn record inside the same shared provider-session scope.

Treat this as an ownership-model problem rather than another stale-record special case. Map every producer and consumer of provider-turn state, including the embedded foreground PM, persistent Messenger, read-only sidecars, manual typed turns, Codex app-server, Claude stream-json, completion hooks, the durable intent inbox, and Swift terminal delivery. Determine the smallest safe containment and the durable end-state in which only explicitly identified foreground work can hold the foreground prompt-delivery gate. Preserve genuine manual-turn and pending-draft protection, ordered exactly-once command claims, stale-output suppression, scoped preemption, restart recovery, and privacy-safe diagnostics. Do not use a blind timeout, global record clear, arbitrary newest-record match, or automatic provider restart.

As part of the architecture work, assess the final MCP `2026-07-28` stateless protocol revision and whether its model can remove related hidden session coupling in Relay Runner. The revision removes the protocol-level `initialize` / `initialized` handshake and `Mcp-Session-Id`, makes every request self-describing, states that a stdio process or connection is not a conversation/session, and requires application state spanning requests to be referenced by an explicit handle. Relay's `relay-orchestrator-mcp`, `relay-actions-mcp`, and `relay-vision-mcp` are currently hand-rolled stdio servers advertising `2024-11-05`; comments claiming newer revisions are backward-compatible must be re-evaluated because `2026-07-28` is a breaking protocol era.

Keep the applicability boundary explicit. Voice prompt injection currently travels through Relay's bridge, durable inbox, shared provider-turn ledger, and embedded terminal rather than through an MCP request, while the Messenger uses Codex app-server or Claude stream-json with MCP disabled. A protocol-version bump alone therefore cannot fix the captured delay. Investigate whether MCP's explicit per-request identity and handle pattern should inform Relay's internal ownership envelope, and separately whether upgrading or dual-speaking the local MCP adapters would address other reconnect, process-lifetime, routing, observability, or hidden-session problems without breaking the installed Codex and Claude clients.

- [ ] Reproduce the captured failure deterministically without raw prompt content: a Messenger or sidecar child shares or inherits the foreground provider-session identity, publishes an active foreign lifecycle record, the embedded foreground provider is idle, and a queued command remains in `safe_boundary_wait` until the foreign record completes.
- [ ] Correlate the durable inbox, delivery ledger, provider-turn records, process roles, native provider session/turn identifiers, and completion events to prove whether each command was lost, delayed, duplicated, retried, or delivered exactly once.
- [ ] Inventory every producer and consumer of `RELAY_PROVIDER_SESSION_ID` and provider-turn state, including subprocess environment inheritance, and document the current trust and ownership boundaries for the embedded PM, Messenger, sidecars, manual turns, Codex, and Claude.
- [ ] Define an explicit provider-neutral ownership envelope for state that may gate delivery. At minimum evaluate app session, provider, actor role, producer identity, native session and turn, source command and intent, lifecycle state, and recovery generation; no consumer may infer conversation ownership solely from a process, connection, inherited environment variable, or globally shared file.
- [ ] Specify the smallest safe containment, including whether Messenger and sidecar subprocess environments should exclude foreground-only identity and whether the delivery gate should require an explicit foreground role. Treat environment sanitization as defense in depth rather than the sole correctness boundary.
- [ ] Specify the durable end-state and compare bounded alternatives such as role-scoped records in the existing ledger, per-app-session storage, or an authoritative broker with atomic lifecycle transitions. Recommend the least complex design that removes cross-role and cross-session aliasing rather than adding time-based release heuristics.
- [ ] Preserve genuine typed/pasted drafts and active manual foreground turns, exactly-once ordered inbox claims, stale-current reply suppression, scoped replacement/preemption, idempotent late or duplicate completion handling, process-crash recovery, app teardown, and restart recovery.
- [ ] Define measurable delivery guarantees and a deterministic fault-injection matrix covering idle foreground plus busy Messenger, concurrent Messenger and PM work, Messenger/sidecar crash, missing or late hooks, native session drift, two app sessions, rapid queued commands, and no-provider-turn startup.
- [ ] Compare MCP `2026-07-28` with Relay's current `2024-11-05` hand-rolled stdio implementations, including removed initialization/session assumptions, per-request `_meta`, `server/discover`, cancellation, request-scoped state, explicit application handles, and the breaking backward-compatibility boundary.
- [ ] Establish an evidence-backed Codex and Claude client compatibility matrix for Relay's three local MCP adapters. Determine whether to remain on the legacy protocol temporarily, dual-speak, adopt a Tier 1 SDK, or migrate directly; do not assume the installed clients support the new revision merely because the protocol and SDKs do.
- [ ] State explicitly which long-standing Relay issues stateless MCP could plausibly improve and which it cannot. In particular, determine whether any MCP-based delivery design can inject unsolicited user turns safely, or whether MCP remains only a tool-server boundary and voice delivery must retain its own durable channel.
- [ ] Produce an implementation-ready recommendation with responsible code boundaries, migration and rollback sequencing, focused Python/Swift/protocol tests, mounted Codex and Claude UAT, privacy-safe diagnostics, and observable success criteria.
- [ ] Recommend a minimal dependency-ordered set of follow-up implementation tickets, separating the urgent voice-delivery ownership repair from an MCP protocol migration when they do not share a safe release boundary. Do not modify product source code during the spike.

**Conclusions**

- Root cause: foreground ownership is aliased through one inherited string. The app creates one `RELAY_PROVIDER_SESSION_ID`, exports it before starting the bridge, and the bridge passes it into `voice_bridge.py`; Messenger and sidecar provider subprocesses then inherit their parent environment because their `Popen` calls supply no `env`. Their lifecycle hooks can consequently create foreign records in the foreground scope (`ProcessManager.swift:929-940,1068-1095`; `scripts/relay-bridge:1050-1074`; `messenger.py:353-367,674-687`).
- The failure is deterministic without prompt content: create a queued synthetic command, publish an uncorrelated Messenger/sidecar `UserPromptSubmit` carrying the foreground provider-session ID, and the hook writes `state=active, origin=manual`; Swift treats every active record in that provider-session scope as a delivery barrier and emits `safe_boundary_wait`. Publishing the matching foreign Stop changes it to `completed_manual`, after which the next 200 ms delivery poll claims the command once. Existing tests already prove the same indistinguishable record shape blocks until exact release (`relay_completion_hook.py:691-776,807-849`; `EmbeddedTerminal.swift:843-917,1274-1316,1424-1440`; `EmbeddedTerminalSessionTests.swift:1657-1717`).
- The captured command was delayed, not lost or duplicated: RR-321 records approximately 182 seconds of `provider_turn` deferral followed by one delivery. The inbox prevents a second item from materializing while an earlier item is delivered or claimed and advances only after claim/ack observation (`RR-321.md:19`; `intent_inbox.py:273-369`). No captured incident artifacts are present to independently recompute the 182-second correlation.
- Producer/consumer inventory: the embedded Codex/Claude foreground and genuine typed turns invoke `relay_completion_hook.py`; the same hook can run in inherited Messenger or sidecar providers; the hook creates and terminalizes records; Swift terminal teardown also terminalizes scoped records. Consumers are Swift prompt delivery, ProcessManager liveness/recovery, completion correlation, voice-bridge claim acknowledgement and missing-final arbitration, and the durable inbox via `provider_turn_seen`. Messenger and sidecars should never be delivery-gate producers even though sidecars have their own inbox lifecycle (`relay_completion_hook.py:415-510,691-919`; `EmbeddedTerminal.swift:1482-1504`; `ProcessManager.swift:299-455`; `voice_bridge.py:1765-2027,2050-2153`).
- Current records cannot distinguish a genuine foreground manual turn from a foreign provider process: they contain provider-session, provider, origin, native session/turn, command/intent and state, but no app-session, actor role, producer identity, gate authority or recovery generation. The hook falls back to the inherited provider-session value, while Swift gates solely on provider-session plus `state=active` (`relay_completion_hook.py:396-401,753-803`; `EmbeddedTerminal.swift:1424-1440`).
- The required ownership envelope should be `{schema_version, app_session_id, provider, actor_role, producer_id, gate_scope, foreground_gate_handle, native_session_id, native_turn_id/local_turn_seq, source_command_seq/id, intent_id, lifecycle_state, recovery_generation, event_id, timestamps, release_reason}`. Only records with the current app session, recovery generation, foreground gate handle, provider, and `actor_role` of `foreground_pm` or `foreground_manual` may hold `gate_scope=prompt_delivery`. Process, connection, native session, inherited environment, newest record, or global file membership must never independently grant gate authority.
- Smallest safe containment: give Messenger and sidecar subprocesses explicit sanitized environments that remove foreground-only identity, hook, reply-helper and turn-ledger variables; assign explicit non-gating roles; and require Swift to filter on an explicit current foreground role and gate handle. Keep `RELAY_APP_SESSION_ID` only for sanitized diagnostics if needed. This prevents the captured alias immediately, while role/handle validation—not environment hygiene—forms the correctness boundary (`messenger.py:359-367,679-687`; `sidecar_lane.py:47-132`; `EmbeddedTerminal.swift:1430-1440`).
- Durable end-state recommendation: retain the existing ordered inbox but move provider lifecycle into a versioned, app-session-keyed authoritative broker with atomic, idempotent transitions and a single Swift-readable projection. Role-scoped records alone are smallest but leave unlocked JSON read-modify-write races; per-app-session files isolate sessions but not roles; an atomic broker removes both cross-role/session aliasing and concurrent-writer loss. Current Python and Swift writers independently replace the same JSON snapshot (`relay_completion_hook.py:415-454`; `EmbeddedTerminal.swift:1482-1504`).
- Preserve current safeguards independently of the new gate: terminal draft tracking remains the first barrier; genuine foreground manual turns remain active until exact Stop/StopFailure/process-exit/teardown; the inbox retains FIFO stable delivery/claim/ack identities; stale finals remain suppressed; cancellation remains item/ticket scoped; terminal events are idempotent. Note that startup currently rewinds delivered/claimed leases to pending, so crash-window exactly-once execution still depends on stable identities and downstream idempotency rather than transport alone (`EmbeddedTerminal.swift:862-917,1207-1316`; `intent_inbox.py:28-100,106-175,221-369`; `relay_completion_hook.py:828-919`).
- Measurable guarantees: with no draft or authorized foreground active turn, claim within 500 ms p95; a busy Messenger/sidecar adds zero gate delay; after an exact foreground terminal event, the next item claims within 500 ms p95; FIFO order follows `(command_seq, within_turn_order, ordinal)`; each intent has one accepted claim/ack identity and one terminal effect; cross-app/role records never change eligibility; diagnostics contain identities, roles, states, ages and release reasons but no prompt, response, transcript path or terminal content (`intent_inbox.py:273-324`; `EmbeddedTerminal.swift:1274-1286,1443-1479`; `relay_completion_hook.py:1-8,580-623`).
- Fault matrix: idle foreground plus busy Messenger must claim normally; concurrent PM/Messenger work blocks only on PM; Messenger/sidecar crash cannot hold the gate; late or duplicate terminal events are no-ops after the first atomic transition; native-session drift may reconcile only within one foreground handle and unique native turn; two app sessions and recovery generations are isolated; rapid commands lease one at a time; no-turn startup is immediately eligible; app teardown terminalizes only its generation. A missing foreground completion signal must fail safe and retain the command durably until an exact provider event, process-exit or teardown signal—never a blind timeout.
- MCP cannot repair this voice delay. Voice injection uses the bridge, SQLite inbox, provider-turn state and embedded PTY, while Messenger uses Codex app-server or Claude stream-json with MCP explicitly disabled. The ticket states this boundary directly, and the subprocess command lines confirm empty MCP configurations (`RR-321.md:23-25`; `messenger.py:323-351,653-672`; `sidecar_lane.py:47-99`).
- All three MCP adapters are hand-rolled newline-delimited stdio JSON-RPC servers advertising `2024-11-05`. They implement legacy `initialize`, `notifications/initialized`, `tools/list` and `tools/call`; cancellation is accepted as a no-op. They do not implement `server/discover`, request-scoped identity/handle validation, meaningful cancellation, or `_meta` propagation. The comments claiming all newer revisions are backward-compatible are invalid for the ticket-provided breaking `2026-07-28` era (`relay-actions-mcp/Server.swift:3-18,95-163`; `relay-vision-mcp/Server.swift:11-24,93-151`; `relay-orchestrator-mcp/Server.swift:12-16,92-140`; `RR-321.md:23,44`).
- Compatibility matrix: all three adapters are registered with both Codex and Claude and currently target the same legacy protocol; installed-client support for `2026-07-28` is unproven for both providers. Remain on legacy temporarily, then dual-speak only after mounted handshake tests. Do not migrate directly. Prefer a Tier 1 Swift SDK only if a follow-up verifies support for both legacy stdio and `2026-07-28`; the current package has no MCP SDK dependency (`scripts/relay-bridge:1014-1047,1535-1560`; `Package.swift:7-45`).
- Stateless MCP can improve adapter reconnect behavior, per-request routing/observability, cancellation and explicit application handles. Relay Actions/Vision already open fresh app-socket connections per tool call, and the orchestrator re-reads its daemon port per request, so some reconnect coupling is already bounded (`ConfirmationClient.swift:3-20,46-55`; `relay-orchestrator-mcp/HTTPClient.swift:3-8,33-46`). Stateless MCP cannot provide unsolicited user-turn injection through a standard tool-server boundary; voice delivery must retain its own durable channel. MCP's explicit request identity and handle model should nevertheless be copied into Relay's internal ownership envelope.

**Uncertainties**

- The spike was constrained to read-only inspection; no reproduction, test, build or mounted UAT was executed. The reproduction is derived from current control flow and existing fixtures.
- The snapshot does not contain the captured inbox database, provider-turn ledger or delivery-event log, so the reported 182-second timing and exactly-once outcome are accepted from RR-321 rather than independently recomputed.
- Installed Codex and Claude versions and their `2026-07-28` MCP support are absent from the snapshot. Registration code proves configuration intent, not handshake compatibility.
- The final `2026-07-28` protocol details are accepted from the refined ticket because network access was forbidden; exact wire schemas and available Tier 1 Swift SDK support could not be refreshed.
- No provider-neutral mechanism can safely infer that a still-running foreground provider is idle after every completion signal is missing. That case must retain durable work and fail safe until another authoritative lifecycle signal exists.
- Current `/tmp` singleton paths imply that simultaneous app-owned sessions are not fully isolated. The proposed two-app-session guarantee requires explicit app-session storage or broker keys and dedicated tests.
