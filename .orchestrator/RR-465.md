## Description

On 2026-11-06 between 20:41 and 20:52 local time the app watchdog relaunched the voice bridge five times, each recorded in the support diagnostics as `bridge_recovery` with `reason=bridge-lost bridge_seen=true`. The bridge process was running and its log shows no error at any of those moments; it was killed by the recovery itself. The same burst pattern appears in the diagnostics on 2026-11-03. Every restart happened while the Mac was under heavy memory pressure (swap 7.8 GB of 9.2 GB used, load average about 14 on 10 cores, about 37 Claude and Codex processes from running workers).

Two defects combine to lose the user's spoken reply (read at commit 0d212a6a):

1. **Liveness probes spawn child processes and treat a spawn failure as "dead".** `ProcessManager.bridgeDaemonAlive()` (Sources/relay-runner/Process/ProcessManager.swift:247) spawns `/usr/bin/pgrep -f voice_bridge.py`; the fallback `recordedBridgeProcessAlive()` (line 922) spawns `/bin/ps`. Both return `false` when `Process.run()` throws. When both are false, `AppState.bridgeWatchdogAction` (Sources/relay-runner/App/AppState.swift:3925) gets `bridgeProcessAlive == false`, skips the 60 s `liveBridgeUnreachableGrace`, and returns `.recoverDaemon` on a single sample. The only guard is the 15 s `bridgeRecoveryCooldown`.
2. **Recovery deletes the completion hook's turn ledger.** `removeBridgeRuntimeFiles()` (ProcessManager.swift:2360) and the bridge's own shutdown path (services/voice_bridge.py, the `finally` block near line 5755) delete `/tmp/voice_provider_turns.json` and the session spool's `voice_cmd_claimed.json`. `relay_completion_hook._find_turn_record` (services/relay_completion_hook.py:780) correlates a Stop event only through that v1 JSON file, even though the same turn is still `active` in the broker database `/tmp/relay_intent_inbox.sqlite3` and its projection `/tmp/voice_provider_turns_v2.json`. After a restart mid-turn the Stop finds no record, publishes nothing, the turn stays open until the next prompt orphans it, and `relay_reply.py` refuses with "claimed command unavailable". Observed for commands 173 to 175 on 2026-11-06: only the messenger fallback was spoken.

Scope: make the watchdog robust to transient probe failure, and make a bridge restart within the same provider session preserve enough state for the hook to publish the final reply. Keep the existing behaviour that a genuinely dead bridge is recovered, and that `end_session` / explicit stop still clean the runtime files.

## Acceptance criteria

- [ ] `bridgeDaemonAlive()` and `recordedBridgeProcessAlive()` check the pid in `/tmp/voice_bridge.pid` with `kill(pid, 0)` (plus a cheap command-line check that does not spawn a process, e.g. `proc_pidpath` / `sysctl KERN_PROCARGS2`) before any `pgrep`/`ps` fallback. A probe that cannot run (spawn failure, EAGAIN, ENOMEM) returns "unknown", not "dead".
- [ ] `bridgeWatchdogAction` returns `.recoverDaemon` for `bridge-lost` only after at least two consecutive samples report the daemon dead, or after `liveBridgeUnreachableGrace` has elapsed; an "unknown" sample never counts as dead. Covered by unit tests in `tests/RelayRunnerTests/BridgeRecoveryTests.swift` or `WatchdogSessionRecoveryTests.swift`, including a sequence `alive, unknown, unknown, alive` that produces no recovery and `dead, dead` that does.
- [ ] A watchdog recovery (`startBridgeRecovery` with reason `bridge-lost`, `menu-session-lost` or `voice-delivery-timeout`) whose provider session id is unchanged no longer deletes `/tmp/voice_provider_turns.json` or the spool's `voice_cmd_claimed.json`; explicit stop (`killBridge(stopRequested: true)`, `end_session`) still removes them. Covered by a test.
- [ ] `relay_completion_hook._find_turn_record` falls back to the broker database (or its v2 projection) when the v1 file has no matching record for the session, so a Stop after a mid-turn bridge restart still produces `completed_final` and a delivered `authoritative_reply`. Covered by a Python test under `tests/` that deletes the v1 file between prompt submit and Stop.
- [ ] `support-diagnostics` `bridge_recovery` events include which probe failed (`pid_signal`, `pgrep`, `ps`, or `socket_missing`) in the summary, so the next occurrence is diagnosable without app logs.
- [ ] `swift test --filter 'BridgeRecoveryTests|BridgeConsumerLivenessTests|WatchdogSessionRecoveryTests|BridgeRestartDeliveryTests'` and `/opt/homebrew/bin/python3 -m unittest discover -s tests -p 'test_relay_completion_hook*.py'` and `-p 'test_provider_turn_broker.py'` pass.
- [ ] `docs/orchestrator.md` describes the two-sample rule and that the final reply survives a watchdog restart.
