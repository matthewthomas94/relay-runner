## Description

Diagnose and fix the recurring production regression where double-tapping Option no longer replays the most recent eligible Relay Runner speech. The failure has persisted across several attempts, so do not treat this as another isolated metadata toggle or assume that passing unit tests prove the installed behavior.

Establish the failing boundary end to end before changing code: global and local `NSEvent` delivery; `CapsLockGesture` double-tap recognition; `STTEngine` polling and timestamped `__PLAY__`; bridge routing through `play_or_replay`; speech-coordinator replay selection and freshness; `TTSWorker` retained audio/text and process lifecycle; and actual audio start/completion. Distinguish a missing gesture from a dropped FIFO control, an ineligible or superseded speech intent, a lost replay buffer, and an audio-process failure. Also distinguish first play from replay after a confirmed initial `played` event, and deferred Queue playback from Auto mode.

Treat RR-252, RR-256, RR-271, and the recent `1e44b81` progress-speech replayability fix as prior evidence, not proof of correctness. Explain which prior assumption or test boundary allowed the current regression to survive. Preserve a privacy-safe diagnosis in this ticket's run log, then implement the smallest durable repair at the authoritative ownership boundary rather than adding another independent timeout or fallback.

## Acceptance criteria

- [ ] Reproduce the current failure on the supported installed Relay Runner build and in a deterministic test harness before implementing the repair; record which end-to-end boundary drops or rejects replay without logging response or transcript content.
- [ ] The diagnosis traces one correlated double-Option attempt through modifier detection, gesture polling, FIFO receipt, replay selection, TTS preparation, audio-process start, and terminal speech lifecycle state, clearly distinguishing an absent stage from a delayed one.
- [ ] After an eligible utterance has reached `played`, one valid double-tap Option replays that utterance audibly exactly once without requiring a second gesture, whether Relay Runner is frontmost or in the background.
- [ ] Replay works for the latest eligible authoritative final, work-lifecycle utterance, and command-scoped progress utterance, including the progress path changed by `1e44b81`; non-replayable handoffs or suppressed speech are handled according to the documented policy.
- [ ] Deferred Queue mode (`auto_play = false`) retains the current response for first play and subsequent replay, while Auto mode retains a completed utterance for replay; switching modes does not silently discard the authoritative replay target.
- [ ] Replay ownership survives normal TTS process completion and cleanup, but never resurrects canceled, failed, stale, superseded, secret, or unrelated test-fixture speech.
- [ ] Rapid duplicate Option gestures cannot double-start or overlap speech. Double-tap Control cancellation, confirmation yes/no handling, onboarding practice, double-tap Shift, ordinary Option-modified typing, and newest-command freshness remain correct.
- [ ] Global modifier-monitor installation, failure, recovery, and active monitor identity are observable with privacy-safe diagnostics, and retry does not install duplicate local or global monitors.
- [ ] Focused Swift tests exercise real modifier down/up timing, foreground/background monitor paths, retry recovery, confirmation arbitration, and exactly one emitted play control per accepted gesture.
- [ ] Focused Python tests exercise the actual `__PLAY__`/`play_or_replay` boundary, first-play-versus-replay state, Queue and Auto modes, completed TTS process cleanup, progress/final/lifecycle eligibility, cancellation, supersession, and Codex/Claude completion paths.
- [ ] The final verification observes `started` and `played` for the replayed utterance; `REPLY_ACCEPTED`, intent acceptance, enqueue, waiting-preview publication, or `queued` alone do not count as audible success.
- [ ] A freshly built installed app passes a mounted smoke test with repeated physical double-Option replay attempts in both foreground and background. If environment permissions prevent this validation, keep that item open and report the exact permission blocker rather than claiming completion.
- [ ] The run log records the root cause, why RR-252/RR-256/RR-271/`1e44b81` coverage missed it, the minimal repair boundary, tests run, installed build identity, and mounted playback evidence.
