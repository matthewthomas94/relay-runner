## Description

Resolve the verified and high-confidence first-run Workspace reliability gaps identified in the startup audit. The service runtime must not accept a Python version that later fails to import the orchestrator. Onboarding must establish real orchestrator readiness rather than deferring installation to the first Work request, and readiness must reflect the loaded launchd job and health endpoint rather than only a plist on disk.

Also make project creation and Workspace reopening reliable on cold state: avoid blocking Git work on the UI path, await registry/route readiness before opening Work, and make Registry V2 the consistent source for dashboard and ready-ticket sweep behavior. Preserve existing provider parity, user data, and non-destructive recovery behavior.

## Acceptance criteria

- [x] The supported service runtime either requires Python 3.11 or later, or provides and tests a compatible TOML import path for every accepted Python version.
- [x] Onboarding installs or verifies the orchestrator and reports a bounded, actionable failure with retained safe diagnostics when it cannot become healthy.
- [x] Readiness verifies launchd/process state and the orchestrator health endpoint; a stale, unloaded, or crashing launch agent triggers repair or a clear recovery path.
- [x] Project creation does not perform unbounded Git work on the main UI path, and Workspace opens only after the newly registered project route is available.
- [x] Dashboard ingestion and ready-ticket dispatch use the same Registry V2 project model, with regression coverage for a newly registered V2 project.
- [x] Automated coverage includes Python 3.10-or-supported-version behavior, stale launch-agent recovery, daemon crash/slow readiness, cold project creation, and Registry V2 dispatch.
- [ ] A clean-user or second-Mac run verifies first Workspace creation for both Codex and Claude setups, with any unavailable external checks recorded explicitly.
