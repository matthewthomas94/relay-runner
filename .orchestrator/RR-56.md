## Description

Make Relay voice steering automatic enough that a new spoken command can redirect the active orchestrator at any point in a session.

RR-52 added cooperative preemption checkpoints to the generated Codex and Claude relay instructions. That helps, but the product behavior should not rely only on the foreground LLM remembering to poll before every action. When a new voice command arrives, Relay Runner should surface it as newest intent, suppress stale TTS, and prevent stale orchestration steps from creating, editing, or dispatching tickets after the user has redirected.

The implementation should define the runtime contract between `services/voice_bridge.py`, generated provider instructions, and any app/daemon state needed to mark an active command/action as superseded. Already-running shell commands or MCP calls may still be cooperative when providers cannot hard-cancel them, but all follow-up work, TTS, and dispatch decisions should respect the newest Relay command.

Provider parity matters. Codex and Claude should get the same newest-intent-wins semantics, with any unavoidable provider limitation documented in product terms.

## Acceptance criteria

- [ ] A new Relay voice command received while the foreground orchestrator is working is surfaced promptly as newest intent, without waiting for the previous request to finish its full response.
- [ ] Stale TTS is suppressed when a newer command exists, including responses generated after the newer command arrived.
- [ ] Stale orchestration actions cannot create, edit, or dispatch tickets after a newer command supersedes them.
- [ ] The runtime records enough command/action generation or sequence metadata to tell which command a ticket edit or dispatch belongs to.
- [ ] The behavior of already-running shell commands and MCP calls is explicitly defined; if hard cancellation is not available, the next follow-up action must checkpoint and obey newest intent.
- [ ] Codex and Claude generated instructions share the same steering contract, and any provider-specific limitation is documented.
- [ ] Deterministic tests cover two rapid voice commands where the second edits/replaces the ticket work that the first was about to create or dispatch.
- [ ] Regression tests cover ordinary single-command voice sessions, bridge control commands, and TTS replay/stop controls.
