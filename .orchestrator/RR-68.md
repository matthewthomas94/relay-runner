## Description

Add validation and product handling for the update lifecycle around Relay Runner's bundled services.

Relay Runner is not just a menu-bar binary. The installed app ships helper MCP binaries, shell scripts, and Python services. Existing work in RR-60 handles stale orchestrator schema recovery after app/service updates; OTA updates must preserve that behavior and make the user experience deliberate when a new app bundle lands.

This ticket should verify the complete lifecycle from an older installed app to a newer installed app using Sparkle artifacts, especially with active or recently active Codex/Claude sessions.

Implementation guidance:

- Confirm Sparkle replacement preserves the bundle id, signing identity, and TCC attribution for Relay Actions/Relay Vision helpers.
- Ensure active voice/orchestrator services do not keep running stale code indefinitely after the app updates.
- Reuse or extend the existing stale-daemon restart logic rather than creating a second service-management path.
- If an update cannot install while a session is active, surface a clear user action instead of silently failing.
- Add a manual verification document if the full signed/notarized Sparkle flow cannot be exercised in unit tests.

## Acceptance criteria

- [ ] A documented old-version to new-version OTA test proves the app updates and relaunches from `/Applications`.
- [ ] After update/relaunch, bundled MCP binaries and Python services resolve from the new app bundle.
- [ ] Existing orchestrator stale-schema recovery still works after OTA update.
- [ ] Active Codex and Claude session behavior is explicitly considered; any intentional restart/deferral behavior is documented.
- [ ] TCC-sensitive helpers keep attribution to `Relay Runner` after update.
- [ ] Failure modes such as app running from DMG, missing appcast, unsigned archive, or active-session deferral produce actionable UI/log output.
- [ ] Verification includes `swift test`, Python tests where relevant, and packaging/appcast validation commands.
