## Description

Relay Runner is moving from one session at a time to one session per project, each in its own Workspace terminal tab (see RR-394/RR-395). The decision is to keep **one** voice pipeline (STT, voice bridge, messenger, TTS) and route it to the **focused** project's session only. Background sessions keep running but do not speak.

Today the whole voice path assumes one session per machine:
- Fixed `/tmp` paths in `Sources/relay-runner/Process/ProcessManager.swift` (~lines 19–57) and `RelayVoiceCommandDelivery.Paths` in `Sources/relay-runner/Terminal/EmbeddedTerminal.swift` (~1054–1069): `voice_bridge.sock`, `voice_cmd_ready(.meta)`, `voice_cmd_claimed.json`, `voice_command_state.json`, `voice_cmd_manual_ack.json`, `voice_provider_turns_v2.json`, `voice_provider_session_id`, `voice_bridge.cwd/.provider/_heartbeat/_stop_requested`, `voice_in.fifo`, `tts_in.fifo`, `tts_control.sock`.
- `services/voice_bridge.py` (~90–93, 369–407) uses the same paths plus `relay_intent_inbox.sqlite3` and `relay_speech_events.jsonl`.
- `ProcessManager.killBridge` uses `pkill -f voice_bridge.py` (~812–825).
- `services/messenger.py` (~843–863) keeps one `_session_id` passed as `--resume`.
- `AssistantSessionStore` has a single `activeContext`.
- Voice input is written to the single PTY `childfd` (`EmbeddedTerminal.swift` ~3311).

Answer: what state must become per-session versus stay shared, and how focus changes rebind the pipeline without dropping or misrouting a claimed command. Cover:
1. Which files/sockets/inbox rows need a session key, and which can stay global.
2. What happens to an in-flight claimed command, a pending TTS reply, or an active recording when focus switches mid-turn.
3. How a background session's `__ORCHESTRATOR_REPLY__` and worker lifecycle events are captured (badge) instead of spoken, and whether they replay on refocus.
4. Messenger: one messenger re-bound per focus vs one per session; cost and latency.
5. Whether the bridge needs restarting on focus change, or can be re-targeted live.
6. Fit with the voice-turn contract in `services/instructions/` (stale-output suppression, `relay_command_seq`/`intent_id` mutation authority, scoped cancellation).

**Conclusions**

- Inventory, per-session key. Give each session a spool dir keyed by a stable key (e.g. its transportSessionID). Move into it: voice_cmd_ready and .meta, voice_cmd_claimed.json, voice_cmd_manual_ack.json, voice_command_state.json, voice_command_authorizations.json, voice_provider_session_id, relay_terminal_manual_submission.json, relay_terminal_delivery_events.jsonl, voice_bridge_heartbeat(.pid), voice_bridge_launch.command. Intent-inbox rows need a session_key column. voice_provider_turns_v2.json may stay shared, filtered by provider_session_id, which records already carry.
- Inventory, shared vs re-bound. Shared: voice_in.fifo, voice_bridge.sock, tts_in.fifo, tts_control.sock, voice_state.sock, the tutorial TTS socket, the orchestrator daemon and port, the launchd label, stop_requested, and the messenger_outcomes DB (already keyed by repo_path). Add a session field to the command-actions journal and the speech-events log. Re-bound on focus: the bridge target (provider session, spool paths, cwd, provider, orchestrator_session), voice_bridge.cwd/.provider, the board now/prev files, messenger context, and AppState's active context and focused terminal.
- Bridge: re-target it live; don't restart it on focus. A restart would kill the warm messenger, TTS and any in-flight claim. It also can't work today: every launch runs `relay-bridge --start-daemon`, while killBridge and the watchdog use a global `pkill -f voice_bridge.py`. Add a `__FOCUS__` control message on voice_bridge.sock that swaps a lock-guarded target record (PROVIDER_SESSION_ID is currently a module constant). Launches must stop restarting the daemon, and only app quit (or closing the last tab) may kill it.
- Routing rule: no command is lost or misrouted. The app stamps session_key when recording starts and the bridge keeps it through publish. The command is written only to that session's spool and inbox. Each tab owns its own RelayVoiceCommandDelivery bound to its spool paths, so only that terminal can claim the command. This removes today's moveItem claim race on the single global ready file. Commands never move between sessions. Stale-output checks, authorization and ack all stay inside the origin session.
- Focus switch, idle and recording. Idle: send `__FOCUS__` and update AppState.focusedSession atomically. The next utterance targets the new session and nothing is in flight. Recording: the utterance stays bound to the session_key captured at record start and is published there. If that session is now in the background, its reply becomes a badge. Show a visual cue naming the target. Cancelling the recording on switch is an acceptable alternative, but binding at start loses no speech.
- Focus switch, claimed command or TTS playing. Claimed command in flight: it keeps running in the origin PTY and delivery state machine (acknowledge or supersede as normal). Its later `__ORCHESTRATOR_REPLY__` reaches the bridge, which badges it instead of speaking it. TTS playing: stop playback on tts_control.sock, end the messenger generation for that session, and store the full reply text in the origin session's badge. Never cancel the provider command itself because of a focus change.
- Badge design. Each session keeps unread_count, its last N replies with command keys, and lifecycle-event counts. The bridge writes there when a reply's session isn't focused. Worker lifecycle events already queue durably in the orchestrator's messenger_outcomes table, keyed by repo_path. Leave a background project's outcomes undelivered and show the count. On refocus, deliver them as the existing 'N updates accumulated while away' summary. Replies don't replay automatically: they show visually, with an explicit read-out action (`__REPLAY__` exists).
- Messenger: use one shared MessengerRuntime with per-session context partitions (context deque, current command, generation), switched on focus. One per session means up to 4 warm processes and up to 4x subscription and memory cost, though only the focused one speaks. Codex re-bind: one thread/start RPC on its ephemeral thread (no resume, fast). Claude: the messenger's own --resume _session_id must be per partition or cleared, and swapping it needs a respawn (estimated a few seconds) unless context is prefixed into the next ask. The messenger provider comes from global config.
- Codex and Claude parity. Spool, routing, badge and re-target are provider-neutral. The differences are in native binding: Claude starts with `--session-id <uuid>` or `--resume <native>`, and the bridge waits for a Claude-only session-start hook. Codex uses `resume <id> --cd <cwd>`, and a zero-turn thread can't be resumed (resumableNativeSessionID). Each session's binding is already stored per context. Per-session provider-turn records must keep provider_session_id so the foreground-turn filters work for both providers.
- Fit with the voice-turn contract. Stale-output suppression, seq/id/intent_id mutation authority and dispositions all hold per session if 'the current command' means the session's own state file. Three gaps: the instructions hard-code /tmp claim and state paths; the orchestrator daemon and the MCP claimedRelayCommand read single global state and authorization files; and the inbox's retire_stale_foreground and materialize_next act globally. That means cross-session cancellation, wrongly rejected mutations, and head-of-line blocking. Cancellation scope all_work must mean all work in this session.
- RR-394 can absorb: the session-spool path provider and per-session env export from prepareNewSession/launchScript; one EmbeddedTerminalSession plus RelayVoiceCommandDelivery per tab with injected paths; the AppState focusedSession plus per-session binding model; and the badge UI. Separate tickets: live bridge re-target and multi-session orchestrator registration; the session-scoped intent inbox; reply-helper session key plus route-or-badge; messenger partitions; per-session daemon and MCP authorization; instruction updates; per-session watchdog recovery.
