## Description

Let users turn the actionable conclusions of a completed branchless spike into one or more refined implementation tickets. The spike result is evidence and context, not ticket prose by itself: the foreground PM must split recommendations into coherent units, resolve the owning project, add acceptance criteria and dependencies, and show the proposed tickets for explicit confirmation before changing a board.

Created follow-up tickets must remain in backlog by default. They should retain a concise provenance link to the originating spike ticket and run while excluding raw transcripts, hidden reasoning, secrets, and irrelevant investigation detail. Repeating the same request must not allocate duplicate IDs or create duplicate cards, and creating follow-ups in another registered project must use that project's current canonical board and counter rather than the spike's checkout.

This workflow depends on RR-276's branchless spike lifecycle and durable result contract. It must not auto-dispatch implementation work merely because the spike completed or recommended a change.

## Acceptance criteria

- [ ] A completed spike exposes a clear action in Workspace and an equivalent voice/text PM command for proposing follow-up tickets from its findings.
- [ ] Relay Runner converts recommendations into concise, independently actionable ticket drafts with title, description, acceptance criteria, priority, dependencies, and worker-sizing fields rather than copying the spike report verbatim.
- [ ] The user can review, edit, accept, or reject each proposed ticket before any repository mutation; accepting one proposal does not implicitly accept the rest.
- [ ] Each accepted ticket records concise provenance to the originating spike ticket and run without including raw provider transcript, chain-of-thought, secrets, or unrelated research material.
- [ ] Same-project and explicitly selected cross-project follow-ups allocate IDs from the current canonical target board, verify branch ancestry and `next_id`, and commit each accepted batch atomically without touching unrelated changes.
- [ ] Ambiguous project ownership produces one targeted clarification instead of guessing or writing into the workspace root.
- [ ] New follow-up tickets are created in backlog and never auto-promoted or dispatched solely because the originating spike completed.
- [ ] Dependencies between proposed tickets and any prerequisite work are preserved; a spike recommendation alone does not satisfy an implementation dependency.
- [ ] An idempotency key derived from the originating spike run and accepted proposal prevents duplicate cards and counter advancement on retries, repeated voice delivery, or app restart.
- [ ] Partial failure reports exactly which proposals were committed and which were not, preserving recoverable drafts without reusing or skipping IDs silently.
- [ ] Codex and Claude produce the same proposal, confirmation, privacy, persistence, and lifecycle behavior through the provider-neutral PM contract.
- [ ] Focused daemon and Swift tests cover proposal rendering, per-ticket confirmation, project routing, canonical ID allocation, atomic commits, deduplication, privacy filtering, backlog-only creation, and restart recovery.
