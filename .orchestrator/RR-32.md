## Description

The board's global `Control+Option` hotkey is only installed when Relay Runner has Input Monitoring. In the live app state that prompted this ticket, Relay Runner had `inputMonitoring = denied`, so the board could still open through the menu/MCP socket path, but the physical hotkey did nothing and the user had no obvious onboarding recovery path.

Reintroduce Input Monitoring as a clear first-run onboarding step for Relay Runner app permissions. The flow should explain why it matters for global keyboard features such as the activation key and board hotkey, while preserving the current graceful fallback that voice can still work with microphone permission alone.

This is distinct from the per-parent Accessibility/Screen Recording wizard for Codex, Claude, Terminal, and other agent parents. Input Monitoring here is a Relay Runner app permission and should be guided in Relay Runner's own onboarding/settings flow.

## Acceptance criteria

- [ ] First-run onboarding includes a visible Input Monitoring step when Relay Runner does not have that permission.
- [ ] The copy explains that Input Monitoring enables global keyboard capture, including non-Caps-Lock activation keys and the `Control+Option` board hotkey.
- [ ] Users can skip or defer Input Monitoring without blocking microphone-only voice use, but the deferred state is visible in the final onboarding/status summary.
- [ ] Granting Input Monitoring after onboarding installs or restores the board hotkey without requiring the user to discover a hidden restart sequence.
- [ ] Settings/Status provides a clear recovery action for denied or revoked Input Monitoring.
- [ ] The flow keeps provider parity: Codex and Claude users see the same Relay Runner app permission guidance, with parent-app permissions handled separately.
- [ ] Verification covers a fresh onboarding path with Input Monitoring missing, a deferred/denied path, and a later grant/recovery path where the board hotkey becomes active.
