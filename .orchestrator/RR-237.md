## Description

Run an investigation-first performance audit of Relay Runner's sustained
responsiveness. The app can become broadly sluggish while work is active or
the Workspace reports that it is checking for updates. Pointer hover feedback
can stop responding, eligible ticket drags can fail to start or reach a lane,
and the embedded terminal can develop substantial typing latency. The problem
appears broader than Workspace reveal animation speed and may involve one
shared bottleneck or several independent ones.

Establish reproducible workloads and profile the current source build and a
freshly installed app. Measure rather than assume the cause. In particular,
distinguish:

- Workspace dashboard reload/status polling from Sparkle software-update
  checks and other periodic work;
- an eligible drag whose events are delayed or lost from an intentionally
  blocked lane transition or worker-owned ticket;
- keyboard-event-to-PTY latency from provider TUI processing and
  PTY-output-to-SwiftTerm rendering latency; and
- main-thread or actor starvation from CPU, filesystem, Git, process,
  database, animation, or rendering pressure elsewhere in the app.

Use RR-209 and RR-219's Workspace latency instrumentation, RR-231's mounted
card-drag regression path, RR-235's dashboard polling correction, and RR-236's
private terminal diagnostics as relevant starting evidence. Verify their
current behavior instead of presuming that an earlier fix still covers the
reported sustained-load failure.

This ticket should produce a defensible root-cause report and a small,
prioritized remediation plan. When the accepted audit identifies remediation
work, its structured completion handoff must automatically materialize that
plan as visible follow-up tickets through the normal PM/orchestrator
ticket-authoring path. The audit worker must not edit unrelated
`.orchestrator/` files directly, and generated tickets must remain in Backlog
rather than dispatching without explicit user direction.

Do not fold a broad performance rewrite into the investigation. Bounded
diagnostic instrumentation is in scope when needed to obtain evidence;
production behavior changes should be performed as separate follow-up work.

## Comparative research

Use relevant open-source implementations as testable references, not as
authority to replace Relay Runner's architecture:

- **Ghostty** (`ghostty-org/ghostty`) is the primary terminal comparison.
  Examine its dedicated terminal read, write, and render work, Metal-backed
  macOS surface, on-demand redraw/caching, and narrow SwiftUI wrapper around
  AppKit-owned terminal state. Identify which boundaries or measurements are
  applicable to an embedded terminal before proposing any adoption.
- **SwiftTerm** (`migueldeicaza/SwiftTerm`) is Relay Runner's current terminal
  engine. Relay Runner is pinned to `1.14.0`, has the optional Metal renderer
  available, and does not currently enable it. Compare the current
  CoreGraphics path with `setUseMetal(true)`, and evaluate `1.15.0` rather
  than assuming an upgrade is automatically beneficial. That release includes
  mouse-reporting fixes and Metal buffer-growth and packaged-app crash fixes
  that affect the validity of performance and interaction testing.
- **CodeEdit** (`CodeEditApp/CodeEdit`) is a native SwiftUI macOS workspace
  with an embedded SwiftTerm terminal. Compare its retained
  `LocalProcessTerminalView` cache, `NSViewRepresentable` boundary, state
  ownership, and relevant performance fixes with Relay Runner's persistent
  `RelayTerminalView`, dashboard polling, and Workspace invalidation graph.

The audit may add a small number of stronger comparators discovered during
research, but every cited project must map an exact source path or design
choice to a Relay Runner hypothesis and benchmark. Repository popularity or a
generic claim of being fast is not evidence. Replacing SwiftTerm, embedding
`libghostty`, or introducing another UI architecture is out of scope unless
the measurements justify a separate proposal.

## Acceptance criteria

- [ ] Record a reproducible test matrix for Project Workspace and Program
      Workspace while idle, during a foreground provider turn, during one and
      several worker runs, during dashboard refresh, and while the
      **Checking for updates** state is visible.
- [ ] Repeat the relevant scenarios in a fresh installed build and a debug
      build, recording the macOS version, hardware, app version/commit,
      project size, ticket count, provider, and workload so results can be
      compared.
- [ ] Measure pointer-event-to-hover-feedback and drag-start/drop-feedback
      latency through the mounted board hierarchy. Verify an eligible
      Backlog-to-Queued drag separately from transitions that policy
      intentionally rejects, including manual movement into In Progress.
- [ ] Measure terminal keyboard-event-to-SwiftTerm-send,
      SwiftTerm-send-to-PTY-write, PTY-output-to-render, and visible input
      latency under idle, high-output, active-worker, and Workspace-visible
      workloads.
- [ ] Compare equivalent Codex and Claude sessions and a provider-independent
      terminal or harness where practical, identifying which latency is
      shared app behavior and which is provider-TUI-specific.
- [ ] Inventory recurring and event-triggered work while Workspace is open,
      including dashboard/status polling, repository and ticket reads,
      ready/review sweeps, run-state refresh, software-update checks, timers,
      animations, and terminal transcript diagnostics. Record frequency,
      execution context, cancellation/coalescing behavior, and overlap.
- [ ] Capture Time Profiler, hangs/hitches, CPU, memory, and I/O evidence for
      each reproduced stall. Any material main-thread gap or actor backlog is
      tied to concrete call stacks, source symbols, duration, and trigger.
- [ ] Determine with evidence whether the symptoms share a root cause or are
      separate bottlenecks. Rank each confirmed finding by user impact,
      frequency, confidence, and expected remediation cost; clearly label
      hypotheses that remain unproven.
- [ ] Benchmark SwiftTerm's current CoreGraphics renderer against its Metal
      renderer using representative interactive and high-output workloads,
      recording input latency, frame/hitch behavior, CPU, GPU, memory,
      correctness, and fallback behavior. Compare pinned `1.14.0` with
      `1.15.0` where the result could change an upgrade recommendation.
- [ ] Compare Ghostty and CodeEdit at concrete source paths and pinned
      revisions. For each potentially useful pattern, document the Relay
      Runner hypothesis it suggests, the local measurement that supports or
      rejects it, and whether to adopt, adapt, or reject it.
- [ ] Commit
      `docs/investigations/RR-237-responsiveness-audit.md` with the reproduction
      recipe, measurements, profiles, confirmed root causes, ruled-out causes,
      comparative-repository findings, and before/after latency budgets
      proposed for remediation verification.
- [ ] The report recommends the smallest ordered set of follow-up tickets,
      with scope, dependencies, verification method, and likely files or
      subsystems for each.
- [ ] Accepting the audit automatically materializes every recommended
      remediation item as a visible `.orchestrator/` Backlog ticket through a
      structured PM/orchestrator handoff. RR-237's completion is not reported
      to the user until the generated ticket IDs have been recorded in the
      audit report or run log.
- [ ] Each generated ticket has an evidence-backed description, independently
      verifiable acceptance criteria, priority, dependencies, likely files or
      subsystems, relevant latency targets, and explicit worker sizing. Ticket
      IDs and `.orchestrator/config.toml` are updated atomically, and no
      generated ticket is automatically dispatched.
- [ ] The audit worker edits only RR-237 within `.orchestrator/`; follow-up
      ticket creation remains PM/orchestrator-owned. The spike does not
      implement the remediation tickets or perform an unbounded refactor.
- [ ] Any diagnostic code added for the audit is bounded, disabled or
      negligible in normal release use, avoids separately recording terminal
      input or secrets, has focused tests where applicable, and passes the
      relevant Swift and Python test suites.
