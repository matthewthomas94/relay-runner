## Description

Fix the replay-state regression where an eligible Relay Runner message can be replayed after its playback finishes, but becomes unavailable if the user stops that playback partway through and then double-taps Option again. Stopping the active audio process must not discard the underlying current-command speech intent or its retained replay target. The next replay gesture should restart the same eligible message from the beginning without requiring a new assistant response or app restart.

Treat cancellation of one playback attempt separately from cancellation, revocation, or supersession of the underlying message. A double-Control stop during initial playback or during a replay should end audio promptly and publish the correct stopped lifecycle state while retaining that message as the latest eligible replay target. A later double-Option should create one fresh playback attempt for that same message. Continue rejecting speech whose command or intent was actually canceled, replaced, stale, superseded, privacy-ineligible, or otherwise non-replayable.

This is a focused follow-up to RR-274. Its implementation must use the same authoritative speech-coordinator and TTS ownership boundary rather than adding a parallel replay cache or gesture fallback. Update the broad replay contract as needed so the phrase canceled speech does not conflate a stopped audio attempt with invalidated message eligibility.

## Acceptance criteria

- [ ] A deterministic regression starts an eligible message, stops playback after audible speech has begun but before completion, then shows the next valid double-Option replaying that same message from the beginning exactly once.
- [ ] The behavior works when the interrupted attempt is the message's initial playback and when it is a later replay of a message that previously completed.
- [ ] Double-Control or the supported playback-stop control terminates the active audio process promptly, records one stopped or canceled playback attempt, and retains the underlying message as the current replay target.
- [ ] Repeated replay, mid-message stop, and replay cycles remain functional without requiring a new response, a second Option gesture, terminal input, session restart, or Relay Runner relaunch.
- [ ] Playback cancellation and message eligibility are modeled separately at the authoritative speech-coordinator and TTS boundary; no independent cache, blind timeout, or gesture-specific fallback becomes a second source of truth.
- [ ] A replay after an interrupted attempt starts from the beginning, never overlaps the canceled process, never produces duplicate audio, and leaves only one managed playback process active.
- [ ] Actual command or intent cancellation, replacement, supersession, stale-current suppression, privacy ineligibility, failed synthesis, and non-replayable handoffs still clear or reject the target according to policy and cannot be resurrected by Option replay.
- [ ] The fix covers eligible authoritative finals, work-lifecycle speech, and current-command progress speech in Queue and Auto modes for both initial play and later replay.
- [ ] Lifecycle evidence distinguishes an interrupted attempt from a completed one: the stopped attempt is not reported as played to completion, while the later successful replay reaches started and played for the same eligible speech identity.
- [ ] The message-waiting, replay, speaking, and canceled visual states remain synchronized with the retained target so the UI does not claim replay is available when the coordinator will reject it, or hide replay when it is valid.
- [ ] Focused Python tests cover initial-play interruption, replay interruption, repeated stop and replay, cached and regenerated audio, Queue and Auto modes, supersession, command cancellation, stale speech, and exact-once process cleanup; focused Swift tests cover Option and Control gesture ordering and UI state transitions.
- [ ] A freshly built installed app passes a mounted physical-gesture smoke test that plays a response, stops it mid-message, replays it successfully, stops that replay, and replays it successfully again in foreground and background; the run log records build identity and started, stopped, and played lifecycle evidence.
