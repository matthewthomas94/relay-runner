## Description

Audit whether Relay Runner can centralize macOS privacy permissions so users grant sensitive capabilities to **Relay Runner.app** instead of every possible agent host, such as Codex, Claude, Terminal, Warp, or other shells.

Target architecture to evaluate: agent-facing MCP tools and installed skills should act as thin clients. Any action requiring Accessibility, Screen Recording, microphone, speech, or other TCC-gated capability should be requested through Relay Runner's app-owned control plane, and Relay Runner.app should validate, instrument, and execute the privileged action under its own bundle identity. This should preserve ActionGlow and Relay state visibility, and should avoid native fallback paths from agent-hosted processes.

The audit must also identify limits. Some macOS permissions are inherently target-specific or caller-specific, such as Apple Events automation grants, app-specific browser extension permissions, shell/file-system access, or any API where launching from an MCP helper changes the responsible process. The outcome should clearly separate what can be centralized from what still requires secondary permissions or a different product design.

## Acceptance criteria

- [ ] Inventory current and planned Relay Runner capabilities that require macOS privacy permissions, including voice capture, TTS playback, screen observation, mouse/keyboard control, app/window inspection, browser/app automation, file access, and MCP helper launch paths.
- [ ] For each capability, identify the macOS permission involved, the current responsible process or bundle, and whether it can be executed by Relay Runner.app on behalf of Codex, Claude, Terminal, or another agent host.
- [ ] Propose an app-owned permission-broker architecture using Relay Runner's local sockets, MCP servers, or XPC-style boundaries where agent-hosted tools send requests and Relay Runner.app performs the privileged operation.
- [ ] Explicitly document which permissions cannot be fully centralized and why, including any Apple Events per-target grants or actions that must remain attributable to the agent host.
- [ ] Ensure the proposal preserves the Relay stack rule: privileged screen manipulation/observation goes through RelayActions/RelayVision plus ActionGlow, with no native computer-use fallback.
- [ ] Cover provider parity for Codex and Claude, including installed skills, MCP registration, Start Session launch paths, and terminal-launched sessions.
- [ ] Define a verification plan that proves the agent host can lack secondary TCC grants while Relay Runner.app performs the privileged action successfully.
- [ ] Identify onboarding/settings/status UI changes needed to explain the reduced permission model and any unavoidable secondary grants.
- [ ] Add or update docs/specs/tests for the chosen design direction if implementation work is split into follow-up tickets.
