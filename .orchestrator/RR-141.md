## Description

Make Relay Runner the sole macOS privacy-permission owner for Relay Actions and Relay Vision. Today the MCP helper processes perform permission-gated work directly, so macOS may ask users to grant Accessibility or Screen Recording to the parent app that launched the helper, such as Codex, Claude, Terminal, Warp, or VS Code. That makes onboarding noisy and provider-dependent.

Change the architecture so the MCP servers remain the provider-facing protocol adapters, but forward permission-bound work to the running Relay Runner app process. The Relay Runner app must perform the actual simulated input and screenshot capture, so macOS privacy prompts and ongoing permission checks apply to Relay Runner rather than the agent host.

Implementation should prefer the existing local socket plumbing over new dependencies. If a new package or external dependency appears necessary, stop and document why before adding it.

Relevant current code:

- `Sources/relay-actions-mcp/InputTools.swift` posts input events from the MCP process.
- `Sources/relay-vision-mcp/ScreenshotTool.swift` captures screenshots from the MCP process.
- `Sources/relay-actions-mcp/PermissionPreflight.swift` currently checks parent-attributed permissions.
- `Sources/relay-runner/Overlay/ActionsConfirmBus.swift` already hosts a local socket for app-side messages.
- `Sources/relay-runner/Permissions/PermissionsManager.swift` already tracks Relay Runner's Accessibility and Screen Recording grants.

The desired model is similar to bridge-host patterns used by macOS automation tools: the app process owns permission-bound automation while CLI/MCP clients only send requests and receive structured results.

## Acceptance criteria

- [ ] Relay Actions MCP tools for click, type, key, and scroll no longer perform Accessibility-gated input directly in the MCP helper process; they forward to the Relay Runner app and return the app's result.
- [ ] Relay Vision MCP screenshot capture no longer performs ScreenCaptureKit capture directly in the MCP helper process; it forwards to the Relay Runner app and returns the captured image result.
- [ ] When Relay Runner is not running or its app-side tool host is unavailable, MCP tools return a clear actionable error telling the user to start Relay Runner.
- [ ] Permission prompts and preflight checks for Accessibility and Screen Recording are owned by Relay Runner's app process, not by Codex, Claude, Terminal, or other parent apps.
- [ ] Existing ActionGlow/tool-fired behavior still occurs for successful Relay Actions and Relay Vision requests.
- [ ] Socket handling is not made less safe: keep requests local to the active user/session, add peer validation or a defensible equivalent if the implementation changes the socket surface, and use timeouts for request/response paths.
- [ ] Onboarding/readiness/docs stop presenting parent-app Accessibility and Screen Recording as the normal requirement for Relay Actions or Relay Vision.
- [ ] Provider parity is preserved: Codex and Claude keep equivalent MCP tool names, request shapes, errors, and onboarding behavior.
- [ ] Tests cover the new request forwarding path, app-unavailable errors, and the onboarding/readiness copy or state changes where practical.
- [ ] Build and focused tests pass; if full app permission behavior needs manual verification, record the exact manual check in the run log.
