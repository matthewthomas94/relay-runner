## Description

Fix the dispatch failure modes exposed by a production investigation in another Relay Runner-managed repo. A ticket stored in an uncommitted `.orchestrator/` directory was absent from its worker worktree, so every worker exited without completing it. The daemon then dispatched the same structurally impossible work repeatedly, reaching 24 attempts without a cap, backoff, or identical-failure circuit breaker. The daemon had also cached its worker provider at startup, so a later config switch to Claude continued launching Codex workers. The Workspace/PM surfaces understated the incident instead of showing the repeated attempts and root-cause error.

Treat the source repo's current ticket file as the dispatch snapshot. A successful dispatch must make that exact ticket available at `<worktree>/.orchestrator/<ID>.md` even when the board or ticket is untracked or has uncommitted edits; if that cannot be done safely, fail before spawning a provider process with an actionable error. Copy only the selected ticket and preserve the normal worker-owned claim/completion commit flow.

Bound automatic recovery. Use a small finite retry budget with backoff, stop earlier when consecutive attempts have the same deterministic failure signature, and preserve an explicit human re-dispatch path after the underlying problem is corrected. The ticket and run history must retain enough state to explain why automatic dispatch stopped.

Resolve the effective worker provider from current configuration for every dispatch rather than daemon-startup state. An explicit orchestrator worker override may remain authoritative; otherwise follow the current `[general] provider` (with legacy command compatibility) and use a documented fallback only when neither is set. Apply the provider's current model and effort mapping after resolution.

Surface the effective provider, attempt count, terminal failure/circuit-breaker reason, and actionable last error in the existing Workspace/PM status paths. Keep the implementation upstream in source and release/build inputs; do not patch an installed app bundle.

## Acceptance criteria

- [ ] Dispatching a ready ticket whose `.orchestrator/` directory or ticket file is untracked creates a worker that can read and claim the exact ticket snapshot; no provider process is spawned if snapshot materialization fails.
- [ ] Dispatching a tracked ticket with uncommitted edits gives the worker the edited dispatch snapshot rather than stale committed prose or metadata.
- [ ] The materialized ticket follows the existing worker claim, completion, review, and merge lifecycle without copying unrelated board files or user changes into the worktree.
- [ ] Automatic retries have a finite, tested attempt cap and bounded backoff, and consecutive identical deterministic failures open a circuit before unbounded worker creation.
- [ ] A circuit-broken or retry-exhausted ticket does not auto-dispatch again, retains its attempt/error history, and can be explicitly retried after corrective action.
- [ ] Changing provider configuration while the daemon is running affects the next dispatch without a daemon restart; explicit orchestrator override, `[general] provider`, legacy command compatibility, and fallback precedence are covered by tests.
- [ ] Codex and Claude dispatches use their own current model/effort mappings and expose equivalent lifecycle, retry, and error behavior.
- [ ] Workspace and PM status show the effective worker provider, total attempt count, stopped/retry state, and actionable last failure instead of presenting repeated failures as one stuck run.
- [ ] Regression coverage reproduces the untracked-ticket loop and stale-provider timeline from the report, and the full Python and relevant Swift test suites pass.
