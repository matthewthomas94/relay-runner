## Description

Once tickets visibly move into "In progress" when a worker is running (RR-11), the next gap is *what the agent is doing right now*. A ticket sitting in "In progress" for 8 minutes is opaque — is the worker editing files, running a build, stuck on a permission prompt, or hung? Surface a one-line activity chip on each in-progress ticket card describing the worker's most recent meaningful action.

The cleanest source for this is the worker's structured event stream. `claude` supports `--output-format stream-json`, which emits `tool_use` events as they happen. If the daemon spawns the worker with that flag (or already captures the stream), it can parse the most recent `tool_use` and surface a short human-readable summary: `"Editing PerimeterOverlay.swift"`, `"Running swift build"`, `"Committing"`, `"Reading 12 files"`, `"Waiting for permission: Bash"`.

Plumb that summary into the runs-index entry (the JSON file introduced in RR-11), and render it as a chip on the in-progress card.

## Acceptance criteria

- Daemon captures live `tool_use` events from each worker — either by spawning `claude` with `--output-format stream-json` and parsing the stream, or by another equivalent mechanism if the worker invocation is structured differently today. Whatever mechanism is chosen, it must not block the worker or swallow its output for other consumers.
- For each active run, the daemon derives a **short activity summary** (≤60 chars) from the most recent meaningful tool call. Examples: `"Editing PerimeterOverlay.swift"`, `"Reading 3 files"`, `"Running: swift build"`, `"Committing"`, `"Waiting for permission"`. Idle / no-op tool calls (e.g. `TodoWrite`) should not overwrite a more meaningful prior activity within a short debounce window (~5s).
- The activity summary is added as a new field `activity: string?` on each runs-index entry (`~/Library/Application Support/relay-runner/orchestrator/runs.json`). Updated on every meaningful tool-use event.
- Board renders the activity field as a chip on the corresponding in-progress ticket card. The chip is visually subordinate to the existing status pill (smaller, lower contrast) — it's "additional context", not the primary signal.
- When a run ends, the activity chip disappears within ~1s. When no run is active for a ticket, no chip is rendered.
- Chip text truncates with ellipsis if the rendered width would overflow the card; full text available on hover (if the board supports tooltips) or as accessibility label.
- Manual verification:
  - Dispatch a ticket that does several distinct operations (e.g. reads files, edits, runs a build). Watch the chip update through phases — should reflect the current operation, not the first one.
  - If a worker stalls (no events for >30s), chip shows `"Idle"` or similar so the user knows the worker isn't actively doing anything.
- Don't touch the bundled `.app`'s scripts — DMG-build action is the source of truth.
- Commit message references RR-12.

## Notes

- This ticket depends on RR-11 — assumes the runs-index file format and the board's runs-file reader already exist. If RR-11 isn't merged at dispatch time, stop and surface that.
- Be careful with `--output-format stream-json` — its precise shape is documented in the Claude Code docs. If you're parsing it, write a tiny tolerant parser that ignores unknown event kinds; the format evolves.
- The summary derivation is intentionally heuristic — over-engineering a "perfect" mapping from tool name → summary is out of scope. Aim for usefulness, not exhaustive correctness. The mapping table can live in a single switch statement in the daemon and grow over time.
- If parsing the stream proves brittle, an alternative is having the worker emit `.relay/activity.txt` from inside the workspace and the daemon tails that file. Worker-side cooperation is more reliable but requires updating `services/orchestrator_workflow.md` to instruct the worker. Pick whichever is simpler in practice.
- The `Idle` / stall-detection threshold (30s above) is a starting point. Tune based on what feels right when watching real runs.
