## Description

Define an implementation-ready policy that keeps only the 25 most recent Relay tickets in each project's local active working set and stores older ticket history durably in GitHub. Remove the existing 30-day materialization threshold implemented by RR-285 and replace it with a deterministic count-based boundary. Ticket age must not independently retain or evict a ticket; canonical activity time is used only to rank the newest 25. Preserve the existing project-owned `refs/heads/relay/artifacts` authority and remote archive model rather than creating a second ticket store or publishing Relay data onto the source branch.

Make the phrase "stored locally" technically and visibly precise. Distinguish the repo-root `.orchestrator/` materialization from locally reachable Git objects, the archive catalog, attachments, derived search indexes, caches, and local run logs. Do not claim that a ticket is remote-only while its complete content remains intentionally retained in another local store. Recommend the smallest safe design that meets the user's storage goal without destructive history rewriting, force-pushing, or silently changing a project's configured Git remote.

Define which 25 tickets are retained using a stable recency key grounded in canonical ticket activity, with a deterministic tie-breaker. Account for active work, nonterminal tickets, dependencies, live worker/reviewer snapshot leases, restored history, reopened tickets, attachments, concurrent multi-device updates, and projects with fewer than 25 tickets. If safety exemptions can temporarily place more than 25 ticket files in the local materialization, specify the exact exemptions, explain why a strict cap would be unsafe, and make the overage observable rather than silently weakening the policy.

For any ticket leaving the local active set, require proof that its immutable ticket content and eligible attachments are reachable from the verified project artifact ref on the user-selected GitHub remote before local eviction. Offline, missing-remote, authentication, non-fast-forward, remote-integrity, shallow-clone, and interrupted-sync failures must retain or restore the local copy and surface an actionable blocked state. The policy must not create a GitHub repository, select a remote, expose a private project, use GitHub Issues as a competing authority, or delete recoverable history.

Keep historical tickets discoverable from the board through the compact archive catalog. Specify remote-backed search, detail viewing, restoration/reopening, dependency resolution, and fresh-install recovery without eagerly re-materializing the full archive. Include migration behavior for existing projects governed by the 30-day policy and state how local-only or non-GitHub projects behave until the user explicitly configures a suitable remote.

**Uncertainties**

- Whether “GitHub” includes explicitly configured GitHub Enterprise Server hosts or only `github.com` needs a product decision; remote-host validation and confirmation copy depend on it.
- A strict 25-file cap cannot be guaranteed while more than 25 tickets are simultaneously safety-exempt or remote publication is blocked. Enforcing it would endanger active work; the recommended contract permits observable overage.
- If the intended goal is to cap all local bytes, not just repo-root materialization, the existing ordinary-history model cannot guarantee that without partial-clone tradeoffs or destructive history rewriting. The safe recommendation preserves history and reports local Git bytes truthfully.
