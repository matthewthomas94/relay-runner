## Description

Define an implementation-ready policy that keeps only the 25 most recent Relay tickets in each project's local active working set and stores older ticket history durably in GitHub. Remove the existing 30-day materialization threshold implemented by RR-285 and replace it with a deterministic count-based boundary. Ticket age must not independently retain or evict a ticket; canonical activity time is used only to rank the newest 25. Preserve the existing project-owned `refs/heads/relay/artifacts` authority and remote archive model rather than creating a second ticket store or publishing Relay data onto the source branch.

Make the phrase "stored locally" technically and visibly precise. Distinguish the repo-root `.orchestrator/` materialization from locally reachable Git objects, the archive catalog, attachments, derived search indexes, caches, and local run logs. Do not claim that a ticket is remote-only while its complete content remains intentionally retained in another local store. Recommend the smallest safe design that meets the user's storage goal without destructive history rewriting, force-pushing, or silently changing a project's configured Git remote.

Define which 25 tickets are retained using a stable recency key grounded in canonical ticket activity, with a deterministic tie-breaker. Account for active work, nonterminal tickets, dependencies, live worker/reviewer snapshot leases, restored history, reopened tickets, attachments, concurrent multi-device updates, and projects with fewer than 25 tickets. If safety exemptions can temporarily place more than 25 ticket files in the local materialization, specify the exact exemptions, explain why a strict cap would be unsafe, and make the overage observable rather than silently weakening the policy.

For any ticket leaving the local active set, require proof that its immutable ticket content and eligible attachments are reachable from the verified project artifact ref on the user-selected GitHub remote before local eviction. Offline, missing-remote, authentication, non-fast-forward, remote-integrity, shallow-clone, and interrupted-sync failures must retain or restore the local copy and surface an actionable blocked state. The policy must not create a GitHub repository, select a remote, expose a private project, use GitHub Issues as a competing authority, or delete recoverable history.

Keep historical tickets discoverable from the board through the compact archive catalog. Specify remote-backed search, detail viewing, restoration/reopening, dependency resolution, and fresh-install recovery without eagerly re-materializing the full archive. Include migration behavior for existing projects governed by the 30-day policy and state how local-only or non-GitHub projects behave until the user explicitly configures a suitable remote.

## Acceptance criteria

- [ ] Document the current RR-285 30-day materialization, archive, remote-sync, history, restore, lease, and storage-metrics behavior, and identify the exact code, schema, documentation, and UI boundaries that must change to remove the age threshold and enforce a 25-ticket policy.
- [ ] Specify one count-based retention threshold of 25 tickets per project. No day-, duration-, or age-based threshold remains in eligibility, scheduling, configuration, documentation, metrics, or user-facing language; timestamps are used only for deterministic recency ordering.
- [ ] Define whether the 25-ticket rule applies to the repo-root materialization, all Relay-controlled local copies, or both. Inventory local Git objects, archive catalog data, attachments, derived indexes/caches, and run logs separately, with truthful user-facing storage terminology for each.
- [ ] Select one deterministic recency ordering based on canonical activity metadata and an immutable tie-breaker. Specify the behavior for equal timestamps, missing legacy timestamps, restored or reopened tickets, remote merges, and concurrent multi-device writes.
- [ ] Define the exact eligibility and exemption rules for backlog, ready, in-progress, verification-blocked, awaiting-review, merge-conflict, done, and canceled tickets; active dependencies; and worker/reviewer snapshot leases. Any permitted over-25 state has a bounded reason, visible count, and deterministic return to policy.
- [ ] Require verified fast-forward publication of the immutable ticket, eligible attachments, and updated archive catalog to the configured GitHub `relay/artifacts` ref before a local active copy is removed. Failed or indeterminate publication leaves the ticket locally recoverable and reports a retryable blocked state.
- [ ] Specify safe behavior for no remote, a non-GitHub remote, Local only, paused sync, offline operation, expired authentication, remote deletion, remote divergence, shallow clones, corruption/tampering, and a crash before or after local materialization changes. Relay never guesses or silently changes the remote.
- [ ] Preserve a single project-owned artifact authority. Do not introduce GitHub Issues, the source branch, application-support databases, or provider transcripts as competing ticket stores, and do not use force-push, history rewriting, or destructive garbage collection as routine retention behavior.
- [ ] Define board behavior for the 25 local cards plus older remote history, including search, unavailable/offline states, detail streaming without eager restore, explicit restore/reopen, attachment retrieval, dependency summaries, and an understandable indication of what is local versus remote.
- [ ] Define migration from the existing 30-day rule to count-only retention, including removal of stored age-policy state, a preview, exact candidate list, remote preflight, idempotent archive transaction, rollback/recovery, projects with fewer than 25 tickets, projects already below the cap, and existing archived tickets.
- [ ] Define fresh-install and second-device recovery from GitHub so the initial materialization selects the same deterministic 25-ticket working set without downloading or exposing unrelated source refs.
- [ ] Specify privacy and security constraints for remote ticket content and attachments, including explicit confirmation before enabling remote exposure and retention of the current content allowlist, secret rejection, attachment ownership, type, and size limits.
- [ ] Produce an implementation-ready recommendation with state-machine changes, schema/versioning needs, focused Python and Swift tests, migration and rollback sequencing, mounted GitHub/offline/fresh-install UAT, storage observability, and Codex/Claude parity.
- [ ] Recommend a minimal dependency-ordered set of follow-up implementation tickets. Do not modify product source code during the spike.
